## 기억하는 것처럼 보이는 대화

고객 지원 에이전트와 대화하고 있다고 해봅시다:

```text
User: My name is Sarah, order number ORD-2026-8842.
Agent: Got it, Sarah. Let me check on ORD-2026-8842 ... it's out for delivery, expected tomorrow.
User: What about the one I bought last time?
Agent: Do you mean ORD-2026-8842? That one arrives tomorrow — if you're asking about a different order, could you give me the order number?
```

두 번째 턴에서 에이전트는 당신의 이름이 Sarah라는 것을 분명히 「기억하고」 있고, ORD-2026-8842에 대해 물었다는 것도 기억합니다. 마치 그 세부 정보들을 어딘가에 정리해 두었다가 다음번에 다시 꺼내 올 수 있는 것처럼 보입니다.

진실은 훨씬 더 단순합니다. 요청할 때마다 당신의 코드는 **대화 시작부터 지금까지의 모든 메시지**를 다시 묶어 그대로 모델에 보냅니다.[^S6] 모델은 「당신의 이름이 Sarah라는 것을 기억하고 있다」를 보는 것이 아니라, 「사용자가 말했다: 내 이름은 Sarah」를 매번 처음부터 다시 읽는 것입니다. 이전 턴의 모든 문장, 모든 도구 호출은 당신 자신의 코드에 의해 이번 턴의 요청 안에 배치되어야 합니다. 모델은 스스로 아무것도 저장하지 않습니다.

## API 호출은 스테이트리스다

더 직설적으로 말하면: 한 호출과 다음 호출 사이에 서버에서 조용히 보관되는 것은 아무것도 없습니다. 이 요청이 처리되고 나면 그 토큰들은 모델의 시야에서 사라집니다. 다음 요청이 아무것도 실어 오지 않으면 모델은 백지 상태를 봅니다 — 당신의 이름조차 모릅니다.

그것이 메모리처럼 느껴지는 이유는 호스트 애플리케이션이 당신을 대신해 궂은일을 해주기 때문입니다: 히스토리 메시지 배열 전체를 다시 보냅니다. 이것은 모델의 능력이 아닙니다. 계속 커지는 당신 코드 안의 배열일 뿐입니다. 이 성질에는 이름이 있습니다 — **스테이트리스(stateless)**입니다. 공식 문서의 표현을 빌리면: "The Messages API is stateless, which means that you always send the full conversational history to the API."[^S6] (Messages API는 스테이트리스이며, 이는 항상 전체 대화 히스토리를 API로 보내야 한다는 뜻입니다) 서버는 요청 사이에 세션별 비공개 상태를 보관하지 않습니다. 모든 「메모리」는 클라이언트 자신이 실어 나르고 다시 보내야 합니다.

## 컨텍스트 윈도우에 실제로 담기는 것

모델이 볼 수 있는 모든 것은 **컨텍스트 윈도우**라는 컨테이너 안에 존재합니다. 문서는 요청 안의 모든 것이 포함된다고 명시합니다: "Everything in the request counts toward the context window: the system prompt, every message in messages (including tool results, images, and documents), and your tool definitions. The output Claude generates for the turn, including its extended thinking, counts too."[^S1] (요청 안의 모든 것이 컨텍스트 윈도우에 포함됩니다: 시스템 프롬프트, messages 안의 모든 메시지(도구 결과, 이미지, 문서 포함), 그리고 도구 정의입니다. Claude가 그 턴에서 생성하는 출력도, 확장 사고를 포함해 함께 포함됩니다)

```json
{
  "model": "claude-sonnet-5",
  "system": "You're a customer-support assistant ...",
  "tools": [ { "name": "get_order_status", "...": "..." } ],
  "messages": [
    { "role": "user", "content": "My name is Sarah, order number ORD-2026-8842." },
    { "role": "assistant", "content": "Got it, Sarah ..." },
    { "role": "user", "content": "What about the one I bought last time?" }
  ]
}
```

이 요청에서는 `system`, `tools`, 그리고 `messages` 배열 안의 세 메시지 모두가 컨텍스트 윈도우에 포함됩니다. 모델의 응답이 생성되면 그 출력 토큰들도 같은 이번 턴의 윈도우 사용량에 포함됩니다. 응답에는 **`usage` 필드**가 담겨 있어 그 턴이 실제로 소비한 입력 토큰과 출력 토큰의 수를 알려줍니다: "Every response reports what the request consumed in its `usage` field."[^S1] (모든 응답은 요청이 소비한 것을 `usage` 필드로 보고합니다)

이 요청에 묶여 들어가지 않은 것 — 이를테면 아직 어떤 도구도 조회하지 않은, 데이터베이스에 놓여 있는 주문 레코드 — 은 컨텍스트 윈도우의 일부가 아닙니다. 모델은 그것을 볼 수 없고, 그것이 존재한다는 것을 난데없이 알 수도 없습니다. 그래서 「메모리」는 어떤 메커니즘에 의해 이 요청 안으로 능동적으로 실려 들어와야 합니다. 자동으로 닿을 수 있는 것이 아닙니다.

## 윈도우는 썩는다 — 크다고 더 나은 것은 아니다

윈도우가 담을 수 있는 양에는 상한이 있습니다 — 용량은 모델마다 다르고, 공식 수치는 최대 100만 토큰까지 갑니다: "The context window (up to 1M tokens, depending on the model) holds the conversation history plus the new output Claude generates."[^S1] (컨텍스트 윈도우는(모델에 따라 최대 1M 토큰) 대화 히스토리와 Claude가 생성하는 새 출력을 담습니다) 하지만 그렇다고 가능한 한 가득 채워 넣어야 한다는 뜻은 아닙니다. 문서는 특정 현상, **컨텍스트 로트(context rot)**를 명명합니다: "As token count grows, accuracy and recall degrade, a phenomenon known as *context rot*. This makes curating what's in context just as important as how much space is available."[^S1] (토큰 수가 늘어날수록 정확도와 회상이 저하되며, 이는 컨텍스트 로트로 알려진 현상입니다. 이 때문에 컨텍스트에 무엇을 담을지 선별하는 일은 얼마나 많은 공간이 남아 있는지만큼이나 중요해집니다) 다시 말해, 윈도우가 담는 내용이 많아지고 어수선해질수록 모델은 그 안에서 올바른 답을 끄집어내는 데 더 서툴러집니다 — 이는 컨텍스트에 *무엇을* 넣는지가 얼마나 공간이 남았는지만큼 중요하다는 것을 의미합니다.[^S1]

이는 메모리 설계에 직접 영향을 줍니다: 히스토리 전체를 컨텍스트에 쏟아붓는 것은 공짜가 아니고(윈도우 용량을 채웁니다), 대가가 없는 것도 아닙니다(오래된 정보 더미에 파묻힌, 지금 실제로 관련 있는 한 문장을 찾느라 모델이 더 애를 써야 합니다). 레슨 2에서는 그 **누적**을 실무에서 어떻게 다룰지 — 히스토리를 잘라내는 법, 요약하는 법을, 무한정 커지도록 두지 않고 다루는 방법을 다룹니다.

## 「메모리」라는 단어는 사실 은유다

서두의 그 지원 대화로 돌아가 봅시다. 「에이전트가 당신의 이름이 Sarah라는 것을 기억한다」라고 말할 때, 정확한 표현은 이렇습니다: 당신의 코드가 완전한 히스토리 —「내 이름은 Sarah」를 담은 그 히스토리를— 그대로 모델에 한 번 더 재전송했고, 모델이 이 요청 안에서 그것을 다시 읽었다는 것입니다. 저장도 없고, 회상도 없고, 오직 **재전송**만 있습니다.

이것은 말꼬리를 잡는 것이 아닙니다. 「메모리는 재전송이 만들어 낸 착각이다」라는 것을 이해하는 일은, 진짜로 「기억하는」 에이전트를 어떻게 설계할지에 직접 영향을 줍니다:

- 히스토리 배열이 무한정 커지면 윈도우는 조만간 가득 차고, 그 위에 컨텍스트 로트까지 겪습니다 — 레슨 2가 푸는 문제입니다.
- 어떤 정보가 **여러 세션**에 걸쳐(이 하나의 대화 안뿐 아니라) 지속되어야 한다면, messages 배열에 밀어 넣는 것에 기댈 수 없습니다. 그것은 어딘가 외부에 기록되어야 합니다 — 레슨 3이 다루는 외부 메모리입니다.
- 에이전트가 작업 도중에 「내가 어디까지 진행했는지」를 알아야 한다면, 그 진행 상황 역시 컨텍스트 윈도우 안에서 보이는 **구조화된 상태**여야 하며, 모델이 추측하는 것이 아닙니다 — 레슨 4의 주제입니다.

이 세 갈래는 모두 같은 사실의 서로 다른 따름정리입니다: 모델은 윈도우 안에 있는 것만 압니다. 윈도우 안에 없는 것은 모델에 관한 한 존재하지 않습니다.

### 레벨 1: 컨텍스트 윈도우에 포함되는 것 표시하기

아래는 모델에 보낸 실제 요청(간략화)과, 「똑같이 존재하지만」 이 요청에는 **나타나지 않는** 세 가지입니다:

```json
{
  "model": "claude-sonnet-5",
  "system": "You're an order assistant.",
  "tools": [ { "name": "get_order_status", "input_schema": { "...": "..." } } ],
  "messages": [
    { "role": "user", "content": "Look up ORD-2026-8842 for me" }
  ]
}
```

존재하는 세 가지 추가 항목:

1. 데이터베이스에 있는 ORD-2026-8842 주문 레코드의 실제 내용(아직 어떤 도구도 조회하지 않음)
2. 같은 사용자가 지난주 다른 에이전트와의 세션에서 언급한 배송 주소
3. 이 요청이 처리된 후 모델이 생성하는 응답 텍스트

각각에 대해 판단하세요: 이 네 종류의 내용(`system` / `tools` / `messages` 안의 사용자 메시지 / 위의 세 추가 항목) 중 어느 것이 이 요청의 컨텍스트 윈도우에 포함되고 어느 것이 포함되지 않는지, 각각 한 문장의 이유와 함께 답하세요.

<!-- rubric -->
- `system`, `tools`, `messages` 안의 사용자 메시지가 모두 컨텍스트 윈도우에 포함됨을 올바르게 식별
- 주문 레코드와 지난주 배송 주소는 이 요청에 배치되지 않았으므로 지금은 포함되지 않음을 올바르게 식별
- 모델이 생성한 응답 텍스트는 요청 처리 후에 만들어지지만 **이번 턴의** 윈도우 사용량에 포함됨을 올바르게 식별

<!-- answer -->
참고 답안: `system`, `tools`, `messages` 안의 사용자 메시지는 모두 이 요청 안에 있으므로 셋 다 컨텍스트 윈도우에 포함됩니다. 데이터베이스의 주문 레코드와 지난주 언급된 배송 주소는 이 요청의 어떤 필드에도 나타나지 않으므로, 지금은 모델에게 존재하지 않고 윈도우에도 포함되지 않습니다 — 다만 나중에 어떤 도구가 주문 레코드를 조회해 `tool_result`로 `messages`에 묶어 넣으면, 그 시점에는 이후 어느 턴의 윈도우에 포함됩니다. 모델이 이번 턴에 생성하는 응답 텍스트도 이번 턴의 윈도우 사용량에 포함되는데, 모델의 출력 자체가 윈도우의 일부이기 때문입니다.

판별 기준은 하나뿐입니다: 그것이 모델에 보낸 JSON 요청에 실제로 나타났는가? 나타나지 않았다면, 데이터베이스에 아무리 「객관적으로 실재」하더라도 포함되지 않습니다.

모델의 출력은 놓치기 쉽습니다 — 「생성되는」 것이지만, 생성하는 행위 또한 윈도우 용량을 소비하며, 응답의 `usage` 필드가 그것을 함께 반영합니다.

### 레벨 2: 이 설명에서 잘못된 가정 찾기

한 동료가 자신이 설계 중인 에이전트를 이렇게 설명합니다: 「우리 대화는 이미 20턴 깊이까지 왔고 데이터베이스가 전체 히스토리를 저장하니까, 이번 턴 요청이 사용자의 최신 문장 하나만 보내도 모델은 대화를 이어갈 수 있어. 서버가 같은 세션이라는 걸 아니까.」

이 설명에서 잘못된 가정을 지적하고, 실제로 이렇게 만들어진다면 어떤 상황에서 무너지는지 설명하세요.

<!-- rubric -->
- 오류가 서버가 같은 세션의 히스토리 메시지를 자동으로 연결한다고 가정하는 데 있음을 명확히 식별
- API 호출이 스테이트리스이며 모델은 이 요청이 실제로 실어 나르는 `messages` 내용만 본다는 것을 설명
- 모델이 갑자기 「잊거나」, 엉뚱한 답을 하거나, 에러가 나는 등 구체적인 「여기서 무너진다」 상황을 하나 제시

<!-- answer -->
참고 답안: 잘못된 가정은 「서버가 같은 세션이라는 걸 안다」입니다 — 데이터베이스가 히스토리를 저장하면 모델이 자동으로 그것을 볼 수 있다고 믿는 것입니다. 실제로 API 호출은 스테이트리스이며, 모델은 이 하나의 요청에서 `messages` 배열이 실어 나르는 것만 볼 수 있습니다. 데이터베이스가 히스토리를 저장하는 것과 모델이 이번 턴에 그것을 볼 수 있는 것은 별개의 두 가지입니다. 그 사이에서 클라이언트가 히스토리 메시지를 요청 안에 능동적으로 다시 넣어야 합니다. 이렇게 만들면 21번째 요청은 「what about the one I bought last time」만 보내고, 모델은 아무 컨텍스트도 없는 고립된 질문을 봅니다 — 십중팔구 엉뚱한 답을 하거나 「어느 주문을 말하는 건가요」라고 되물으며, 에이전트가 갑자기 「기억을 잃은」 것처럼 보입니다. 하지만 그것은 결코 「잊은」 것이 아니라, 그저 「본 적이 없는」 것입니다.

<!-- hint -->
스스로 물어보세요: 히스토리가 데이터베이스에 「저장」된 것과, 이번에 모델에 보내는 JSON 요청에 히스토리가 「포함」된 것은 같은 것인가요?

<!-- hint -->
이 레슨의 「API 호출은 스테이트리스다」 절을 떠올려 보세요 — 서버는 요청 사이에 세션별 비공개 상태를 보관하지 않으며, 이는 이 문제의 잘못된 가정에 치명타입니다.

## 정리

- 「에이전트가 이전 대화를 기억한다」는 착각이다: 진실은 호스트 애플리케이션이 매 요청마다 전체 히스토리를 다시 묶어 넣고, 모델 자체는 아무것도 저장하지 않는다는 것이다[^S6]
- API 호출은 스테이트리스다. 서버는 요청 사이에 세션별 비공개 상태를 보관하지 않으므로, 모든 「메모리」는 클라이언트가 능동적으로 실어 날라야 한다[^S6]
- 컨텍스트 윈도우는 이 요청이 실제로 실어 나르는 모든 것을 담는다: 시스템 프롬프트, `messages` 안의 모든 메시지(도구 결과, 이미지, 문서 포함), 도구 정의, 그리고 그 턴에 대한 모델 자신의 출력[^S1]
- 윈도우에는 크기 상한이 있고, 크다고 자동으로 쓰기 좋은 것은 아니다 — 컨텍스트 로트는 토큰을 많이 쌓을수록 정확도와 회상이 저하됨을 뜻한다[^S1]
- 「모델은 윈도우 안에 있는 것만 안다」를 파악하는 것은 다음 세 레슨이 푸는 문제로 곧장 이어진다: 히스토리를 어떻게 관리할지, 메모리를 어떻게 외부화할지, 상태를 어떻게 구조화할지
