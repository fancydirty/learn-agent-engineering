## 追加がデフォルト: 履歴が成長し続ける理由

レッスン1では、モデルが見る履歴は、ホストアプリが毎ターン再送信するものであるという点を示しました。では、実際にどのように送信されるのでしょうか？ 最も単純な実装は**追加**です: ターンが終了すると、そのターンからの新しいメッセージ（ユーザーの言葉、モデルの返信、ツール呼び出しとその結果）を既存の`messages`配列の末尾に追加し、次のターンでは配列全体をそのまま送り返します。

公式ドキュメントは、このデフォルトを明確に述べています: 会話が進むにつれて、各ユーザーメッセージとモデルの返信がコンテキストウィンドウ内に蓄積され、以前のターンはすべて完全に保存されます。"As the conversation advances through turns, each user message and assistant response accumulates within the context window, and previous turns are preserved completely."[^S1] (会話がターンを通じて進むにつれて、各ユーザーメッセージとアシスタントの応答がコンテキストウィンドウ内に蓄積され、以前のターンは完全に保存されます) 誰も積極的に何かを削除していないため、履歴は増加するだけです — 10ターン目には、ウィンドウは10ターン分のコンテンツ全体を保持しており、最新ターンの要約でも自動フィルタリングされたハイライトでもありません。

短い会話では、これは問題になりません。しかし、長時間実行されるエージェントにとって、問題は雪だるま式に大きくなります: すべてのツール呼び出しの完全な引数と完全な戻り値が履歴に詰め込まれ、ファイルを繰り返し読み取りコマンドを実行するタスクは、数十ターン後に`messages`配列を簡単に数万トークンまで押し上げることができます。レッスン1では、ウィンドウには容量の上限があり、それが満杯に近づくほど上限に達しやすいことをカバーしました。より微妙なコストは**コンテキストロット**です — 履歴が長く乱雑になるほど、モデルが今まさに重要な1行を見つけるのが困難になります[^S1]。履歴を無制限に成長させると、最終的に両方の代償を払うことになります。

## 切り詰め: 最も単純で最も粗雑なオプション

最も直接的な対応は**切り詰め**です: ウィンドウがほぼいっぱいになったら、最も古いメッセージのバッチをそのまま切り取り、最新のNターンだけを保持します。これは最も構築が簡単です — 追加のモデル呼び出しも、設計する要約フォーマットもありません。`messages.slice(-N)`の1行で完了です。

しかし、切り詰めが削除するものは永久に失われます。切り取ったバッチに、ユーザーがターン3で述べた重要な制約（「予算は\$5,000以下に抑える」）が含まれていて、エージェントが今ターン40で注文しようとしている場合、その情報は単に消えます。モデルはそれをかつて「見て」、それから「忘れた」とは認識しません — それが決して伝えられなかったかのように振る舞うだけです。

切り詰めには、より隠れた罠もあります。これは前のコース「エージェントツール呼び出し: エージェントに実際に行動させる」のレッスン2「ツール呼び出しの完全なラウンドトリップ」のラウンドトリッププロトコルに直接関連しています: 単純に「最後のNメッセージ」にスライスすることで切り詰めると、`tool_use` / `tool_result`ペアの途中で簡単に切断してしまう可能性があります — 呼び出しを発火した`assistant`メッセージは保持するが、その直後にあった`tool_result`メッセージをスライスオフしてしまいます。その履歴をモデルに送信すると、プロトコル自体が壊れます。ドキュメントは、"Tool result blocks must immediately follow their corresponding tool use blocks in the message history."[^S7] (ツール結果ブロックは、メッセージ履歴内で対応するツール使用ブロックの直後に続かなければなりません) と明示しています。"tool_use ids were found without tool_result blocks immediately after" のようなエラーは、ペアリングが壊れていることを示す信号です[^S7] — モデルは「呼び出しを開始した」ことを見ますが、その呼び出しの結果を受け取ることがなく、次のリクエストは完全に失敗します。

## コンパクション: ウィンドウを1つの要約に圧縮する

切り詰めの問題は、全体のストレッチを破棄することです。情報を完全に捨てずにスペースを解放する方法はありますか？ それが**コンパクション**が解決する問題です。公式Cookbookはそれをこう定義しています: "Compaction distills the contents of a context window into a high-fidelity summary, letting the agent continue with minimal performance degradation when the conversation gets long."[^S2] (コンパクションは、コンテキストウィンドウの内容を高忠実度の要約に蒸留し、会話が長くなったときにエージェントが最小限のパフォーマンス低下で継続できるようにします)

切り詰めの「全体のストレッチを削除する」とは異なり、コンパクションは「全体を書き換える」ものです: 以前の会話履歴は、生のメッセージの長い実行を置き換え、ウィンドウの先頭に留まる単一の**高忠実度の要約**に圧縮されます。要約が保持するのは「何が起こり、何が結論されたか」です; それが削除するのは、一語一語の生の対話の詳細です。

ドキュメントは、このメカニズムのパラメータを詳しく説明しています。デフォルトの**トリガー閾値**があります — コンパクションは、ウィンドウ使用量が150Kトークンに達したときに自動的に発火します; 閾値は構成可能ですが、50Kトークンを下回ることはできません。これはサーバーで強制される下限です[^S2][^S8]。各トリガーは離散的な置換です: 大きな履歴のストレッチが要約と交換され、新しいメッセージはその後で通常どおり追加され続けます。これは1回限りのイベントではありません — ドキュメントは、長い会話が複数回コンパクトできることを明示しており、"The last compaction block reflects the final state of the prompt, replacing content prior to it with the generated summary."[^S8] (最後のコンパクションブロックは、プロンプトの最終状態を反映し、それ以前のコンテンツを生成された要約に置き換えます) 再びコンパクトすると、以前のコンパクションブロックは履歴の残りとともに新しい要約に折り畳まれます; コンパクションは、"user messages, assistant messages, tool calls, tool results, even prior compaction blocks are all flattened into the summary."[^S2] (ユーザーメッセージ、アシスタントメッセージ、ツール呼び出し、ツール結果、さらには以前のコンパクションブロックまでもがすべて要約に平坦化されます) という全トランスクリプト操作です。

コンパクションは無料ではありません。コンパクトする行為には追加のモデル呼び出しがかかり（要約モデルが実行されます）[^S2]、どれほど注意深く書かれても、要約は元の損失のあるバージョンです — "The summary preserves key decisions and facts but may drop specific numbers or exact phrasing."[^S2] (要約は重要な決定と事実を保持しますが、特定の数字や正確な言い回しを削除する可能性があります) 後のステップが、要約されてしまった小さな詳細（たとえば、ある変数の正確なスペル）に依存している場合、その詳細は失われている可能性があります。そのため、コンパクションは「全体的なコンテキストが大きくなりすぎた」という粗粒度の問題に適合しますが、あらゆる種類の履歴膨張の万能薬として機能するわけではありません。

## ツール結果クリアリング: 古くなった部分だけをクリアする

履歴膨張の大きな要因は、ツール呼び出し自体です。エージェントがファイルを読み取ったりコマンドを実行したりするたびに、完全な戻り値が履歴に詰め込まれます — 数千行の長さのファイルを読み取ると、誰もその詳細を必要としなくなった10ターン後でも、それらの数千行が`messages`配列にそのまま残ります。Cookbookはこれを直接指摘しています: "Tool-result clearing addresses the bloat from tool use itself. As an agent pulls in tools and calls them, the results pile up, and deciding how much of that tool output to keep becomes an increasingly important part of managing context."[^S2] (ツール結果クリアリングは、ツール使用自体からの膨張に対処します。エージェントがツールを引き込んで呼び出すと、結果が積み重なり、そのツール出力のどれだけを保持するかを決定することが、コンテキスト管理のますます重要な部分になります)

**ツール結果クリアリング**は、これに直接狙いを定めたメカニズムです: それは "drops old, re-fetchable results while keeping the record that the call happened."[^S2] (呼び出しが発生したという記録を保持しながら、古い再取得可能な結果を削除します) これが重要な区別です — クリアリングは、ツールが返した具体的なコンテンツ（それらの数千行のファイルコンテンツ）を削除しますが、「エージェントがこのパスで`read_file`を呼び出した」という記録を消去しません。そのコンテンツが後で再び必要になった場合、エージェントはどのツールを呼び出し、どの引数を渡したかを知っており、それを再度呼び出してコンテンツを取り戻すかどうかを決定できます。

そのトリガー閾値と保持ポリシーにも明確なデフォルトがあります: クリアリングはウィンドウ使用量が100Kトークンに達したときに発火し、デフォルトで最新の3つのツール呼び出しの完全な結果を保持し、古いツール結果をクリアします[^S2]。100Kトリガーはコンパクションの150Kよりも低く、その役割に適合しています — まず、「最も膨張しやすく、再取得が最も簡単な」ツール出力を処理し、それが十分でない場合は、全体的なウィンドウをコンパクションに引き渡します。

## 3つの中から選ぶ: メンタルモデル

これで2つのメカニズムが手に入り、レッスン3でカバーする外部メモリを加えると3つになります。Cookbookは、それらの分業を整理するコンパクトなメンタルモデルを提供します: "compaction compresses the whole window when it grows too large, clearing drops stale re-fetchable data inside the window, and memory moves information out of the window so it survives across sessions."[^S2] (コンパクションはウィンドウが大きくなりすぎたときに全体を圧縮し、クリアリングはウィンドウ内の古い再取得可能なデータを削除し、メモリはセッション間で存続するように情報をウィンドウの外に移動します)

それらの優先順位と使用例は競合していません — それらは階層化されています:

- ツール結果**クリアリング**は「このコンテンツはまだウィンドウ内にあるが古くなっており、削除しても問題ない。なぜなら再取得できるから」を処理します — 最も的を絞った、最も安価なものです。
- **コンパクション**は「ウィンドウ全体が大きくなりすぎた」を処理します。コンテンツがどこから来たかに関係なく、すべてを1つの要約に書き換えます — より広い範囲ですが、損失があり、追加のモデル呼び出しがかかります。
- **メモリ**（次のレッスンのトピック）は「この情報はこの1つの会話だけに存在すべきではなく、次のセッションまで持続する必要がある」を処理します — 「ウィンドウがすべてを保持できない」をまったく解決しているのではなく、「この会話が終わると、ウィンドウ内のすべてが消える」を解決しています。

このレッスンが冒頭で開いた質問に戻ります: 履歴が成長するだけなのは、誰も積極的にクリアしていないからです。切り詰め、コンパクション、およびツール結果クリアリングは、異なるコストと異なる状況でクリアする3つの方法です — どれを選ぶかは、何を保持したいか、そしてそれを保持するためにどれだけ支払う意思があるかに依存します。

### レベル1: 3つのシナリオに適したメカニズムを選ぶ

以下の3つのシナリオのそれぞれについて、切り詰め、コンパクション、またはツール結果クリアリングのどれが最も適しているかを判断し、理由を説明してください（理由は「膨張の具体的な原因」または「詳細を失う余裕があるか」に基づいている必要があります — 単に「こちらの方が適しているようだ」ではありません）。

1. コードレビューエージェントが`grep_code`を繰り返し呼び出してコードベースを検索し、各呼び出しで数十行のマッチを返します。ウィンドウ使用量は上限に近づいていますが、レビュータスクは完了していません。
2. サポートエージェントがユーザーと60ターンにわたってチャットしています。ウィンドウは全体的に大きくなり、ツール呼び出しと長いユーザーとエージェントの対話の両方を保持しています — コンテンツはあちこちから来ています。
3. メモ取りアシスタントエージェントは、毎日の新しいセッションの開始時に、ユーザーが先週言及した長期的な好み（「辛い食べ物は避ける」）を知る必要があります。このセッション自体は始まったばかりで、ウィンドウはまったくいっぱいではありません。

<!-- rubric -->
- シナリオ1はツール結果クリアリングを選び、膨張が再取得可能なツール戻りコンテンツから来ているという理由を挙げている
- シナリオ2はコンパクションを選び、コンテンツがあちこちから来ており、単一のソースをクリアするのではなく全体の書き換えが必要であるという理由を挙げている
- シナリオ3はメモリを選び（切り詰め/コンパクション/クリアリングではなく）、根本的な問題が「セッション間で存続する」であり、「このウィンドウがすべてを保持できない」ではないという理由を挙げている

<!-- answer -->
参考解答: シナリオ1は**ツール結果クリアリング**を使用すべきです — 膨張のほぼすべては`grep_code`の古い再取得可能な戻り結果から来ているため、呼び出し記録を保持しながら古い結果をクリアすることで、必要に応じて再度検索でき、コンパクションの追加オーバーヘッドは一切ありません。シナリオ2は**コンパクション**を使用すべきです — コンテンツはあちこちから来ており、ツール呼び出しと長い対話の両方があるため、単一ソースの問題ではありません; 全体のスレッドを保持しながらスペースを解放するには、ウィンドウ全体を1つの高忠実度要約に書き換える必要があります。シナリオ3は、切り詰め、コンパクション、またはツール結果クリアリングでは解決できません — このセッションのウィンドウはまったくいっぱいではなく、本当の問題は「先週言及された好みはこのセッションには単に見えない」ということです。これは、**メモリ**が解決する「セッション間で存続する」問題であり、「このウィンドウがすべてを保持できない」問題ではありません。これについては次のレッスンで詳しくカバーします。

まず自分に問いかけてください: このシナリオでは、問題は「この会話のウィンドウがもうすぐスペースがなくなる」ですか、それとも「情報が最後の会話からこの会話に引き継がれない」ですか？ これら2種類の問題は、まったく異なるソリューションを必要とします。

<!-- hint -->
「3つの中から選ぶ」セクションのメンタルモデルを思い出してください — クリアリングはウィンドウ内の古い再取得可能なデータをターゲットにし、コンパクションは大きすぎる全体的なウィンドウをターゲットにし、メモリはセッション間で存続することをターゲットにします。それらの仕事は重なりません。

### レベル2: バグにつながる切り詰めコードを診断する

以下の擬似コードは、ウィンドウ使用量が高すぎるときに履歴をクリアし、最新のメッセージだけを保持しようとします:

```javascript
function trimHistory(messages, maxKeep) {
  if (messages.length <= maxKeep) return messages;
  return messages.slice(-maxKeep);
}
```

ある時点で`messages`配列がまさにこの順序であるとします: `[..., { role: "assistant", content: [tool_use block] }, { role: "user", content: [tool_result block] }, ...]`、そして`maxKeep`がこれら2つのメッセージを分割し、`tool_result`メッセージだけを保持し、`tool_use`メッセージを切り取ることになります。

これがモデルに送信されたときにどのような問題を引き起こすかを説明し、それを回避する修正を提示してください（完全なコードは不要です — アイデアを明確にするだけで構いません）。

<!-- rubric -->
- モデルが対応する tool_use のない tool_result メッセージを見るため、プロトコル構造が壊れていることを指摘している
- 結果を述べている: モデルがエラーになるか混乱した動作をする可能性があり、単に「不完全な情報を持つ」だけではない
- 提案された修正は、カットポイントが tool_use / tool_result ペアの途中に決して着地しないことを保証する必要がある（たとえば、メッセージ数ではなく、完全な「ラウンドトリップ」を単位としてカットする）

<!-- answer -->
参考解答: この方法でカットすると、モデルには対応する`tool_use`ブロックが履歴のどこにも見つからない`tool_result`メッセージが残ります — プロトコルは、すべての`tool_result`の`tool_use_id`が履歴の前の方にある`tool_use`に一致することを要求し、その一致が今壊れているため、モデルは構造の異常でエラーになります（ドキュメントのエラーは「tool_use ids were found without tool_result blocks immediately after」ファミリーです）[^S7]。修正: メッセージをカウントしてカットしないでください — 「1つの完全なラウンドトリップ」を最小単位としてカットします。`assistant`メッセージに`tool_use`ブロックが含まれている場合、それは、その直後にある一致する`tool_result`を運ぶ`user`メッセージと一緒に保持または削除されなければなりません; ラウンドトリップを途中で分割することはできません。

<!-- hint -->
前のコースの「ツール呼び出しの完全なラウンドトリップ」を思い出してください — `tool_use`と`tool_result`は`tool_use_id`で結合されたペアであり、プロトコルはそれらが常に一緒に現れることを期待しています。

<!-- hint -->
「最後のNメッセージを保持する」とカウントするのではなく、アプローチを反転させてください: まず履歴を「1つの完全なラウンドトリップ」ユニットにグループ化し、次に最近のグループをいくつ保持するかを決定します。メッセージ配列を直接スライスする代わりに。

## まとめ

- デフォルトで会話履歴は成長するだけです: 各ターンのメッセージがウィンドウ内に積み重なり、以前のターンは完全に保持され、誰も積極的にクリアしないため、無制限に上昇します
- 切り詰めは最も単純ですが、それが削除するものは不可逆的であり、カットポイントが`tool_use` / `tool_result`ペアの途中に着地すると、ツール呼び出しのプロトコル構造を壊します
- コンパクションはウィンドウ全体の履歴を1つの高忠実度要約に書き換え、デフォルトで150Kトークンで発火します（閾値は50K未満にはできません。サーバーで強制されます）。損失があり、1回の追加モデル呼び出しがかかります; 長い会話は複数回コンパクトされる可能性があり、以前の要約ブロックは新しい要約に折り畳まれます[^S2][^S8]
- ツール結果クリアリングは、呼び出し記録を保持しながら、古い再取得可能なツール出力のみを削除し、デフォルトで100Kトークンで発火し、最後の3つの呼び出しの結果を保持します — コンパクションよりも的を絞っています
- 3つは異なる仕事を持っています: クリアリングは古い再取得可能なデータを処理し、コンパクションは大きすぎる全体的なウィンドウを処理し、メモリはセッション間で存続することを処理します — どれを選ぶかは、膨張の具体的な原因と詳細を失う余裕があるかどうかに依存します
