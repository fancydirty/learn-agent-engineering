# レッスン3: 外部メモリ: ファイルと検索

> 学習目標:
> - セッション間で存続しなければならないメモリが、ウィンドウの外、ファイルに書き込まれなければならない理由を説明する

> - メモリファイルを読み書きするツールに安全なパス境界チェックを追加する
>
> 前提: レッスン2を終え、コンパクションとツール結果クリアリングの違いを理解していること | 前: [レッスン2 <<](./02-managing-conversation-history.md) | 次: [レッスン4 >>](./04-structured-task-state.md)

## セッションが終了すると、ウィンドウ内のすべてが消える

レッスン2は未解決の問題で終わりました: スケジュールアシスタントにユーザーが先週「私は辛い食べ物を食べない」と伝え、今週ユーザーが空のウィンドウで新しい会話を開くと — エージェントはその文が言われたことを全く知りません。

切り詰め、コンパクション、ツール結果クリアリングではこれを修正できません。これら3つはすべて「この1つの会話内でスペースが不足した」を扱います。ここでの問題は異なります: この会話には、最初のターンから先週のコンテンツが全く含まれていませんでした。公式Cookbookは率直に線を引きます — クリアリングとコンパクションは両方とも現在のコンテキストで動作します; 新しいセッションが開始してウィンドウが空のときは、どちらも役に立ちません。メモリがその問題を解決します[^S2]。ウィンドウは、コンテナとして、この1つのセッションが続く限りしか存続しません。セッションを閉じると、他の場所に移動されなかったウィンドウ内のものは本当に消えます。

このセッションを超えて情報を生かし続ける唯一の方法は、セッションが終了する前に、ウィンドウの外のどこか — **外部メモリ**に書き込むことです: この会話のライフサイクルに縛られていないストレージ、通常は単にディスク上のファイルです。次のセッションが開始すると、そのファイルを読み戻し、その内容を新しいコンテキストウィンドウにロードします。

## CLAUDE.md: 人間が書き、毎回完全にロードされる

外部メモリの最も直接的なパターンは、人間が**メモリファイル**を維持し、プロジェクトに保存し、毎セッションの開始時に完全に読み込むことです。Claude CodeのCLAUDE.mdは代表的なケースです: 公式ドキュメントは、CLAUDE.mdファイルが毎セッションの開始時にコンテキストウィンドウにロードされ、会話自体と並んでトークンを消費し、推奨されるサイズターゲットは各ファイルを200行未満に保つことです — ファイルが長いほど、より多くのコンテキストを消費し、指示への遵守度が低下します。[^S3] 200行はソフトな推奨であることに注意してください; 実際のハードリミットは4 MiBです: それより大きいCLAUDE.mdは完全にスキップされます。[^S3]

```markdown
# CLAUDE.md

## Code style
- Indent with 2 spaces, never tabs
- Prefer const; reach for let only when you actually have to

<!-- This note is for future me. It doesn't need to be in the agent's context. -->
## Internal notes
- Gotcha from the last payments-module refactor: xxx
```

このファイルの1つの詳細は注目に値します: 公式ドキュメントは、CLAUDE.md内の**ブロックレベルのHTMLコメント**は、コンテンツがエージェントのコンテキストに注入される前に削除されることを説明しています。[^S3] 言い換えれば、`<!-- -->`の内側に書くものは、人間がファイルを開いたときには表示されますが、エージェントが読むバージョンにはそのコメントが含まれません — これにより、人間は「エージェントのトークン予算を消費せずに自分にメモを残す」方法を得ます。

CLAUDE.mdには、レッスン2のコンパクションに直接結びつく別の特性があります: ドキュメントは、プロジェクトルートのCLAUDE.mdがコンパクションを生き延びることを指摘しています — `/compact`の後、Claudeはそれをディスクから再読み取りし、セッションに再注入します。[^S3] 言い換えれば、このようなファイルはコンパクションによって「偶然保存される」のではありません; それは別途再読み取りされ再注入されます — そのコンパクションがその内容を要約に保持したかどうかにまったく依存しません。

## Autoメモリ: モデルが書き、オンデマンドで検索される

CLAUDE.mdは人間が書き、毎回完全にロードされます。補完的なパターンがあります: 会話が進むにつれて、モデルに覚えておく価値のあるものを書き留めさせ、それを独自のメモリファイルに保存します — Claude Codeはこのメカニズムを**Autoメモリ**と呼びます。CLAUDE.mdとの分業は補完的であり、比較表は違いを明確に示します: CLAUDE.mdはあなたが書き、AutoメモリはClaudeが書きます。[^S3]

モデル自身が書くメモリは通常、2つの層に分かれています: インデックスファイル（たとえば、`MEMORY.md`）と、トピックごとに分類された特定のメモリファイルの山です。インデックスファイルも無制限にロードされるわけではありません — ドキュメントが与えるルールは: 毎会話の開始時に、`MEMORY.md`の最初の200行、または最初の25KB、どちらか先に達した方のみがロードされます; その閾値を超えるコンテンツはセッション開始時にロードされません。[^S3]

これが**オンデマンド検索**です: セッションの開始時に、エージェントはインデックスエントリの要約（「このトピックの詳細なノートはあるファイルにある」のようなもの）のみを見て、各特定のメモリファイルの完全な内容は見ません。ドキュメントは直接的です: トピックファイルは起動時にロードされません; Claudeは情報が必要なときに標準のファイルツールでそれらをオンデマンドで読み取ります[^S3]。現在のタスクが実際に特定のトピックを必要とするときにのみ、その特定のメモリファイルのコンテンツがこのラウンドのコンテキストウィンドウに引き込まれます。

並べて見ると、CLAUDE.mdとAutoメモリはメモリの2つの異なる次元を処理します:

- **CLAUDE.md** — 人間がキュレートし、サイズ管理された、毎回適用されるルールと規約; 「プロジェクトがどのように機能することになっているか」といった安定した情報に適合し、前もって完全にロードされます。
- **Autoメモリ** — 数が多く、特定のタスクにのみ重要な特定の詳細; オンデマンド検索に適合し、このタスクが必要としないメモリにウィンドウ予算が浪費されません。

両方とも外部メモリです。唯一の違いは「誰がそれを書くか」と「いつそれがロードされるか」です — これはレッスン2のメンタルモデルと呼応しています: メモリの目的は、セッション間で存続するように情報をウィンドウの外に移動することであり、その情報が前もって完全にロードされるか、オンデマンドで検索されるかは、それがどれだけ安定しているか、どのくらいの頻度で使用されるかによって決まります。

## メモリファイルの読み書きに安全な境界を追加する

CLAUDE.mdのような人間が書いたファイルでも、Autoメモリのようなモデルが書いたファイルでも、エージェントがメモリファイルを読み書きするためのツールを持つと、具体的なエンジニアリング上の質問に直面します: そのツールは、プロジェクトディレクトリの外のファイルを読み書きするように説得できますか？

文字列プレフィックスマッチだけを行うパスチェックは、「メモリディレクトリをエスケープする」リクエストをブロックするように見えますが、古典的な穴があります。メモリルートが`/project/memory`の場合、単純な`startsWith("/project/memory")`チェックは、`/project/memory-evil`のようなパスも通します。なぜなら、それはその文字列で始まるからです — それがメモリルートの外にある完全に異なるディレクトリであるにもかかわらず。安全な方法は、パスがルートと完全に等しいか、「ルート + パス区切り文字」で始まることを要求することです:

```javascript
const path = require("node:path");
const MEMORY_ROOT = path.resolve("./memory");

async function readMemoryFile({ path: relPath }) {
  const abs = path.resolve(MEMORY_ROOT, relPath);
  const inRoot = abs === MEMORY_ROOT || abs.startsWith(MEMORY_ROOT + path.sep);

  if (!inRoot) {
    return "Refused: path is outside the memory directory, and this tool is not allowed to read files outside it.";
  }

  const fs = require("node:fs/promises");
  return await fs.readFile(abs, "utf-8");
}
```

組み合わせ`abs === MEMORY_ROOT || abs.startsWith(MEMORY_ROOT + path.sep)`が、「ルート自体と等しいパス」または「ルート + セパレータで始まるパス」のみが通過することを実際に保証するものです — `/project/memory-evil`は、どちらの条件も満たさないため、`/project/memory`内のパスと間違えられることはありません。このパターンは、レッスン6で永続的なメモリレイヤーの読み書きツールを構築するときに直接再利用され、レッスン5では、この境界チェックが無力である場合に、メモリファイルがどのような攻撃対象になるかを明確にします。

## 💻 演習

### レベル1: メモに適したメモリの場所を選ぶ

以下の4つの情報のそれぞれについて、CLAUDE.mdとAutoメモリのトピックファイルのどちらに適しているかを決定し、理由を述べてください。

1. 「このプロジェクトは4スペースでインデントし、決してタブを使わない」 — プロジェクトが作成された日から変更されていない。
2. 「先週の水曜日に本番環境のタイムアウトを追跡しました; 根本原因はデータベース接続プールが小さすぎるように設定されていたことで、その時に50に引き上げました」 — 後で同様の問題に役立つかもしれない過去のイベントの一回限りの記録。
3. 「前の会話で、ユーザーは彼らのチームのコードレビュープロセスが最初にlint、次に人間によるレビューであると言及しました」 — このユーザーとやり取りするセッションでのみ関連する。
4. 「この会話で、ユーザーは特定の関数を同期実装に変更する一回限りのリクエストをしました」 — この1つのタスクにのみ関連する; 次のセッションでほぼ確実に出てこない。

<!-- rubric -->
- 項目1はCLAUDE.mdと判断され、「安定していて、毎回役立つ」と言及する理由がある
- 項目2と3はAutoメモリと判断され、「潜在的に大きく、特定のタスクにのみ役立ち、オンデマンド検索に適している」と言及する理由がある
- 項目4は外部メモリをまったく必要としないと判断され、「この1つのセッションにのみ関連し、セッション間で存続する必要がない」と言及する理由がある

<!-- answer -->
参考解答: 項目1は**CLAUDE.md**に適合します — これはプロジェクトが始まって以来安定している規約であり、すべてのセッションで役立ち、CLAUDE.mdの「人間がキュレートし、サイズ管理され、毎回役立つ」という役割に一致します。項目2と3は**Autoメモリ**のトピックファイルに適合します — どちらも時間とともに積み重なる可能性のある特定の歴史的詳細であり、同様の状況が発生したときにのみ検索が必要であり、毎回完全にロードするのには適していません。これがまさにオンデマンドケースです。項目4は外部メモリを**まったく**必要としません — この1つのセッションにのみ関連し、セッション間で存続する必要はありません; それを外部メモリに書き込むことは単なる無駄になります。このような情報は現在のセッションのコンテキストウィンドウに留まり、セッションが終了したときに自然に消え、それが期待される動作です。

<!-- hint -->
2つのテストがあります: この情報は「安定しているか、それとも変化するか」、そして「すべてのセッションで役立つか、それとも特定の状況でのみ役立つか」です。

<!-- hint -->
項目4は「記録すべき」と誤判断しやすいです — しかし、このレッスンが開いた問題を思い出してください: 外部メモリは「セッション間で存続する」を解決するために存在します。1つのセッションにのみ関連する情報は、外部メモリに書き込んでも何も得られず、ストレージと後の検索コストを無駄にするだけです。

### レベル2: バグのあるパスチェックを診断する

以下のコードは、メモリ読み取りツールを`MEMORY_ROOT`ディレクトリ内のファイルに制限しようとしています:

```javascript
const MEMORY_ROOT = "/project/memory";

async function readMemoryFile({ path: relPath }) {
  const abs = require("node:path").resolve(MEMORY_ROOT, relPath);

  if (!abs.startsWith(MEMORY_ROOT)) {
    return "Refused: path out of range.";
  }

  return await require("node:fs/promises").readFile(abs, "utf-8");
}
```

このコードのセキュリティホールを見つけ、チェックをバイパスして`MEMORY_ROOT`の外のファイルを読み取る具体的なパス例を示し、修正されたチェック条件を書いてください。

<!-- rubric -->
- `startsWith`を単独で使用すると同じプレフィックスバイパス問題があることを指摘している
- チェックをバイパスする具体的なパス例を示している（たとえば、`/project/memory-evil`のようなディレクトリに解決される）
- 修正された条件は、「ルート自体と等しい」と「ルート + パス区切り文字で始まる」の両方を含んでいる必要がある

<!-- answer -->
参考解答: ホールは、`abs.startsWith(MEMORY_ROOT)`が「同じプレフィックスだが実際には異なるディレクトリ」というケースを無視する単純な文字列プレフィックスマッチであることです。例: ディレクトリ`/project/memory-evil`がディスク上に存在する場合、`relPath`が解決されて`abs`が`/project/memory-evil/secrets.txt`になると、`"/project/memory-evil/secrets.txt".startsWith("/project/memory")`は`true`を返します — それはその文字列で始まりますが、`memory-evil`は`MEMORY_ROOT`内にない完全に異なるディレクトリであり、チェックがバイパスされます。修正された条件は`abs === MEMORY_ROOT || abs.startsWith(MEMORY_ROOT + path.sep)`であるべきです: ルートと完全に等しいパス、または「ルート + パス区切り文字」で始まるパスのみが、真にルート内にあるとカウントされます。`/project/memory-evil`は`/project/memory`と等しくなく、`/project/memory/`で始まらず、どちらの条件も満たさず、正しく拒否されます。

<!-- hint -->

## まとめ

- セッションが終了すると、外に移動されなかったウィンドウ内のものは永久に失われます; セッション間で情報を保持するには、セッションが終了する前にウィンドウの外の外部メモリに書き込まなければなりません
- CLAUDE.mdは人間が書き、毎セッション完全にコンテキストにロードされ、公式サイズターゲットは200行です（ハードリミット4 MiB、より大きいファイルは完全にスキップされます）; ブロックレベルのHTMLコメントは注入前に削除され、プロジェクトルートのCLAUDE.mdは`/compact`の後に再読み取りされ再注入されます[^S3]
- Autoメモリはモデルが書き、インデックスファイルと特定のトピックファイルに分割されます; インデックスは最初の200行または25KBのみをロードし、トピックファイルは起動時にロードされず、必要なときにオンデマンドで読み取られます[^S3]。そのため、使用されないメモリにウィンドウ予算が浪費されません
- 2つは補完的です: CLAUDE.mdは毎回役立つ安定したルールに適合します; Autoメモリは特定のタスクにのみ必要な大量の詳細に適合します
- メモリファイルの読み書きツールは、安全なパス境界チェックを行う必要があります; 組み合わせ条件`abs === ROOT || abs.startsWith(ROOT + path.sep)`は両方の半分が必要です。単独の`startsWith`チェックには同じプレフィックスバイパスホールがあるためです
