# レッスン4: 副作用と冪等性: 再開時に再実行しても安全なツールはどれか

> 学習目標:
> - 再開時のリプレイが、既定で **at-least-once**（少なくとも1回）の実行セマンティクスになり、exactly-once には決してならない理由を説明する
> - ツール操作が冪等かどうかを判断し、2回走った瞬間に実害を生む副作用を見抜く
> - `tool_use_id`をキーにした**副作用台帳**を設計・実装し、再開時の宙ぶらりんな呼び出しが、実際に実行するかどうかを決める前に台帳を確認するようにする
>
> 前提: レッスン2とレッスン3を読み、`checkpoint.json`に残った宙ぶらりんな`pendingToolUse`の調整ルール（レッスン3）を理解していること。このシリーズの第7コース「Agent Harness Fundamentals: Loops and Control」の`HIGH_IMPACT`ツール集合と実行前の承認ゲートを知っていること | 前: [レッスン3 <<](./03-resume-from-checkpoint.md) | 次: [レッスン5 >>](./05-rewind-and-fork.md)

## 再開が与えるのは at-least-once: レッスン3が積み残した高影響ツール

レッスン3では、`checkpoint.json`から`pendingToolUse`を読み出し、それを使って宙ぶらりんな呼び出し——クラッシュがツール実行と台帳への書き込みのあいだに落ちたもの——をループへ引き戻す方法を学びました。そのときの調整ルールはこうでした。読み取り専用ツールはそのまま再実行する。判断のつかない高影響ツールには`is_error`の`tool_result`を追加し、ループが詰まった状態から抜けられるようにして、問いは人間に返す。これは誠実なフォールバックであり、同時に未解決の問題でもあります。「判断がつかない」とは、そのタスクが自力では先へ進めないということです。つまり、高影響ツールでクラッシュが起きるたびに、誰かが見張っていなければなりません。

根っこにあるのはこれです。再開はその性質上、**at-least-once**の実行セマンティクスを与えます。ツールが本当に成功した後、その結果が`messages`に書き戻される前、あるいはチェックポイントにコミットされる前にプロセスが死ぬことはありえます。そしてその時点で、「このツールは走ったのか、走らなかったのか」は`checkpoint.json`だけでは答えられない問いになります。`read_file`のような読み取り専用ツールなら、わからなくても何も失いません。もう一度読んでも結果は同じです。しかし`send_email`や`create_ticket`、あるいは送金となると、わからないことがそのままインシデントになります。再実行すれば受信者に同一のメールが2通届くかもしれず、重複したチケットがどこからともなくシステムに現れるかもしれません。

これは新しい問題ではありません。このコースの前半で、エージェントはステートフルであり、エラーは積み重なる[^S1]という点を確認しました。1回だけ起きるはずだった副作用を2回実行してしまうことは、その「積み重なり」が取る具体的な形の一つです。エラーは「1回余分に走らせた」で止まりません。その余分な副作用の上に乗って、下流へ転がっていきます。このレッスンでは、レッスン3が開けたままにした穴を塞ぎます。まず**冪等性**という概念を導入し、次に再開ループに**副作用台帳**を取り付けて、「判断がつかない」を「判断がつく」に変えます。

## 冪等とは何か: 1回でも10回でも、同じ効果

**冪等**とは、1回実行しても何回実行しても、最終的な効果が同じになる操作のことです。ここで問題にしているのは*効果*——その操作が外の世界（ファイル、データベース、受信箱）に残す最終状態——であって、各呼び出しが文字通り返す値ではない点に注意してください。

ツールが冪等かどうかを判断するには、質問が一つあれば足ります。「この操作が気づかれないままもう1回走ったとして、外の世界には何かが余分に増えるか、あるいは違う状態になるか？」次の小さな例をその質問にかけてみると、違いはすぐに現れます。

```javascript
// 冪等: ファイルを読むだけなら副作用はない — 何回呼んでも、
// ディスク上にあるものは同じ
async function readFileContent(path) {
  return fs.readFile(path, "utf8");
}

// 非冪等: 呼び出すたびに、配列に本当にもう1行増える
function appendRow(sheet, row) {
  sheet.rows.push(row);
}

// 冪等: 何回呼んでも、42行目は同じ値に収束する
function setLine(doc, lineNo, text) {
  doc.lines[lineNo] = text;
}

// 非冪等: 呼び出すたびに、受信者の受信箱に本当にもう1通増える
async function sendEmail(to, subject, body) {
  return mailer.send({ to, subject, body });
}
```

`readFileContent`は、そもそも副作用がまったくないという理由で冪等です。「残るもの」と呼べるものが何もありません。`setLine`も冪等ですが、こちらは実際に状態を変更します。ただし変更の仕方が**上書き**です。1回呼べば42行目はXになり、10回呼んでも42行目はやはりXのままです。最終状態が呼び出し回数によって変わりません。`appendRow`と`sendEmail`が冪等でない理由は、どちらも同じです。効果が**累積的**だからです。呼び出すたびに外の世界へ本当にもう一つ足されるので、呼び出し回数が最終状態にそのまま現れます。

この境界線を覚えておいてください。上書き型の書き込みはたいてい冪等で、追記型の書き込みはたいてい冪等ではありません。読み取りや「先に確認してから、動くかどうかを決める」型の操作はたいてい冪等で、条件なしの単純な挿入はたいてい冪等ではありません。次のセクションの副作用台帳は、冪等でなく、しかも設計変更では冪等にできない操作を捕まえるためにこそ存在します。

## 副作用台帳: どの副作用がすでに起きたかを書き留める

レッスン2では、ループの走っている現場——`messages`、各種カウンター、まだ台帳に書かれていないツール呼び出し——をチェックポイントに保存し、クラッシュしてもその場から拾い直せるようにする方法を学びました。しかしチェックポイントが答えるのは「ループのどのステップまで到達したか」であって、「そのステップの副作用が実際に起きたか」ではありません。通常運転中はこの二つはほぼ歩調を合わせて動きますが、その隙間にクラッシュが落ちた瞬間に食い違います。レッスン3が高影響ツールの調整を未解決のまま残さざるをえなかったのは、まさにこれが理由です。

この隙間を塞ぐには、**副作用台帳**が要ります。どの副作用がすでに起きたかを、チェックポイントとは別に、ディスク上に書き留めるのです。構造は単純で、`tool_use_id`をキーにしたマップです。

```javascript
// effects.json の形
{
  "toolu_01abc": {
    "name": "create_ticket",
    "result": { "id": "T-1", "title": "顧客の障害報告" },
    "at": "2026-08-26T09:12:03.000Z"
  }
}
```

台帳を書くタイミングは非常に重要です。ツール関数が実際に成功して結果を返した、その瞬間に書きます。しかもレッスン2の「地点B」のチェックポイント（ツール結果が`messages`に入った後に行われる定型の書き込み）よりも一拍*早く*書きます。理由は直接的です。「ツールが成功した」から「地点Bのチェックポイントの書き込みが終わった」までの狭い窓の中にクラッシュが落ちた場合、地点Bのチェックポイントはこれが起きたことを記録する機会を得ていません。再開時に真実を教えてくれるのは、より早く書き終えていた台帳だけです。台帳の書き込み自体も、レッスン2とレッスン3の`.tmp`＋`rename`によるアトミックな書き込みを使わなければなりません。理由は同じで、中途半端に書かれた台帳ファイルは、台帳がまったくないよりも危険だからです。実際には完了しなかった副作用を、あなたに信じ込ませてしまいます。

```javascript
import { promises as fs } from "node:fs";

async function loadEffects(path) {
  try {
    return JSON.parse(await fs.readFile(path, "utf8"));
  } catch {
    return {}; // ファイルが無い、または壊れている場合: 空の台帳として扱い、再開を止めない
  }
}

async function saveEffects(path, effects) {
  const tmp = `${path}.tmp`;
  await fs.writeFile(tmp, JSON.stringify(effects, null, 2));
  await fs.rename(tmp, path); // アトミックな入れ替え。中途半端なファイルを残さない
}
```

台帳が手元にあれば、再開時の調整ルールはレッスン3の「判断がつかない」から「判断がつく」へ格上げされます。`checkpoint.json`から取り出した`pendingToolUse`の`id`を、台帳で引くのです。**ヒット**した場合、その副作用は本当に起きているので、台帳に保存された`result`を取り出して`tool_result`を埋め、二度と実行しません。**ミス**した場合、この呼び出しは開始すらしなかったか、成功しないまま途中で死んだかのどちらかなので、実行しても安全です。このルールはすべてのツールに当てはまります。ただ、冪等なツールにとってはこの照合がどちらに転んでも影響がない、というだけのことです。実際にこれに依存するのは、繰り返されると実害を生む操作のほうです。

ここには単独で述べる価値のある洞察が一つあります。**`tool_use_id`はすでに冪等キーである**、ということです。モデルがツールを名指しするたびに、その呼び出しは "A unique identifier for this particular tool use block"[^S4]（この特定のツール使用ブロックに対する一意な識別子）を伴います。これは公式仕様の`id`フィールドの定義そのままです。同じ名指しが再開時のリプレイによってもう一度見えたとしても、`id`は変わりません。台帳が「この呼び出し」と「さっきのあの呼び出し」を同一の出来事として認識できるのは、まさにこの性質のおかげです。あなたが独自の重複排除の仕組みを考案する必要はありません。

## 2段のゲート: 承認は「やるべきか」を、台帳は「もうやったか」を問う

このシリーズの第7コース「Agent Harness Fundamentals: Loops and Control」では、`runToolUses`に承認ゲートを取り付けました。高影響ツールが実際に走る前に、これから何が起きるかを表示し、人間の確認を待ち、そのうえで初めて通す、というものです[^S3]。このゲートが止めるのは「これはやるべきか」という問いです。このレッスンの副作用台帳が止めるのは別の問い、「これはもうやったか」です。二つのゲートは違うことを問いますが、置かれる場所は同じです。どちらも、モデルがツールを名指しした後、ツールが実際に走る前の瞬間にねじ込まれます。どちらも、確認が済むまでツール関数を実行させません。

この二つを重ねると、`runToolUses`はこうなります。

```javascript
const HIGH_IMPACT = new Set(["send_email", "create_ticket", "delete_file"]);

async function runToolUses(content, toolImpls, opts = {}) {
  const toolUseBlocks = content.filter((b) => b.type === "tool_use");
  const effects = await loadEffects(opts.effectsPath);
  const results = [];

  for (const block of toolUseBlocks) {
    // 冪等性ゲート: この呼び出しはすでに実際に起きているか？
    const recorded = effects[block.id];
    if (recorded) {
      results.push({ type: "tool_result", tool_use_id: block.id, content: recorded.result });
      continue; // 台帳ヒット: 保存済みの結果を再利用し、二度と実行しない
    }

    // 承認ゲート: 高影響な操作は実行前に確認を取る（第7コース）
    if (HIGH_IMPACT.has(block.name)) {
      const ok = await opts.approve?.(block.name, block.input);
      if (!ok) {
        results.push({
          type: "tool_result", tool_use_id: block.id,
          content: "ユーザーがこの高影響な操作を拒否しました。実行していません。", is_error: true,
        });
        continue; // 実行はスキップするが、呼び出しを宙ぶらりんにしないよう tool_result は返す
      }
    }

    let output;
    try {
      output = await toolImpls[block.name](block.input);
    } catch (err) {
      // ツール自体が失敗した: 副作用は起きていないので、正直に is_error を報告する
      results.push({
        type: "tool_result", tool_use_id: block.id,
        content: `ツールの実行に失敗しました: ${err.message}`, is_error: true,
      });
      continue;
    }

    // ここまで来たなら、副作用は本当に起きている。たとえ下の台帳書き込みが失敗しても、
    // 実行失敗として誤報してはならない — is_error を返した時点でモデルはこれが走らなかったと
    // 判断し、新しい tool_use_id で再試行するため、台帳はもうそれを同じ呼び出しとして
    // 認識できなくなる。重複した副作用はそうやってすり抜ける。
    effects[block.id] = { name: block.name, result: output, at: new Date().toISOString() };
    try {
      await saveEffects(opts.effectsPath, effects); // 成功したら即座に書く。まとめ書きはしない
    } catch (err) {
      // 書き込み失敗はツールの問題ではなく運用の問題: モデルには本当の結果を返し、
      // 別途アラートを上げる
      console.error(
        `[台帳の書き込みに失敗] tool_use_id=${block.id} name=${block.name}: ` +
        `副作用は起きたが記録されていない。再開時に再実行の恐れあり。手動確認が必要。原因: ${err.message}`,
      );
    }
    results.push({ type: "tool_result", tool_use_id: block.id, content: output });
  }
  return results;
}
```

この順序は交渉の余地がありません。冪等性ゲートが先に来なければならないのです。理由は明白で、この呼び出しがすでに台帳にあるなら、後から「やるべきか」と尋ねても意味がありません。すでに終わっているからです。しかも尋ねられた人を混乱させるだけです——システムはこれを明らかに完了しているのに、なぜ私に確認を求めてくるのか、と。再開時の宙ぶらりんな呼び出しに対して、最初の問いは常に「これは起きたか」であり、それが片付いて初めて「これはやるべきか」の出番が来ます。

## ツール設計層での冪等性: 火消しではなく、原因を直す

副作用台帳はハーネス側のバックストップです。ツール自体が冪等に設計されていようがいまいが、台帳は`tool_use_id`を使って重複実行を止められます。しかしバックストップはあくまでバックストップであり、より良い投資は原因を直すことです。ツールを変更できるなら、そもそも冪等になるよう設計し、台帳の出番が来ないようにするのです。

その変更の最も一般的な形は、「作成する」を「存在を保証する」に変えることです。

```javascript
// 原因を直す: 本質的に冪等 — 先に確認し、あればそれを返し、作り直さない
async function ensureTicket(input) {
  const existing = await findTicketByTitle(input.title);
  if (existing) return existing;
  return createTicketRecord(input);
}
```

`ensureTicket`を1回呼んでも10回呼んでも、そのタイトルに一致するチケットはシステムにちょうど1枚だけ残ります。最終状態が呼び出し回数によって変わらない——これが冪等の定義そのものです。同じ考え方はファイルの書き込みにも当てはまります。ファイル全体を書く`write_file`は本質的に冪等で、繰り返し呼んでも残る内容は同じです。追記型の`append_file`はそうではなく、呼び出しごとにファイルが1セクションずつ伸びていきます。上書きを選べるなら、追記を選ばないことです。

原因を直すことと火消しをすることは、二択ではありません。役割分担です。冪等に設計できるツールはツール層で解決し、すべての呼び出しに台帳経由の遠回りをさせずに済ませるべきです。そして、業務ロジックの問題として本当に「重複排除してまとめる」ことができない操作——たとえば、異なる時刻に本当に起きた2件の送金で、2つの別個の出来事として認識されるべきであり、設計の工夫で1件に畳み込むことができないもの——については、台帳が唯一のバックストップです。

## 呼応: もう一つのガードレールと、それが割に合うタイミング

このコースは、信頼性はモデルの適応力を、リトライロジックや定期的なチェックポイントのような決定論的なセーフガードと組み合わせることから生まれる[^S1]、という点を出発点にしました。副作用台帳はそのガードレールの一つです。それはモデルに「自分はもうこれをやったか」を判断させません——それは最初からモデルの知覚できる範囲の外にありました。台帳は、ディスク上に書かれた確たる証拠を使って、ハーネスにその判断をモデルの代わりに下させるのです。

同時に、程度の感覚も持っていてください。エージェントが持つツールがすべて読み取り専用なら、このレッスンの台帳はおそらく元が取れません。副作用台帳それ自体が一層の複雑さであり、それを追加するに値する理由は、重複した副作用という現実のリスクを実際に食い止めることです。複雑さは、成果を明らかに改善する場合にのみ追加すべきです[^S3]。判定基準は前のレッスンと同じです。まず自分のツール集合の中に、冪等でない高影響な操作があるかを見ること。あるならゲートは取り付ける価値があります。ないなら、急いで書く必要はありません。

## 💻 演習

### レベル1: 6つのツールを冪等性と再実行リスクで評価する

以下の6つのツールそれぞれについて、次を判断してください。(1) 冪等かどうか。(2) 再開時にその宙ぶらりんな呼び出しが再実行された場合、リスクは高・中・低のどれか、そしてその理由。

- `read_file(path)` — ファイルの内容を読む
- `send_email(to, subject, body)` — メールを送信する
- `ensure_ticket(title, body)` — タイトルで検索し、既存のチケットがあればそれを返し、なければ新規作成する
- `append_log(line)` — ログファイルの末尾に1行追記する
- `set_config(key, value)` — 設定キーに指定の値をセットする（上書き）
- `delete_file(path)` — ファイルを削除する

<!-- rubric -->
- 6つの冪等性判定がすべて正しい（冪等: read_file、ensure_ticket、set_config、delete_file / 非冪等: send_email、append_log）
- リスクレベルが妥当で、単なるラベルではなく理由が付いている（高・中・低には必ず「なぜ」の裏付けがあること）
- ツールの実装の丁寧さに冪等性が依存するケースを少なくとも1つ挙げている（ensure_ticket の検索ロジック、または delete_file が「ファイルが見つからない」をどう扱うか）

<!-- answer -->
`read_file`は冪等で、本質的に副作用がなく、再実行のリスクはゼロです（低）。`send_email`は非冪等です。呼び出すたびに受信者の受信箱へ本当にもう1通入るので、再開時に宙ぶらりんな呼び出しを再実行すると重複送信になります。リスクは高く、台帳を確認した後でなければリプレイは安全になりません。`ensure_ticket`は設計上冪等です。同じタイトルのチケットがすでに存在するときは作成をスキップするので、システムの最終状態が呼び出し回数によって変わりません。ただしその冪等性は「タイトルで検索する」ロジックが健全であることの上に成り立っています。タイムスタンプのように毎回変わるものがタイトルに入っていれば、検索は一致しなくなり、冪等性は名ばかりのものになります。リスクは低〜中と評価し、そのうえで台帳による裏打ちは付けておきましょう。`append_log`は非冪等です。呼び出すたびに本当に1行増えるので、再開時の再実行はログに重複エントリを残します。リスクは中です。重複メールのような業務インシデントではありませんが、ログを汚し、行数を数えたり内容を照合したりする下流のロジックを狂わせる可能性があります。`set_config`は冪等で、上書き型の書き込みです。同じキーに同じ値をセットする限り、何回呼んでも最終状態は同じなので、リスクは低く、再実行して構いません。`delete_file`は冪等です。すでに消えているファイルを削除しても、最終状態はそのファイルが単に存在しない状態と同じなので、リスクは低いです。ただし実装の細部に注意してください。`delete_file`がファイル不在で例外を投げ、呼び出し側がそれを実行失敗として扱うと、再実行が新たな失敗として誤読されます。「ファイルが見つからない」は、冪等性の意味では成功として扱うべきです。

<!-- hint -->
いったんリスクは脇に置いて、6つを二つのグループに仕分けてみてください。上書きする効果と、積み上がる効果です。この境界線はレッスンの本文にあります。仕分けが正しくできれば、冪等性の判定はおおむね自然に決まります。

<!-- hint -->
リスクレベルは「冪等なら低、非冪等なら高」の単純な写しではありません。`append_log`と`send_email`のどちらの結果がより深刻かを考えてみてください。そのうえで、`ensure_ticket`の冪等性がどんな前提の上に成り立っているか、その前提が崩れたときに何が起きるかを考えてみてください。

### レベル2: 台帳のない runToolUses に副作用台帳を追加する

先週、あなたのハーネスは「顧客が障害を報告したのでチケットを起票する」というタスクを処理していました。`create_ticket`を実行して成功の結果を得た——ちょうどそのとき、コンテナがたまたま再起動されて落とされました。結果が`tool_result`に戻る前のことです。プロセスが復帰した後、ハーネスは`checkpoint.json`から`pendingToolUse`を読み、まさにその`create_ticket`呼び出しを見つけました。以下の台帳を持たない`runToolUses`では、選べる手は再実行しかありません。その結果、1件の顧客障害報告が、どこからともなくシステムに現れた重複チケットになりました。

```javascript
// 事故の現場: この runToolUses には副作用台帳がない
async function runToolUses(content, toolImpls) {
  const toolUseBlocks = content.filter((b) => b.type === "tool_use");
  const results = [];
  for (const block of toolUseBlocks) {
    const output = await toolImpls[block.name](block.input);
    results.push({ type: "tool_result", tool_use_id: block.id, content: output });
  }
  return results;
}
```

あなたのタスク: (1) `effects.json`用の`loadEffects`/`saveEffects`という読み書き関数を、アトミックな書き込み（先に`.tmp`、次に`rename`）で書くこと。(2) `runToolUses`を書き直し、「実行前に台帳を確認し、ミスしたときだけ実行し、実行が成功した瞬間に台帳へ記録する」ロジックを追加すること。(3) それを証明するNodeスクリプトを書くこと。書き直した`runToolUses`を同じ`tool_use_id`で2回呼び（再開時のリプレイのシミュレーション）、2回目の呼び出しが本物の`create_ticket`実装を再度走らせないことを示すこと。

<!-- rubric -->
- `loadEffects`/`saveEffects` が対象ファイルを直接書くのではなく `.tmp` ＋ `rename` のアトミックな書き込みを使っている。`loadEffects` はファイル不在を処理し（空オブジェクトを返す）、再開そのものがクラッシュしない
- 書き直した `runToolUses` が実行前に `block.id` で台帳を引き、ヒット時は `toolImpls` を呼ばずに保存済みの `result` を再利用する。台帳の書き込みは実行が本当に成功した後にのみ行い、プレースホルダではなくこの呼び出しの実際の結果を書く
- 検証スクリプトが呼び出し回数を数える偽の `create_ticket` を使い、「同じ tool_use_id での2回目の呼び出しではカウンタが増えない」ことを証明している — 例外が出なかったというだけでなく、台帳の確認が実行を防いだという実際の証拠になっている

<!-- answer -->
```javascript
import { promises as fs } from "node:fs";

async function loadEffects(path) {
  try {
    return JSON.parse(await fs.readFile(path, "utf8"));
  } catch {
    return {};
  }
}

async function saveEffects(path, effects) {
  const tmp = `${path}.tmp`;
  await fs.writeFile(tmp, JSON.stringify(effects, null, 2));
  await fs.rename(tmp, path);
}

async function runToolUses(content, toolImpls, opts) {
  const toolUseBlocks = content.filter((b) => b.type === "tool_use");
  const effects = await loadEffects(opts.effectsPath);
  const results = [];
  for (const block of toolUseBlocks) {
    const recorded = effects[block.id];
    if (recorded) {
      results.push({ type: "tool_result", tool_use_id: block.id, content: recorded.result });
      continue;
    }
    const output = await toolImpls[block.name](block.input);
    effects[block.id] = { name: block.name, result: output, at: new Date().toISOString() };
    await saveEffects(opts.effectsPath, effects);
    results.push({ type: "tool_result", tool_use_id: block.id, content: output });
  }
  return results;
}

// 検証: 同じ tool_use_id でリプレイしたとき、2回目はチケットを起票しない
let calls = 0;
async function createTicket(input) {
  calls += 1;
  return { id: "T-1", title: input.title };
}

const block = {
  type: "tool_use",
  id: "toolu_01abc",
  name: "create_ticket",
  input: { title: "顧客の障害報告" },
};
const effectsPath = "./effects.json";

await runToolUses([block], { create_ticket: createTicket }, { effectsPath });
console.assert(calls === 1, "1回目の呼び出しは実際に実行されるはず");

// 再開のシミュレーション: 同じ tool_use_id が pendingToolUse に再び現れる
await runToolUses([block], { create_ticket: createTicket }, { effectsPath });
console.assert(calls === 1, "2回目の呼び出しは台帳にヒットし、実行されないはず");

console.log("calls =", calls); // calls = 1 と出力され、リプレイが2枚目のチケットを起票しなかったことを示す
```

このコードはNodeで実行して検証済みです。1回目の`runToolUses`呼び出しでは台帳が空なので`create_ticket`が本当に1回実行され、`calls`は1になり、台帳ファイルにその呼び出しの結果が記録されます。2回目の呼び出しは、同じ`tool_use_id`での再開時リプレイをシミュレートしています。`runToolUses`はそのidを台帳の中に見つけ、保存されている`result`をそのまま`tool_result`に落とし込むので、`toolImpls.create_ticket`は二度と呼ばれません——`calls`は1のままです。これこそ副作用台帳が証明すべきことです。再開時のリプレイは、すでに完了した副作用をもう一度起こさせません。

<!-- hint -->
台帳が書かれるかどうかは、ツールが実際に成功したかどうかで決まるのであって、`for`ループがこの地点まで到達したかどうかではありません。`saveEffects`は`toolImpls[...]`の呼び出しの**後**、かつ結果を手にした**後**に置かなければなりません。

<!-- hint -->
検証の眼目は「2回目の呼び出しが例外を投げなかった」ことではなく、「2回目の呼び出しが本物の`create_ticket`実装を再度走らせなかった」ことです。呼び出し回数を数える偽の実装を用意し、前後で比較することだけが、信じるに足る証拠になります。

## まとめ

- 再開は at-least-once の実行セマンティクスをもたらします。ツールが本当に成功した後、結果が台帳に書かれる前にプロセスが死ぬことがあり、チェックポイントだけでは、その宙ぶらりんな呼び出しが走ったかどうかを教えてくれません。レッスン3が高影響ツールの調整を未解決のまま残さざるをえなかった根本原因はここにあります。
- 冪等の定義は、1回実行しても何回実行しても最終的な効果が同じになる操作、です。上書き型の書き込み（`set_config`、`write_file`）はたいてい冪等で、追記型の書き込み（`append_log`、`send_email`）はたいてい冪等ではありません。
- 副作用台帳は、どの副作用がすでに起きたかを`tool_use_id`をキーにしてディスク上に記録します。このキーは、モデルがツールを名指しする際に伴う一意な識別子であり[^S4]、再開時に同じ名指しがリプレイされても変わらないため、本質的に冪等キーになっています。書き込みは`.tmp`＋`rename`のアトミックな書き込みで、ツールが成功したその瞬間に行ってください。
- 再開時の調整ルールはこう格上げされます。`pendingToolUse.id`が台帳でヒットしたら、保存済みの結果を再利用して二度と実行しない。ミスしたら、安全に実行する。
- 承認ゲートは「これはやるべきか」を、副作用台帳は「これはもうやったか」を問います。両者は互いを補完し、どちらも実際の実行の手前に位置し、冪等性ゲートが先に来ます。
- 火消しより原因を直すほうが優れています。ツールを本質的に冪等に設計すれば（「作成」より「存在を保証」、追記より上書き）、すべてに台帳が必要になるわけではなくなります。信頼性はモデルの適応力と決定論的なセーフガードの組み合わせから生まれますが[^S1]、セーフガードもまた複雑さであり、成果を明らかに改善する場合にのみ追加すべきです[^S3]。
