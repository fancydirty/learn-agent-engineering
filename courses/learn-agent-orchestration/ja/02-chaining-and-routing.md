# レッスン2: つなぐ、振り分ける: チェイニングとルーティング

> 学習目標:
> - 4つの仕事を1つに詰め込んだプロンプトをチェーンに分解し、何を差し出して何を得ているかを言語化する
> - チェーンの各ステージのあいだにプログラム的なゲートを取り付け、基準を満たさない中間結果をそこで止める
> - チェイニングが要るのか、ルーティングが要るのか、両方か、どちらも要らないかを判断し、ルーティングの呼び出しを出力を絞った安価な1回として書く
>
> 前提: レッスン1を読了し、`stop_reason`駆動のハーネスループを手書きできること（このシリーズのコース7）、決定的な検証器を理解していること（このシリーズのコース10） | 前: [<< レッスン1](./01-when-one-loop-isnt-enough.md) | 次: [レッスン3 >>](./03-parallelization.md)

## 1つのプロンプトが4つの仕事をすると、1つ落ちる

新機能のヘルプドキュメントを書く必要があります: プロダクト要件を読む → アウトラインを起草する → アウトラインに沿って本文を書く → ドキュメントに非推奨の用語が混ざっていないか点検する。

最初のバージョンは、おそらく4ステップ全部を1つのプロンプトに詰め込んで、ハーネスループへ渡すでしょう。1回目の実行は良さそうに見えます。問題が現れるのは2回目、そして3回目です: 今回はアウトラインは良いのに本文で1節が抜けている。次はテキストは揃っているのに、前バージョンで非推奨になった「ユーザーグループ」が混ざっている。その次は途中でアウトラインを書き直してしまい、本文と噛み合わないアウトラインを納品してくる。

これらの失敗は表面上は別々に見えますが、根は同じです: 1回の呼び出しの中で、モデルは要件の理解、構造の設計、テキストの生成、一貫性の点検を同時にやりくりしなければなりません。どれが押し出されるかをあなたはコントロールできず、それが起きるところを見ることもできません。さらに悪いことに、介入する場所がありません——出力が手に入った時点で4つとも終わっており、「アウトラインが仕様を満たしていない」は最終稿の内側に埋まっています。

レッスン1では「誰がプランを持つか」という軸を扱いました。この一発勝負のプロンプトは、プランをまるごとモデルへ渡しています。このレッスンが最初にやるのは、それを取り返すことです。

## チェイニング: レイテンシと引き換えに正確性を買う

このパターンの公式の定義はたった2文で、どの語も荷重を負っています。

プロンプトチェイニングは、タスクを一連のステップへ分解し、各LLM呼び出しが前の呼び出しの出力を処理します。プロセスがまだ軌道上にあることを確かめるために、任意の中間ステップにプログラム的なチェック（下図の"gate"を参照）を足せます[^S1]。このワークフローを使うとき: このワークフローは、タスクを簡単かつきれいに固定のサブタスクへ分解できる状況に理想的です。主な目的は、各LLM呼び出しをより易しいタスクにすることで、レイテンシと引き換えにより高い正確性を得ることです[^S1]。

「各LLM呼び出しをより易しいタスクにする」——この半文が診断と処方の両方を与えています。4つの仕事をする1回の呼び出しは難しいタスクです。アウトラインを起草するだけで本文は一切書かない1回の呼び出しは易しいタスクです。チェイニングは仕事の量を減らしません——1回の呼び出しでモデルが完了しなければならない仕事を、単純にするのです。

コストは値札にそのまま印字されています: レイテンシです。ステージを1つ足すごとに、完全な往復が1回増えます。Anthropicは同じ記事の冒頭でこの会計を並べています——エージェント的システムは、より良いタスク性能と引き換えに、しばしばレイテンシとコストを差し出すので、このトレードオフが意味を持つのはどんなときかを検討すべきだ、と[^S1]。「遅くて高い」はチェイニングの偶発的な副作用ではありません。

```text
要件 ──▶ アウトライン起草 ──▶ 本文執筆 ──▶ 用語点検 ──▶ 納品
```

各区間の入力は、前の区間の出力です。1つのリンクが曲がれば、下流はすべてそれに従います。

## 各ステージは完全なハーネスループ

チェーンの1ステージは「1回のAPI呼び出し」ではありません——**完全なハーネスループ**です。このシリーズのコース7で手書きしたあのwhileループと同じもの: messagesを送り、`stop_reason`を確認し、`tool_use`ならツールを実行して結果を送り返し、そうでなければテキストを返す。

この使い方には出典があります。Anthropicがエージェントの評価の仕方を説明したとき、推奨されたセットアップはまさにこの形でした: LLM APIを直接呼ぶこと、単純なエージェントループ（LLM APIの呼び出しとツールの呼び出しが交互に並ぶのを包むwhileループ）、評価タスク1つにつきループ1つ、各評価エージェントには単一のタスクプロンプトとあなたのツールを与えること[^S3]。あの記事は評価の話でしたが、ビルディングブロックそのものは汎用です: 1つのタスク、1つのループ、コード駆動。チェイニングとは、このブロックを並べてつなぎ、順序をコードに決めさせることです。

以降のレッスンでは同じ記法を使います:

```javascript
// runAgentは、コース7のハーネスループを関数で包んだもの
// 入力: 自己完結した1つのタスクプロンプト＋このステージが使えるツール。出力: 走りきったあとの最終テキスト
const answer = await runAgent(client, task, tools);
```

チェーン全体は、ひと目で読める逐次的なコードです:

```javascript
const outline = await runAgent(client, outlineTask(req));
const g1 = gateOutline(outline);        // ゲート1: アウトラインの構造は正しいか？
if (!g1.ok) fail(g1.why);               // 違うならここで止める——下流へ送らない

const doc = await runAgent(client, writingTask(outline));
const g2 = gateTerms(doc);              // ゲート2: 禁止された非推奨の用語を含むか？
if (!g2.ok) fail(g2.why);

const report = await runAgent(client, checkTask(doc), { read_glossary });
```

この数行に**入っていない**ものに注目してください: 「次に何をするかをモデルが決める」余地がありません。順序はハードコードされており、中間結果の`outline`と`doc`はただのスクリプト変数です。モデルは各ステージの内側では相変わらず自律的です（好きなだけツールを呼べます）が、ステージ間の制御はコードの手にあります。副次的な利点として、各ステージのプロンプトはたった1つのことについて厳しくできます。アウトラインのプロンプトは見出しだけを要求し、本文を書くことを禁じます。執筆のプロンプトは文体と禁止用語に集中します——この2組の要求は、1つのプロンプトに詰め込めば衝突します。

この形はプロダクトにも現れます。Claude Codeの公式ドキュメントは、複数ステップのワークフローについてこう勧めています: Claudeにサブエージェントを順番に使わせる。それぞれが自分のタスクを完了してClaudeへ結果を返し、Claudeが関連するコンテキストを次のサブエージェントへ渡す[^S4]。違いはレッスン1の軸に着地します——プロダクトの形では「何を渡すか」をClaudeが決めます。スクリプトを書くなら、それはあなたのコードです。

## ゲート: コース10の検証器をステージ間へ移す

定義の最後の半文こそが、「1つの大きなプロンプト」を超えてチェイニングが実際に足しているものです: プロセスがまだ軌道上にあることを確かめるために、任意の中間ステップにプログラム的なチェックを足せる[^S1]。原文はこのチェックを"gate"と呼んでおり、しかも引用符付きです: `(see "gate" in the diagram below)`——片方がストレート、片方がカーリーで、出典どおりです。ここでの誤植ではありません。

「プログラム的」が鍵です: 別のモデル呼び出しではなくコードであり、`if`文が数個あるだけです。

このシリーズのコース10は決定的な検証器を教えました: コードで正誤を判定できるものに、お金を払ってモデルへ尋ねない。あのコースは検証器を**終端状態**に取り付けました——全部走ったあとで、出力が受け入れ可能かを確かめる。チェイニングは、同じチェックに新しい設置場所を与えます: **ステージのあいだ**です。

```javascript
function gateTerms(doc) {
  const hits = BANNED.filter((w) => doc.includes(w));
  if (hits.length > 0) {
    return { ok: false, why: `ドキュメントに禁止された非推奨の用語が含まれています: ${hits.join(', ')}` };
  }
  return { ok: true };
}
```

7行、モデル呼び出しはゼロ、同じ入力なら常に同じ判定です。まさにあの「本文に非推奨の用語が混ざる」失敗を止めます。アウトラインの章見出しがいくつあるかを数えるゲートも、同じくらい単純です。

ゲートが落ちたときに何をするかは設計上の判断です: **止めてエラーを報告する**（このチェーンをまだ調整中のときに最善ですが、失敗メッセージはどのステージで落ちたかを言わなければなりません。さもないと「うまくいかなかった」ことだけが分かり、どのステージのプロンプトを直せばよいか分かりません）、**失敗の理由を同じステージのプロンプトへ戻して再試行する**（リトライ上限つきで）、**記録して代替値で続行する**（このステージが荷重を負っていないときだけ）。レベル2の演習は1つ目のやり方を使います。

これはこのシリーズのコース6の会計も片づけます: 委任する仕事には自己完結したプロンプトが要る——目的、出力フォーマット、使えるツール、境界の4つを全部書き出すこと。各ステージのタスクは、まさにその形をした委任プロンプトです。この4要素には正確な一次出典があり、レッスン4がオーケストレーターの委任の仕方を扱うときに1項目ずつ解きほぐします。

## ルーティング: まず分類し、それから振り分ける

チェイニングが扱うのは「1つのタスクをステップへ分けること」です。もう1つのクラスのタスクは、まったく違う形をしています: 入ってくるのは1種類のものではなく、いくつかの種類のもので、それぞれに固有の扱い方があります。

公式の定義はこうです: ルーティングは入力を分類し、専門化された後続タスクへ差し向けます。このワークフローは関心の分離と、より専門化されたプロンプトの構築を可能にします。このワークフローがなければ、ある種類の入力に向けた最適化が、他の入力での性能を損ないかねません[^S1]。

最後の一文が、ルーティングが存在する理由です。カスタマーサポートのメールが返金、障害、請求の3カテゴリに分かれるとしましょう。あなたは1つのプロンプトで全部を扱っています。返金をうまく扱うために「まず注文番号と決済チャネルを確認すること」という行を足す。このルールは障害のメールにとっては純粋なノイズで、モデルはそれを使って、白画面を報告してきた人に決済チャネルを尋ねます。あなたは「障害なら注文番号を聞かないこと」という行をもう1つ足し、プロンプトはパッチの上にパッチを生やしはじめます。

このワークフローを使うとき: ルーティングは、別々に扱ったほうが良い明確なカテゴリがあり、かつ分類そのものをLLMまたはより伝統的な分類モデルやアルゴリズムで正確に扱える複雑なタスクでうまく働きます[^S1]。この最後の前提条件はケーキの飾りではありません: 分類が間違うと、それは目立たない形で間違います——障害のフローへ振り分けられた返金メールは、良心的なトラブルシューティングの返信を受け取ります。

コードの上では、ルーティングはチェイニングより単純です:

```javascript
const HANDLERS = {
  refund: handleRefund,
  incident: handleIncident,
  billing: handleBilling,
  other: handleFallback,
};
const LABELS = Object.keys(HANDLERS);

async function classify(client, letter) {
  const raw = await runAgent(client, [
    '目的: 下記のカスタマーサポートのメールを分類する。',
    `出力フォーマット: 次の中から選んだ1語だけを出力する: ${LABELS.join(', ')}。説明なし、句読点なし。`,
    `メール: ${letter}`,
  ].join('\n'));

  const label = raw.trim();
  return LABELS.includes(label) ? label : 'other';   // 表に無ければフォールバックへ
}

const category = await classify(client, letter);
const reply = await HANDLERS[category](client, letter);
```

注目に値することが3つあります。

**分類呼び出しの出力を1語へ絞ること**——このシリーズのコース10も、LLMジャッジを論じるときに同じ手を使いました: 許される値を列挙し、説明なしと言う。出力を絞ることで、パースのステップが決定的になります。**表に無ければフォールバックへ**——あの`LABELS.includes(label) ? label : 'other'`という行は、防御的な小うるささではありません。モデルはときどき「incidentだと思いますが、別の何かかもしれません」と返してきて、そうすると`HANDLERS[その文字列まるごと]`は`undefined`になり、次の行がクラッシュします。フォールバックの分岐を1つ残しておけば、分類の不確かさはこの1行の中に封じ込められます。

**分類器はモデルである必要がありません**——定義は、伝統的な分類モデルやアルゴリズムも数に入ると明示しています[^S1]。メールが固定フォーマットの注文番号を持っていたり、専用のフォームの入口から来ていたりするなら、正規表現1本で十分ですし、そのほうがずっと速いです。

振り分けたあとは、各ハンドラは何であっても構いません: ハーネスループでも、チェーンでも、モデルをまったく使わないコードの一区間でも。

## 現行のAPIの語彙に見るルーティングの2つの変種

上のルーティングの定義は2024年末のパターンの記事から来ており、その記事にはツールのエコシステムに関する記述が古くなっているというバナーが載っています。だから確認しておく価値があります: このパターンは現行のファーストパーティの語彙の中でまだ生きているのか。生きていますし、名指しで呼ばれています。Claudeプラットフォームのマルチエージェントオーケストレーションのドキュメントには、ルーティングである項目が2つあります:

- **専門化（Specialization）**: 単一のエージェントにあらゆる能力を積み込むのではなく、セキュリティのエージェントやドキュメントのエージェントのように、ドメインに絞ったシステムプロンプトとツールを持つエージェントへルーティングする[^S6]。これが`HANDLERS`テーブルの公式の言い回しです。
- **エスカレーション（Escalation）**: 複雑なサブタスクの一部について、より能力の高いエージェントやモデルに相談する[^S6]。

2つ目は別に触れておく値打ちがあります: これは**トピック**ではなく**難易度**で振り分けます。分類器が判定するのは「これは返金か障害か」ではなく「このメールは自分の安いティアで扱えるか」です。これはトピックの分類より正確に判定するのが難しいので、エスカレーションの経路にはもっと安定した書き方があります: まず安いティアを走らせ、出力がゲートを通らなければエスカレートする——判定の難しい分類問題を、チェック可能な検証問題へ取り替えるのです。

## 分けないときを知る

**チェーンのリンク1つ1つがレイテンシを足します。** これは実装が最適化されていないからではなく、公式の定義が設定した価格です: レイテンシと引き換えにより高い正確性を得る[^S1]。ユーザーは全区間の合計を待ちます。ユーザーがUIの前で同期的に結果を待っているなら、チェーンにもう1本リンクを足す前に、その人がまだそこにいるかを考えてください。

**カテゴリが1つしかないなら、ルーティングは純粋なオーバーヘッドです。** ルーティングの利益は関心の分離から来ます[^S1]。入力が本当に1種類しかないなら、分類呼び出しのコストとレイテンシを払って、見返りはゼロ、おまけに誤分類の機会が1つ増えます。

**タスクをきれいに分けられないなら、無理に分けないこと。**「簡単かつきれいに固定のサブタスクへ分解できる」という条件には歯があります[^S1]。全体を何度も行き来して見ないとうまく直せない草稿を、「まず構造を直す、それから文言を直す」に分けたら、2つ目のステージは1つ目のステージが書き残さなかった理由にアクセスできず、字面だけを見て直すことになります。この場合は1つのループ、1つのコンテキストのほうが実際に良い——これはまさにレッスン1の逆向き条件の使いどころです。

**迷ったら、まず測ること。** Anthropicはこれを2度言いました: 複雑さを足すのは、それが結果を明白に改善するときだけにすべきだ[^S1]。このシリーズのコース10の評価のトラックは、まさにこのために作られています: 単一プロンプト版を走らせてスコアを取り、分割版を走らせてもう1つスコアを取り、差がどれだけあるか、その追加の数秒のレイテンシに見合うかを見る——それが、同僚との議論に持っていける証拠です。

最後に、境界を引いておきます。チェイニングとルーティングはどちらも**形が固定された**オーケストレーションです: チェーンが何ステージ持つか、ルーターがどのカテゴリを持つかは、すべてコードを書く時点で決まっています。複数のステージを同時に走らせてから集約するのはレッスン3の並列化であり、入力を見るまでサブタスクがいくつあるかすら分からないのはレッスン4のオーケストレーター・ワーカーです。

### レベル1: チェイニングか、ルーティングか、どちらでもないかを判断する（コードなし）

以下の4つのタスクそれぞれについて、チェイニングを使うか、ルーティングを使うか、両方か、どちらも使わないかを判断してください。結論に加えて、次のことをはっきり書いてください: チェイニングと判断したなら、ステージ間のプログラム的なゲートは何をチェックしますか？ ルーティングと判断したなら、分類器はどこに置き、カテゴリはいくつで、モデルですかコードですか？

1. カスタマーサポートのメールボックスが毎日数百通を受け取る。返金／障害／請求の3カテゴリはまったく違う扱い方をするのに、現在は1つのプロンプトを共有していて、あるカテゴリの文言を変えると別のカテゴリに影響が出る。
2. 英語の契約書について、まず構造化されたリスク意見書（各項目に条項の位置、リスクレベル、説明を含む）をレビューで作り、それからこの意見書を、チームごとに中国語版と日本語版へ翻訳する。
3. 混在したチケットのキュー: 1ステップで答えられる「パスワードのリセット」もあれば、ログを確認し、診断し、解決策を提案し、返信を書く必要のある「データ移行の失敗」——複数ステップのタスクもある。
4. ユーザーが入力欄に1文を打ち込む。あなたはその誤字を直して、修正済みの文を返す必要がある。

<!-- rubric -->

- 4つの結論はそれぞれ: ルーティング／チェイニング／両方／どちらでもない
- タスク1の理由は「ある種類の入力に向けた最適化が、他の入力での性能を損ないかねない」に着地し、カテゴリの集合を示していること。その集合にはフォールバックのカテゴリが含まれていること
- タスク2は、2つの翻訳版に順序上の依存がないこと（並列化はレッスン3に譲るので、認識できていれば十分）を指摘し、具体的なゲートを最低1つ示していること
- タスク3は2層構造を説明していること: 外側は複雑さで振り分け、複雑と判断された分岐が内側でチェーンになる
- タスク4は「1回の呼び出しで十分」と明示し、理由が、分割のレイテンシが利益に見合わないことに着地していること
- どのゲートも純粋なコードでチェックできること。「モデルに受け入れ可能か見てもらう」ではいけない

<!-- answer -->

**1. カスタマーサポートのメールをトピックで振り分ける — ルーティング。**

判断基準がユースケースにぴったり一致します: 別々に扱ったほうが良い明確なカテゴリがあり、分類そのものを正確に扱える[^S1]。設問にある「あるカテゴリの文言を変えると別のカテゴリに影響が出る」という一文は、公式の言明「このワークフローがなければ、ある種類の入力に向けた最適化が、他の入力での性能を損ないかねない」の実演版です[^S1]。分類器は先頭に置き、カテゴリの集合は`refund / incident / billing / other`。「other」が、最初の3つに当てはまらないメールと、モデルが期待どおりのフォーマットで応答しなかったケースを受け止めます。安いモデルの呼び出し1回、出力は1語へ絞る。返金メールの大半が固定のアフターサービスのフォームの入口から来るなら、その経路は先に純粋なコードのルールでショートカットできます。

**2. 契約書のレビューで構造化された意見書を作り、それから翻訳する — チェイニング。**

タスクは固定のサブタスクへきれいに分けられます: レビュー、翻訳。2ステップ目の入力は1ステップ目の出力であり、これはまさにチェイニングの定義の形です[^S1]。2つの言語のあいだに順序上の依存はありません——この「同じステップを複数のアイテムにわたって繰り返す」形はレッスン3の並列化の領分で、ここでは認識して、2つの直列ステージとして書かないことができれば十分です。

ゲートはレビューと翻訳のあいだに置き、内容ではなく構造をチェックします。すべて純粋なコードです: 出力が`JSON.parse`で配列へパースできること。各項目が`clause`、`level`、`note`の3フィールドを持つこと。`level`が`high / medium / low`の集合に入ること。配列の長さが0より大きいこと（意見が0件の契約書は、完璧な契約書というより、前のステップが軌道を外れた可能性のほうが高い）。翻訳のステージは、自分の入力が壊れていることを発見できません。壊れたものを忠実に2言語へ翻訳するだけなので、このゲートが上流で止めなければなりません。

**3. 混在したチケット — 両方。**

外側がルーティング、内側がチェイニングです。分類器はキューの入口に置き、判定するのはトピックではなく複雑さで、カテゴリは`1ステップで答えられる / 診断が要る / other`にできます。「1ステップで答えられる」は1回の呼び出し、あるいはテンプレートへ直行。「診断が要る」はチェーンへ展開します: ログを確認 → 原因を診断 → 解決策を提案 → 返信を書く。これは難易度による振り分けであり、公式の語彙のエスカレーションと同じカテゴリです——あの項目は、複雑なサブタスクの一部についてより能力の高いエージェントやモデルに相談すると言っており[^S6]、ここでは「より能力の高いエージェント」をチェーンへの展開に取り替えています。

チェーンの内側には、純粋なコードのゲートを最低2つ置きます: 診断ステージの出力は最低1本のログ行への参照を持つこと（タイムスタンプのフォーマットを正規表現でチェック）、返信を書くステージの出力は解決策のステージが与えたチケット番号を含むこと（文字列の包含チェック）。複雑さの分類器そのものを正確にするのが難しいなら、「まず1ステップで答えられるものとして処理し、出力がゲートを通らなければエスカレートする」へ切り替えてください。

**4. 1文の誤字修正 — どちらでもない。**

1回の呼び出しで十分です。きれいに分離できる固定のサブタスクは存在せず（「誤りを見つける」と「誤りを直す」を別々にやっても、2つ目のステージはやはり文全体を読み直すことになり、空回りに等しい）、別々に扱う必要のあるカテゴリもありません。分割のコストは具体的です: 往復のレイテンシが1回増え、ユーザーは入力欄を見つめて結果を待っています。チェイニングの位置づけはレイテンシと引き換えに正確性を買うことであり[^S1]、その前提は実際に正確性を得られることです——このタスクでは得られません。本当に品質を上げたいなら、まずプロンプトに例をいくつか足してください。Anthropicもパターンの手前にこの道を残しています: 多くのアプリケーションでは、検索とコンテキスト内の例で単一のLLM呼び出しを最適化すれば、たいてい十分です[^S1]。

<!-- hint -->

パターンの判断へ急ぐ前に、各タスクにまず2つ問いかけてください: 入ってくるのは「1種類のもの」ですか、それとも「いくつかの種類のもの」ですか？ 1種類なら、それぞれがより単純で、順序が固定されたステップへ分けられますか？ 1つ目の問いが「いくつかの種類のもの」ならルーティングを考え、2つ目の問いが「はい」ならチェイニングを考えてください。

<!-- hint -->

ゲートを書くときは自己点検してください: このチェックを`if`と文字列関数で書けますか、そして同じ入力なら常に同じ結論になりますか？ 書いているうちに「このアウトラインが十分に良いかモデルに判定してもらう」になってしまったら、それはこのレッスンの言うプログラム的なチェックではありません——それはレビューのループで、レッスン5に譲ります。

### レベル2: 3ステージのチェーンを書き上げて動かす（コードを書く）

冒頭のドキュメント執筆のタスクを3ステージのチェーンとして実装する`chain.mjs`を書いてください: **アウトライン起草 → アウトラインに沿って本文執筆 → 用語の一貫性点検**、あいだにゲートを2つ。要件:

1. スタブclientを使うこと（このシリーズのコース8〜11で使ったやり方）: 固定の応答キュー、ネットワークなし、コストなし、同じ入力なら常に同じ結果。
2. `runAgent(client, task, tools)`は本物のハーネスループであること——`stop_reason`で判定し、`tool_use`ならツールを実行して結果を送り返す。ステージ3では実際にツール呼び出しを1回通すこと（用語集を読む）。
3. ゲート1: アウトラインは`## `で始まる章見出しをちょうど3つ含むこと。ゲート2: 本文は禁止された非推奨の用語を含まないこと（2〜3語の表を自分で定義する）。どちらも純粋なコードで、モデル呼び出しの追加なし。
4. ゲートが落ちたら、どの**ステージ**で落ちたかと理由を印字し、非ゼロのコードで終了すること。3ステージすべて通ったら0で終了すること。
5. 固定応答のセットを2組用意して2回走らせること: 全部通る回と、2つ目のゲートで止まる回。両方の実行の実際の出力と終了コードを貼ること。

<!-- rubric -->

- スタブclientがFIFOの応答キューであり、キューが空になったら黙って`undefined`を返すのではなくエラーになること（さもないとチェーンが通ったつもりで、実際は空回りしている）
- `runAgent`が本物の`while`ループと`stop_reason`の分岐を持ち、1回の`await`で返してしまわないこと。ステージ3の応答列に`tool_use`が含まれ、ツールの分岐が実際に実行されること
- 2つのゲート関数がclientを呼ばず、戻り値が失敗の理由を持ち、同じ入力なら常に同じ出力であること
- 失敗メッセージが、どのステージのあいだかと、具体的にどの語に当たったかを書き出していること。「失敗」とだけ印字するのは不可
- 終了コード: 全部通れば0、ゲート失敗なら非ゼロ（引数エラーなどは別の非ゼロコードでよい）
- 2組目の応答がゲート2を発火させ、ステージ3が本当に走っていないこと（出力にそこからの印字が無い）
- 貼られた出力が実際に実行されたものであること: ステージ番号、当たった語、終了コードがすべてスクリプトと一致すること

<!-- answer -->

完全なスクリプト:

```javascript
// chain.mjs — 3ステージのチェーン: アウトライン起草 → 本文執筆 → 用語点検
// このレッスン自身の図解用スクリプト——一次資料にオーケストレーションスクリプトのコードサンプルは存在しない
// 使い方: node chain.mjs pass    (3ステージすべて通る)
//         node chain.mjs stale   (2つ目のゲートで止まる)

const BANNED = ['ユーザーグループ', 'サブアカウント'];

// ---------- スタブclient: 固定の応答キュー、ネットワークなし ----------
const say = (t) => ({ stop_reason: 'end_turn', content: [{ type: 'text', text: t }] });
const useTool = (id, name, input = {}) => ({
  stop_reason: 'tool_use',
  content: [{ type: 'tool_use', id, name, input }],
});

function makeStubClient(script) {
  const queue = [...script];
  return {
    messages: {
      async create() {
        if (queue.length === 0) throw new Error('スタブキューが空: スクリプトが想定より多くモデルを呼びました');
        return queue.shift();
      },
    },
  };
}

// ---------- 1ステージ ＝ 1つの完全なハーネスループ ----------
async function runAgent(client, task, tools = {}) {
  const messages = [{ role: 'user', content: task }];
  while (true) {
    const res = await client.messages.create({
      model: 'claude-sonnet-4-5',
      max_tokens: 2048,
      messages,
      tools: Object.values(tools).map((t) => t.schema),
    });
    messages.push({ role: 'assistant', content: res.content });

    if (res.stop_reason !== 'tool_use') {
      return res.content
        .filter((b) => b.type === 'text')
        .map((b) => b.text)
        .join('\n')
        .trim();
    }

    const results = [];
    for (const block of res.content) {
      if (block.type !== 'tool_use') continue;
      const tool = tools[block.name];
      results.push({
        type: 'tool_result',
        tool_use_id: block.id,
        content: tool ? await tool.run(block.input) : `未知のツール: ${block.name}`,
      });
    }
    messages.push({ role: 'user', content: results });
  }
}

// ---------- 2つのゲート: 純粋なコード、モデルには尋ねない ----------
function gateOutline(outline) {
  const headings = outline.split('\n').filter((l) => l.startsWith('## '));
  if (headings.length !== 3) {
    return { ok: false, why: `アウトラインは章見出しちょうど3つを要求しますが、実際に数えたのは${headings.length}つです` };
  }
  return { ok: true, detail: `章: ${headings.map((h) => h.slice(3)).join(' / ')}` };
}

function gateTerms(doc) {
  const hits = BANNED.filter((w) => doc.includes(w));
  if (hits.length > 0) {
    return { ok: false, why: `ドキュメントに禁止された非推奨の用語が含まれています: ${hits.join(', ')}` };
  }
  return { ok: true, detail: `禁止用語リスト${BANNED.length}件、ヒット0件` };
}

function fail(where, why) {
  console.error(`\n✗ gate failed @ ${where}`);
  console.error(`  理由: ${why}`);
  console.error('  チェーンはここで止まります。以降のステージは走りません。');
  process.exit(1);
}

// ---------- ツール ----------
const glossary = {
  schema: {
    name: 'read_glossary',
    description: 'プロダクトの用語集を読み、「旧用語 → 新用語」の対応を返す',
    input_schema: { type: 'object', properties: {}, required: [] },
  },
  run: async () => 'ユーザーグループ → チームスペース\nサブアカウント → メンバーアカウント\n承認フロー → ワークフロー',
};

// ---------- 3組の固定応答 ----------
const OUTLINE = ['## 権限モデル', '## チームスペースの作成とメンバー管理', '## よくある質問'].join('\n');

const CLEAN_DOC = [
  '## 権限モデル',
  'メンバーアカウントはそれぞれ1つのチームスペースに属し、権限はチームスペース内のロールで決まります。',
  '## チームスペースの作成とメンバー管理',
  '管理者はコンソールでチームスペースを作成したあと、メンバーアカウントを招待して参加させられます。',
  '## よくある質問',
  'メンバーアカウントは複数のチームスペースに同時に所属でき、権限は和集合になります。',
].join('\n');

const STALE_DOC = CLEAN_DOC.replace('メンバーアカウントを招待して参加させられます', 'サブアカウントを招待して参加させられます');

const REPORT = '用語の一貫性の点検に合格: 全文で「チームスペース」と「メンバーアカウント」に統一されており、非推奨の用語の混入はありません。';

const SCRIPTS = {
  pass: [say(OUTLINE), say(CLEAN_DOC), useTool('t1', 'read_glossary'), say(REPORT)],
  stale: [say(OUTLINE), say(STALE_DOC)],
};

// ---------- チェーン本体 ----------
const mode = process.argv[2] ?? 'pass';
if (!SCRIPTS[mode]) {
  console.error(`未知のモード: ${mode} (使えるもの: ${Object.keys(SCRIPTS).join(', ')})`);
  process.exit(2);
}
const client = makeStubClient(SCRIPTS[mode]);
const req = '「チームスペース」機能のヘルプドキュメントを書く。読者は初めて権限を設定する管理者。';

console.log(`モード: ${mode}`);

console.log('[1/3] アウトライン起草');
const outline = await runAgent(client, [
  '目的: 下記の要件に対するヘルプドキュメントのアウトラインを起草する。',
  '出力フォーマット: 章のタイトルだけを、1行に1つ、"## "で始めて、ちょうど3つ出力する。',
  'ツールの指針: このステージにツールは不要。',
  '境界: タイトルを並べるだけで、本文は書かない。',
  `要件: ${req}`,
].join('\n'));
const g1 = gateOutline(outline);
console.log(g1.ok ? `      ゲート1 通過 — ${g1.detail}` : '      ゲート1 失敗');
if (!g1.ok) fail('ステージ1 → ステージ2 (アウトラインの構造)', g1.why);

console.log('[2/3] アウトラインに沿って本文執筆');
const doc = await runAgent(client, [
  '目的: 下記のアウトラインに沿ってヘルプドキュメントの本文を書く。',
  '出力フォーマット: アウトラインの"## "見出しを保ち、節ごとに1〜2文を書く。',
  'ツールの指針: このステージにツールは不要。',
  `境界: 新しい用語だけを使い、次を禁止する: ${BANNED.join(', ')}。`,
  `アウトライン:\n${outline}`,
].join('\n'));
const g2 = gateTerms(doc);
console.log(g2.ok ? `      ゲート2 通過 — ${g2.detail}` : '      ゲート2 失敗');
if (!g2.ok) fail('ステージ2 → ステージ3 (禁止された非推奨の用語)', g2.why);

console.log('[3/3] 用語の一貫性を点検');
const report = await runAgent(
  client,
  [
    '目的: 下記のドキュメントの用語が一貫しているかを点検する。',
    '出力フォーマット: 一文の結論。',
    'ツールの指針: まずread_glossaryを呼んで用語表を取得し、それから全文と突き合わせる。',
    '境界: 用語の問題だけを報告し、ドキュメントを書き直さない。',
    `ドキュメント:\n${doc}`,
  ].join('\n'),
  { read_glossary: glossary },
);

console.log(`\n--- 点検の結論 ---\n${report}`);
console.log('\n✓ 3ステージ、2ゲートすべて通過。');
process.exit(0);
```

出力と突き合わせて見る値打ちのあることが3つあります。2回目の実行には`[3/3]`の行が無く、ステージ3は本当に走っておらず、まずいものは下流へ流れていません。失敗メッセージは「ステージ2 → ステージ3」と具体的な語「サブアカウント」をピンポイントで示すので、執筆ステージのプロンプトを直しに行けばよいと分かります。`stale`のキューには応答が2つしかありません——いつかゲート2が誤って削除されたら、スクリプトはステージ3へ歩いていき、応答を得られず、スタブclientが「スタブキューが空」を投げます——失敗の仕方が静かではなく、大きな音を立てます。ついでに請求書も計算しておくと、`pass`の実行は実際にはモデルを4回呼んでいます——用語を点検するステージ3がツールの往復を1回通ったからです。ステージ数は3、往復数は4であり、コストは往復数で計算すべきです。

<!-- hint -->

チェーンをつなぐ前に、スタブclientと`runAgent`を別々に動かしてください。`say(...)`を1つだけ含むキューでステージを1つ走らせ、`undefined`ではなくテキストが返ることを確認する。ツールの分岐も別に検証する: キューの1つ目の応答を`tool_use`で止め、2つ目を締めのテキストにすれば、ループはちょうど2周するはずです。

<!-- hint -->

「どのステージで落ちたか」は、書くときに`fail()`へ引数として渡すべきものです。あとからスタックを見て分かることを期待しないでください。ゲートごとに「ステージX → ステージY」という固定の言い回しを与え、落ちたときに具体的な当たった語と一緒に印字してください。終了コードには`process.exit(1)`を使い、`throw`で済ませないこと——`throw`が生むのも確かに終了コード1ですが、スタックの情報が、あなたが丁寧に印字した数行を覆い隠します。

## まとめ

- チェイニングはタスクを一連のステップへ分解し、各呼び出しが前の出力を処理することで、1回の呼び出しをより易しいタスクにします[^S1]。その価格は明示されています: 主な目的は、レイテンシと引き換えにより高い正確性を得ることです[^S1]。
- チェーンの1ステージは1回のAPI呼び出しではなく、完全なハーネスループです——Anthropicが評価のために推奨したセットアップが、まさにこのビルディングブロックです: 1つのタスク、1つのwhileループ、コードから直接APIを呼ぶ[^S3]。
- 分割したあとに増える位置こそが鍵です: プロセスがまだ軌道上にあることを確かめるために、任意の中間ステップにプログラム的なチェックを足せます[^S1]。これはコース10の決定的な検証器を、別の設置場所へ移したものです——終端状態から、ステージのあいだへ。プロダクトの形では、サブエージェントが順番に実行され、それぞれが完了したら上のレイヤーが関連するコンテキストを次へ渡す、という見え方になります[^S4]。
- ルーティングは入力を分類して専門化された後続タスクへ振り分け、関心の分離とより専門化されたプロンプトを得ます。それが無ければ、ある種類の入力に向けた最適化が、他の入力での性能を損ないかねません[^S1]。前提条件: 明確なカテゴリがあり、分類そのものをLLMまたは伝統的な分類アルゴリズムで正確に扱えること[^S1]。
- 分類呼び出しの出力は1つのラベルへ絞り、表に当てはまらない答えを受け止めるフォールバックの分岐を1つ残すこと。
- このパターンは現行のファーストパーティの語彙の中で生きています: 専用のプロンプトとツールを持つエージェントへドメインで振り分けることを専門化と呼び、複雑なサブタスクの一部についてより能力の高いエージェントやモデルに相談することをエスカレーションと呼びます[^S6]——後者は難易度で振り分けるルーティングです。
- 無理に分けないこと: カテゴリが1つしかないならルーティングは純粋なオーバーヘッドであり、タスクをきれいに分けられないのに無理に分ければステージのあいだで情報を落とします[^S1]。迷ったらまず測ること——複雑さは「結果を明白に改善する」という敷居を越えなければなりません[^S1]。
