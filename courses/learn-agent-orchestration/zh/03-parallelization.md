# 第 3 课：并行化：分段与投票

> 学习目标：
> - 分清并行化的两个变体——分段与投票——各自解决什么问题，并守住「输出由程序聚合」这半句定义划出的边界
> - 用 `Promise.all` 和一个自己写的并发池把分段落成代码，让汇合只回传引用、不回传载荷
> - 算清扇出的三笔账（结果回灌上下文、真实产品的并发上界、投票的 N 倍 token），并据此判断一个提案该不该并行
>
> 前置要求：读完第 1、2 课，手上有第 2 课那个 `runAgent()` 封装 | 上一课 [第 2 课 <<](./02-chaining-and-routing.md) | 下一课 [第 4 课 >>](./04-orchestrator-workers.md)

## 12 份文档，同一条链，排了一个小时

第 2 课那条链现在能跑了：出提纲 → 过一道关卡 → 写正文 → 再过一道关卡 → 查术语。本课把三个阶段的提示词换成审阅用的——抽要点、给改写建议、核对术语，链的形状一根手指头没动。挂到一份文档上跑完，大概六七分钟。

然后产品那边丢过来一个目录：12 份文档，每份都要走同一遍审阅。

你写了个 `for` 循环，跑起来去泡咖啡。一小时后回来，日志停在第 9 份，第 10 份正在抽要点。

这个小时里，机器几乎一直在等。等第 1 份的 API 返回，才开始发第 2 份的请求；等第 2 份跑完四个阶段，才轮到第 3 份。可以问一句很实在的话：第 3 份文档的审阅结论，有没有一个字依赖第 2 份的结果？

没有。它们是 12 份互不相干的文档，各自的审阅报告谁先出来都一样。链式里那种等待是有理由的——下一步的输入就是上一步的输出，不等不行。这里没有这个理由，这 12 次运行只是被 `for` 循环排成了队。

本系列第 6 门课已经讲过扇出-汇总的协作形状和多视角投票是怎么回事。这一课把它落成代码，顺便把账算清楚：扇出不是免费的，快是真的快，代价也是真的。

## 定义：可以同时开工，输出由程序聚合

先把原话摆出来。LLM 有时可以同时处理任务、输出由程序聚合；这个工作流叫并行化，有两个关键变体[^S1]：

- **分段（Sectioning）**：把一个任务拆成互相独立的子任务，并行跑[^S1]。12 份文档各审一遍，就是分段。
- **投票（Voting）**：同一个任务跑多次，拿到多样化的输出[^S1]。同一段文案让三个视角各评一次，就是投票。

什么时候用它：拆开的子任务能并行、可以换来速度，或者需要多个视角、多次尝试来换更高置信度的结果[^S1]。还有一句容易被跳过、但很值钱的补充——考虑点很多的复杂任务，每个考虑点交给单独一次 LLM 调用来处理，注意力更聚焦，通常表现更好[^S1]。这句话是说：分段和投票不只是省时间的手段，把「法务、安全、品牌」三件事塞进一个提示词里，和让三次调用各盯一件事，出来的质量本来就不一样。

定义里还有半句得钉住：**输出由程序聚合**。扇出去的结果回来之后，是你的代码在做判断、做筛选、做汇总——不是再叫一个模型来读完 12 份报告写个总结。让模型来做汇总是另一个模式，第 4 课的编排者干的就是那件事，这一课先把这条线划清楚。现行的 Claude 平台文档在多代理编排里也列了 Parallelization：并行扇出独立的子任务（检索多个来源、分析不同文件），再由协调者汇总结果[^S6]——注意那一版里做汇总的是协调者，而这一课要写的是程序聚合那一版[^S1]。同一个词，聚合那一端谁来做，是两码事。

## 分段：把 for 循环换成 Promise.all

串行版本长这样，总耗时是 12 份之和：

```javascript
const reports = [];
for (const doc of docs) {
  reports.push(await runAgent(client, reviewTask(doc)));
}
```

分段版本只改一行，总耗时接近最慢的那一份：

```javascript
const reports = await Promise.all(
  docs.map((doc) => runAgent(client, reviewTask(doc))),
);
```

`runAgent()` 站的还是第 2 课那个封装的位置——一次完整的 harness 循环，内部按 `stop_reason` 转。本课的桩响应都一步到位（`end_turn`），所以文末脚本里的版本省掉了工具分支，是个简化版；接真 client 或要用工具时，把第 2 课那个带工具分发的版本原样搬回来。并行化不改这个循环本身的任何一行，它只是不再让这些循环排队。

聚合在下一行发生，做聚合的是这段代码：

```javascript
const blockers = reports.filter((r) => r.level === "高");
const total = reports.reduce((n, r) => n + r.issues, 0);
console.log(`${docs.length} 份文档，${total} 处待修，${blockers.length} 份含高风险项`);
```

这三行里没有第二次模型调用。`filter`、`reduce`、一个阈值判断，全是确定性的代码——同样的 12 份报告进去，永远出同样的一行结论。这正是把聚合留在程序里的好处：扇出去的那 12 次是不确定的，汇合这一步是确定的，出了问题你知道该怀疑哪一边。

`Promise.all` 有个脾气要提前知道：任何一个 promise reject，整个 `await` 就 reject，其他 11 份哪怕已经跑完，结果也拿不到。审 12 份文档，第 7 份撞上一次 500 就全盘作废、其他 11 份白跑，这个代价不合理。要么换 `Promise.allSettled`，要么像本课练习那样在每个 worker 内部 `try/catch` 把失败收成一条记录——扇出的每一路都该能单独失败。

## 为什么并行不只是快

如果并行只是「同一件事更早做完」，那它就是个性能技巧，不值得单开一课。真正的理由在上下文那一侧。

Anthropic 复盘他们的多 Agent 研究系统时说得很直白：检索的本质是压缩——从庞大的语料里提炼洞见。子代理带着**各自的上下文窗口**并行工作，同时探索问题的不同侧面，再把最重要的 token 压缩后交给主研究代理。每个子代理还提供了关注点分离——不同的工具、不同的提示词、不同的探索轨迹——这减少了路径依赖，让每一路调查都能独立做透[^S2]。

把这两句拆开看，扇出至少买到三样东西：

1. **窗口容量**。他们把这条架构判断写成了结论：把工作分布到拥有独立上下文窗口的多个代理上，是在为并行推理增加容量[^S2]。第 1 课讲过，真正到头的不是窗口大小，是「一个循环」这个形状；扇出绕开单窗口上限的办法不是把窗口撑大，是多开几个。
2. **关注点分离**。三个子代理拿着不同的工具和提示词，天然不会互相污染。
3. **减少路径依赖**。一个循环里，第 3 步的判断会被第 2 步的措辞带偏；三条独立轨迹不会共享同一个偏差。

现行平台文档也给了同方向的说法：多个代理可以带着各自隔离的上下文并行行动，这有助于提升产出质量，也能改善完成时间[^S6]。注意它把质量放在前面。

速度那一侧他们给了个数字，语境要一起抄下来：他们早期的代理是顺序检索，慢得难受；为了提速引入了两级并行——主代理并行起 3-5 个子代理而不是串着起，子代理并行使用 3 个以上的工具。这些改动**对复杂查询把研究时间砍掉最多 90%**[^S2]。

这个数字必须连着它的三个限定条件用：它是**延迟**数字，不是质量数字；它限定在**复杂查询**上（简单查询本来也没多少可并行的）；它来自**他们自家的那套系统**。你把 `for` 换成 `Promise.all` 之后能省多少，取决于你的子任务有多少真的独立、每一路有多慢、以及并发被卡在哪——这一课后半段全在讲这个。

## 第一笔账：汇合会把省下的上下文吃回去

扇出的时候大家都盯着「同时跑几路」，翻车通常翻在回来那一步。

Claude Code 的子代理文档把这个成本写在明面上：子代理完成时，结果会回到你的主对话；跑很多子代理、每个都返回详细结果，会消耗掉可观的上下文[^S4]。子代理本来是用来**保护**主对话上下文的——把探索和实现挡在主对话之外[^S4]——可一旦回传的东西太重，保护就反过来了。

同一篇复盘给了处置办法，而且给得很具体：与其要求子代理把所有东西都通过主代理来传达，不如实现工件系统——让专门的代理把产出创建成能独立留存的东西。子代理调用工具把工作存进外部系统，然后只把**轻量引用**传回协调者[^S2]。

翻译成写代码时的一句口诀：**传引用，不传载荷**。

```javascript
// 汇合侧收到的不是 12 份报告，是 12 条这样的记录
{ id: "api-auth", file: "out/api-auth.md", summary: "结论: 3 处待修, 风险等级 高" }
```

差别有多大，本课练习里的脚本会给你一个真实数字：8 份产出落盘一共 1668 字节，回到汇合侧的只有 643 字节，而且这个比例随文档变长会迅速拉开——报告长十倍，回传那一坨还是一行摘要加一个路径。谁需要看全文，照着路径去读就是了。

这条路顺带买到别的东西。工作流文档提到，运行时会随着运行推进逐步追踪每个代理的结果，这正是一次运行可以在同一会话内恢复的原因；把工作扇给很多小代理的工作流，因此比一条长代理保住了更多进度[^S5]。产出落在外面、逐条留痕——留痕这半句跟本系列第 11 门课讲观测是同一个道理；「中途挂了不用从头再来」那半句，是本系列第 9 门课「让长任务经得起中断」的地盘。

## 第二笔账：并发从来不是无界的

写下 `Promise.all(docs.map(...))` 的那一刻，你其实是在说「并发数 = 数组长度」。数组是 12 还好，是 200 就是另一回事了。

看三个真实产品各自的上界：

- Claude Code：默认情况下，一个会话里有 20 个子代理正在跑时，再用 Agent 工具起一个就会失败，报 `Concurrent subagent limit reached`，而且错误信息会明确告诉 Claude 不要重试[^S4]。
- Claude Code 的工作流运行时：最多 16 个并发代理，当 Claude Code 可用的 CPU 更少时（包括在受限的容器里）会更少[^S5]；单次运行总共 1000 个代理封顶[^S5]。
- Managed Agents：最多支持 25 个并发线程；协调者可以调用同一个代理的多个副本，这些副本各自开线程[^S6]。

三个不同团队、三种不同实现，全都设了上界，数字还都不大。这件事本身就是教学材料：**无界扇出是事故，不是优化**。（第 4 课会讲一个真实的翻车案例——早期的代理会为一个简单查询起 50 个子代理[^S2]。到那时你会发现，「谁来决定起几个」这个问题比「上限是多少」更棘手。）

最省事的限流是分批：

```javascript
// 分批：每批 3 个，批与批之间串行
const reports = [];
for (let i = 0; i < docs.length; i += 3) {
  const batch = docs.slice(i, i + 3);
  reports.push(...(await Promise.all(batch.map((d) => runAgent(client, reviewTask(d))))));
}
```

能用，但有个木桶效应：每一批都要等本批最慢的那个跑完，才开下一批。三份文档里有一份特别长，另外两条路就干等着。

并发池没有这个问题——固定开 N 条「泳道」，每条泳道跑完手上这个就立刻从共享游标里取下一个，永远有 N 个在飞：

```javascript
async function pool(items, limit, worker) {
  const results = new Array(items.length);
  let cursor = 0;
  const lanes = Array.from({ length: Math.min(limit, items.length) }, async () => {
    while (true) {
      const i = cursor++;
      if (i >= items.length) return;
      results[i] = await worker(items[i], i);
    }
  });
  await Promise.all(lanes);
  return results;
}
```

十来行，不需要装任何依赖。`cursor++` 在单线程的 JavaScript 里是安全的——两次 `await` 之间的同步代码不会被打断，不存在两条泳道抢到同一个下标的情况。练习里你会给它补上 `try/catch`，让单路失败不拖垮整批。

`limit` 该填几？没有普适答案，它是你的 API 配额、下游服务承受力、单路耗时三者的交集。但填一个具体的数字，跟不填，是两种工程。

## 第三笔账：投票要付 N 倍 token

投票的定义只有一句：同一个任务跑多次，拿到多样化的输出[^S1]。落成代码也很短：

```javascript
const angles = ["法务口径", "安全口径", "品牌口径"];
const opinions = await Promise.all(
  angles.map((angle) => runAgent(client, reviewTask(doc, angle))),
);

// 阈值写在代码里：三票中两票说有问题就打回
const flagged = opinions.filter((o) => o.verdict === "有问题").length;
const decision = flagged >= 2 ? "打回" : "放行";
```

这里的聚合还是程序做的——`filter` 加一个阈值。阈值定在几票，是产品决策，写死在代码里，随时可以改、可以对账，不该交给模型临场发挥。高风险场景可以把阈值调到「一票否决」，低风险场景可以要求三票全中才拦。

账很直白：**投 N 次就是 N 倍的 token**。这笔钱要放到第 1 课那个乘数上一起看——按他们的数据，Agent 用掉的 token 大约是聊天交互的 4 倍，多 Agent 系统大约是聊天的 15 倍；正因如此，多 Agent 系统需要任务本身价值够高，高到能覆盖这份性能提升的成本[^S2]。三视角投票的价签是在单 Agent 那个 4 倍上再乘 3；注意别拿 15 倍再乘 3——那个 15 倍里已经含了扇出的账。

所以投票不是「多跑几遍求个心安」，它得换到具体的东西。工作流文档说得比较清楚：把计划搬进代码之后，工作流能施加一种可重复的质量模式，而不只是跑更多代理——它可以让独立的代理**对抗式地互审**彼此的发现，之后才上报；或者从几个角度各起草一份计划，再互相权衡，这样得到的结果比单趟跑一遍更值得信[^S5]。

「独立的代理互审」这几个字，跟本系列第 10 门课那条规矩是一回事：干活的不当自己的裁判。同一个上下文里让模型自查，它多半会为刚才的输出辩护；换一路独立的上下文、换一套提示词，它才有可能真的挑出毛病。投票和互审买的不是「多数」，是**独立性**。

顺带说一句边界：一个模型的三次调用不是三个独立的判断者，它们共享同样的训练偏差。投票能过滤掉的是采样噪声和单次注意力的疏漏，过滤不掉系统性偏见。别把它当成投出来就一定对的机制。

## 分寸：独立性是前提，不是可选项

这一课所有的收益都建立在一个前提上，前面反复出现，值得单独拎出来：子任务之间必须真的互不依赖。

Claude Code 的文档在讲多个子代理同时调查时特意补了一句：每个子代理独立探索自己那块，然后 Claude 综合这些发现，而**这种做法在各条研究路径互不依赖时效果最好**[^S4]。反过来的条件写在多 Agent 复盘里：有些领域要求所有代理共享同一份上下文，或者代理之间有很多依赖，这类领域今天并不适合多 Agent 系统；比如大多数编码任务里真正可并行的部分比研究少，而且 LLM 代理目前还不太擅长实时协调和向其他代理委派[^S2]。

判断一个提案该不该并行，只需要问一句：**第二路要不要等第一路的结论才知道该干什么？**

- 要等 → 这不是并行化的形状。上一步的输出是下一步的输入，那是第 2 课的链式。
- 不要等 → 分段。
- 同一件事想要几个独立判断 → 投票。

第一种情况最容易被含糊过去：明明有依赖，却因为「大概能凑合」硬扇出去。结果是几路代理各写各的、彼此不知道对方的结论，汇合时你得手工把矛盾抹平——省下的时间全花在抹平上，还多付了 token。

## 边界：这一课的拆分是预定义的

最后钉一个词，它是第 4 课的入口。

这一课所有的例子里，**子任务是谁定的**？是你。12 份文档，是你从目录里读出来的；三个视角，是你在数组里写死的。代码跑起来之前，扇出几路、每路干什么，全都定了。这叫**预定义**的拆分。

它的对面是：由模型来决定拆成几份、每份干什么。原典把这个差别当成两个模式之间的关键分水岭——编排者-工人工作流里，一个中心 LLM 动态地拆解任务、把子任务委派给工人 LLM，再综合它们的结果[^S1]；虽然形状上跟并行化很像，但关键差异在于灵活性：**子任务不是预定义的，而是由编排者根据具体输入决定的**[^S1]。

所以两者的分界不在「同时跑几路」，而在「谁写的那个数组」。数组是你写的，就是这一课；数组是模型当场生成的，就是下一课。上一课的路由已经把一个决策交给了模型（走哪条分支），下一课交出去的是更大的一块：分解本身。

### Level 1：五个扇出提案，判形状、找坑

下面五个提案都摆在你桌上。给每一个判一个类别——**分段** / **投票** / **不该并行**——并说清理由。对判成分段或投票的，还要补上两句处置：并发怎么定，汇合怎么收。

1. 12 份互相独立的产品文档，每份都要走同一套审阅流程。
2. 一段将要发到官网首页的高风险文案，需要从法务、安全、品牌三个角度各评一次。
3. 一个数据库迁移脚本，要求先备份、再改表结构、最后回填数据，三步严格按序。
4. 40 个模块要做技术债评估，但评估规则要求每个模块参考上一个模块得出的结论，逐步收敛出一份统一口径。
5. 一条用户输入要判断是否属于违规内容，误判代价很高，希望结论的置信度比单次调用更高。

<!-- rubric -->

- 五条全部给出明确类别，判断依据落在「第二路要不要等第一路的结论」这个问题上，不是凭规模大小或直觉
- 第 3、4 条都判为不该并行，且第 4 条的理由必须点出是**结论依赖**（不是「数量太多」也不是「怕出错」）
- 每一条判成分段或投票的（第 1、2、5 条），都写出了并发处置（设上界／分批或并发池）和汇合处置（传引用或只回传结构化结论），两样缺一不可
- 第 5 条要提到阈值由代码来定，并说明高风险场景下阈值应当更严
- 指出投票的成本是 N 倍 token，不能对所有输入无差别开投票

<!-- answer -->

参考答案：

**第 1 条 —— 分段。** 12 份文档互不引用，第 3 份的结论不需要第 2 份的任何东西，典型的独立子任务并行[^S1]。并发处置：别写 `Promise.all(docs.map(...))` 直接 12 路全发，用并发池压到 3-5 路；12 份看着不多，同一段代码明天就会被拿去跑 200 份，上界要从第一天就在。汇合处置：每份审阅报告落到 `out/<id>.md`，回传只给文件路径加一行结论摘要——很多子代理各自返回详细结果会吃掉大量上下文[^S4]，正确做法是把产出存进外部系统、只把轻量引用传回协调者[^S2]。坑：`Promise.all` 一路 reject 会丢掉其余全部结果，每一路要单独 `try/catch`，失败的那份记下来单独重跑。

**第 2 条 —— 投票。** 同一段文案跑三次、每次换一个视角，正是「同一任务跑多次拿多样化输出」[^S1]；而且考虑点多的复杂任务，每个考虑点单独一次调用、注意力更聚焦，通常表现更好[^S1]，比把三个口径塞进一个提示词强。并发处置：三路可以直接一起发，规模小到不用池；真要批量处理一堆文案，那就是「外层分段 × 内层投票」，外层必须限流，否则并发数是文案数乘以 3。汇合处置：三份意见回来后由代码判定——比如三票里两票说有问题就打回，阈值写死在代码里。坑：三次调用来自同一个模型，共享同样的偏差，投票能压掉采样噪声但压不掉系统性偏见；另外这条走一次就是三倍 token，只对高风险文案开，不要全量开。

**第 3 条 —— 不该并行。** 备份 → 改表 → 回填，后一步的前提是前一步成功，这是纯粹的顺序依赖，属于第 2 课的链式形状，阶段之间还应该加程序化关卡（备份没成功就不许往下走）。硬扇出去的后果比慢严重得多：数据损坏。

**第 4 条 —— 不该并行。** 这一条最像陷阱：40 个模块听上去就是分段的样子，但评估规则要求每个模块参考上一个模块的结论，这就在子任务之间建立了依赖。原话很明确：多个子代理同时调查，在各条研究路径互不依赖时效果最好[^S4]；要求共享同一份上下文、或代理之间依赖很多的领域，今天并不适合多 Agent[^S2]。可行的改法是先改需求：如果「统一口径」可以先由一次调用定好、再作为固定输入发给 40 路，那依赖就被拆掉了，第二步可以并行；口径必须逐个演进的话，只能串行。

**第 5 条 —— 投票，并且配阈值。** 需要更高置信度的判断，正是并行化的第二类适用场景：需要多个视角或多次尝试来换更高置信度[^S1]。并发处置：3 到 5 路一起发，别更多——超过这个数收益递减，token 却线性涨。汇合处置：代码统计票数，高风险场景用「一票否决」而不是简单多数，拿不定的样本转人工。坑：先算账再上线——Agent 大约用掉聊天交互 4 倍的 token，多 Agent 系统大约 15 倍，这类系统需要任务价值高到能覆盖成本[^S2]；违规判断只对灰区样本开投票，明显合规的输入单次调用就够了。

<!-- hint -->

每条只问一个问题：第二路要不要等第一路的结论，才知道自己该干什么。要等，就不是并行化的形状，条目有几十几百都不改变这一点。第 4 条里的「40 个模块」是干扰项，真正决定答案的是「参考上一个模块得出的结论」那半句。

<!-- hint -->

「同一个任务跑很多遍」和「很多个不同任务各跑一遍」是两个不同的变体，别混。另外，判成投票的那两条还欠一样东西：几票算数？这个阈值得写在代码里，而且误判代价越高，阈值应该比简单多数更严。

### Level 2：写一个有界扇出，跑给自己看

写一个能真跑的 `fanout.mjs`（Node 18+，不装任何依赖），要求：

- 自带一个桩 `client`，冒充 `messages.create`，不联网，每个条目的耗时和结论写死，这样两次运行可以逐字对比
- 8 个条目，每个条目由一次 `runAgent()` 处理（沿用第 2 课那个封装的形状）
- 自己实现一个并发池，上限 3，同时在跑的 worker 不得超过 3；单路失败不能拖垮整批
- 每个 worker 把产出写进 `out/` 目录的文件；汇合时只收集文件路径和一行摘要，不把报告正文带回来
- 最后打印一张汇总表（条目 / 耗时 / 结论 / 结果文件），并打印落盘字节数与回传字节数的对比
- 判定路径带退出码：全部成功 `exit 0`，有任何一条失败或结果文件为空 `exit 1`
- 跑通之后把并发上限从 3 改成 8 再跑一遍（改代码或用环境变量都行），验证完成顺序变了、结果集没变；为了让顺序真的会变，写死的耗时**别按数组顺序递增也别全相等**（比如 120/40/200/60/30/150/80/45），否则两种并发下完成顺序会碰巧一样

<!-- rubric -->

- 并发池是自己写的（固定 N 条泳道 + 共享游标，或等价实现），没有引入第三方依赖，且同时在跑的 worker 数确实不超过 `limit`
- 每个 worker 内部有 `try/catch`（或等价处理），一路失败时其余各路仍然跑完并进入汇总表
- 产出真的写进了 `out/` 下的文件，回传对象里只有路径和摘要这类轻量字段，没有报告正文
- 判定分支两条路都成立：全成功时 `process.exit(0)`，有失败或空文件时 `process.exit(1)` 并打印哪一条失败
- 两次运行的输出都是真实跑出来的，完成顺序不同（前提是耗时安排满足上面那条）、结果集指纹相同，并且能解释为什么顺序会变而结果不变

参考答案：完整脚本如下，本课作者在 Node 上真实跑过，下面两段输出是直接贴的运行结果。

```javascript
// fanout.mjs —— 分段扇出: 8 个条目, 并发上限 3, 汇合只传引用
// 跑法: node fanout.mjs          默认并发 3
//       LIMIT=8 node fanout.mjs  并发 8
import { mkdir, writeFile, rm, stat } from "node:fs/promises";
import { createHash } from "node:crypto";
import path from "node:path";

const OUT_DIR = "out"; // 相对路径: 回传的引用更轻, 也不受运行目录影响
const LIMIT = Number(process.env.LIMIT ?? 3);

// ---------- 1. 输入: 8 个互相独立的条目 ----------
const DOCS = [
  { id: "api-auth", title: "API 鉴权说明" },
  { id: "billing-faq", title: "计费常见问题" },
  { id: "onboarding", title: "新手引导" },
  { id: "webhook-guide", title: "Webhook 接入指南" },
  { id: "rate-limit", title: "限流策略" },
  { id: "sdk-migration", title: "SDK 迁移说明" },
  { id: "error-codes", title: "错误码表" },
  { id: "security-notes", title: "安全须知" },
];

// ---------- 2. 桩 client: 冒充 messages.create, 不联网 ----------
// 每个 id 的耗时和结论都写死, 这样两次运行可以逐字对比
const FAKE = {
  "api-auth": { ms: 120, issues: 3, level: "高" },
  "billing-faq": { ms: 40, issues: 1, level: "低" },
  onboarding: { ms: 200, issues: 4, level: "中" },
  "webhook-guide": { ms: 60, issues: 2, level: "中" },
  "rate-limit": { ms: 30, issues: 0, level: "低" },
  "sdk-migration": { ms: 150, issues: 5, level: "高" },
  "error-codes": { ms: 80, issues: 2, level: "低" },
  "security-notes": { ms: 45, issues: 1, level: "中" },
};

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

function createStubClient() {
  return {
    messages: {
      async create({ messages }) {
        const last = messages[messages.length - 1].content;
        const id = /<doc id="([^"]+)">/.exec(last)?.[1];
        const f = FAKE[id];
        if (!f) throw new Error(`桩 client 不认识的条目: ${id}`);
        await sleep(f.ms); // 冒充一次网络往返
        const findings = Array.from(
          { length: f.issues },
          (_, i) => `- 第 ${i + 1} 节: 表述与现行接口不一致, 需要复核`,
        ).join("\n");
        return {
          stop_reason: "end_turn",
          content: [
            {
              type: "text",
              text: `# 审阅报告: ${id}\n\n## 发现\n${findings || "- 无"}\n\n结论: ${f.issues} 处待修, 风险等级 ${f.level}`,
            },
          ],
        };
      },
    },
  };
}

// ---------- 3. runAgent: 第 2 课那个封装的简化版（桩只走 end_turn，省掉工具分支）----------
async function runAgent(client, task) {
  const messages = [{ role: "user", content: task.prompt }];
  for (let turn = 0; turn < 8; turn++) {
    const res = await client.messages.create({
      model: "claude-sonnet-4-5",
      max_tokens: 2048,
      messages,
    });
    const text = res.content
      .filter((b) => b.type === "text")
      .map((b) => b.text)
      .join("\n");
    if (res.stop_reason === "end_turn") return text;
    messages.push({ role: "assistant", content: res.content });
    messages.push({ role: "user", content: "继续" });
  }
  throw new Error(`${task.id}: 超出回合上限仍未收敛`);
}

// ---------- 4. 并发池: 上限 LIMIT, 不装依赖 ----------
async function pool(items, limit, worker) {
  const results = new Array(items.length);
  let cursor = 0;
  const lanes = Array.from(
    { length: Math.min(limit, items.length) },
    async () => {
      while (true) {
        const i = cursor++;
        if (i >= items.length) return;
        try {
          results[i] = { ok: true, value: await worker(items[i], i) };
        } catch (err) {
          results[i] = { ok: false, id: items[i].id, error: String(err) };
        }
      }
    },
  );
  await Promise.all(lanes);
  return results;
}

// ---------- 5. 一个 worker = 一次 runAgent + 一次落盘 ----------
const completionOrder = [];

async function reviewOne(client, doc) {
  const t0 = Date.now();
  const report = await runAgent(client, {
    id: doc.id,
    prompt: `审阅下面这份文档, 列出与现行接口不一致的地方, 最后一行以"结论:"开头给出待修数量和风险等级。\n\n<doc id="${doc.id}">${doc.title}</doc>`,
  });
  const file = path.join(OUT_DIR, `${doc.id}.md`);
  await writeFile(file, report, "utf8");
  const summary = report.split("\n").find((l) => l.startsWith("结论:")) ?? "无结论";
  completionOrder.push(doc.id);
  // 回传给协调者的只有这一小坨: 引用 + 一行摘要
  return { id: doc.id, file, summary, ms: Date.now() - t0, bytes: Buffer.byteLength(report) };
}

// ---------- 6. 主流程 ----------
const client = createStubClient();
await rm(OUT_DIR, { recursive: true, force: true });
await mkdir(OUT_DIR, { recursive: true });

const wallStart = Date.now();
const settled = await pool(DOCS, LIMIT, (doc) => reviewOne(client, doc));
const wallMs = Date.now() - wallStart;

const failed = settled.filter((r) => !r.ok);
const done = settled.filter((r) => r.ok).map((r) => r.value);

console.log(`并发上限: ${LIMIT}  条目: ${DOCS.length}  墙钟: ${wallMs}ms`);
console.log(`完成顺序: ${completionOrder.join(" → ")}`);
console.log("");
console.log("条目             耗时     结论                       结果文件");
console.log("-".repeat(78));
for (const d of DOCS) {
  const r = done.find((x) => x.id === d.id);
  if (!r) {
    console.log(`${d.id.padEnd(16)} ${"—".padEnd(8)} 失败                       —`);
    continue;
  }
  console.log(
    `${r.id.padEnd(16)} ${String(r.ms + "ms").padEnd(8)} ${r.summary.padEnd(26)} ${r.file}`,
  );
}
console.log("-".repeat(78));

const payload = done.reduce((n, r) => n + r.bytes, 0);
const carried = Buffer.byteLength(
  JSON.stringify(done.map((r) => ({ file: r.file, summary: r.summary }))),
);
console.log(`落盘产出: ${payload} 字节   汇合回传: ${carried} 字节`);

// 结果集指纹: 与并发数无关, 两次运行必须一致
const digest = createHash("sha256")
  .update(done.map((r) => `${r.id}:${r.bytes}:${r.summary}`).sort().join("|"))
  .digest("hex")
  .slice(0, 12);
console.log(`结果集指纹: ${digest}`);

// ---------- 7. 判定 ----------
for (const r of done) {
  const s = await stat(r.file);
  if (s.size === 0) failed.push({ id: r.id, error: "结果文件为空" });
}
if (failed.length > 0 || done.length !== DOCS.length) {
  console.error(`判定: 失败 ${failed.length} 个 / 共 ${DOCS.length} 个`);
  for (const f of failed) console.error(`  ${f.id}: ${f.error}`);
  process.exit(1);
}
console.log("判定: 通过");
process.exit(0);
```

两次运行值得对照着看三处：

1. **完成顺序变了。** 并发 3 时先跑的是前三个条目，谁先跑完谁就腾出泳道给第 4 个，顺序由「起跑时间 + 各自耗时」共同决定；并发 8 时八个一起起跑，完成顺序就是耗时从小到大（30 → 40 → 45 → 60 → 80 → 120 → 150 → 200 毫秒）。扇出的完成顺序是不确定的，任何依赖「先回来的先处理」的逻辑都会在这里翻车。
2. **结果集没变。** 汇总表按 `DOCS` 的固定顺序打印，指纹两次都是 `dd4a82283a3d`。这是设计出来的：汇总表遍历的是输入数组而不是完成顺序，指纹在算之前先 `sort()`。**并发数是性能参数，不该影响结果**——把这条做成可验证的断言，改并发时才敢放心改。
3. **汇合只搬走了不到四成。** 1668 字节落盘、643 字节回传，8 个条目就差出这么多；条目变成 200 个、每份报告长十倍，落盘那一侧会涨到几百 KB，回传那一侧还是一行摘要加一个路径。

把某个条目的 id 故意改错（比如写成 `rate-limitX`）再跑一次，判定路径会走另一条分支：

```text
$ node fanout.mjs; echo "exit=$?"
…（逐条与汇总表略：rate-limitX 那一行标为 失败，其余 7 份照常落盘）
判定: 失败 1 个 / 共 8 个
  rate-limitX: Error: 桩 client 不认识的条目: rate-limitX
exit=1
```

注意另外 7 条仍然跑完并且落了盘——这是池里那个 `try/catch` 换来的。换成 `Promise.all(DOCS.map(reviewOne))`，这一路 reject 会让整个 `await` reject，另外 7 份已经跑完的成果一个都拿不到。

<!-- hint -->

先把「并发上限」和「批」这两件事分开想。分批是「每批等最慢的那个跑完再开下一批」，并发池是「固定开 N 条泳道，每条跑完手上这个立刻取下一个」。写池的时候用一个共享的 `cursor` 变量当取号机，开 N 个 async 函数各自 `while` 循环取号即可——JavaScript 是单线程的，`cursor++` 不会被打断。

<!-- hint -->

「结果集不变」怎么证给自己看？别肉眼比对两屏输出。把每条结果压成一个短字符串（`id:字节数:摘要`），排序后拼起来算个 sha256 取前 12 位打出来。顺序无关的指纹一致，才是真的不变。另外记得汇总表要遍历输入数组、不要遍历完成顺序，否则表格本身就会随并发数抖动。

## 小结

- 并行化的定义是「LLM 有时可以同时处理任务、输出由程序聚合」，两个变体是分段（把任务拆成独立子任务并行跑）和投票（同一任务跑多次拿多样化输出）[^S1]
- 它的适用条件是子任务可并行提速、或需要多视角与多次尝试来换更高置信度；考虑点多的复杂任务，每个考虑点单独一次调用、注意力更聚焦，通常表现更好[^S1]
- 扇出买到的不只是速度：子代理带着各自的上下文窗口并行探索、再把最重要的 token 压缩回来，还带来关注点分离（不同工具、提示词、探索轨迹）与更少的路径依赖[^S2]；把工作分布到拥有独立上下文窗口的代理上，是在为并行推理增加容量[^S2]
- 提速的数字要连语境一起记：他们的 Research 引入两级并行（主代理并行起 3-5 个子代理、子代理并行用 3 个以上工具）后，对复杂查询把研究时间砍掉最多 90%[^S2]——这是他们自家系统上的延迟数字，不是质量数字
- 汇合是第一笔账：子代理完成后结果回到主对话，很多子代理各自返回详细结果会消耗大量上下文[^S4]；解法是工件系统——子代理把产出存进外部系统，只把轻量引用传回协调者[^S2]
- 并发从来不是无界的：Claude Code 默认 20 个并发子代理、超了就报错并明说不要重试[^S4]；工作流运行时最多 16 个并发代理（CPU 少时更少）、单次运行 1000 个代理封顶[^S5]；Managed Agents 最多 25 个并发线程[^S6]
- 投票的账是 N 倍 token，要放进那个乘数里一起算——按他们的数据，Agent 约为聊天的 4 倍、多 Agent 系统约为聊天的 15 倍，任务价值得高到能覆盖它[^S2]；换来的应该是可重复的质量模式，比如独立代理对抗式互审、或从几个角度各起草再互相权衡[^S5]
- 独立性是前提：多个子代理同时调查，在各条研究路径互不依赖时效果最好[^S4]；要求共享同一份上下文、或代理之间依赖很多的领域今天并不适合[^S2]——有依赖就回到链式的形状
- 这一课的拆分全是预定义的（数组是你写的）；子任务不预定义、而由编排者根据具体输入决定，是编排者-工人与并行化的关键差异[^S1]，也是下一课的主题
