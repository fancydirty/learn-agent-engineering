# 第 2 课：串起来、分下去：链式与路由

> 学习目标：
> - 把一个塞了四件事的提示词拆成一条链，说清这么拆换来了什么、付出了什么
> - 在链的环与环之间安上程序化关卡，让不合格的中间结果停在该停的地方
> - 判断一个任务该链式、该路由、两者都用还是都不该动，并把路由写成一次输出收紧的廉价调用
>
> 前置要求：读完第 1 课，能手写以 `stop_reason` 驱动的 harness 循环（本系列第 7 门课），了解确定性验证器（本系列第 10 门课） | 上一课 [第 1 课 <<](./01-when-one-loop-isnt-enough.md) | 下一课 [第 3 课 >>](./03-parallelization.md)

## 一个提示词干四件事，总有一件会掉链子

你要给一个新功能写帮助文档：读产品需求 → 列一份提纲 → 按提纲写正文 → 检查全文有没有用错旧称。

第一版你多半是把这四步写进一个提示词，交给一个 harness 循环。第一次跑出来看着还行，问题出在第二次、第三次：这回提纲很好，正文却少写了一节；下回正文完整，通篇混着上一版就废掉的「用户组」；再下回它写到一半回头改提纲，交出来的提纲和正文对不上。

这几次失败长得不一样，根子是同一个：这一次调用里，模型要同时扛住理解需求、设计结构、生成文字、做一致性核对四件事，哪件挤掉哪件你控制不了，也看不见。更麻烦的是你没有插手的位置——等你拿到输出，四件事已经全做完了，「提纲不合格」这个事实被埋在最终稿里。

第 1 课讲过「谁持有计划」这根轴。这个一次性提示词把计划整个交给了模型。本课第一件事，就是把它拿回来。

## 链式：拿延迟换准确率

官方给这个模式的定义只有两句，每个词都在承重。

链式（prompt chaining）把一个任务分解成一串步骤，每次 LLM 调用处理上一次调用的输出；你可以在任何一个中间步骤加上程序化检查，确保整个过程还在轨道上[^S1]。什么时候用它：任务能被干净利落地分解成固定的子任务时。主要目的是拿延迟换更高的准确率——办法是让每次 LLM 调用都变成一个更容易的任务[^S1]。

「让每次调用变成更容易的任务」这半句把病因和药方一起给了。一次调用扛四件事是难任务；一次调用只列提纲、什么都不写是容易任务。链式没有把工作变少，是把每一次要求模型完成的工作变简单了。

代价明码写在标价里：延迟。每多一个阶段就多一次完整往返。官方在同一篇文章开头就摊开过这笔账——agentic 系统常常是拿延迟和成本去换任务表现，你应该想清楚这个交换在什么时候划算[^S1]。「又慢又贵」不是链式的意外副作用。

```text
需求 ──▶ 出提纲 ──▶ 按提纲写正文 ──▶ 查术语 ──▶ 交付
```

每一段的输入是上一段的输出。前一环歪了，后面只会照着歪下去。

## 每个阶段是一个完整的 harness 循环

链上的一个阶段不是「一次 API 调用」，而是**一个完整的 harness 循环**——就是你在本系列第 7 门课手写的那个 while 循环：发消息、看 `stop_reason`、是 `tool_use` 就执行工具再把结果发回去、不是就返回文本。

这个用法有出处。官方讲怎么给 Agent 做评测时给的跑法就是这个形状：直接调 LLM API、用简单的 agentic 循环（把 LLM 调用与工具调用交替包起来的 while 循环），一条评测任务配一个循环，每个评测 Agent 拿到一条任务提示词和你的工具[^S3]。那篇讲的是评测，这个构件本身是通用的：一条任务、一个循环、由代码驱动。链式就是把这样的构件串起来，用代码决定顺序。

后面几课都用同一个记号：

```javascript
// runAgent 就是本系列第 7 门课那个 harness 循环包了一层函数
// 输入：一条自包含的任务提示词 + 这个阶段能用的工具；输出：跑完之后的最终文本
const answer = await runAgent(client, task, tools);
```

整条链就是一段你能一眼读完的顺序代码：

```javascript
const outline = await runAgent(client, 提纲任务(req));
const g1 = gateOutline(outline);        // 关卡 1：提纲结构对不对
if (!g1.ok) fail(g1.why);               // 不合格就停在这，别往下送

const doc = await runAgent(client, 写作任务(outline));
const g2 = gateTerms(doc);              // 关卡 2：有没有出现禁用旧称
if (!g2.ok) fail(g2.why);

const report = await runAgent(client, 检查任务(doc), { read_glossary });
```

请注意这几行里**没有**的东西：没有「模型决定下一步做什么」的余地。顺序是写死的，中间结果 `outline`、`doc` 是脚本里的普通变量。模型在每个阶段内部仍然自主（它想调几次工具就调几次），但阶段之间的控制权在代码手上。附带好处是每段提示词可以只针对一件事写严：出提纲那段要求只输出标题、一个字正文都不许写，写正文那段专心讲文风和禁用词——这两套要求塞进一个提示词里是会打架的。

这个形状在产品里也见得到。Claude Code 官方文档对多步骤工作流的建议是：让 Claude 按顺序使用子代理，每个子代理完成自己的任务、把结果交回来，Claude 再把相关的上下文传给下一个[^S4]。区别落在第 1 课那根轴上——产品形态里决定「传什么过去」的是 Claude 自己，你写脚本的时候那是你的代码。

## 关卡：把本系列第 10 门课的验证器搬到环与环之间

定义里最后半句，才是链式比「一个大提示词」真正多出来的东西：你可以在任何一个中间步骤加上程序化检查，确保过程还在轨道上[^S1]。原文给这种检查起的名字是 gate，而且是打了引号的：`(see "gate” in the diagram below)`——引号一边直一边弯，原文如此，不是这里打错。

「程序化」是重点：它是代码，不是又一次模型调用，就是几行 `if`。

本系列第 10 门课教过确定性验证器：能用代码判定对错的事，就别花钱去问模型。那门课把验证器安在**终态**上——跑完了，检查产出合不合格。链式给同一种检查提供了一个新位置：**环与环之间**。

```javascript
function gateTerms(doc) {
  const hits = BANNED.filter((w) => doc.includes(w));
  if (hits.length > 0) {
    return { ok: false, why: `成文出现禁用旧术语：${hits.join('、')}` };
  }
  return { ok: true };
}
```

七行，一次模型调用都没有，同样的输入判定永远一样。它挡住的正是「正文混进旧称」那种失败；数一数提纲有几个章节标题的那道关卡同样简单。

关卡失败时做什么是个设计决策：**停下并报错**（最适合你还在调这条链的时候，但失败信息里必须写清挂在哪一环，否则你只知道「不行」，不知道该改哪段提示词）、**把失败原因塞回同一阶段的提示词重试**（配次数上限）、或者**记一笔用兜底值继续**（只有这一环不承重时才行）。第 2 级练习用第一种。

顺带说本系列第 6 门课的账：派给别人干的活，提示词必须自包含——目标、输出格式、能用什么工具、边界在哪，四样都得写全。链上每个阶段的任务就是一份这样的派活提示词。这四要素有准确的一手出处，第 4 课讲编排者怎么派活时会拿出来逐条对。

## 路由：先分类，再分发

链式管的是「一件事分几步做」。另一类任务的形状完全不同：进来的不是一件事，是好几种事，各有各的做法。

官方的定义是：路由（routing）对输入做分类，然后把它导向一个专门化的后续任务。这个工作流带来关注点分离，也让你能写更专门化的提示词。没有它，为一类输入做的优化可能会伤害其他输入的表现[^S1]。

最后那句是路由存在的理由。假设客服来信有退款、故障、账单三类，你用一个提示词处理全部。为了把退款处理好，你加了一条「先确认订单号和支付渠道」；这条规则对故障来信是纯干扰，模型会拿着它去问一个正在报页面白屏的用户要支付渠道。你再加一条「如果是故障就别问订单号」，提示词开始长出补丁的补丁。

什么时候用它：任务复杂、存在几个明显不同、分开处理更好的类别，并且分类这件事本身能被准确完成——用 LLM 做分类可以，用更传统的分类模型或算法也可以[^S1]。最后这个前提条件不是锦上添花：分错了错得很隐蔽——一封退款信被送进故障流程，会得到一份认认真真的故障排查回复。

代码上，路由比链式还简单：

```javascript
const HANDLERS = {
  退款: handleRefund,
  故障: handleIncident,
  账单: handleBilling,
  其他: handleFallback,
};
const LABELS = Object.keys(HANDLERS);

async function classify(client, letter) {
  const raw = await runAgent(client, [
    '目标：给下面这封客服来信分类。',
    `输出格式：只输出一个词，从这几个里选：${LABELS.join('、')}。不要解释，不要加标点。`,
    `来信：${letter}`,
  ].join('\n'));

  const label = raw.trim();
  return LABELS.includes(label) ? label : '其他';   // 收不进表里就走兜底
}

const category = await classify(client, letter);
const reply = await HANDLERS[category](client, letter);
```

三处值得注意。

**分类调用要把输出收紧到一个词**——本系列第 10 门课讲 LLM 裁判时用过同一招：把可选值列出来、明说不要解释，收紧之后解析这一步才有可能是确定性的。**收不进表里就走兜底**——那行 `LABELS.includes(label) ? label : '其他'` 不是防御性洁癖，模型偶尔会回「我觉得可能是故障，也可能是别的」，这时 `HANDLERS[那串话]` 是 `undefined`，下一行就炸了；留一条兜底分支，分类的不确定性就被关在这一行里面。

**分类器不一定要是模型**——定义里明说了传统分类模型或算法也算[^S1]，来信带着固定的订单号格式、或者来自某个专门的表单入口，一条正则就够了，还快得多。

分发出去之后，每个 handler 可以是任何东西：一个 harness 循环、一条链、甚至一段完全不含模型的代码。

## 现行 API 词汇里的两个路由变体

上面那份路由定义来自 2024 年底的模式文章，页面自己挂着横幅说其中的工具生态描述已经过时。所以有必要核对：这个模式在现行的第一方词汇里还活着吗？活着，而且被单独点了名。Claude 平台的多代理编排文档里有两条就是路由：

- **专门化（Specialization）**：把活路由给带有领域专属系统提示词和工具的代理，比如一个安全代理、一个文档代理，而不是把所有能力都塞进同一个代理里[^S6]。这就是 `HANDLERS` 那张表的官方说法。
- **升级（Escalation）**：对其中一部分复杂子任务，去咨询一个能力更强的代理或模型[^S6]。

第二条值得单拎出来：它按**难度**分发，而不是按**主题**分发。分类器不判断「这是退款还是故障」，而判断「这封信我这个便宜档位能不能处理」。这件事比主题分类更难判准，所以升级这一路有个更稳的写法：先按便宜档位跑，产出过不了关卡再往上升——把一个难判断的分类问题换成一个可判定的验证问题。

## 分寸：什么时候不该拆

**链每加一环，就加一段延迟。** 这不是实现没优化，这是官方给这个模式定的价：拿延迟换更高的准确率[^S1]。用户等的是每一段的和。如果用户是在界面上同步等结果，链再往长里加之前，先想想人还在不在。

**类别只有一个时，路由是纯开销。** 路由的收益来自关注点分离[^S1]。输入其实只有一种的话，你就付了一次分类调用的钱和延迟，什么也没换到，还多了一个分错的可能。

**任务分不干净时，别硬拆。** 「干净利落地分解成固定的子任务」这个条件是有牙齿的[^S1]。一份要来回看全局才能改好的稿子，拆成「先改结构、再改措辞」，第二环拿不到第一环没写下来的那些理由，只会照着字面改。这时候一个循环、一个上下文反而更好——这正是第 1 课那些反向条件的用处。

**拿不准就先量。** 官方这句话说了两遍：只在复杂度**能被证明**改善了结果的时候才考虑增加它[^S1]。本系列第 10 门课的评测跑道就是干这个的：先跑单提示词版本量一个分数，再跑拆开的版本量一遍，差多少、值不值那几秒延迟，这才是能拿去和同事吵的依据。

最后划一下边界。链式和路由都还是**固定形状**的编排：链有几环、路由有哪几类，写代码的时候就定死了。多个阶段同时跑再聚合，是第 3 课的并行化；连子任务有几个都要等看到输入才知道，是第 4 课的编排者-工人。

### Level 1：判断该链式、该路由，还是都不动（不写代码）

下面四个任务，逐个判断该用链式、该用路由、两个都用，还是两个都不该用。除了结论，还要写清楚：判了链式，两环之间的程序化关卡查什么；判了路由，分类器放在哪、有几个类别、是模型还是代码。

1. 客服信箱每天进来几百封信，退款、故障、账单三类的处理方式完全不同，现在共用一个提示词，改一类的措辞就会影响另一类。
2. 一份英文合同，要先审出一份结构化的风险意见（每条含条款位置、风险等级、说明），再把这份意见翻译成中文和日文两个版本，交给不同的团队。
3. 一个混合工单队列：既有「密码重置」这种一步就能答完的，也有「数据迁移失败」这种要查日志、定位、给方案、写回复的多步任务。
4. 用户在输入框里敲了一句话，你要把里面的错别字改掉，返回改好的那句话。

<!-- rubric -->

- 四题的结论分别是：路由 / 链式 / 两个都用 / 两个都不用。
- 第 1 题的理由要落到「为一类输入优化可能伤害其他输入」上，并给出类别集合，且必须含一个兜底类别。
- 第 2 题要指出两个翻译版本之间没有先后依赖（并行留给第 3 课，认出来即可），并给出至少一道具体的关卡。
- 第 3 题要说清两层结构：外层按复杂度路由，被判为复杂的那一支内部才是链。
- 第 4 题要明确说「一次调用就够」，理由落在拆分带来的延迟和收益不成比例上。
- 每道关卡都必须是纯代码可判的，不能是「让模型看一眼合不合格」。

<!-- answer -->

**1. 客服来信按主题分发 —— 路由。**

判据正好对上适用条件：存在几个明显不同、分开处理更好的类别，并且分类本身能被准确完成[^S1]。题干里「改一类的措辞就会影响另一类」这句，就是官方那句「没有路由，为一类输入优化可能会伤害其他输入的表现」的现场版[^S1]。分类器放在最前面，类别集合是 `退款 / 故障 / 账单 / 其他`，「其他」接住分不进前三类的信和模型没按格式回话的情况；一次廉价模型调用即可，输出收紧到一个词。如果退款信大多来自某个固定的售后表单入口，这一路可以先用一条纯代码规则短路掉。

**2. 合同审阅出结构化意见再翻译 —— 链式。**

任务能干净分成固定的子任务：审阅、翻译；第二步的输入就是第一步的输出，这正是链式的定义形状[^S1]。两个语种之间没有先后依赖，这种「同一步在多个条目上重复」的形状是第 3 课并行化的活，本题只要认出它、别把它写成串行的两环。

关卡放在审阅和翻译之间，查结构不查内容，都是纯代码：输出能被 `JSON.parse` 解析成数组；每一项都有 `clause`、`level`、`note` 三个字段；`level` 落在 `高 / 中 / 低` 这个集合里；数组长度大于 0（一份合同审出零条意见，多半是上一步跑歪了，而不是合同完美）。翻译阶段发现不了自己的输入是坏的，只会把坏东西如实翻成两种语言，所以这道关卡得卡在它前面。

**3. 混合工单 —— 两个都用。**

外层路由，内层链。分类器放在队列入口，判的不是主题而是复杂度，类别可以是 `一步可答 / 需要排查 / 其他`。「一步可答」直接走一次调用甚至模板；「需要排查」才展开成一条链：查日志 → 定位原因 → 给方案 → 写回复。这就是前面讲的按难度分发，形状上和官方词汇里的升级同类——官方那一条说的是就一部分复杂子任务去咨询更强的代理或模型[^S6]，这里把「更强的代理」换成了展开一条链。

链内部至少两道纯代码关卡：定位阶段的输出必须带上至少一条日志行的引用（正则查时间戳格式），写回复阶段的输出必须包含方案阶段给出的那个工单编号（字符串包含判断）。如果复杂度分类器本身不好写准，就换成「先按一步可答处理，产出过不了关卡再升级」。

**4. 一句话改错别字 —— 两个都不该用。**

一次调用就够。这里没有能干净分出来的固定子任务（「找错」和「改错」分开做，第二环还得把整句重看一遍，等于白跑），也没有需要分开处理的类别。拆开的成本却是实打实的：多一次往返的延迟，而用户正盯着输入框等结果。链式的定位是拿延迟换准确率[^S1]，前提是准确率真的能换来——这个任务上换不来。真要提质量，先给提示词加几个示例；官方也把这条路留在了模式前面：对很多应用来说，用检索和上下文示例把单次 LLM 调用优化好，通常就够了[^S1]。

<!-- hint -->

先别急着判模式，先问每个任务两个问题：进来的东西是「一件事」还是「好几种事」？如果是一件事，它能不能分成几个各自都更简单、而且顺序固定的步骤？第一问答「好几种事」就往路由想，第二问答「能」就往链式想。

<!-- hint -->

写关卡时有个自检：这道检查你能不能用 `if` 和字符串函数写出来，且同样的输入永远得到同样的结论？如果写着写着变成了「让模型判断这份提纲够不够好」，那它就不是这一课说的程序化检查——那是评审回路，留到第 5 课。

### Level 2：把三阶段链写出来并跑通（写代码）

写一个 `chain.mjs`，把开头那个写帮助文档的任务实现成三阶段链：**出提纲 → 按提纲写正文 → 查术语一致性**，中间两道关卡。要求：

1. 用桩 client（本系列第 8 到 11 门课一直用的那套做法）：一个固定响应队列，不联网、不花钱，同样的输入永远跑出同样的结果。
2. `runAgent(client, task, tools)` 是真的 harness 循环——按 `stop_reason` 判断，`tool_use` 就执行工具再把结果发回去。第三阶段要真的走一次工具调用（读术语表）。
3. 关卡 1：提纲必须恰好包含 3 个以 `## ` 开头的章节标题。关卡 2：正文里不得出现禁用旧术语（自己定一张两三个词的表）。两道都是纯代码，不再调模型。
4. 关卡失败时打印挂在**哪一环**、为什么，然后以非零退出码结束；三个阶段全过则以 0 退出。
5. 准备两组固定响应跑两次：一次全过，一次让第二道关卡拦下。把两次的真实输出和退出码都贴出来。

<!-- rubric -->

- 桩 client 是先进先出的响应队列，队列空了要报错而不是静默返回 `undefined`（否则你会以为链跑通了，其实是空转）。
- `runAgent` 里有真正的 `while` 循环和 `stop_reason` 分支，不是一次 `await` 就返回；第三阶段的响应序列里含一个 `tool_use`，让工具分支被真的执行到。
- 两个关卡函数都不调用 client，返回值里带上失败原因，同样输入永远同样输出。
- 失败信息里写出是哪两个阶段之间挂的、命中的具体是哪个词——只打印「失败」不算过。
- 退出码：全过 0，关卡失败非零（参数错误之类可以再给一个不同的非零码）。
- 第二组响应触发的是关卡 2，且第三阶段确实没有跑（输出里看不到它的打印）。
- 贴出来的输出是真跑出来的：阶段编号、命中的词、退出码都和脚本对得上。

<!-- answer -->

完整脚本：

```javascript
// chain.mjs —— 三阶段链：出提纲 → 写文档 → 查术语
// 本课自己写的示意脚本——一手材料里没有编排脚本的代码样本
// 用法：node chain.mjs pass    （三阶段全过）
//       node chain.mjs stale   （第二道关卡拦下）

const BANNED = ['用户组', '子账号'];

// ---------- 桩 client：固定响应队列，不联网 ----------
const say = (t) => ({ stop_reason: 'end_turn', content: [{ type: 'text', text: t }] });
const useTool = (id, name, input = {}) => ({
  stop_reason: 'tool_use',
  content: [{ type: 'tool_use', id, name, input }],
});

function makeStubClient(script) {
  const queue = [...script];
  return {
    messages: {
      async create() {
        if (queue.length === 0) throw new Error('桩队列已空：脚本比预设多调了一次模型');
        return queue.shift();
      },
    },
  };
}

// ---------- 一个阶段 = 一个完整的 harness 循环 ----------
async function runAgent(client, task, tools = {}) {
  const messages = [{ role: 'user', content: task }];
  while (true) {
    const res = await client.messages.create({
      model: 'claude-sonnet-4-5',
      max_tokens: 2048,
      messages,
      tools: Object.values(tools).map((t) => t.schema),
    });
    messages.push({ role: 'assistant', content: res.content });

    if (res.stop_reason !== 'tool_use') {
      return res.content
        .filter((b) => b.type === 'text')
        .map((b) => b.text)
        .join('\n')
        .trim();
    }

    const results = [];
    for (const block of res.content) {
      if (block.type !== 'tool_use') continue;
      const tool = tools[block.name];
      results.push({
        type: 'tool_result',
        tool_use_id: block.id,
        content: tool ? await tool.run(block.input) : `未知工具：${block.name}`,
      });
    }
    messages.push({ role: 'user', content: results });
  }
}

// ---------- 两道关卡：纯代码，不问模型 ----------
function gateOutline(outline) {
  const headings = outline.split('\n').filter((l) => l.startsWith('## '));
  if (headings.length !== 3) {
    return { ok: false, why: `提纲要求恰好 3 个章节标题，实际数到 ${headings.length} 个` };
  }
  return { ok: true, detail: `章节：${headings.map((h) => h.slice(3)).join(' / ')}` };
}

function gateTerms(doc) {
  const hits = BANNED.filter((w) => doc.includes(w));
  if (hits.length > 0) {
    return { ok: false, why: `成文出现禁用旧术语：${hits.join('、')}` };
  }
  return { ok: true, detail: `禁用词表 ${BANNED.length} 条，命中 0 条` };
}

function fail(where, why) {
  console.error(`\n✗ gate 失败 @ ${where}`);
  console.error(`  原因：${why}`);
  console.error('  链在这里停住，后面的阶段不会跑。');
  process.exit(1);
}

// ---------- 工具 ----------
const glossary = {
  schema: {
    name: 'read_glossary',
    description: '读取产品术语表，返回「旧术语 → 新术语」对照',
    input_schema: { type: 'object', properties: {}, required: [] },
  },
  run: async () => '用户组 → 团队空间\n子账号 → 成员账号\n审批流 → 流程',
};

// ---------- 三段固定响应 ----------
const OUTLINE = ['## 权限模型', '## 团队空间的建立与成员管理', '## 常见问题'].join('\n');

const CLEAN_DOC = [
  '## 权限模型',
  '每个成员账号归属一个团队空间，权限由团队空间的角色决定。',
  '## 团队空间的建立与成员管理',
  '管理员在控制台新建团队空间后，可邀请成员账号加入。',
  '## 常见问题',
  '成员账号可同时属于多个团队空间，权限取并集。',
].join('\n');

const STALE_DOC = CLEAN_DOC.replace('可邀请成员账号加入', '可邀请子账号加入');

const REPORT = '术语一致性检查通过：全文统一使用「团队空间」与「成员账号」，未见旧称混用。';

const SCRIPTS = {
  pass: [say(OUTLINE), say(CLEAN_DOC), useTool('t1', 'read_glossary'), say(REPORT)],
  stale: [say(OUTLINE), say(STALE_DOC)],
};

// ---------- 链本体 ----------
const mode = process.argv[2] ?? 'pass';
if (!SCRIPTS[mode]) {
  console.error(`未知模式：${mode}（可用：${Object.keys(SCRIPTS).join('、')}）`);
  process.exit(2);
}
const client = makeStubClient(SCRIPTS[mode]);
const req = '把《团队空间》功能的帮助文档写出来，读者是第一次配权限的管理员。';

console.log(`模式：${mode}`);

console.log('[1/3] 出提纲');
const outline = await runAgent(client, [
  '目标：为下面这份需求列一份帮助文档提纲。',
  '输出格式：只输出章节标题，每行一个，以「## 」开头，恰好 3 个。',
  '工具指引：本阶段不需要工具。',
  '边界：只列标题，不要写正文。',
  `需求：${req}`,
].join('\n'));
const g1 = gateOutline(outline);
console.log(g1.ok ? `      gate 1 通过 —— ${g1.detail}` : '      gate 1 挂了');
if (!g1.ok) fail('阶段 1 → 阶段 2（提纲结构）', g1.why);

console.log('[2/3] 按提纲写文档');
const doc = await runAgent(client, [
  '目标：按下面的提纲写出帮助文档正文。',
  '输出格式：保留提纲的「## 」标题，每节写 1-2 句。',
  '工具指引：本阶段不需要工具。',
  `边界：只用新术语，禁止出现：${BANNED.join('、')}。`,
  `提纲：\n${outline}`,
].join('\n'));
const g2 = gateTerms(doc);
console.log(g2.ok ? `      gate 2 通过 —— ${g2.detail}` : '      gate 2 挂了');
if (!g2.ok) fail('阶段 2 → 阶段 3（禁用旧术语）', g2.why);

console.log('[3/3] 查术语一致性');
const report = await runAgent(
  client,
  [
    '目标：检查下面这份文档的术语是否前后一致。',
    '输出格式：一句话结论。',
    '工具指引：先调用 read_glossary 拿到术语表，再对照全文。',
    '边界：只报术语问题，不改写文档。',
    `文档：\n${doc}`,
  ].join('\n'),
  { read_glossary: glossary },
);

console.log(`\n--- 检查结论 ---\n${report}`);
console.log('\n✓ 三个阶段、两道 gate 全过。');
process.exit(0);
```

第一次运行，三个阶段全过（Node v26.3.0）：

```text
$ node chain.mjs pass
模式：pass
[1/3] 出提纲
      gate 1 通过 —— 章节：权限模型 / 团队空间的建立与成员管理 / 常见问题
[2/3] 按提纲写文档
      gate 2 通过 —— 禁用词表 2 条，命中 0 条
[3/3] 查术语一致性

--- 检查结论 ---
术语一致性检查通过：全文统一使用「团队空间」与「成员账号」，未见旧称混用。

✓ 三个阶段、两道 gate 全过。
$ echo $?
0
```

第二次运行，写作阶段吐出了带旧称的正文，第二道关卡拦下：

```text
$ node chain.mjs stale
模式：stale
[1/3] 出提纲
      gate 1 通过 —— 章节：权限模型 / 团队空间的建立与成员管理 / 常见问题
[2/3] 按提纲写文档
      gate 2 挂了

✗ gate 失败 @ 阶段 2 → 阶段 3（禁用旧术语）
  原因：成文出现禁用旧术语：子账号
  链在这里停住，后面的阶段不会跑。
$ echo $?
1
```

三处值得对着输出看：第二次运行里没有 `[3/3]` 那一行，第三阶段真的没跑，坏东西没往下游流；失败信息定位到了「阶段 2 → 阶段 3」和具体的那个词「子账号」，你知道该去改写作阶段的提示词；`stale` 那组队列只有两条响应，万一哪天关卡 2 被误删，脚本会走到第三阶段、拿不到响应，桩 client 抛出「桩队列已空」——失败方式是响亮的，不是静默的。顺带把账算准：`pass` 这一趟其实调了四次模型——第三阶段查术语走了一次工具往返，阶段数是三，往返数是四，成本要按往返数算。

<!-- hint -->

先把桩 client 和 `runAgent` 单独跑通再接链。用一条只含一个 `say(...)` 的队列跑一个阶段，确认返回的是文本而不是 `undefined`；工具那条分支单独验：让队列第一条响应停在 `tool_use`、第二条才是收尾文本，循环应该正好转两圈。

<!-- hint -->

「哪一环挂了」要在写 `fail()` 的时候当成参数传进去，别指望事后从堆栈里看出来。给每道关卡固定「阶段 X → 阶段 Y」的字样，失败时连同命中的具体词一起打印。退出码用 `process.exit(1)`，别只 `throw`——`throw` 出来的退出码确实是 1，但栈信息会盖住你精心打印的那几行。

## 小结

- 链式把任务分解成一串步骤、每次调用处理上一次的输出，让每一次调用都变成更容易的任务[^S1]；它明码标价：主要目的就是拿延迟换更高的准确率[^S1]。
- 链上的一个阶段是一个完整的 harness 循环，不是一次 API 调用——官方给评测推荐的跑法就是这个构件：一条任务、一个 while 循环、代码直接调 API[^S3]。
- 拆开之后多出来的位置才是重点：你可以在任何中间步骤加程序化检查，确保过程还在轨道上[^S1]。这就是本系列第 10 门课的确定性验证器换了个安装位置——从终态挪到环与环之间；产品形态里它长成子代理按序执行，每个完成后由上层把相关上下文传给下一个[^S4]。
- 路由对输入分类、分发到专门化的后续任务，换来关注点分离和更专门化的提示词；没有它，为一类输入优化可能会伤害其他输入的表现[^S1]。前提是类别清晰、且分类本身能被准确完成，LLM 或传统分类算法都行[^S1]。
- 分类调用要把输出收紧成一个标签，并留一条兜底分支接住收不进表里的回答。
- 这个模式在现行第一方词汇里活着：按领域分发到带专属提示词与工具的代理叫专门化，就一部分复杂子任务去请更强的代理或模型叫升级[^S6]——后者就是按难度分发的路由。
- 别硬套：类别只有一个时路由是纯开销，任务分不干净时硬拆会在阶段之间丢信息[^S1]。拿不准就先量，复杂度要过「能被证明改善了结果」这一关[^S1]。
