# レッスン4: LLM ジャッジ: ルーブリック、フォーマット、そして判定させてはいけないもの

> 学習目標:
> - 自由記述テキストの出力に対する多次元ルーブリックを書き、各次元の問いを明確にし、1つの成功基準を評価しきるのに複数のルーブリックが必要になることを理解する
> - ジャッジの出力をプログラムが扱える形に絞り込む。先に根拠、次にスコア、0.0–1.0 と合否の組み合わせ、そして別々の側面を複数のジャッジに評価させるより1回の呼び出しのほうが安定しやすい理由を説明する
> - ジャッジの3つの失敗モード——自分の作業を採点する、問題を探せと言われたので必ず見つける、エージェントの自己申告だけを信じる——を認識し、それぞれに実行可能な緩和策を示す
>

## レッスン3の天井と、LLM ジャッジの居場所

リサーチエージェントにタスクを渡しました。国内の EV 充電補助金がこの3年でどう変わったかをまとめ、2ページのブリーフにすること。15分間動き続け、検索ツールを呼び、PDF を取得し、1,800語を書き上げました。読んだ感じはもっともらしい。

さて検証したいのですが、レッスン3の決定的チェックはここでは1つも使えません。走らせるテストスイートはなく、読み取るビルドの終了コードもなく、`output == golden_answer` に渡す `golden_answer` も書けません——同じブリーフを2人のアナリストに書かせても、同一のテキストにはならないからです。

これは想像力の欠如ではありません。この種の出力とはそういうものです。Anthropic が自社のマルチエージェント・リサーチシステムを振り返ったとき、彼らははっきりこう述べています。リサーチの出力は自由記述テキストで、唯一の正解を持つことはまれなのでプログラム的に評価するのが難しく、こうした出力の採点には LLM が自然に適している[^S2]。

ただし、そのブリーフを気軽に別のモデルに投げて「これどう？」と聞く前に、LLM ジャッジが公式のランキングのどこに位置するかを理解しておいてください。採点方法を選ぶ原則は "fastest, most reliable, most scalable"（最速・最も信頼でき・最もスケールする）です[^S5]。コードベースの採点は最も速く最も信頼でき、極めてスケールしますが、ルールベースの厳密さを緩める必要のある複雑な判断ではニュアンスを欠きます[^S5]。LLM ベースの採点は速く柔軟でスケールし、複雑な判断にも向いています——そして公式ガイダンスは同じ一文の中に前提条件を添えています。まず信頼できることを確かめるテストをしてから、スケールさせること[^S5]。人間による採点は最も柔軟で品質も高いものの、遅くコストがかかるため、可能なら避けます[^S5]。

真ん中の選択肢に付いているこの前提条件は、免責文ではなくハードな要件として扱ってください。LLM ジャッジは「より賢いチェック」ではなく、モデル呼び出しです。間違えることがあり、お金がかかり、同じ入力に対して実行のたびに違うスコアを出すこともあります。その価値はただ一点——決定的チェックが届かないところに届くことです。

だからこのレッスンは「モデルに出力を採点させる方法」の話ではありません。それは簡単です——どんなプロンプトでも数字は返ってきます。このレッスンの主題は、その数字を信頼に足るものにすることです。ルーブリックをどう構成するか、出力をどう制約するか、誰にジャッジを走らせるか、どう壊れるか、そしてそもそも聞くべきでないのはいつか。

## ルーブリック: 「良い」を個別に答えられる問いに分解する

ルーブリックというと堅く聞こえます。平たく言えば採点表です。漠然とした「これは良いか」を具体的な問いに分解し、それぞれ個別に答え、個別にスコアを付けます。

なぜ分解するのか。「このブリーフは良いか」と聞けば、モデルは漠然とした賞賛か漠然とした批判を返します。「ブリーフ内のすべての主張が、引用元のソースに現れているか」と聞けば、モデルは主張を1つずつ確認できます。ほとんどのユースケースでは、複数の成功基準に沿った多次元の評価が必要です[^S5]。

Anthropic のリサーチエージェントは5次元のルーブリックを使っていました[^S2]。各次元の背後には、実在の失敗モードがあります。

- **事実の正確性——主張はソースと一致しているか？** モデルが「2023年に補助金が30%減った」と書いたとき、引用された文書に本当にその数字があるか。この次元はハルシネーションを捕まえます。
- **引用の正確性——引用されたソースは主張と対応しているか？** 前の次元とは逆向きで、この2つを混同する人は多いです。前者は「この記述に裏付けがあるか」を問い、こちらは「この文に付いたリンクは、本当にこの話題を論じているか」を問います。よくあるエージェントの失敗は、主張自体は正しいのに、タイトルが関連ありそうに見えただけのソースが貼られている、というものです。
- **完全性——要求されたすべての側面をカバーしているか？** 「この3年」と言ったのに去年のことしか書いていない、「変化」と言ったのに現状しか書いていない。要求を1つずつ確認するのであって、文章がきれいかどうかを評価するのではありません。
- **ソースの品質——一次ソースか、質の低い二次ソースか？** この次元が捕まえる問題が一番たちの悪いものです。Anthropic の人間テスターはこう見つけました。初期のエージェントは、学術 PDF や個人ブログのような権威はあるが検索順位の低いソースよりも、SEO 最適化されたコンテンツファームを一貫して選んでいた[^S2]。出力は完全に普通に読めるのに、土台が腐っています。
- **ツール効率——適切なツールを、妥当な回数で呼んだか？** 同じ答えに3回の検索でたどり着くのと30回かかるのとでは、コストが桁で違います。この次元が評価するのはプロセスの経済性であって、「私が指定した手順に従ったか」ではありません——後者が機能しないことはレッスン2で説明したとおりです。

この5次元はリサーチタスク向けのものです。タスクが違えば必要な組み合わせも変わります。持ち帰るべきなのは分解の方法です。「この出力が壊れるとしたら、どう壊れるか」から出発し、そこから次元を導き、失敗モード1つにつき次元1つを対応させます。もう1つ見落とさないでください。あるユースケース、あるいはそのユースケースの特定の成功基準1つですら、全体的に評価するには複数のルーブリックが必要になることがあります[^S5]。1枚の採点表ですべてを覆えると期待しないでください。

## 出力フォーマット: 1回の呼び出し、1つのスコア、1つの合否

**まず判定の形から。** Anthropic は複数のジャッジに別々のコンポーネントを評価させる——コンポーネント1つにつきジャッジ1つ——という構成を試しました。結果は、単一のプロンプトによる単一の LLM 呼び出しで 0.0-1.0 のスコアと合否グレードを出力させる方式が、最も一貫していて人間の判断とも合致した、というものでした[^S2]。

公平を期すなら、評価を複数の LLM 呼び出しに分割し、各呼び出しで1つの側面を評価するというやり方も、公式ガイダンスが記述してきた評価自動化のパターンそのものです[^S1]。どちらのアプローチも間違いではありません。違いは、「単一呼び出しのほうが良い」が Anthropic 自身の実システム上での比較から出てきた結論だという点です[^S2]。推奨する進め方は、まず単一呼び出しから始め、分割したほうが精度が上がるという証拠が得られたときにだけ分割することです。

**次に、出力をどれだけきつく縛るか。** ジャッジプロンプトに関する公式ガイダンスは "empirical or specific"（経験的または具体的）です。たとえば LLM に 'correct' または 'incorrect' だけを出力させる、あるいは1〜5のスケールで判定させる。純粋に定性的な評価は、素早く大規模に扱うのが困難です[^S5]。平たく言えば、ジャッジが「全体的な品質は許容範囲だが、一部の細部の扱いがやや粗い」と返してきても、あなたの手元には何も残りません——そういう回答を200件平均することはできず、今日が昨日より良いかも分からず、結局1件ずつ読むはめになります。それならジャッジに聞く意味は何でしょうか。

**決定的なテクニック: 先に根拠を書かせ、次にスコアを出させ、根拠は捨てる。** 公式ガイダンスはこれを明示しています。評価スコアを出す前にまず LLM に推論させ、その推論は捨てる——これは評価性能を高め、とくに複雑な判断を要するタスクで効きます[^S5]。「捨てる」は「見るな」という意味ではありません。推論はジャッジにとっての足場です——正確に判定するには、「3段落目の主張はトランスクリプトのどの部分に対応するか」を先に書き出す必要があります。ただしそのテキストが下流の集計に入ってはいけません。レポートが欲しいのはスコアと合否で、推論はログに送られ、スコアが怪しく見えたときにあなたを待っています。

**主観的な次元はどうするか。** 二値にできない次元もあります。たとえば「このブリーフのトーンは顧客に送るのに適切か」。公式ガイダンスは道具を1つ用意しています。LLM ベースのリッカート尺度で、主観的な態度や認識を LLM に判定させるものです[^S5]——リッカート尺度とは「強く反対 / 反対 / どちらでもない / 賛成 / 強く賛成」のような、目盛りが固定されたアンケート形式のことです（何段階にするかは調査設計上の慣習であって、公式が定めたものではありません）。原則は変わりません。目盛りを固定して与え、自由記述にさせないことです。

まとめると、ジャッジの出力はおおよそ次のような形になります（例は最初の3次元のみ。`source_quality` と `tool_efficiency` も同じ形なので、簡潔さのため省略しています）。プログラムが読むのは `score` と `verdict` で、`reasoning` はレビュー用に永続化します。

```json
{
  "factual_accuracy": { "reasoning": "2段落目の「30%減」はソースAの4ページに逐語で存在する。4段落目の「複数の地域で支給が停止された」は3つのソースのいずれにも裏付けがない。", "score": 0.5 },
  "citation_accuracy": { "reasoning": "5件の引用のうち4件は主張と一致。引用3のリンクは同じサイトの別記事を指している。", "score": 0.8 },
  "completeness": { "reasoning": "タスクは過去3年を要求したが、ブリーフは2024年と2025年しか扱っていない。", "score": 0.6 },
  "verdict": "fail"
}
```

## 作業した本人にジャッジさせない

ここで魅力的な近道が見えてきます。最後にエージェント自身に採点させればいい。何をやったかは本人が一番よく知っている、と。

その誘惑は抑えてください。理由は2つです。**1つめは公式の経験則です。** 1つのモデルインスタンスがユーザーのクエリを処理し、別のインスタンスが不適切な内容や要求をスクリーニングするというガードレールの実装は、同じ LLM 呼び出しにガードレールと本体の応答の両方を担わせるより、うまくいく傾向があります[^S1]。この経験はもともとコンテンツモデレーション（一方が応答し、もう一方がスクリーニングする）を説明したものですが、「同じ呼び出しに2つの帽子をかぶらせない」という原則はここにも当てはまります。「同じ呼び出し」と言っている点に注意してください——問題は共有されたコンテキストであって、知能が足りないことではありません。**2つめはメカニズムです。** Claude Code 公式ドキュメントは、まっさらなサブエージェントのコンテキストで動くレビュアーは差分とあなたが与えた基準しか見えず、その変更を生んだ推論は見えないため、結果そのものを独自の土俵で評価する、というプラクティスを記述しています[^S4]。

これを逆から読むと、自己採点が失敗する理由が見えます。出力を生んだ推論の連鎖が、まだコンテキストにぶら下がったままなのです。モデルはたった今「こう書くのが正しい」と自分を納得させたところで、あなたはすぐさま「これは正しいか」と聞く。返ってくるのは同じ理屈の繰り返しである可能性が高い。得られるのは独立した判断ではなく、自己反復です。

**ジャッジが甘すぎる、あるいは厳しすぎるのが心配なら**、公式ガイダンスがノブを1つ用意しています。あるコンテンツが不適切かどうかの評価では、複数のプロンプトに異なる側面を評価させたり、投票のしきい値を変えたりして、偽陽性と偽陰性のバランスを取ります[^S1]。検証のシナリオでは、偽陽性は「問題ないものを壊れていると報告する」ことで、誤報に悩まされ続けます。偽陰性は「壊れているものを通す」ことで、まずい成果物が出荷されます。3人のジャッジのうち2人が fail と言って初めて fail とするのは、1人が fail と言えば fail とするより甘い設定です——どちらを選ぶかは、あなたのシナリオでどちらの誤りのコストが高いかで決まります。

## ジャッジはどう壊れるか

別インスタンスに切り替え、ルーブリックも書いた。それでもジャッジは壊れます。壊れ方には予測がつきます。

**その1: 問題を探せと言われたレビュアーは、必ず問題を見つける。** 最も直感に反し、最もコストが高い壊れ方です。公式ドキュメントは明確です。ギャップを探すよう指示されたレビュアーは、作業が健全であっても何かしら報告するのが普通です。そう指示されたのだから、というだけの理由で[^S4]。その帰結は「役に立たない提案が数件」では済みません。同じ箇所は、すべての指摘を追いかけると過剰設計につながると指摘しています——余分な抽象化レイヤー、防御的なコード、起こり得ないケースのためのテスト[^S4]。あなたのエージェントは自己エスカレーションのループに入ります。レビュアーが3つ提案し、あなたが直し、再レビューがさらに3つ提案し、コードは厚くなり、本当の問題は手つかずのまま残ります。

こういうレポートを見たことがあるはずです。「`parseDate` に空文字列への防御を追加することを推奨」——しかし上流がすでに非空を保証している。「この3つの定数を設定ファイルに切り出すことを推奨」——しかし3年間変更されていない。「ネットワークタイムアウトのリトライテストを追加することを推奨」——しかしこのパスにネットワーク呼び出しはない。3つとも間違いではなく、3つともやる価値はなく、しかしレビューレポートに混ざると本物の問題と見分けがつきません。

公式ガイダンスは緩和策を示しています。正しさや明示された要件に影響するギャップだけを報告するようレビュアーに指示し、それ以外は任意扱いにすること[^S4]。これをそのままジャッジプロンプトに書き、「その他の提案」の行き先も用意します——`optional_notes` フィールドを追加し、これは採点に関与しないと明記します。書く場所があれば、スタイルの好みを減点理由に押し込む必要がなくなります。

**その2: エージェントの自己申告は証拠ではない。** 近道として、エージェントの最終サマリーだけをジャッジに渡す人は多いです。「権威あるソースを3件取得し、相互チェックしたうえで補助金率を確定しました」。ジャッジはそれを読み、プロセスは堅実そうだと考え、高いスコアを付けます。しかしこの記述は証拠ではありません。ツール評価に関する公式ガイダンスがこの点を突いています。エージェントがフィードバックや応答で省略したことのほうが、含めたことよりも重要な場合が多い——LLM は必ずしも自分が意味することを口に出さない[^S3]。「3件のソースで相互チェックした」と書いていても、実際には検索を1回しか呼んでいないかもしれません。言及されないリトライの失敗、空の結果を受け取ってもなお捏造を続けたその瞬間こそ、あなたが最も見る必要のあるものです。解決策も直截です。生のトランスクリプト（ツール呼び出しとツールの応答を含む）をレビューして、エージェントの思考連鎖に明示されていない挙動を捕まえること[^S3]。解決策に翻訳すると、**ジャッジの入力には自己申告だけでなく生ログを含めなければならない**、ということです。とくに「ツール効率」の次元にはこれが要ります——実際の呼び出し回数と、その呼び出しが正しかったかを評価するのであり、その情報はログにしか存在しません。

**その3: 問いそのものが曖昧である。** 厳密にはこれはジャッジが壊れているのではなく、あなたが壊れた問いを与えているのです。評価設計に関する公式ガイダンスは、避けるべきカテゴリに名前を付けています。人間でも評価の合意に達するのが難しいような曖昧なテストケースです[^S5]。これはジャッジを検証しているときに見つかります。あなたと同僚が同じ出力を判定して、逆の結果になる。あわててジャッジプロンプトを直そうとしないでください——ジャッジが「不正確」なのは、この問いに正確な答えが存在しないからです。人間が合意できるところまで基準を精緻化するか、このケースを取り除くかです。これを使ってジャッジの一致率を計算しても、自分を欺く数字が出てくるだけです。

## レビュー・修正ループを作るべきとき

ジャッジが終わったらそこで完了なのか、それともそのフィードバックをエージェントに戻して修正させ、もう一度ジャッジするのか。このループは魅力的で、そして簡単にトークンを燃やす永久機関になります。

公式ガイダンスは、このワークフローが本当に適合する場合の2つのシグナルを示しています[^S1]。1つめは、人間がフィードバックを言語化すると LLM の応答が明らかに改善すること。2つめは、その種のフィードバックを LLM 自身が提供できること。同じ箇所には前提も添えられています。このワークフローがとくに効くのは、明確な評価基準があり、反復的な洗練が測定可能な価値をもたらす場合です[^S1]。

この2つの条件を入場テストとして使ってください。やり方は単純です。まずあなたがジャッジになり、エージェントにフィードバックを書き、修正後に実際に良くなるかを見ます。**人間が書いたフィードバックで動かないなら、LLM が書いたフィードバックではもっと動きません**。その時点で直すべきなのはプロンプトかツールであって、レビュー層を足すことではありません。逆に人間のフィードバックが明らかに効くなら、2つめの条件を確認します——ルーブリックに照らして LLM にフィードバックを書かせ、あなたのものと比べます。両方通ったら、そのループは作る価値があります。

## 見合った使い方: ジャッジもまたモデル呼び出しである

レッスン3のランキングに戻ります。採点方法を選ぶ原則は最速・最も信頼でき・最もスケールすることであり[^S5]、コードベースの採点はその3つすべてで LLM ベースの採点より上位です[^S5]。つまりジャッジは、決定的チェックが届かないところに置くのであって、その置き換えではありません。同じブリーフに対する正しい階層はこうなります。

```text
第1層（決定的、ミリ秒、コストゼロ）
  JSON / Markdown として妥当か？ 長さは要求範囲内か？
  引用リンクは到達可能か（HTTP ステータス）？ 引用数 >= 3 か？
  1つでも落ちたら → 即 fail、ジャッジは呼ばない

第2層（LLM ジャッジ、秒オーダー、トークン課金）
  5次元ルーブリックによるスコアリング + 合否
  入力: タスク要件 + 出力 + 生ログ（ツール呼び出しと応答）

第3層（人間、遅くて高い、抜き取りのみ）
  ジャッジは fail と言ったが腑に落ちない
  ジャッジが pass と言ったものを無作為抽出し、系統的な甘さを監視する
```

第1層で捕まるものを第2層に送って料金を払わないでください——フォーマットとして妥当ですらない出力に、受け入れられないと教えてもらうためのモデル呼び出しは不要です。第3層は省けません。エージェントをテストする人間は、評価が見逃すエッジケースを見つけます[^S2]。先ほどの「一貫してコンテンツファームを選ぶ」バイアスも、人間によるテストで見つかったものです[^S2]。

**このレッスンの境界**: 評価セットをどう組むか、このジャッジを何件のケースに対して走らせるかはレッスン5です。ジャッジを繰り返し実行可能な評価ハーネスに組み込んでレポートを出すのはレッスン6です。このレッスンが解くのは、1回の判定をどう信頼に足るものにするかだけです。

### レベル1: 壊れたジャッジプロンプトを診断する（コードなし）

誰かがリサーチエージェントに「セルフチェック」を足しました。プロンプトはこれです。

```text
あなたはこの業界ブリーフを書き終えたところです。では自分のサマリーを評価してください。

```

**あなたのタスク:** ① このプロンプトの欠陥を**4つ以上**挙げ、それぞれこのレッスンで扱ったどのルールに対応するかを書いてください（どのルールで、なぜ違反なのか）。② 「こう書くべき」という説明ではなく、そのまま使える動作するバージョンに書き直してください。

<!-- hint -->
ヒント1: **誰が判定するのか**（このジャッジの立場に問題はないか）、**何を判定するのか**（何が良いかをジャッジは知っているか）、**どう出力させるのか**（返ってきたものをあなたのプログラムは扱えるか）——この3つの角度から順に見てください。それぞれの角度から少なくとも1つの欠陥が出てきます。
<!-- /hint -->

<!-- hint -->
ヒント2: 最後の「できるだけ網羅的に」「思いつく改善提案をすべて」に注目してください。「ジャッジはどう壊れるか」の1つめの壊れ方に戻り、これが何を生み、そのすべてを実装したら何が起きるかを考えてみましょう。そのうえで自問してください。ジャッジが事実を検証するために必要な**元資料**は、このプロンプトのどこにありますか。
<!-- /hint -->

<!-- rubric -->
自己評価基準:
- 欠陥を4つ以上特定し、それぞれがレッスンのルールに対応している。次のうち少なくとも4つを含む: ① 作業したモデル自身に採点させており「作業する側とゲートキーパーを分ける」に違反、② ルーブリックがなく「良い」が個別に答えられる次元に分解されていない、③ 出力フォーマットの制約がなく、純粋に定性的なフィードバックは素早く大規模に扱えない、④ スコアと合否がなく、バージョン間で比較できない、⑤ 「先に根拠、次にスコア」の順序がない、⑥ 「網羅的に / 思いつく提案をすべて」が粗探しを促し、1つずつ追いかけると過剰設計になる、⑦ ジャッジに必要な入力を与えていない——タスク要件も、元資料も、ツール呼び出しログもない。
- 書き直しは箇条書きではなく**そのまま使える完全なプロンプト**であり、最低限これらを含む: まっさらなコンテキストのレビュアーという立場（このプロンプトは執筆した呼び出しに追記するのではなく、独立した新しい呼び出しに送ると明記）、レビュー対象の出力とその元資料・ログのプレースホルダー、各次元が何を問うのかを述べたルーブリック、次元ごとの 0.0–1.0 スコア、全体の合否、「先に根拠を書き、次にスコアを出す」順序の要求、「正しさや明示された要件に影響する問題だけを報告し、それ以外は任意の提案に回して採点に含めない」制約、固定された JSON 出力フォーマット。
- 書き直しに「……は良いと思いますか」のような基準のない問いが含まれていない。
<!-- /rubric -->

<!-- answer -->
**パート1: 欠陥と対応するルール**

1. 「あなたはこの業界ブリーフを書き終えたところです……では自分のサマリーを評価してください」——作業したモデル自身が判定しています。違反: 1つのモデルインスタンスがユーザーのクエリを処理し、別のインスタンスがスクリーニングするというガードレールの実装は、同じ LLM 呼び出しに両方を担わせるよりうまくいく傾向があります[^S1]。まっさらなコンテキストのレビュアーはその結果を生んだ推論が見えないため、結果そのものを独自の土俵で評価します[^S4]。
2. 「このサマリーは良いと思いますか」——ルーブリックがありません。違反: ほとんどのユースケースは複数の成功基準に沿った多次元の評価を必要とし[^S5]、ある基準1つですら複数のルーブリックを要することがあります[^S5]。
3. 「長所と短所を詳しく評価し」——純粋に定性的なフィードバックで、スコアもフォーマットもありません。違反: LLM には 'correct' / 'incorrect' や1〜5を出力させること。純粋に定性的な評価は素早く大規模に扱うのが困難です[^S5]。
4. 「先に根拠、次にスコア」を要求していません。違反: 評価スコアを出す前にまず LLM に推論させ、その推論は捨てる——これは評価性能を高め、とくに複雑な判断を要するタスクで効きます[^S5]。
5. 「できるだけ網羅的に」「思いつく改善提案をすべて」——粗探しを促しています。違反: ギャップを探すよう指示されたレビュアーは、作業が健全でも何かしら報告するのが普通で、すべての指摘を追いかけると過剰設計につながります[^S4]。対処は、正しさや明示された要件に影響するギャップだけを報告させることです[^S4]。
6. 元のタスク要件、元資料、ツール呼び出しログがありません。違反: エージェントが省略したことのほうが含めたことより重要な場合が多く、生のトランスクリプト（ツール呼び出しと応答）をレビューして自己説明にない挙動を捕まえる必要があります[^S3]。

**パート2: 書き直し（そのまま使える版）**

```text
あなたは独立したレビュアーです。以下の業界ブリーフの執筆には関与しておらず、
その執筆過程も見えません。以下のタスク要件、元資料、実行ログだけに基づいて、
ブリーフそのものを判定してください。

【元のタスク要件】{{task_spec}}
【レビュー対象のブリーフ】{{report}}
【ブリーフが引用したソースの全文】{{source_documents}}
【今回の実行の生ログ: ツール呼び出しとツールの応答】{{raw_transcript}}

【ルーブリック】各次元に個別に答えてください:
1. factual_accuracy: ブリーフ内のすべての主張は元資料の中に見つかるか。
   元資料にない数値、日付、名称、結論は不正確とみなす。要約や言い換えは
   不正確に数えない。
2. citation_accuracy: 各引用のリンク先ソースは、それが支える主張を実際に論じているか。
   ソースは存在するが内容が主張と一致しない場合はここで減点する（次元1には影響しない）。
3. completeness: タスク要件に挙げられたすべての側面がカバーされているか。要件を1行ずつ確認する。
4. source_quality: 一次ソース（原典、公式発表、学術資料）を使っているか、それとも
   検索順位は高いが質の低い二次的な焼き直しか。
5. tool_efficiency: 実行ログに基づき、適切なツールが使われたか、呼び出し回数は明らかに
   冗長でないか。ログだけを根拠にし、ブリーフ自身のプロセス説明を信用しないこと。

【採点の要求】
- 順序: 各次元について、まず根拠を書く（ブリーフのどの文、元資料のどの部分、ログのどの呼び出しかを
  具体的に指すこと。問題が見つからなければ「該当なし」と書く）。
  根拠を書き終えてから、スコアを出す。
- score: 0.0 から 1.0。1.0 はこの次元で問題が見つからなかったこと、0.0 は重大な失敗を意味する。
- verdict: すべての次元が 0.7 以上、かつ factual_accuracy が 0.9 以上なら "pass"、そうでなければ "fail"。
- 正しさ、またはタスク要件の達成に影響する問題だけを報告すること。言い回し、構成、
  書式の好みはすべて optional_notes に入れる。このフィールドは採点に関与せず、
  verdict にも影響しない。
- 以下の JSON 構造で厳密に出力し、JSON の外にテキストを出さないこと。

【出力フォーマット】
{
  "factual_accuracy":  { "evidence": "", "score": 0.0 },
  "citation_accuracy": { "evidence": "", "score": 0.0 },
  "completeness":      { "evidence": "", "score": 0.0 },
  "source_quality":    { "evidence": "", "score": 0.0 },
  "tool_efficiency":   { "evidence": "", "score": 0.0 },
  "optional_notes": [],
  "verdict": "<pass or fail>"
}
```

プロンプトの中には書かれていないが同じくらい重要なことがもう1つあります。このプロンプトは**まっさらな独立した呼び出し**で送ってください（執筆履歴を持たない新しい会話かサブエージェントを立ち上げる）。立場のところで「あなたは独立したレビュアーです」とどれだけ説得力をもって宣言しても、執筆した呼び出しに追記したなら、レビュアーには執筆時の推論がすべて見えたままです。

最後の2つのしきい値（0.7 と 0.9）はあなた自身が選んだ数字であり、これらの数字を与える公式ソースはありません。目的は合否を計算可能にすることです。レベル2のジャッジ検証を終えたら、ここに戻って調整してください。

### レベル2: 「議事録から会議サマリーを作る」ための完全なジャッジ方式を設計する

シナリオ: あなたのエージェントは毎日、会議の議事録を、結論とアクションアイテムを含むサマリーノートに圧縮しています。サマリーは標準解のない自由記述テキストですが、誤りのコストは高い——アクションアイテムを1つ落とせば、そのタスクは誰もやりません。

**あなたのタスク:** ① 3次元のルーブリック（事実への忠実さ、要点のカバー、アクションアイテムの欠落なし）を設計してください。各次元は 0.0–1.0 と全体の合否を持ち、各次元が何を問い、何が減点になるのかを明記します。② **完全なジャッジプロンプト**を書いてください。先に根拠、次にスコアという順序と、厳格な出力フォーマットの制約を含めます。③ 「ジャッジ自身を検証する」手順を設計してください。人間がラベル付けした良い例・悪い例の小さなセットを用意し、ジャッジを走らせ、一致率を比べ、一致率が不十分なときに**何から先に直し、何を後回しにするか**を明示します。実際に API を呼ぶ必要はありません。成果物はプロンプト、JSON、手順そのものです。

<!-- hint -->
ヒント1: 3つの次元は3つのスローガンではありません。それぞれが「何が減点で、何が減点でないか」に答えている必要があります。たとえば忠実さなら、議事録にない情報をサマリーに書いたら減点、3文を1文に凝縮したのは減点ではない。この境界をプロンプトに書き込むことで、ジャッジは安定します。アクションアイテムの次元は、もう1つ別のこともカバーする必要があります——担当者と期限が入れ替わっていないかどうかです。
<!-- /hint -->

<!-- hint -->
ヒント2: 人間がラベル付けする例を、すべて良い例にはできません。悪い例は次元ごとに作ってください。1つは議事録にない数字を入れたもの、1つは結論の出た議題を1つ落としたもの、1つはアクションアイテムの担当者を間違えたもの。こうしておけば、ジャッジがあなたと食い違ったときに、どの次元の定義が明確でなかったのかがすぐ分かります。それから、あなたと同僚が同じケースで食い違ったときは、ジャッジではなくまずそのケースを疑ってください。
<!-- /hint -->

<!-- rubric -->
自己評価基準:
- **ルーブリック**: 3つの次元それぞれに「何が減点 / 何が減点でない」の明確な境界があり、次元名だけで終わっていない。アクションアイテムの次元が「欠落」と「担当者または期限の誤り」の両方をカバーしている。
- **プロンプト**: 完全でそのまま使え、議事録とサマリーのプレースホルダーを含む。レビュアーが執筆者ではないと明記している。各次元でまず根拠を書かせ（議事録・サマリーの具体的な位置を指す）、その後にスコアを出させている。0.0–1.0 のスコアがあり、判定ルール付きの合否がある。「正しさに影響する問題だけを報告し、それ以外は採点対象外のフィールドに回す」制約がある。固定の JSON フォーマットと、それ以外を出力しない要求で終わっている。
- **検証方式**: 人間がラベル付けした例のセット（良い例 + 次元ごとに個別に設計した悪い例）を含む。まず人間が1件ずつ判定し、次にジャッジが同じバッチを走り、合否と次元ごとのスコアで一致率を比べ、食い違いがどの次元に集中しているかを個別に見る。
- **修正の順序**を理由付きで明示している。順序は、まず例と基準そのものを確認（人間同士でも食い違う曖昧なケースは書き直すか取り除く）→ 次にジャッジプロンプトを直す（次元の定義を足す、正例・負例を足す、出力を締める）→ そのあとでようやくモデルの変更や複数プロンプトの投票を検討する。
- 「ジャッジの検証が通るまで全ケースにスケールさせない」と明記している。しきい値は自分で決めてよいが、自分で決めたものだと述べ、公式の数字を捏造していない。
<!-- /rubric -->

**1. 3次元のルーブリック**

- **faithfulness**: サマリーのすべての記述が議事録の中に見つかるか。減点: 議事録にない数値、氏名、日付、結論。「誰かが提案した」を「会議で決定した」に格上げすること（強度のエスカレーション）。減点しない: 要約、統合、言い換え。
- **coverage**: 複数人が議論した話題、または明確な結論が出た話題がすべて言及されているか。減点: 結論の出た議題を落とすこと。結論を逆に書くこと。減点しない: 一度だけ通りすがりに触れられ結論の出なかった内容を落とすこと。
- **action_items**: 議事録にある「誰がいつまでに何をするか」のコミットメントがすべてリストに入っているか。減点: 1件の欠落。担当者の誤り。期限の誤り、または議事録が述べていない期限の捏造。減点しない: 議事録が本当に期限を述べておらず、サマリーが「未定」と正確に記していること。

全体の verdict: どれか1つの次元が 0.6 未満、または faithfulness が 0.8 未満なら fail、そうでなければ pass。この2つのしきい値は自分で決めた出発点です。手順3の検証のあとで調整します。

**2. 完全なジャッジプロンプト**

```text
あなたは会議サマリーノートの独立したレビュアーです。このサマリーの執筆には関与しておらず、
その生成過程も見えません。以下の会議議事録とルーブリックだけに基づいて、このサマリーを
判定してください。

【元の会議議事録】{{transcript}}
【レビュー対象のサマリー】{{summary}}

【ルーブリック】
1. faithfulness: サマリーのすべての記述は議事録の中に見つかるか。
   - 減点: 議事録にない数値、氏名、日付、結論をサマリーに書いている。
     「誰かが提案した」を「会議で決定した」と表現している（結論の強度を上げている）。
   - 減点しない: 複数の文を1文に凝縮している。言い換えている。議題と無関係な
     雑談を省いている。
2. coverage: 議事録の中で複数人が議論した話題、または明確な結論が出た話題は、
   すべてサマリーに言及されているか。
   - 減点: 結論に至った議題を落としている。ある話題の結論を逆に書いている。
   - 減点しない: 一度だけ通りすがりに触れられ、結論の出なかった内容を落としている。
3. action_items: 議事録にあるすべての「誰がいつまでに何をするか」のコミットメントが、
   サマリーのアクションアイテム一覧にあり、担当者と期限が誤っていたり入れ替わっていたり
   しないか。
   - 減点: アクションアイテムが1件欠けている。担当者が別人になっている。期限が誤っている。
     議事録が期限を述べていないのに期限を捏造している。
   - 減点しない: 議事録が本当に期限を決めておらず、サマリーが「期限未定」と正確に
     書いている。

【採点の要求】
- 順序: 各次元について、まず根拠を書き、その後にスコアを出す。根拠は具体的であること——
  サマリーのどの文が議事録のどの部分に対応するかを指す（原文の断片を引用すれば十分）。
  その次元に問題がなければ「該当なし」と書く。
- score: 0.0 から 1.0。1.0 はこの次元がまったく問題ないこと、0.0 は重大な失敗を意味する。
- verdict: どれか1つの次元が 0.6 未満、または faithfulness が 0.8 未満なら "fail"、
  そうでなければ "pass" を出力する。
- 正しさ、またはこのノートを業務の参照資料として使えるかどうかに影響する問題だけを報告すること。
  言葉づかい、項目の並び順、詳しさの好みはすべて optional_notes に入れる。このフィールドは
  採点に関与せず、verdict にも影響しない。
- 以下の JSON 構造で厳密に出力し、JSON の外にテキストを出さないこと。説明もコードフェンスも不要。

【出力フォーマット】
{
  "faithfulness": { "evidence": "", "score": 0.0 },
  "coverage":     { "evidence": "", "score": 0.0 },
  "action_items": { "evidence": "", "score": 0.0 },
  "optional_notes": [],
  "verdict": "<pass or fail>"
}
```

プログラム側が集計に使うのは3つの `score` と `verdict` だけです。`evidence` と `optional_notes` はディスクに永続化し、スコアが怪しく見えたときのレビューに使います。レベル1と同じく、このプロンプトはまっさらな独立した呼び出しに送り、サマリーを生成した呼び出しに追記しないでください。

**3. ジャッジ自身を検証する手順**

手順1、例のセットを作る。実際の会議議事録を12〜20件用意し（この規模は自分で決めた出発点であって、公式ソースに基づくものではありません）、各会議にサマリーを2件——良い例と悪い例——を対応させます。悪い例は次元ごとに設計します。

```json
{
  "cases": [
    { "id": "m01-good", "summary": "s/m01-good.md", "human_verdict": "pass",
      "human_notes": "3次元とも問題なし" },
    { "id": "m01-bad-faith", "summary": "s/m01-bad-faith.md", "human_verdict": "fail",
      "broken_dimension": "faithfulness",
      "human_notes": "サマリーは「予算80万円が承認された」と書いているが、議事録には「承認に上程した」としかない" },
    { "id": "m02-bad-coverage", "summary": "s/m02-bad-cov.md", "human_verdict": "fail",
      "broken_dimension": "coverage",
      "human_notes": "結論の出た議題であるベンダー切り替えが、セクションごと丸ごと抜けている" },
    { "id": "m03-bad-actions", "summary": "s/m03-bad-act.md", "human_verdict": "fail",
      "broken_dimension": "action_items",
      "human_notes": "「金曜までにドラフト」の担当者は李さんだが、サマリーは王さんと書いている" }
  ]
}
```

手順2、まず人間が判定する。あなたと同僚1人が、**ジャッジの出力を見ずに**それぞれ独立して合否を判定し、理由を書きます。2人の判定が食い違ったケースは別に取り分けます——手順4で扱います。

手順3、ジャッジを走らせ、2つを比べる。**合否の一致率**（ジャッジの `verdict` が人間のラベルと一致した割合）と、**次元の帰属の的中率**（悪い例について、ジャッジが最も大きく減点した次元が、あなたが付けた `broken_dimension` と一致するか）です。後者のほうが多くを明らかにすることがよくあります——合否がたまたま合っていても帰属が外れているなら、次元の定義が明確でないということです。

手順4、不十分だったときは、この順序で直します。**順序を入れ替えてはいけません**。

1. **まず例と基準を確認する。** 食い違いが、あなたと同僚も食い違ったケースに集中しているなら、問題はジャッジではなく問いの側にあります。人間でも評価の合意に達するのが難しい曖昧なテストケースは、評価設計が避けるべきものです[^S5]。人間が合意できるところまで基準を精緻化するか、できないならそのケースを取り除きます。
2. **次にジャッジプロンプトを直す。** 基準が明確で人間も合意しているのにジャッジがまだ外すなら、それはプロンプトの問題です。食い違いが集中している次元に対して、「何が減点 / 何が減点でない」をより厳密に書き、正例・負例を1〜2件挿入し、出力フォーマットをさらに締めます。同じバッチを再実行します。
3. **そのあとでようやくモデルと構造に手を付ける。** プロンプトをかなり具体的にしてもジャッジが不安定なら、より強いモデルへの切り替えや、複数のプロンプトにそれぞれ1次元を評価させて投票のしきい値で合否をまとめる方式を検討します——投票のしきい値こそ、偽陽性と偽陰性のバランスを取るためのノブです[^S1]。この手順が最後に来るのは、コストと複雑さの両方が上がるからです。

手順5、しきい値を決めてからスケールする。一致率のしきい値は自分で決めてください（この数字を与える公式ソースはありません。誤判定のコストに基づいて決めます）。しきい値に達するまでは、ジャッジを全ケースにスケールさせないこと——LLM ベースの採点に対する公式ガイダンスは、まず信頼できることを確かめるテストをしてからスケールさせよ、です[^S5]。それ以降も、ジャッジプロンプトを変えるたびにこの小さなバッチを再実行し、壊していないことを確認します。

## まとめ

- 自由記述テキストの出力には唯一の正解がなくプログラム的な評価が難しいため、こうした出力の採点には LLM が自然に適しています[^S2]。ただし LLM ベースの採点に対する公式の位置づけは「速く、柔軟で、スケールし、複雑な判断に向く——前提条件として、まず信頼できることを確かめるテストをしてからスケールさせる」です。人間による採点は最も柔軟で品質も高いものの、遅くコストがかかるので可能なら避けます[^S5]。
- ルーブリックは「良い」を個別に答えられる問いに分解します。リサーチタスク向けの出来合いの分解は5次元です。事実の正確性、引用の正確性、完全性、ソースの品質、ツール効率[^S2]。あるユースケース、あるいはその中の1つの成功基準ですら、全体的に評価するには複数のルーブリックが必要になることがあります[^S5]。
- 出力の形については、単一のプロンプトによる単一の LLM 呼び出しで 0.0-1.0 のスコアと合否グレードを出す方式が、実測で最も一貫し人間の判断とも合致しました[^S2]。LLM には 'correct' / 'incorrect' や1〜5を出力させること。純粋に定性的な評価は素早く大規模に扱うのが困難です[^S5]。評価スコアを出す前にまず LLM に推論させ、その推論は捨てる——これは評価性能を高め、とくに複雑な判断で効きます[^S5]。主観的な次元には LLM ベースのリッカート尺度が使えます[^S5]。
- 作業した本人にジャッジさせない。1つのモデルインスタンスがクエリを処理し別のインスタンスがスクリーニングするガードレールは、同じ呼び出しに両方を担わせるよりうまくいく傾向があります[^S1]。まっさらなコンテキストのレビュアーは出力とあなたの基準しか見えず、その出力を生んだ推論は見えないため、結果そのものを独自の土俵で判定します[^S4]。複数プロンプトによる評価と投票のしきい値は、偽陽性と偽陰性のバランスを取ります[^S1]。
- ギャップを探すよう指示されたレビュアーは、作業が健全でも何かしら報告するのが普通で、すべての指摘を追いかけると過剰設計につながります。対処は、正しさや明示された要件に影響するギャップだけを報告させ、それ以外は任意扱いにすることです[^S4]。
- ジャッジにエージェントの自己申告だけを渡さないこと。省略したことのほうが含めたことより重要な場合が多く、LLM は必ずしも自分が意味することを口に出しません[^S3]。生のトランスクリプト（ツール呼び出しとツールの応答）をレビューして、自己説明にない挙動を捕まえます[^S3]。
- レビュー・修正ループを作る価値があるかは2つのシグナルで決まります。人間がフィードバックを言語化すると LLM の応答が明らかに改善すること、そしてその種のフィードバックを LLM 自身が提供できることです[^S1]。
- ジャッジもまたモデル呼び出しであり、コストとノイズを伴います。採点方法を選ぶ原則は最速・最も信頼でき・最もスケールすることであり、コードベースの採点はその3つすべてで上位です[^S5]——決定的チェックで捕まえられるものをジャッジに送ってはいけません。自動評価の先には人間による抜き取りが依然として必要で、エージェントをテストする人間は評価が見逃すエッジケースを見つけます[^S2]。
