## 「何を検証するか」から「どう検証するか」へ

レッスン2を終えた時点で、具体的な成功基準が書き出せているはずです。本レッスンで使う例を取り上げましょう。エージェントが一群の売上CSVを読み、タイトル、チャネル別の項目、合計を持つ `report.json` に集約する、というものです。レッスン2で学んだのは、この基準を終状態として枠づけること——ファイルが存在する、フィールドが揃っている、合計が項目の件数の総和と一致する——であって、「ファイルを読み、次に合計を計算し、次にファイルを書く」といったターンごとのプロセス確認ではありません。

基準は手元にあります。次の問いは実務的なものです。**その基準と突き合わせるために、何を使うのか？**

目視で確認することもできます。別のモデルに読ませてフィードバックをもらうこともできます。あるいは、JSONを読み込んで件数を合計し、一致しなければ非ゼロで終了する十数行のNodeを書くこともできます。3つとも結論には辿り着きますが、コストと信頼性は大きく違います。

公式ドキュメントは順位付けの原則を示しています。**最も速く、最も信頼でき、最もスケールする採点方法を選ぶ**[^S5]。このものさしで測ると、3つのカテゴリははっきり順番に並びます。

- **コードベースの採点**——最も速く最も信頼でき、極めてスケールする。弱点は、ルールに縛られない柔軟さを要する複雑な判断のニュアンスを扱えないこと[^S5]。
- **LLMベースの採点**——速く柔軟で、スケールし複雑な判断にも向くが、まず信頼性を確かめてからスケールさせること[^S5]。（レッスン4で扱います。）
- **人間による採点**——最も柔軟で品質も高いが、遅く高価。可能なら避けること[^S5]。

ここでの「信頼できる」は**同じ入力なら毎回同じ判定**という意味です。コードベースの採点が首位なのは賢いからではなく、予測可能な形で愚かだからです——今日は雰囲気で通し、明日は言い回しで落とす、ということをしません。コンピューティングにおいて、決定的システムは同一の入力に対して毎回同じ出力を生成しますが、非決定的システム——エージェントのような——は同じ開始条件でも異なる応答を生成しうる[^S3]。本レッスンで扱う「決定的な検証器」は、その予測可能に愚かな検査のことです。決定的なものが、非決定的なものを評価するわけです。

評価タスクの設計に関わる原則がもう1つあります。**自動採点が可能になるように問題を構成する**（たとえば多肢選択、文字列一致、コードによる採点、LLMによる採点）[^S5]。自動化の目があるところでは、それを取りにいってください。

## 検証器のメニュー: 信号を返すものなら何でもよい

「検証器」と言うと専用のフレームワークのように聞こえますが、ハードルはずっと低いところにあります。公式ドキュメントの定義はほとんど無愛想なくらいです。**検査とは、Claude が会話の中で読み取れる信号を返すもの全般である。テストスイート、ビルドの終了コード、linter、出力を fixture と diff するスクリプト、あるいはデザインと比較するブラウザのスクリーンショット**[^S4]。

このリストを分解しましょう。`npm test` を走らせて全部グリーンなら合格で、コードの成果物には最適です——コードによる解決策は自動テストで検証可能です[^S1]。ビルドの終了コードは最も手軽です。ツールチェーンがすでにアサーションを書いてくれているからです。linter だけでは十分ではありませんが、「犯すべきでないミス」の床としては優秀です。diff スクリプトは、今回の実行の出力を、あらかじめ用意した fixture ファイル（正解と分かっているサンプル）と比較するもので、出力が安定していて形式が固定の場合に向きます。スクリーンショット比較は、フロントエンドのスタイルを調整しているときのためのものです。

工学的な実践の注記を1つ。コンパイラや静的型チェッカー（`tsc --noEmit` のような）も、終了コードと読みやすいエラー位置を出すため、実際のプロジェクトではこの用途でよく使われます。これは私の補足であって公式のリストにはありません——公式のお墨付きとして扱わないでください。

これらの方法は排他的ではありません。検証器は**スペクトラム**をなします——一方の端は「fixture との完全な文字列一致」、もう一方の端は「Claude に判定を頼む」です[^S3]。本レッスンは左半分を扱い、レッスン4が右へ進みます。

## 最小形: `output == golden_answer`

スペクトラムの左端はこう見えます[^S5]。

```text
output == golden_answer
```

等値比較があるだけです。これは完全一致（exact match）と呼ばれます。モデルの出力があらかじめ定めた正解と一致するかを測るもので、**通常は空白と大文字小文字を正規化したうえで**行います。単純で曖昧さのない指標で、感情分析（positive、negative、neutral）のように答えが明確に区分されるタスクに最適です[^S5]。

ここでの「正規化」は平たい話です。比較する前に、意味を担っていない差異を消しておくということです。コードにするとこうなります。

```javascript
// 感情の3分類: 答えは positive / negative / neutral のいずれかでなければならない
function grade(output, goldenAnswer) {
  const normalize = (s) => s.trim().toLowerCase();
  return normalize(output) === normalize(goldenAnswer);
}

grade("Positive\n", "positive"); // true — 大文字小文字と改行は消えた
grade("positive.", "positive");  // false — しかしピリオド1つでまだ落ちる
```

2つ目の呼び出しの結果はじっと見る価値があります。`trim()` と `toLowerCase()` は改行と大文字小文字を救いますが、あのピリオドは救いません。正規化をどこまで進めるべきかは、**あなたのタスクにとって**どの差異が無関係かで決まります——どんなライブラリも代わりに下せない判断です。本レッスン後半の落とし穴の節は、その判断を誤ったときに何が起きるかの話です。

## 検証器の出力を読めるものにする

先ほどの定義には飛ばされがちな一節がありました。信号は**Claude が会話の中で読み取れるもの**でなければならない[^S4]、という部分です。この一節が、検証スクリプトの出力の書き方を決めます。2つの失敗メッセージを比べてみてください。

```text
FAIL: 検証に通りませんでした
```

```text
FAIL  report.json
  - total が不一致: 申告値 48、items の count 合計 50
```

前者はエージェントに「間違っている」とだけ告げ、あとは推測に任せます。後者はどのフィールドが落ちたか、期待値は何か、実際の値は何かを告げます——次のターンでその数値を直接直しにいけます。同じ pass/fail でも、情報量は桁違いです。公式ガイダンスの別の一節も同じことを言っています。**成功を主張するのではなく、Claude に証拠を示させる**——テスト出力、実行したコマンドとその返り値、あるいは結果のスクリーンショット。証拠をレビューするほうが自分で検証をやり直すより速く、見ていなかったセッションでも機能する[^S4]。あなたの検証スクリプトは、その証拠の生産者です。それが曖昧なら、証拠も曖昧になります。

実務的な規則を2つ。合格は終了コード `0`、不合格は非ゼロを使うこと（CIやシェルの `&&` がそのまま利用できます）。標準出力には1行に1つの失敗を、「どのフィールドが、何を期待し、何だったか」を明記して書くこと。

## pass/fail があると、エージェントの振る舞いが変わる

実行中、エージェントには環境からの信号が必要です。"During execution, it's crucial for the agents to gain “ground truth” from the environment at each step (such as tool call results or code execution) to assess its progress."（実行中、エージェントが各ステップで環境から「ground truth」——ツール呼び出しの結果やコード実行の結果など——を得て自らの進捗を評価することが決定的に重要である）[^S1]。検証器がなければ、得られる進捗の信号は自分が今書いた段落だけです——完了したと思えば、完了なのです。検証器があれば、環境の中に、自分の判断から独立した事実の出どころが存在することになります。

そこで振る舞いの連鎖が変わります。**pass か fail を出すものを Claude に渡せば、ループは自分で閉じる。Claude が作業し、検査を実行し、結果を読み、検査が通るまで反復する**[^S4]。言い換えれば、エージェントはテスト結果をフィードバックとして解を反復できる[^S1]、ということです。

本シリーズのコース7で手書きしたようなハーネスループでは、実装は検査をツールとして公開することになります。

```javascript
const tools = [
  { name: "write_file", /* ... */ },
  {
    name: "run_check",
    description: "verify.mjs を実行して report.json を検査し、PASS/FAIL と項目ごとの失敗理由を返す",
    input_schema: { type: "object", properties: {}, required: [] },
  },
];

import { execFile } from "node:child_process";

// ユーティリティ: verify.mjs を実行し、終了コードと出力の両方を集める
// （promisify(exec) は使わないこと——非ゼロ終了で例外を投げるが、その非ゼロこそ欲しい信号なので）
function runVerify() {
  return new Promise((resolve) => {
    execFile("node", ["verify.mjs", "report.json"], (err, stdout, stderr) => {
      resolve({ code: err?.code ?? 0, stdout: stdout + stderr });
    });
  });
}

async function runTool(name, input) {
  if (name !== "run_check") return runOtherTool(name, input);
  const { code, stdout } = await runVerify();
  // 肝心な点: 終了コードと標準出力をそのまま通す。「失敗した」に圧縮しない
  return `exit code: ${code}\n${stdout}`;
}

while (response.stop_reason === "tool_use") {
  const toolUse = response.content.find((block) => block.type === "tool_use");
  const output = await runTool(toolUse.name, toolUse.input);
  messages.push({ role: "assistant", content: response.content });
  messages.push({
    role: "user",
    content: [{ type: "tool_result", tool_use_id: toolUse.id, content: output }],
  });
  response = await client.messages.create({ model, tools, messages });
}
```

検証器の出力は `tool_result` を経由して会話に流れ戻ります。モデルは `total が不一致: 申告値 48、items の count 合計 50` を読み、次のターンでそれを直しにいきます。あなたは1ステップも関与していません。

便利な拡張が2つあります。**その1、検査は末尾だけに置く必要はありません。** レッスン2で、複雑なワークフローは、すべての中間ステップを検証するのではなく、特定の状態変化が起きているはずの個別のチェックポイントに分割できると扱いました[^S2]。それらの検証チェックポイントは、決定的な検査を置く自然な着地点です——「すべてのCSVを読み終えた後、行数は個々のファイルの行数の総和と一致するはず」のように。同じ振り返り記事は、エージェントの適応性を、リトライロジックや定期的なチェックポイントといった決定的な安全策と組み合わせることにも触れています[^S2]（そこでの「チェックポイント」は、本シリーズのコース9で扱った状態保存型のリカバリーチェックポイントを指す点に注意してください）。

**その2、1種類の検証はAPI層まで前倒しできます。** ツール定義に `strict: true` を加えると、Claude のツール呼び出しが常にスキーマと厳密に一致することを保証できます[^S6]。スキーマは、あなたによるパラメータ構造の宣言です。

```json
{
  "name": "write_report",
  "description": "集約結果を report.json に書き出す",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "title": { "type": "string" },
      "items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": { "name": { "type": "string" }, "count": { "type": "integer" } },
          "required": ["name", "count"]
        }
      },
      "total": { "type": "integer" }
    },
    "required": ["title", "items", "total"]
  }
}
```

この1行があるだけで、「フィールド名のタイプミス」「count を文字列で渡した」といった構造上の問題は、「自分でコードを書いて確認するもの」からプラットフォームレベルの保証へと変わります。ツールは、決定的システムと非決定的エージェントのあいだの契約であり[^S3]、`strict` はその契約をインターフェースに書き込む方法です。

ただしこれが取り締まるのは構造であって、意味ではありません。`total` が実際にすべての `count` の総和と等しいかについて、スキーマは何も語れません——その部分は依然として自分で検証します。

## 落とし穴: 厳しすぎる検証器は正しい出力を弾く

これが決定的な検査の最もよくある壊れ方であり、しかも起きても気づかないことが多いものです。

ツール評価に関する公式ガイダンスは鋭いです。**書式、句読点、有効な言い換えのような見せかけの差異のせいで正しい応答を弾いてしまう、厳しすぎる検証器は避けること**[^S3]。

「見せかけの差異」が鍵となる語です。同じ正しい答えでも、末尾に空白が付いているかもしれないし、`positive` を `Positive` と書くかもしれないし、単語のあいだの空白が1つではなく2つかもしれません。これらの差異は**タスクにとって**何の意味も持ちませんが、バイト単位で比較する検証器にとっては致命的です。壊れ方の向きも陰湿です。エラーを通してしまうのではなく、**正しい出力を罰する**のです——これが偽陰性です。

具体的な破綻と修正を示します。fixture のタイトルは `2026 年 Q1 チャネル集計` です。エージェントの `report.json` はデータがすべて正しく、ただタイトルの前後に空白があり、語のあいだの空白が2つ多いだけです。素朴で厳格な検証器はこうなります。

```javascript
// strict.mjs — 素朴で厳格な版
import { readFileSync } from "node:fs";

const GOLDEN_TITLE = "2026 年 Q1 チャネル集計";
const data = JSON.parse(readFileSync(process.argv[2], "utf8"));

if (data.title === GOLDEN_TITLE) {
  console.log("PASS");
  process.exit(0);
} else {
  console.log(`FAIL: title が不一致、実際の値は ${JSON.stringify(data.title)}`);
  process.exit(1);
}
```

実行すると、実際の出力はこうです。

```text
$ node strict.mjs spacey.json
FAIL: title が不一致、実際の値は "  2026 年   Q1 チャネル集計\n"
```

内容が完全に正しいレポートが、末尾の改行1つで落とされました。この結果がエージェントに戻されれば、タイトルの空白をいじりにいきます——タスクとは無関係な方向にです。

修正は関数1つです。

```javascript
function normalize(text) {
  return text.replace(/\s+/g, " ").trim().toLowerCase();
}

if (normalize(data.title) === normalize(GOLDEN_TITLE)) { /* PASS */ }
```

`replace(/\s+/g, " ")` は連続する空白を1つに畳み、`trim()` は前後を削り、`toLowerCase()` は大文字小文字を揃えます。この変更後、同じファイルが通ります——完全なスクリプトと実際の実行結果は、以下の演習のレベル2にあります。

逆方向の注意も1つ。正規化は「多ければ多いほど良い」ものではありません。句読点まで削ってしまうと、`total: 48` と `total: 4.8` のような本物のエラーをならしてしまうかもしれません。判断基準はいつも同じです——**この差異は意味を担っているか？** 担っているなら厳しく。担っていないなら正規化してください。

## 決定的な検査の天井はどこか

決定的な検証器には、はっきりした適用範囲の境界があります。

**第1の境界は自由記述テキストです。** 調査の成果物は自由記述テキストであり、唯一の正解を持つことがまれなので、プログラムによる評価が困難です[^S2]。要約に対して `output == golden_answer` を書くことはできません——同じ素材を与えられても、よく書けた2本の要約はまったく異なる言い回しを使いうるからです。この種の判断はレッスン4の領域に渡ります。

**第2の境界は「より広いシステム要件に合っているか」です。** コードによる解決策は自動テストで検証可能ですが、"However, whereas automated testing helps verify functionality, human review remains crucial for ensuring solutions align with broader system requirements."（しかし、自動テストは機能の検証に役立つ一方で、解決策がより広いシステム要件に沿っていることを保証するには、人間によるレビューが依然として決定的に重要である）[^S1]。あるパッチが全テストに合格しながら、モジュール全体を保守不能にする悪い設計であることはありえます。マルチエージェントの振り返り記事も同じことを響かせています。自動評価のある世界でも、手作業のテストは依然として不可欠です[^S2]。

決定的な検査が受け持つのは「間違っていてはいけないものが間違っていない」という床の部分です。その床より上には、別の道具が必要になります。

## 釣り合い: 何にでも検証器が要るわけではない

逆向きの誤りもよくあります。使い捨てのスクリプトのために完全な検証スイートを構築してしまうことです。

エージェントが一度実行したら削除するデータ移行スクリプトを書いたのに、あなたは構造検証、fixture 比較、リグレッションサンプルを整備する——検証器を書く時間が、出力を目で確かめる時間を上回っています。

判断のものさしは相変わらずあの一文です。**複雑さの追加を検討すべきなのは、それが結果を明らかに改善する場合だけである**[^S1]。検証器に限って言えば、自分に問うべきことがあります。

- この検査は何回実行されるのか？1回きりで、しかもあなたがすぐそばで見ているなら、目のほうが速いかもしれません。
- それがない場合、エラーが発見されるまでどれくらいかかるのか？「すぐ、目の前で見ているから」と「下流が壊れたとき、2日後」では、結論はまったく変わります。
- このタスクでプロンプトを何回反復する予定か？1回を超えた瞬間から、前後を比較する安定したものさしが必要になります。さもないと「良くなったのか」は常に当て推量のままです。

一方、書かなければならないのはいつかについて、公式ガイダンスは厳しい言い方をしています——**常に検証手段（テスト、スクリプト、スクリーンショット）を用意すること。検証できないなら、リリースしない**[^S4]。

### レベル1: 6つの出力に検証器を選ぶ（コード不要）

以下はエージェントのよくある出力6種です。それぞれについて答えてください。どんな検証器を使いますか。なぜそれを選びますか。

1. JSON の設定ファイル（サービス名、ポート、タイムアウト）
2. 「金額の降順」でソートされた CSV
3. 自由記述の要約（長いレポートから抽出した300語）
4. コードのパッチ（既知のバグの修正）
5. ファイル名のリスト（エージェントがこれらのファイルを処理したと主張している）
6. 感情ラベル（コメントに対して positive / negative / neutral を出力する）

6つすべてに答えたら、もう1つの問いに答えてください。**この6つのうち、決定的な検査だけでは判定できないのはどれか？** それらについて、決定的な検査でもなお押さえられる床は何か。レッスン4の手法に残されるのは何か。

<!-- hint -->
それぞれをこの問いから始めてください。「この出力にとって、どの差異が意味を担い、どれが見せかけか？」意味を担う部分がアサートすべきものを決め、見せかけの部分が正規化して消すべきものを決めます。たとえば2番では行の順序が意味を担いますが（タスクがソートなので）、改行コードが `\n` か `\r\n` かは意味を担いません。

<!-- hint -->
「fixture ファイルとのバイト単位の diff」を万能の答えとして既定にしないでください。より頑健なやり方はたいてい、固定のサンプルと比較するのではなく、**出力から性質を計算してそれをアサートする**ことです。2番なら、fixture の CSV と diff するのではなく「隣り合う行の金額が単調非増加である」とアサートします——そうすれば別のデータに差し替えてもスクリプトは動き続けます。

<!-- rubric -->
- 6項目すべてに具体的な検証器があり、pass/fail を生む形になっている（「品質を確認する」では不可）
- 少なくとも4項目の理由づけが「どの差異が見せかけで、正規化や回避が必要か」に触れており、単に「スクリプトで確認する」で終わっていない
- 3番（自由記述の要約）が決定的な検査だけでは判定しきれないと明示し、決定的な検査で押さえられる床（長さ、必須の固有表現が現れること、出典にない数値が入っていないこと）を述べ、品質の判定はレッスン4に委ねている

- 5番（ファイル名リスト）について「順序は通常意味を担わない」と認識し、順序付きの比較ではなく集合としての比較を行うべきだとしている
- 6番（感情ラベル）について、これが完全一致の典型的な場面だと認識し、先に空白と大文字小文字を正規化することに触れている

<!-- answer -->
**1. JSON の設定ファイル → スキーマ検証＋いくつかの意味的アサーション。**
スキーマが構造を取り締まり（フィールドの有無、型の正しさ、必須フィールドが埋まっていること）、そのうえでスキーマが表現できないアサーションを少し足します。ポートが 1〜65535 の範囲にあること、タイムアウトが正の数であることなど。fixture の設定ファイルとバイト単位で diff してはいけません——キーの順序、インデント、末尾のカンマはすべて見せかけの差異で、毎日のように誤警報を起こします。設定がツール呼び出しを通じてエージェントに生成されるものなら、構造の側は `strict: true` でAPI層まで前倒しすることさえできます[^S6]。

**2. ソートされた CSV → スクリプトで読み込んで性質をアサートする。**
列名が正しいこと、行数が正しいこと、隣り合う行の金額が単調非増加であることをアサートします。3つ目がタスクの核心で、最初の2つは「ソートは正しいがデータが半分消えている」を防ぎます。これは特に fixture ファイルとの diff を使うべきではありません。改行コード、数値の書式（`1000` と `1000.00`）、末尾の空白はすべて見せかけですし、入力データを差し替えると fixture が無効になります。

**3. 自由記述の要約 → 決定的な検査が床を押さえ、品質の判定はレッスン4へ。**
調査の成果物は自由記述テキストであり、唯一の正解を持つことがまれなので、プログラムによる評価が困難です[^S2]。それでも床は押さえられます。語数が所定の範囲にあること、指定した固有表現（人名、製品名、四半期）が現れること、元のレポートにない数値が入っていないこと。しかし「要点を捉えられたか」「意図を取り違えていないか」は、ルーブリックに基づくLLM裁判官の採点が必要です——それがレッスン4の内容です。

**4. コードのパッチ → テストスイート＋ビルドの終了コード＋linter、人間のレビューを後ろ盾に。**
コードによる解決策は自動テストで検証可能であり[^S1]、その3つはまさに公式の検査メニューに載っています[^S4]。しかし **"However, whereas automated testing helps verify functionality, human review remains crucial for ensuring solutions align with broader system requirements."**（しかし、自動テストは機能の検証に役立つ一方で、解決策がより広いシステム要件に沿っていることを保証するには、人間によるレビューが依然として決定的に重要である）[^S1]——パッチが全テストに合格しつつ、保守性を殺す設計であることはありえます。

**5. ファイル名のリスト → 集合としての比較（先にソートしてから比較するか、`Set` を使う）。**
ファイル名の**順序**は通常意味を担いません。`a.csv` が `b.csv` の前に処理されたか後かは、タスクが完了したかどうかに影響しません。順序付きの行単位 diff は、順序が違うだけで誤警報を出します。もう1つ確認を足しましょう。これらのファイルが実際にディスク上に存在するか——エージェントが報告した処理済みファイルが実際の状態と食い合わないのは、典型的な失敗モードです。

**6. 感情ラベル → 正規化したうえでの完全一致。**
`output == golden_answer`[^S5]、比較の前に空白と大文字小文字を正規化します。これはまさに完全一致が得意とするところです。答えが明確に区分されるタスクで、有効な値は3つだけ[^S5]。モデルが `Positive.` や `Sentiment: positive` を出力することに注意してください——正規化がその種の見せかけの装飾を許容できるようにするか、あるいはプロンプトで出力形式を強く固定してしまうかです。

**決定的な検査だけでは判定できないのはどれか:** 3番は全体が、そして4番の「より広いシステム要件に合っているか」の層が該当します。この2つはレッスン4のLLM裁判官へ、あるいは人間へ渡ります。

### レベル2: 実際に動く `verify.mjs` を書く

**タスクの設定。** エージェントは次の要件を満たす `report.json` を生成する必要があります。

- `title` を持ち、型は文字列
- `items` を持ち、配列で、各要素は `name`（文字列）と `count`（整数）を持つ
- `total`（整数）を持ち、`total` はすべての `count` の総和と等しい
- `title` は fixture のタイトル `2026 年 Q1 チャネル集計` と一致すべき

3層の検査を行うNodeスクリプト `verify.mjs` を書いてください。**構造検証**、**`total` の整合性チェック**、**空白を正規化したうえでのタイトル比較**の3層です。使い方は `node verify.mjs report.json`、合格なら終了コード0、不合格なら1で終了し、理由を1行に1つ出力します。

書き終えたら、それを検証するためのサンプルファイルを3つ作ってください。完全に正しいもの、`total` が本当に計算間違いしているもの、そして「内容はすべて正しいがタイトルに余分な空白があるもの」です。3つ目は合格しなければなりません——正規化が偽陰性を救ったことの証明になります。

<!-- hint -->
3つの層には依存順序があります。構造が通らないうちは、急いで `total` を計算しないこと。`items` がそもそも配列でなければ、それに `.reduce()` を呼ぶと例外が飛び、明快な「items が配列ではない」が読みにくいスタックトレースに変わってしまいます。型は、構造の層がエラーを集めて早期に `return` し、残り2層は構造が通った場合にだけ走る、という形です。

<!-- hint -->
タイトルを正規化するとき、`trim()` は前後の空白しか取り除かず、語のあいだの余分な空白は取り除きません。両方に対処するには `text.replace(/\s+/g, " ").trim()` を使ってください。まず連続する空白（改行やタブを含む）をすべて通常の空白1つに畳み、それから前後を削ります。整数の確認には `typeof x === "number"` を使わないこと——`3.5` も number だからです。`Number.isInteger(x)` を使ってください。

<!-- rubric -->
- 終了コードで判定を表現している: 合格は `process.exit(0)`、不合格は `process.exit(1)`
- 構造検証が `title` が文字列であること、`items` が配列であること、各要素が文字列の `name` と整数の `count` を持つこと、`total` が整数であることを網羅している
- JSON のパース失敗が個別に捕捉され、読める形のエラーとして報告されている。例外がプロセスを落とすままにしていない
- 構造検証が失敗したときは、総和と比較を実行せずに早期リターンしている
- `total` の整合性が、ハードコードされた数値との比較ではなく、その場で計算した「すべての `count` の総和」を使っている
- `title` の比較が、比較前に正規化している。最低でも連続する空白の畳み込みと前後の削除を行っている
- `total` と `title` の失敗メッセージに、期待値と実際の値の両方が含まれている
- 3つのサンプルファイルの判定が PASS、FAIL（`total` の不一致）、PASS になっており、3つ目の合格が正規化のおかげであることを示せている

<!-- answer -->
完全なスクリプト:

```javascript
// verify.mjs
import { readFileSync } from "node:fs";

const GOLDEN_TITLE = "2026 年 Q1 チャネル集計";

// 正規化: 連続する空白を畳み、前後を削り、大文字小文字を揃える
function normalize(text) {
  return text.replace(/\s+/g, " ").trim().toLowerCase();
}

export function verify(raw) {
  const errors = [];

  let data;
  try {
    data = JSON.parse(raw);
  } catch (err) {
    return { pass: false, errors: [`JSON のパースに失敗: ${err.message}`] };
  }

  if (data === null || typeof data !== "object" || Array.isArray(data)) {
    return { pass: false, errors: ["トップレベルが JSON オブジェクトではありません"] };
  }

  // 第1層: 構造検証
  if (typeof data.title !== "string") {
    errors.push("title が存在しないか、文字列ではありません");
  }
  if (!Array.isArray(data.items)) {
    errors.push("items が存在しないか、配列ではありません");
  } else {
    data.items.forEach((item, i) => {
      if (item === null || typeof item !== "object") {
        errors.push(`items[${i}] がオブジェクトではありません`);
        return;
      }
      if (typeof item.name !== "string") {
        errors.push(`items[${i}].name が存在しないか、文字列ではありません`);
      }
      if (!Number.isInteger(item.count)) {
        errors.push(`items[${i}].count が存在しないか、整数ではありません`);
      }
    });
  }
  if (!Number.isInteger(data.total)) {
    errors.push("total が存在しないか、整数ではありません");
  }

  // 構造が落ちたら先へ進まない。進むとエラーが連鎖する
  if (errors.length > 0) {
    return { pass: false, errors };
  }

  // 第2層: total の整合性
  const sum = data.items.reduce((acc, item) => acc + item.count, 0);
  if (sum !== data.total) {
    errors.push(`total が不一致: 申告値 ${data.total}、items の count 合計 ${sum}`);
  }

  // 第3層: タイトル比較、先に正規化する
  if (normalize(data.title) !== normalize(GOLDEN_TITLE)) {
    errors.push(
      `title が不一致: 正規化後は "${normalize(data.title)}"、期待値は "${normalize(GOLDEN_TITLE)}"`
    );
  }

  return { pass: errors.length === 0, errors };
}

const path = process.argv[2];
if (!path) {
  console.error("使い方: node verify.mjs <report.json>");
  process.exit(2);
}

const result = verify(readFileSync(path, "utf8"));
if (result.pass) {
  console.log(`PASS  ${path}`);
  process.exit(0);
}
console.log(`FAIL  ${path}`);
for (const e of result.errors) {
  console.log(`  - ${e}`);
}
process.exit(1);
```

サンプル3つ。`good.json`——すべて正しいもの:

```json
{
  "title": "2026 年 Q1 チャネル集計",
  "items": [
    { "name": "直販", "count": 12 },
    { "name": "代理店", "count": 30 },
    { "name": "オンラインセルフ", "count": 8 }
  ],
  "total": 50
}
```

`broken.json`——`items` と `title` は `good.json` と同一で、最後の行だけを変え、`total` が本当に計算間違いしているもの（12 + 30 + 8 = 50 なのに 48 と書いている）:

```json
  "total": 48
```

`spacey.json`——`items` と `total` は `good.json` と同一で、タイトルだけを、前後に空白があり、途中に空白が2つ余分にあり、末尾に改行がある版に差し替えたもの。これが偽陰性のケースです:

```json
  "title": "  2026 年   Q1 チャネル集計\n",
```

実行します（`node --version` は v26.3.0。スクリプトは新しい構文を使っていないので、古いバージョンでも動きます）:

```text
$ for f in good.json broken.json spacey.json; do node verify.mjs "$f"; echo "  exit code: $?"; done
PASS  good.json
  exit code: 0
FAIL  broken.json
  - total が不一致: 申告値 48、items の count 合計 50
  exit code: 1
PASS  spacey.json
  exit code: 0
```

3つの判定が、本レッスンの3つの要点に対応しています。`good.json` が通るのがベースラインです。`broken.json` は捕まり、失敗メッセージに期待値と実際の値の両方が入っています（`申告値 48、items の count 合計 50`）。エージェントはこの1行を読めばどの数値を直せばよいか分かります。`spacey.json` は通ります——`title` の比較をバイト単位で書いていたら、これは偽の不合格になり、エージェントは次のターンをタスクとは無関係な改行いじりに費やしていたでしょう。正規化がこの偽陰性を救ったのです。落とし穴の節の `strict.mjs` を同じファイルに対して実行すると、正規化がない場合にどう見えるかが分かります:

```text
$ node strict.mjs spacey.json
FAIL: title が不一致、実際の値は "  2026 年   Q1 チャネル集計\n"
```

## まとめ

- 採点方法の順位付けの原則は「最も速く、最も信頼でき、最もスケールする」です。コードベースの採点は3つすべてで首位に立ち、引き換えに、ルールに縛られない柔軟さを要する複雑な判断のニュアンスを扱えません[^S5]。
- 検査は、Claude が会話の中で読み取れる信号を返すものなら何でもよいのです。テストスイート、ビルドの終了コード、linter、出力を fixture と diff するスクリプト、デザインと比較するスクリーンショット[^S4]。
- 検証器はスペクトラムをなします。左端は fixture との完全な文字列一致、右端は Claude に判定を頼むこと[^S3]。最小形は `output == golden_answer` だけで、通常は空白と大文字小文字を正規化したうえで行い、答えが明確に区分されるタスクに最適です[^S5]。
- pass/fail があれば、ループは自分で閉じます。作業し、検査を実行し、結果を読み、通るまで反復する[^S4]。それは、エージェントが進捗を評価するために各ステップで環境から「ground truth」を得る必要があるからであり[^S1]、テスト結果をフィードバックとして反復できる理由でもあります[^S1]。
- 複雑なワークフローは、すべての中間ステップを検証するのではなく、特定の状態変化が起きているはずの個別の検証チェックポイントに分割できます[^S2]。構造検証の1種類は、`strict: true` でAPI層まで前倒しして、ツール呼び出しがスキーマに厳密に従うようにすることさえできます[^S6]。
- 最大の落とし穴は厳しすぎる検証器です。書式、句読点、有効な言い換えのような見せかけの差異のせいで、正しい応答を弾いてしまいます[^S3]。修正は、先に正規化してから比較し、厳しさは本当に意味を担う部分のために取っておくことです。
- 決定的な検査には天井があります。調査の成果物はプログラムによる評価が困難であり[^S2]、自動テストは機能を検証しますが、"human review remains crucial for ensuring solutions align with broader system requirements"（解決策がより広いシステム要件に沿っていることを保証するには、人間によるレビューが依然として決定的に重要である）[^S1]、そして自動評価が成熟していても手作業のテストは依然として不可欠です[^S2]。
- 使い捨てのスクリプトに完全な検証器を作らないこと——複雑さの追加を検討すべきなのは、それが結果を明らかに改善する場合だけです[^S1]。ただし逆向きに、検証できないなら、リリースしないこと[^S4]。
