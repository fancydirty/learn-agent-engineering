## 3回実行して、3回とも「不合格」

エージェントに検証を追加しようと決めます。最初の衝動はほぼ全員に共通しています。「標準的なやり方」を記録するのです。タスクを一度手作業で通し、すべてのステップを書き留める——ステップ1では `search` を呼ぶはず、ステップ2では `fetch_page`、ステップ3では `write_note`——それを解答例として保存します。以後、エージェントが実行するたびに、呼び出し列をこの解答と1ステップずつ突き合わせる。1つでも食い違えば不合格。

3回実行しました。3回とも不合格でした。

出力を確認します。3本の要約はいずれも事実が正しく、出典も信頼でき、求めた観点をすべて押さえています。違ったのは経路だけでした——1回目は3つのソースを検索してそれで十分だった。2回目は10検索した。3回目は検索の前にまず用語の定義を調べた。これはまさに Anthropic が自社のマルチエージェント調査システムで観測したことです。出発点が同一でも、エージェントは目標に到達するまでにまったく異なる、しかし有効な経路を取りうる。あるエージェントは3つのソースを検索し、別のエージェントは10検索する。あるいは同じ答えを見つけるのに異なるツールを使う[^S2]。

失敗したのはエージェントではありません。あなたの検証方法です。

## そもそも「正しい手順」が何かを、あなたは知らない

従来の評価には、深いところに埋め込まれた既定の前提があります。入力Xが与えられたら、システムは経路Yをたどって出力Zを生成するはずだ——毎回同じ手順で[^S2]。この前提は決定的システムではあまりに自然に成り立つため、それが前提であることに気づかないまま過ごす人がほとんどです。エージェントはそれを一瞬でひっくり返します。

本当に居心地が悪いのは「経路が変わる」だけではありません。次の一文です。

> "Because we don’t always know what the right steps are, we usually can't just check if agents followed the “correct” steps we prescribed in advance. Instead, we need flexible evaluation methods that judge whether agents achieved the right outcomes while also following a reasonable process."[^S2]
>
> （正しい手順が何かを常に把握しているわけではないため、あらかじめ規定した「正しい」手順にエージェントが従ったかどうかを確認するだけでは、たいてい済みません。代わりに、妥当なプロセスを踏みつつ正しい結果に到達したかどうかを判定する、柔軟な評価手法が必要です）

「正しい手順が何かを常に把握しているわけではない」——これが肝です。あなたが記録した経路は、唯一の正しい経路ではありません。それはその時**たまたま自分が通った経路**にすぎません。それを解答例に格上げしたので、他のすべてのやり方が誤りになってしまったのです。

後半にも注目してください。「妥当なプロセスを踏みつつ」。これはプロセスを完全に無視しろという意味ではありません。1つの固定された経路をものさしにするな、という意味です。

## 終状態評価: プロセスではなく結果を判定する

Anthropic のアプローチは直接的です。ターンごとの分析ではなく終状態の評価に集中する——特定のプロセスに従ったかを判定するのではなく、正しい最終状態に到達したかを判定する[^S2]。この方法は、エージェントが同じ目標に別の経路で到達しうることを認めたうえで、意図した結果を届けることは保証します[^S2]。

まず「終状態」を平たく定義しておきます。タスク完了後に環境で観測でき、事後に検証できる状態のことです。ファイルシステムにどのファイルが現れたか、あのデータベースレコードのフィールドが今どんな値か、チケットにどのラベルが付いているか、返ってきたJSONに `status: "resolved"` があるか。

便利なリトマス試験があります。終状態は**名詞**であって動詞ではない、というものです。「`rename_file` を呼んだ」は動詞、「すべてのファイル名がある形式に一致している」は名詞です。検証が受け付けるのは名詞だけです。

```text
タスク: downloads/ の請求書PDFを "日付_取引先.pdf" にリネームする

ステップ基準の検証（脆い）              終状態基準の検証（安定）
1. list_files を呼ぶ                    downloads/ に元のファイル名が残っていない
2. 各ファイルで read_pdf を呼ぶ          各ファイル名が ^\d{8}_[a-z0-9-]+\.pdf$ に一致する
3. extract_date を呼ぶ                  ファイル数が実行前と一致し、消失も増加もない
4. 各ファイルで rename_file を呼ぶ       ファイル名の日付がPDF内容の請求日と一致する
```

左の列は、結果が同一であっても、エージェントが個別の4回の読み取りの代わりに一括読み取りを1回使った瞬間に不合格になります。右の列はどう読んだかを気にしません——「downloads/ が今どうなっているか」を記述しているだけで、そこに至った経緯とは無関係だからです。

終状態のアサーションを書くときに見落としやすい箇所があります。**変わってはいけないものも書き留める**ことです。上の「ファイル数が実行前と一致」がそれにあたります。エージェントが2つのファイルを同じ名前にリネームして2つ目が1つ目を上書きした場合でも、「すべてのファイル名が妥当」という検査は完璧に通ってしまいます。終状態のアサーションは「期待した変化が起きた」と「期待しない変化が起きていない」の両方を守らなければなりません。

## 複雑なワークフロー: 評価をチェックポイントに分割する

終状態評価は「プロセスを完全に無視する」ことではありません。出典の次の一文が逃げ道を示しています。複雑なワークフローでは、すべての中間ステップを検証しようとするのではなく、特定の状態変化が起きているはずの個別のチェックポイントに評価を分割する[^S2]。

言い回しに注目してください——「特定の状態変化が起きているはず」、やはり状態であり、名詞です。観測点を「ゴール地点」から「途中の数箇所」に移しただけです。

> **用語衝突の注意**: 本シリーズのコース9で言う「チェックポイント」は**コンテキストの保存**を指します。エージェントの実行中の状態をディスクに書き出し、クラッシュ後にそこから再開できるようにするもので、目的はリカバリーです。本レッスンで言う「チェックポイント」は**状態の検証**を指します。フローのある地点で期待した状態変化が起きたことを確認するもので、目的は妥当性の確認です。位置はしばしば重なりますが（チェックポイントを打つ場所で検証も行うのは自然です）、解こうとしている問題が違います。議論で混ぜると混乱するので、以下では前者を「リカバリーチェックポイント」、本レッスンのものを「検証チェックポイント」と呼び分けます。

検証チェックポイントを追加する価値があるかは、3つを見て判断します。

- **ワークフローが長く、終状態が起点から遠すぎる**。失敗したとき「ゴールに届かなかった」ことしか分からず、どこから逸れたのかが分かりません。
- **不可逆な操作がある**。メールの送信、在庫の引き落とし、ファイルの上書き——終状態がエラーを明かす頃には手遅れです。
- **中間出力が後続ステップの土台になっている**。マイグレーションスクリプトがテーブルを作ってからデータを流し込む場合、テーブル構造が間違っていれば投入したデータはすべてゴミになり、やり直しのコストが跳ね上がります。

どれにも当てはまらないなら、追加しないでください。

どこに置くか。**状態が実質的に変化する地点**であって、ツール呼び出しのたびではありません。

```text
タスク: ユーザーテーブルを旧スキーマから新スキーマへ移行する

検証チェックポイント1（テーブル作成後）: new_users テーブルが存在し、カラムが目標スキーマと完全に一致する
検証チェックポイント2（データ投入後）: new_users の行数 == old_users の行数、主キーの重複がない
終状態: アプリが新テーブルを読んでスモークテスト（最も基本的な「動くか」の確認）に合格し、old_users が old_users_backup にリネームされている

検証しないもの: CREATE TABLE を書いたのかテンプレートから複製したのか、
一括で投入したのかバッチに分けたのか、何バッチか、1バッチ何行か。
```

チェックポイント2つ、終状態1つ。3つのアサーションが移行全体を統治します。「すべての中間ステップを検証する」方式を採っていたら、このワークフローは何十ものアサーションを生み、その大半は正当な実装差を罰するだけのものになったでしょう。

## 成功基準の定め方: 測定可能、達成可能、多次元

「正しい終状態」というひと言は、具体的な数値か明確な判定に着地させないと、結局「正しそうに見える」に逆戻りします。公式ドキュメントは成功基準に2つの必須要件を課しています。

- **測定可能であること**: 定量的な指標か、明確に定義された定性的スケールを使う（スケールとは採点ルーブリックのチェックリストのことで、書き方の具体はレッスン4で扱います）。数値は明快さとスケーラビリティをもたらしますが、定性的な尺度も定量的な尺度とともに一貫して適用されるなら価値がありえます[^S5]。
- **達成可能であること**: 業界ベンチマーク、過去の実験、AI研究、専門知識に基づいて目標を設定する。成功指標が現在のフロンティアモデルの能力に対して非現実的であってはなりません[^S5]。

そしてもう1つ。ほとんどのユースケースは、複数の成功基準にまたがる多次元の評価を必要とします[^S5]。

公式ドキュメントの完全な例は一文です（括弧内の注記は原文のものです）。

> "The sentiment analysis model should achieve an F1 score of at least 0.85 (Measurable, Specific) on a held-out test set* of 10,000 diverse Twitter posts (Relevant), which is a 5% improvement over the current baseline (Achievable)."[^S5]
>
> （感情分析モデルは、多様な10,000件のTwitter投稿からなるホールドアウトのテストセット上で、少なくとも0.85のF1スコアを達成すべきである。これは現在のベースラインから5%の改善にあたる）

この一文は分解する価値があります。各構成要素が、それぞれ特定の失敗モードを封じているからです。

| 構成要素 | 何を封じるか |
| --- | --- |
| F1スコア | 「だいたい良さそう」を封じる。F1（適合率と再現率の調和平均、0から1）は計算可能な数値で、2人がやれば同じ結果になる |
| 少なくとも0.85 | 事後にゴールポストを動かすことを封じる。実行してから「合格」を定義すれば、いつでも合格になる |
| 10,000件の投稿 | サンプルが小さすぎることによる偶然の結果を封じる。これは公式の例に出てくる規模であって、普遍的な閾値ではない |
| ホールドアウトのテストセット | 評価セットに合わせたチューニングを封じる。見たことのある問題での高得点は数に入らない |
| 多様なTwitter投稿 | きれいなサンプルでだけ見栄えがして、実分布が来ると崩れることを封じる |
| ベースラインから5%改善 | 非現実的な目標を封じる。願望ではなく、すでに到達済みの水準を基準点にしている |

最後の行が「達成可能」の具体的なやり方です。閾値は願望から逆算するものではなく、現状から小さく一歩進めたものです。ベースラインがないなら、最も素朴な実装を1バージョン走らせて、そのスコアをベースラインにします。ベースラインすら走らせられないうちは、急いで数値を決めないでください。

もっと手前の問いもあります。Anthropic はエージェントが向くシナリオをこう記述しています。エージェントが最も価値を発揮するのは、会話と行動の両方を必要とし、**明確な成功基準があり**、**フィードバックループを可能にし**、意味のある人間の監督を組み込めるタスクである[^S1]。これを逆から読んでください——どうやってもこのタスクの成功基準が書けないなら、問題は検証のステップにあるのではなく、そのタスクは丸ごとエージェントに単独で走らせるべきではなかったのです。基準が書けないなら、最初から最後まで見ているしかありません——レッスン1で述べたとおり、その時点であなた自身が検証ループになります。

## 軌跡アサーション: 追加してよいが、決め打ちにしない

終状態評価は「結果が正しいか」を捕まえますが、1種類の問題を取り逃がします。渡した新しいツールを、エージェントが本当に認識しているかどうかです。

公式ドキュメントは任意の追加要素を提示しています。プロンプトと応答のペアごとに、そのタスクを解く際にエージェントが呼ぶと期待するツールを任意で指定でき、評価の中で各ツールの目的をエージェントが把握できているかを測れる[^S3]。これが軌跡アサーションです——順序を判定せず、回数も判定せず、あるツールが軌跡に現れたかどうかだけを判定します。

役に立つ場面はこうです。`search_internal_docs` ツールを追加したばかりで、社内プロセスに関する質問ではそれを使ってほしい。ところがエージェントは公開ウェブを検索し、十分似た答えを見つけてしまい、終状態の検証は通ってしまいます。その違いが見えるのは軌跡だけです。

限界はすぐ次の一文に書かれています。タスクを正しく解く有効な経路は複数ありうるため、過剰な指定や特定の戦略への過剰適合は避けるようにする[^S3]。

具体的な境界線はこうです。

- 「集合として含む」だけをアサートし、順序も回数もアサートしない
- 本当に気にかけている1つか2つのツールだけを挙げる。列全体を書き写さない——それはまた記録と再生です
- 軌跡アサーションは失敗したが終状態は合格の場合、観測として記録するにとどめ、評価全体を不合格にしない
- あくまで任意の追加要素であって既定ではありません。既定は依然として終状態です[^S2]

```javascript
// 評価ケース1件の形: 終状態の判定は必須、軌跡アサーションは任意
const evalCase = {
  id: 'invoice-rename-003',
  prompt: 'downloads/ の今月分の請求書を date_vendor.pdf にリネームして',
  // 必須: 実行後に環境がどうなったかを確認する（書き方はレッスン3で）
  checkEndState: async (env) => { /* ... */ },
  // 任意: 順序や呼び出し回数を問わず、少なくともこれらのツールに触れたことを期待する
  expectedTools: ['read_pdf', 'rename_file'],
};
```

## 合格率の先: ほかに何を記録するか

評価を1回まわして合格率しか手に入らなければ、あなたは何も言えなくなります——78%とは何を意味するのか。次に調整すべきはプロンプトなのかツールなのか。

公式ドキュメントは、トップレベルの正確度に加えてこれらの指標を集めることを推奨しています。個々のツール呼び出しとタスクの総実行時間、ツール呼び出しの総回数、トークンの総消費量、ツールのエラー[^S3]。これらの指標は判定には参加しません。**診断**に参加します。

公式ドキュメントは2つの読み取り方を示しています。

- 冗長なツール呼び出しが多いなら、ページングやトークン上限のパラメータを適正化する余地があるかもしれない[^S3]
- 無効なパラメータによるツールエラーが多いなら、ツールの説明をより明確にするか、より良い例を付ける余地があるかもしれない[^S3]

この2つに共通しているのは、指を向ける先が**ツールの設計**であって、モデルではないことです。冗長な呼び出しが多いのは、たいてい一度に20件しか取れないので10ページめくらざるをえないからです。パラメータエラーが多いのは、たいていツールの説明がそのフィールドにどんな形式が必要かを説明していないからです。これらの問題はツール側に根があります——システムプロンプトに「呼び出しを減らせ」「パラメータを丁寧に書け」と足すだけではたいてい効きません。ツールのパラメータ設計と説明を直す必要があります。

この筋をたどるとさらにいくつか出てきます（以下は公式のお墨付きではなく、上の2つから外挿した工学的判断です。自分のデータで確かめてください）。合格率は変わらないのにトークン消費が倍になったなら、その変更は無料ではありません。あるカテゴリのタスクだけ所要時間のばらつきが大きいなら、リトライや堂々巡りが隠れている可能性が高い。エラーが1つのツールに集中しているなら、まずそのツールを見るべきで、プロンプトを疑うのは後です。

評価の1回の実行は、少なくとも次の列を落とすべきです。レッスン6で評価ハーネスを組むときにそのまま使います（列幅を節約するため、入出力トークンは1列にまとめます）。

```text
case_id | passed | duration_ms | tool_calls | tokens_in | tokens_out | tool_errors
```

## 境界線: やってはいけない3つのこと

**その1: すべての中間ステップを検証しようとしないこと**[^S2]。本レッスンで最も破られやすい境界線です。「多く検証するほど安全」という直感があまりに強いからです。実際の結果は逆になります。アサーションが細かいほど正当な差異が罰され、評価はノイズだらけになり、やがて赤を無視し始めます——その時点で完全に無価値です。

**その2: 軌跡アサーションを既定にしないこと**。軌跡アサーションの追加はあまりに安価で、`expectedTools` にもう1エントリ書くのは何の労力もいりません。10エントリ目にはもう実質的に戦略を規定しており、形式上「アサーション」と呼んでいるだけになります。追加するたびに自分に問うてください。このツールが呼ばれなかったら、出力は本当に壊れるのか。答えが「必ずしもそうではない」なら、追加しないことです。

**その3: 実行後に閾値を決めないこと**。0.82というスコアを見て「0.8で十分だろう」と言うのも、0.86を見て「0.85は必要だ」と言うのも、同じ自己欺瞞です。閾値は実行前に決め、その根拠を書き留めてください。

以下の4つのタスクについて、それぞれ次を書いてください。(1) どんな**終状態**を検証するか。(2) 検証チェックポイントを追加するか、どこに、なぜ。

参考解答:

**1. 一括リネーム**

終状態: `invoices/` のファイル数が実行前と一致する。すべてのファイル名が `^\d{8}_[a-z0-9-]+\.pdf$` に一致する。ファイル名の日付がPDF内容の請求日と一致することを抜き取りで確認する。実行前と実行後で全ファイルの内容ハッシュの集合が同一である（これが「変わってはいけないものが変わっていない」を守ります——リネームは内容を変えるべきではないし、同名の上書きでファイルを失うべきでもありません）。

検証チェックポイント: 必要です。リネームは上書きを伴う不可逆な操作であり、2つ目の判断基準に直接あたります。やり方は**成果物**を2段階に変えることです。まず `old_name → new_name` の完全な対応表ファイル（`rename-map.json` のようなもの）を生成し、それからリネームを実行します。検証チェックポイントは「対応表を生成した、リネームはまだ実行していない」地点に置きます。そこで期待される状態変化は「対応表ファイルが存在する」ことであり、200件すべてを網羅しているか、新しい名前同士が衝突していないか、形式がすべて妥当かを検証し、壊れていれば1ファイルも上書きされる前に止めます。これはタスクの成果物を変えている（中間出力として対応表が1つ増える）のであって、内部の経路を規定しているのではない点に注意してください。どうPDFを読むか、どう日付を抽出するか、どちらを先に計算するかは、依然としてまったく気にしません。

**2. 調査して要約を書く**

終状態: 3社すべての価格帯が要約に現れている。すべての事実主張に出典が付いている。すべての出典のリンクが開けて、その内容が実際にその主張を支持している。公開価格がない部分は「公開価格は見つからなかった」と明示されており、数字が捏造されていない。これらの終状態の一部はプログラムで検証できます（リンクの到達可能性、3社すべてが現れているか、各段落に出典が1つ以上あるか）。一部は人間か裁判官が必要です（出典が本当にその記述を支持しているか）——それぞれレッスン3とレッスン4の内容です。

チェックポイント: 不要です。ワークフローは長いのですが、どのステップも可逆で（検索を外して検索し直すコストはゼロ）、中間出力が後続ステップの土台にもなっていません。どうしても追加するなら、「出典リストを集め終え、執筆はまだ始めていない」地点に検証チェックポイントを置き、3社それぞれに出典が1つ以上あるかを確認します——1社まるごとの欠落は、早く捕まえるほうが安上がりです。

**3. 失敗しているテストを直す**

終状態: もともと失敗していたケースが合格するようになっている。テストスイート全体の他のケースも依然として合格している（1つを直すために別を壊していない）。`user.spec.ts` 自体が変更されていない。最後の1つは、実装ではなくアサーションのほうを書き換えることを防ぎます——テストの変更を明示的に許すタスクなら、「テストファイルの変更は人間のレビューが必要」に差し替えてください。

チェックポイント: 不要です。4つの中で最も気楽なケースです。終状態そのものが pass/fail を出力するコマンドであり、1回実行すれば答えが出ます。途中にチェックポイントを差し込むのは純粋な過剰です。

**4. チケットの分類とラベル付け**

終状態: 500件すべてにタグが付き、欠落もnull値もない。すべてのタグ値が許可された4値の範囲に収まっており、範囲外は誤り。人手でラベル付けしたホールドアウトのサンプル上で、正確度またはクラスごとのF1が事前に設定した閾値に達している。4クラスへの分布が明らかに偏っていない（480件が全部「その他」のような場合——総合正確度は良く見えるかもしれませんが、それでも警報を鳴らすべきです）。

チェックポイント: 書き込み方によります。1件ずつDBに書き込むなら（部分的に不可逆）、「最初の50件にタグを付けた」地点にチェックポイントを置き、タグ値が正当か、分布が不条理でないかを検証し、壊れていれば早期に止めます。完全なラベル付け結果を先に作ってから一括でDBに書き込むなら、その中間出力自体が自然なチェックポイントの位置なので、追加のものは要りません。

<!-- hint -->

ヒント1: 書いたものが終状態かどうかを判定するには、「名詞か動詞か」のものさしを使ってください。「`rename_file` を呼んだ」は動詞、「すべてのファイル名がある形式に一致している」は名詞です。検証が受け付けるのは名詞だけです。

<!-- hint -->

ヒント2: 検証チェックポイントを追加するかどうかは、3つだけを見ます——ワークフローはどれだけ長いか、不可逆な操作があるか、後続ステップが中間出力を土台にするか。どれにも当てはまらないなら追加しないでください。追加しても評価がノイズだらけになるだけです。

### レベル2: 曖昧な要件を多次元の成功基準に書き直す（コード不要）

元の要件は一文です。「今週の議事録をまとめて。出典は信頼できるようにして」

これを測定可能な**多次元**の成功基準に書き直してください。各次元について4項目すべてを書きます。指標の名前、どう測るか、閾値はいくつか、**なぜその閾値が現実的に達成可能なのか**。そのうえで、どの次元が終状態を検証し、どの次元が中間チェックポイントを設けるかを、理由とともに決めてください。次元は3つ以上。コードは不要です。

<!-- rubric -->

ルーブリック:

- 次元が3つ以上あり、それぞれに「指標 / 測り方 / 閾値 / 閾値の根拠」の4項目がすべて書かれている。1項目でも欠けていれば不完全。かつ次元同士が実質的に重複しておらず、それぞれ異なる失敗モードを封じている
- 閾値が思いつきで書かれていない。現在のベースライン、同じタスクにおける人間のパフォーマンス、小規模な試験実行での観測のいずれかに基づいている[^S5]。100%に設定した次元があるなら、それが純粋に機械的に確認できるものであり、モデルが失敗しても再実行すればよいだけであることを説明している。「100%」をスローガンとして使っていない
- 各次元がどの方法で採点されるか（プログラムで可能 / 人間か裁判官が必要）が明示され、どの次元が終状態を検証しどの次元が中間チェックポイントを設けるかが、理由とともに明確になっている

<!-- answer -->

参考解答:

まず「信頼できる」という語を分解します。これは少なくとも3つの別々のことを混ぜています。出典の形式が正しいか、出典が指す先が実在するか、その出典が本当にその主張を支持しているか。分解しないと、それぞれに閾値を設定できません。

**次元1: 出典の解決率**

- 指標: 議事録中の出典のうち、具体的なソース（音声のタイムスタンプ、共有ドキュメントの段落アンカー、チャットメッセージID）を特定できるものの割合
- 測り方: プログラムで。合意した形式に従って各出典をパースし、ソース側のシステムに問い合わせて存在を確認する
- 閾値: 100%
- 根拠: この次元はモデルの判断に依存せず、形式の制約と存在確認だけです。パースに失敗したらエージェントに書き直させ、通るまで繰り返します。満点を要求してよいのは、この種の純粋に機械的な確認だけです

**次元2: 出典の支持品質**

- 指標: 抜き取った「主張と出典」のペアのうち、出典の内容が実際にその主張を支持しているものの割合
- 測り方: 人間かLLM裁判官が必要（レッスン4の内容）。まず人手で一定量にラベルを付けてベースラインにする
- 閾値: 0.9以上。かつ不合格サンプルに「出典は存在するが内容が主張とまったく無関係」のような重大な誤りが含まれていないこと
- 根拠: 100%を要求しないのは、「支持しているとみなす」こと自体の境界が曖昧だからです。同じ一群に2人がラベルを付けても完全には一致しません。閾値は同じタスクにおける人間同士の一致率の近辺に置くべきです——公式が「達成可能」に求めるのは、既存のベンチマーク、過去の実験、専門知識に基づいて目標を設定することであって、恣意的に1.0に決めることではありません[^S5]

**次元3: カバレッジの網羅性**

- 指標: 今週のすべての会議に対応するセクションが議事録にある。各会議で下された決定と割り当てられたToDoがすべて列挙されている
- 測り方: 会議の網羅はプログラムで検証できます（カレンダーにN件の会議があるなら議事録にもNセクションあるはず）。決定とToDoの漏れは人手の抜き取りか裁判官が必要です
- 閾値: 会議カバレッジは100%。決定とToDoの再現率は0.85以上
- 根拠: 会議まるごとの欠落は重大な誤りであり、機械的に確認できるので許容すべきではありません。ToDoを1件取りこぼすのは元素材に左右されます——音声の中で漠然と触れられた「これは自分が追いかけます」は、人間が聞いても全員が拾えるとは限りません。1.0に設定するのは自分で穴を掘る行為です

**次元4（任意）: 形式の適合**

- 指標: 出力が合意したテンプレート（タイトル、参加者、決定、ToDo、出典ブロックの5部構成）に適合している
- 測り方: プログラムで。正規表現かスキーマ検証
- 閾値: 100%
- 根拠: 純粋な形式であり、次元1と同じ理屈です。適合しなければ書き直させます

**どれが終状態を検証し、どれがチェックポイントを設けるか**

- 出典の解決率、形式の適合、会議カバレッジ: 終状態を検証します。3つとも実行後に一度計算する機械的な確認であり、途中で確認しても追加の利得はありません
- 出典の支持品質: 中間チェックポイントを設けます。この次元は最も高価で（人間か裁判官が必要）、系統的な逸脱も起こしやすい。「最初の会議の議事録を書き終えた」地点で数件を抜き取り、出典の付け方が根本的に間違っていれば、以降の会議もすべて同じように間違うことになります。早く止めるほど得です
- 決定とToDoの再現率: 終状態を検証します。ただし「どの会議で最も漏れが多かったか」を指標に記録し、モデルの問題なのか、その数件の会議の音声がもともと不明瞭なのかを区別できるようにします

**なぜ多次元が譲れないのか**: 次元同士が互いを掘り崩すからです。出典の解決率だけを見れば、エージェントは出典を減らして書けば満点を取れます。カバレッジの網羅性だけを見れば、音声を一字一句書き写せば通ります。組み合わせて固定すれば、抜け道は狭まります——そもそもほとんどのユースケースは、複数の成功基準にまたがる多次元の評価を必要とするのです[^S5]。

<!-- hint -->

ヒント1: まず「信頼できる」を、重複しないいくつかのものに分解してください。1つの形容詞の下には、たいてい3つか4つの異なる確認が隠れています。分解しないままでは、書ける閾値は曖昧な数値にしかなりません。

<!-- hint -->

ヒント2: 閾値を決める前に「人間ならこれをどこまでできるか」を問うてください。人間が100%に届かないなら、100%は目標ではなく言い訳です——その次元は永遠に合格しないことが確定し、あなたはすぐに無視し始めます。逆に、純粋な形式、純粋な存在確認といった機械的な検証は、適合しなければ書き直させればよいので、100%に設定するのはむしろ妥当です。

## まとめ

- 従来の評価は「入力Xを与え、経路Yをたどり、出力Zを得る」を前提にしますが、エージェントはこの前提を満たしません。出発点が同一でも、まったく異なる、しかし有効な経路を取りうる——あるものは3つのソースを検索し、別のものは10検索します[^S2]
- 正しい手順が何かを常に把握しているわけではないので、規定した手順に従ったかを確認するだけでは済みません。妥当なプロセスを踏みつつ正しい結果に到達したかを判定する、柔軟な評価手法を使ってください[^S2]
- 既定の方式は、ターンごとの分析ではなく終状態の評価です。特定のプロセスに従ったかではなく、正しい最終状態に到達したかを判定します[^S2]。終状態は動詞ではなく名詞であり、「期待した変化が起きた」と「期待しない変化が起きていない」の両方を守らなければなりません
- 複雑なワークフローでは、「特定の状態変化が起きているはず」を確認する個別のチェックポイントに評価を分割し、すべての中間ステップを検証しようとしないこと[^S2]。ここで言う「チェックポイント」は状態の検証を指し、コース9のコンテキスト保存のチェックポイントとは別物です
- 成功基準は測定可能（定量的な指標か、明確に定義された定性的スケール）で、達成可能（業界ベンチマーク、過去の実験、専門知識に基づいた目標）でなければならず、ほとんどのユースケースは多次元の評価を必要とします[^S5]
- 公式ドキュメントは「明確な成功基準があること、フィードバックループを可能にすること」を、エージェントが最も価値を発揮する条件に挙げています[^S1]。逆から読めば、成功基準を書けないタスクは、丸ごとエージェントに単独で走らせるべきではありません。最初から最後まで見ているしかなくなります
- 軌跡アサーションは任意の追加要素です。どのツールを呼ぶと期待するかを指定して、ツールの目的を把握できているかを測れますが、有効な経路は1本ではないので、過剰な指定や特定の戦略への過剰適合は避けてください[^S3]
- 合格率のほかに、実行時間、呼び出し回数、トークン消費、ツールエラーも記録してください。冗長な呼び出しが多いならページングとトークン上限のパラメータの調整を、無効なパラメータのエラーが多いならツールの説明と例をより明確にすることを検討します[^S3]
