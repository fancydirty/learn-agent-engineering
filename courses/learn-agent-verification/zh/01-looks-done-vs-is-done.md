# 第 1 课：「看起来做完了」不等于「做完了」

> 学习目标：
> - 说清 Claude 为什么会在「工作看起来做完了」的地方停下来，以及这时候验证这份活儿落到了谁头上
> - 用确定性系统和非确定性系统的对照，解释传统测试「输入 X 走路径 Y 得到输出 Z」的假设在 Agent 身上为什么不成立
> - 拿到一份完工汇报，能分清哪几句是断言、哪几句是证据，并指出还缺什么才够验收
>
> 前置要求：完成本系列前 9 门课，能手写 `stop_reason` 驱动的 harness 循环、理解检查点与恢复机制 | 下一课 [第 2 课 >>](./02-what-to-verify.md)

## 周二写完，周五才发现坏了

周二下午，你让 Agent 给内部后台加一个「批量导入用户」的功能：上传 CSV，解析，校验字段，写库。需求你交代得挺清楚，然后就去开会了。

回来的时候会话已经停了。最后一条消息长这样：

```text
已完成。

- 新增 src/importer/parseCsv.js，负责解析与字段映射
- 新增 src/importer/validate.js，校验邮箱格式与必填项
- 在 POST /api/users/import 上接好了批量写入

实现遵循了现有模块的代码风格，运行过程中没有出现错误。
```

你翻了下 diff。函数拆得干净，命名和旁边的模块对得上，边界情况看着也想过——空文件返回了明确的错误，邮箱正则不是那种一眼就有毛病的写法。你合了，上线了。

周五下午，运营在群里发了一句：「导入进去 400 个空用户是怎么回事？」

原因很朴素。运营那份 CSV 是从 Excel「另存为」出来的，文件开头带一个 BOM——三个字节的不可见字符 `﻿`，Excel 习惯往 UTF-8 文件头上加。于是第一列的列名被解析成了 `﻿email` 而不是 `email`，字段映射整个落空，每一行都成了「所有字段都是 undefined」。那校验那层呢？校验的是「邮箱格式对不对」，undefined 走的是另一条分支，被当成「这列没填」放过去了。

这事儿里没有谁偷懒。Agent 写的代码是能跑的，它自测时用的 CSV 是它自己造的——它造的 CSV 当然不带 BOM。你审 diff 的时候看的是「这段代码写得对不对」，不是「这段代码碰上真实世界的输入会怎么样」。两边都尽了力，中间照样漏。

问题出在**它停下来的那一刻**。Agent 停下的时候，手里的信息是「我写完了、我读了一遍、看着没问题」。它没有停在「我确认做完了」，它停在「看起来做完了」。而这两件事，从会话记录里你是读不出区别的。

## 它是在「看起来做完了」的地方停下的

Claude Code 官方文档把这件事讲得很直白：Claude 在工作看起来做完的时候就会停下来；在没有一个它自己能跑的检查的情况下，「看起来做完了」就是它唯一拿得到的信号，于是你自己变成了那个验证环节——每一个错误，都得等你去发现[^S4]。

这句话值得逐字读两遍。它说的不是「Claude 偶尔会偷懒」，也不是「模型能力还不够」。它说的是一个结构性事实：**如果整条链路上没有任何东西能给出一个客观结果，那么「看起来做完了」是这个系统里存在的唯一信号。** 模型只能拿这个信号做决策，它没有别的可拿。

同一份文档给这个现象起了名字：trust-then-verify gap——Claude 产出一份看起来可信的实现，而这份实现不处理边缘情况[^S4]。翻成大白话就是「先信、后验，中间那段空档」。你先信了（代码看着挺好），验的动作要么没发生，要么发生得太晚（周五下午，运营在群里）。上面那个 BOM 的例子，就是这个空档的标准形态：不是代码写错了，是没人问过「Excel 导出的文件会怎么样」。

这里还有一层容易被忽略的东西。文档给的修法后半句是：**验证不了的，就别上线**[^S4]。这句话的重心不在「验证」，在「别上线」——它承认了有些东西你就是验不了。验不了的时候，正确的动作不是「那就凭感觉信一次」，是缩小范围、改需求、或者干脆先不发。

## 断言和证据，差在哪儿

回头看那条完工消息。把它拆成一句一句，然后对每句问同一个问题：**这句话我能不能不看代码、只看它贴出来的东西，就核实一遍？**

- 「新增 `src/importer/parseCsv.js`」——能核实。文件在不在，一看便知。这是证据（虽然是最弱的那种）。
- 「实现遵循了现有模块的代码风格」——不能核实。这是模型对自己工作的评价。断言。
- 「运行过程中没有出现错误」——听着像证据，其实是断言。它说的是它调的那些工具没抛异常，不是产出对了。工具全部返回成功、结果全错，是完全可能的。
- 「校验邮箱格式与必填项」——不能核实。这句描述的是意图，不是行为。代码里那个正则到底放行了什么、拦住了什么，这句话一个字都没说。

差别在哪儿？**证据是可以被第二个人原样重跑一遍的东西**：一条命令加它的原样输出、一个退出码、一组失败用例的名字、一张截图、一个 before/after 的数字对比。**断言是只能选择信或不信的东西**：「逻辑是对的」「应该没问题」「已优化」「不会再出现类似情况」。

官方文档给的建议正是这条线：让 Claude 拿证据出来，而不是口头宣称成功——测试的输出、它跑了哪条命令以及那条命令返回了什么、或者结果的截图；审证据比你自己把验证重跑一遍快，而且对你压根没在旁边看着的那些会话同样有效[^S4]。

最后半句是关键。你要是全程盯着，「断言 vs 证据」这个区分不太值钱——你自己看见了。但只要你离开过屏幕，会话记录里剩下的就只有文字，而文字里断言和证据长得一样自信。

## 为什么 Agent 尤其吃这一套

传统软件里我们也会遇到「看起来对但其实错了」，为什么到了 Agent 这儿要单开一门课？

因为传统测试建立在一个假设上，而 Agent 不满足这个假设。

先看定义。在计算领域，确定性系统在给定相同输入时每次都产出相同输出；而非确定性系统——比如 Agent——即使起始条件相同，也可能生成不一样的响应[^S3]。这不是「有 bug 所以不稳定」，这是它的工作方式。就算你的提示词一个字都没改，两次运行的决策也不确定[^S2]。

于是传统评估的那个前提塌了。传统评估往往假设 AI 每次都走一样的步骤：给定输入 X，系统应该沿路径 Y 产出输出 Z[^S2]。多 Agent 系统不这么工作。**即便起点完全相同，Agent 也可能走出完全不同、但都合法的路径去达成同一个目标**——一个 Agent 搜三个来源，另一个搜十个；或者它们用不同的工具找到同一个答案[^S2]。

具体是什么样？大概是这样：

```text
同一个任务，同一段提示词，跑两次

第一次：read_file(schema.sql) → grep("user_id") → edit(models/user.js)
        → run_tests → 完成

第二次：list_dir(src/) → read_file(models/user.js) → read_file(models/order.js)
        → edit(models/user.js) → edit(models/order.js) → run_tests
        → run_tests → 完成
```

这两条轨迹你没法说哪条「不对」。第二次多读了一个文件、多改了一处、测试跑了两遍，可能是它绕了远路，也可能是它发现了第一次漏掉的耦合。你要是写一个断言去卡「必须先 read schema.sql」，第二次就红了——但第二次说不定做得更好。

**照着预设步骤核对轨迹这条路，在这里是走不通的**：因为我们并不总知道正确的步骤是什么，通常没法只检查 Agent 有没有遵循我们事先规定的「正确」步骤[^S2]。

再加一层：错误在 Agent 系统里是**复利**的。传统软件里的小毛病，到了 Agent 身上能把整件事带沟里——一步失败会让 Agent 转去探索一条完全不同的轨迹，结果变得没法预测[^S2]。这跟传统程序里「一个函数返回了错值、往上传一层」不是一回事。Agent 拿到一个坏结果之后，会**基于这个坏结果重新做决策**：文件读错了，它可能得出「这个模块不存在」，然后新建一个；然后围绕这个新建的模块继续干活。等你看到最终产出的时候，错误已经不在原来那个位置了，它长成了另一副样子。

Anthropic 自己的结论也在这儿：Agent 的自主性意味着更高的成本和复利式错误的可能，因此建议在沙箱环境里做充分测试，配上恰当的护栏[^S1]。还有一句更直接的——模型可能会连续跑很多轮，你必须对它的决策有某种程度的信任[^S1]。

注意「某种程度的信任」这个措辞。它不是说「你得信它」，是说这份信任必须有个来源。而信任的来源只有两种：你亲眼看着（那 Agent 就没帮你省下什么），或者有个东西替你看着。这门课整个就是在讲第二种。

## 出路：给它一个自己能跑的检查

前面那一堆铺垫，收到一句话上：**给 Claude 一个它能跑的检查**——测试、构建、一张用来比对的截图。这是「一个你得盯着的会话」和「一个你可以走开的会话」之间的差别[^S4]。

差别是怎么产生的？给 Claude 一个能产出 pass 或 fail 的东西，循环就能自己闭合：Claude 干活、跑检查、读结果、然后迭代到检查通过为止[^S4]。

这句话在本系列第 7 门课的 harness 循环上是能对上号的。先看你现在这个循环停在哪儿：

```javascript
let response = await client.messages.create({ tools, messages });
while (response.stop_reason === "tool_use") {
  messages.push({ role: "assistant", content: response.content });
  const toolResults = await runToolUses(response.content);
  messages.push({ role: "user", content: toolResults });
  response = await client.messages.create({ tools, messages });
}
// 循环停在这里：stop_reason 从 "tool_use" 变成了 "end_turn"
```

`end_turn` 是什么意思？它的意思是模型自己觉得这一轮说完了。**仅此而已。** 它不代表活干对了，甚至不保证话说完了——这个循环只认 `tool_use`，`stop_reason` 变成别的任何值它都会退出，包括输出被 `max_tokens` 拦腰截断的那种。退出条件里，压根没有任何一项跟「产出的质量」有关。

那把检查接进来是什么样？两个位置都能接。

位置一，把检查做成一个它能调的工具，让它在循环里自己跑：

```javascript
const tools = [
  ...editTools,
  {
    name: "run_checks",
    description:
      "运行 importer 模块的测试套件。返回退出码与失败用例名。" +
      "修改 src/importer/ 下任何文件之后都必须调用一次。",
    input_schema: { type: "object", properties: {}, required: [] },
  },
];
```

位置二，在循环退出之后加一道门，不信它的自述、自己跑一遍：

```javascript
// while 循环跑完了，先别急着当成完成
messages.push({ role: "assistant", content: response.content }); // 模型的收尾回复也要进历史
let verdict = await runChecks(); // { exitCode, failed: ["BOM 头解析", ...] }

while (verdict.exitCode !== 0) {
  messages.push({
    role: "user",
    content: `检查没通过，失败用例：${verdict.failed.join("、")}。修完再报告。`,
  });
  response = await client.messages.create({ tools, messages });
  // ……回到上面那个 tool_use 循环继续跑，直到它再次收尾……
  messages.push({ role: "assistant", content: response.content }); // 每次收尾回复同样要进历史
  verdict = await runChecks();
}
```

代码本身没什么花样，关键是**退出条件换人了**：从「模型说它不想再调工具了」换成了「一段确定性代码返回了 0」。前者是模型的自我评价，后者不是。

那「检查」可以是什么？官方文档给的范围比想象中宽：任何能返回一个 Claude 在对话里读得到的信号的东西——一套测试、一个构建的退出码、一个 linter、一个把输出和固定样本（fixture）做 diff 的脚本、或者一张跟设计稿比对的浏览器截图[^S4]。

fixture 这个词解释一下：就是一份你事先存好的「标准答案文件」，跑完拿产出跟它比，一个字符都不能差。听起来笨，但在「输出格式必须稳定」这类任务上，它是最省事也最可靠的一种检查。

这条思路跟 Anthropic 对 Agent 执行过程的建议是一致的：在执行期间，让 Agent 在**每一步**都从环境里拿到「ground truth」（真实反馈，比如工具调用的结果或者代码执行的结果）来评估自己的进展，这一点很关键[^S1]。注意「从环境里拿」——不是从自己的推理里拿。模型的推理是它自己生成的，环境的返回值不是。

## 接下来五课要解决什么

有了「给它一个能跑的检查」这条主线，剩下的问题就具体了。

**第 2 课：验什么。** 既然照着预设步骤核对轨迹走不通，那验哪儿？答案是终态优先——评判它有没有到达正确的最终状态，而不是有没有遵循某个特定过程；对复杂流程，把评估拆成若干个「此处应该发生某个状态变化」的检查点[^S2]。这一课还会讲怎么把一个模糊的需求变成可测量的成功标准。

**第 3 课：确定性验证器。** 能跑出 pass/fail 的检查怎么挑、怎么写。精确匹配、脚本比对、测试套件各自适合什么场合，以及一个反直觉的坑：验证器过严会把对的答案判错。具体的验证器清单和取舍顺序在那一课，这里先不展开。

**第 4 课：LLM 当裁判。** 自由文本没法用字符串比对，只能请一个模型来打分。量表怎么写、输出格式怎么限定、先推理还是先给分、以及为什么干活的那个模型不该自己当裁判——本课那道题里已经碰到过这条了。量表的具体设计放在第 4 课。

**第 5 课：评测集。** 一条检查管一个任务，一组任务才叫评测集。怎么从真实用法里攒用例、边缘情况怎么补、留出集是干嘛的、以及「多少条才算够」——这些都在第 5 课回答，答案可能比你以为的小得多。

**第 6 课：动手搭。** 把前面五课接起来：一条评测任务一个 harness 循环，跑完出报告，改一版提示词就能看到分数变没变。

## 分寸：别给每件小事都套上验收流程

看到这儿，容易走到另一个极端：以为每个任务都得配测试、配裁判、配评测集。不是的。

Anthropic 的原话是：**只有当复杂度带来可证明的改进时，才值得加这份复杂度**[^S1]。同一篇文章还有一句更具体的路线建议——从简单的提示词开始，用充分的评估去优化它，只有在更简单的方案不够用的时候，才加上多步的 Agent 系统[^S1]。

对应到验证这件事上，判断标准差不多是这几条：

- **这个任务会不会重复跑？** 一次性的脚本、临时的数据处理、你打算看着它跑完的三分钟活儿，配一套验收机制是亏的。会反复跑的、会被别人改的、会在你不在场时跑的，值。
- **出错的代价谁承担？** 改个文案错了你自己回滚一下就完了。改结算逻辑错了，是财务在承担。代价越靠后、越难回滚，越该在前面卡一道。
- **你现在验它花多少时间？** 如果每次都得手动点开三个页面对一遍，那这三个页面的对比就是最该被脚本化的东西——这个成本你已经在付了，只是没意识到。

还有一种情况值得单说：**有些检查你已经有了，只是没接给 Agent。** 项目里那套测试、那个 lint 命令、那个构建脚本，多半早就存在。把它写进任务描述、或者做成一个工具，成本几乎是零，但会话的性质就变了。这是投入产出比最高的一步，也是本课程后面几课的起点。

### Level 1：分清断言和证据

下面是三份 Agent 的完工汇报，来自三次不同的会话。逐份判断：这份汇报里，哪些是断言、哪些是证据？然后写出**每一份还缺哪几样具体的证据**，才够你把它当成「验收通过」。

不用写代码，用文字回答。

**汇报 A**

```text
已完成。我重构了 src/importer.js，把字段映射抽成了独立函数 mapFields()，
逻辑比之前清晰不少。改动没有影响现有行为。
```

**汇报 B**

```text
已完成。运行 npm test -- importer 后输出：

  PASS  test/importer.test.js
  Tests: 14 passed, 14 total
  Time:  1.842 s

新增的 3 个用例分别是 "handles BOM in header"、"rejects duplicate email"、
"errors on missing column"。未运行完整测试套件，只跑了 importer 这一组。
```

**汇报 C**

```text
已完成。修复了 BOM 头导致字段映射失败的问题。我又检查了一遍代码，
逻辑是对的，应该不会再出现类似问题了。另外顺手优化了一下解析性能。
```

<!-- rubric -->

- 三份都给出了「以断言为主 / 以证据为主」的判定，且判定结果是：B 以证据为主（是三份里唯一接近可验收的），A 和 C 以断言为主
- 对每一份都至少指出一样**具体的**缺失证据——形式上是命令加它的原样输出、失败到通过的对比、before/after 的数字之类——而不是笼统写一句「缺测试」
- 点出了 C 里「我又检查了一遍代码」属于干活的模型给自己打分，不能算独立验证；并且注意到「顺手优化了性能」是一处范围外改动，没有任何 before/after 的基准数据支撑

<!-- answer -->

**汇报 A：几乎全是断言。**

- 「把字段映射抽成了独立函数 `mapFields()`」——弱证据。函数在不在、叫什么名字，看 diff 能核实，但这只说明改动发生了，不说明改动是对的。
- 「逻辑比之前清晰不少」——断言。这是审美判断，没法核实，也不是验收该关心的事。
- 「改动没有影响现有行为」——**这是最危险的一句**。它本身是一个完全可以被验证的命题（重构的定义就是行为不变），但汇报里没有给出任何验证。一句可验证的话被当成断言说出口，比一句不可验证的话更容易骗过人，因为它听上去像结论。

缺什么才够验收：

1. 重构前后跑同一套测试的输出，两份都要，能看出用例数和通过数没变（这是「行为不变」的最低证据）
2. 如果 `importer.js` 原本没有测试覆盖，那就得先说清这一点——「没有测试所以无法证明行为不变」是一个诚实的状态，比「改动没有影响现有行为」有用得多
3. 改动范围：`git diff --stat`，确认它只动了 `src/importer.js`，没有顺手改别的

**汇报 B：主体是证据。**

- 命令 `npm test -- importer` 加上原样输出，你可以照着重跑一遍，这是标准的证据形态。
- 三个新用例的名字被列了出来，覆盖的方向能看出来（BOM、重复邮箱、缺列）。
- 「未运行完整测试套件，只跑了 importer 这一组」——这句话很值钱。它主动交代了自己没做什么。一份汇报里出现「我没做 X」，通常说明它对自己的边界有概念。

缺什么才够验收：

1. 完整测试套件的结果。局部通过不排除这次改动打坏了别的模块——这正是复利式错误最爱藏的地方
2. 用例名只是名字。`"handles BOM in header"` 这个用例内部到底断言了什么，得看一眼源码或者更详细的输出；名字对而断言写空了的用例，跑起来一样是绿的
3. 严格说还应该有一次「先看它红」的记录：把修复回退掉、确认这三个用例会失败。一个从来没红过的用例，无法证明它在测什么

**汇报 C：断言，加一处未经验证的范围外改动。**

- 「修复了 BOM 头导致字段映射失败的问题」——断言。说了做了什么，没说结果怎么样。
- 「我又检查了一遍代码，逻辑是对的」——干活的模型在给自己打分。它复查时读到的还是自己那套推理，而那套推理本来就是自洽的。这一句不能当成独立验证。
- 「应该不会再出现类似问题了」——断言，而且是最没有信息量的那种。「应该」「不会再」这类措辞里没有任何可核实的内容。
- 「顺手优化了一下解析性能」——范围外改动。没有 before/after 的数字，甚至没说改了哪里、用什么手段优化的。这一处的风险高于它修的那个 bug：修 bug 至少有一个明确的目标，「顺手优化」没有。

缺什么才够验收：

1. 一个复现 BOM 的用例，以及它从失败到通过的对比输出（这是唯一能证明「修好了」的东西）
2. 性能声明的基准数据：改动前后跑同一份输入的耗时，以及测量方式。拿不出来的话，正确动作是把这处改动撤掉、单独提，而不是让它跟着 bug 修复一起合进去
3. 完整测试套件的结果——BOM 的修法通常动的是解析入口，最容易顺带影响别的分支

**一句话总结这三份**：判断标准始终只有一个——**这句话我能不能不看代码、只看它贴出来的东西就核实一遍？** 能核实的是证据，只能选择信或不信的是断言。B 之所以最好，不是因为它写得最长，是因为它贴的东西你能原样重跑。

<!-- hint -->

对每一句话问同一个问题：**我能不能不打开代码、只凭它贴出来的内容，把这句话核实一遍？** 能，是证据；只能选择信或不信，是断言。别被句子的语气带跑——「改动没有影响现有行为」语气很确定，但它没给你任何可以核实的东西。

<!-- hint -->

「没报错」「逻辑是对的」「应该不会」「已优化」——这几种说法有个共同点：主语都是模型对自己工作的评价。反过来想想，真能核实的东西长什么样？一般带着命令行、退出码、用例名、耗时、行数这类具体的东西，而且能被第二个人原样重跑一遍。特别留意汇报 A 里那种「本来可以验证、但没给验证」的句子，它比纯粹的空话更容易蒙混过关。

### Level 2：给一个小任务设计证据清单

任务是这个：

> 写一个脚本，把 `data/contacts.csv` 里 `email` 列重复的行去掉，只保留每个邮箱**第一次出现**的那一行，结果写回同一个文件。

假设你把这个任务交给 Agent，它跑完了，报告「已完成，重复行已去除」。

请你设计一份**证据清单**：验收这个任务时，你要求看到哪几样东西？每一样写清楚是什么形式（一条命令加它的输出？一段 before/after 对比？一个文件？）。然后回答第二个问题：**这几样里，哪一个能让循环自己闭合**——也就是能让 Agent 自己跑、自己读结果、自己改到过为止，不需要你在场？

不用写完整代码，命令和伪代码就够。

<!-- rubric -->

- 清单里至少有一样是「一条命令加它的原样输出」的形式，并且写清了改动**前后**各要看什么，而不是只看改完之后的结果
- 明确指出了哪一样检查能产出 pass/fail 让循环自己闭合，理由落在「不需要人来解读、有明确的期望值」上，而不是「这条最重要」；并且识破了单条指标可以被作弊——「重复数为 0」这类指标靠清空文件也能达成，所以真正能让循环闭合的检查得把「无重复、保留首次出现、行数符合期望」这类断言捆进同一个退出码，而不是单押其中一条
- 意识到「没有重复了」不等于「做对了」，清单里有至少一条是防误删的（比如验证保留的是首次出现那行、非重复行原样未动、或者有备份/`git diff` 可回滚）

<!-- answer -->

**证据清单**

**1. 改动前后的行数**

```text
改动前：wc -l data/contacts.csv   →  1204
改动后：wc -l data/contacts.csv   →  1187
```

两个数字都要。只给改动后那个数字没有意义——你不知道它是从多少变过来的。另外记得留意表头行算不算在内，这种一行的偏差最容易在验收时被忽略过去。

**2. 重复邮箱的数量（这一条的期望值是 0）**

```text
cut -d, -f2 data/contacts.csv | tail -n +2 | sort | uniq -d | wc -l
改动前 → 17
改动后 → 0
```

关键在于这条命令**跟 Agent 写的那个脚本是相互独立的**。如果拿它自己的脚本再跑一遍去证明它自己对，那什么都没证明——去重脚本里的 bug 会原封不动地出现在校验里。用另一套工具算出来的 0，才是证据。

**3. 保留的确实是第一次出现的那一行**

挑一个原文件里重复过的邮箱，贴出它在原文件里的全部出现（带行号），再贴出结果文件里剩下的那一行：

```text
改动前：
  grep -n "li.wei@example.com" data/contacts.csv
  42:1042,li.wei@example.com,李伟,2024-03-11
  877:1877,li.wei@example.com,李伟（重复导入）,2025-01-20

改动后：
  grep -n "li.wei@example.com" data/contacts.csv
  42:1042,li.wei@example.com,李伟,2024-03-11
```

留下的是第 42 行那条，不是第 877 行那条。这一条单靠「重复数为 0」是查不出来的——把两条里的哪一条删掉，重复数都会变成 0。

**4. 非重复行没被动过**

```text
git diff --stat data/contacts.csv
 data/contacts.csv | 17 -----------------
 1 file changed, 17 deletions(-)
```

只有删除、没有新增行，也没有「修改」（在 diff 里表现为一删一增）。这一条挡的是「顺手把日期格式统一了一下」「顺手 trim 了空格」这类范围外改动。

**5. 可回滚的痕迹**

写回原文件是破坏性操作。要么有备份文件路径（`data/contacts.csv.bak`），要么这个文件本来就在 git 里、`git checkout` 一句话能退回去。这一条不是「证明做对了」，是「做错了能退」——但它同样属于验收要看的东西。

**哪一个能让循环自己闭合**

第 2 条最接近，但**单靠它不够**。

先说它为什么接近：它是清单里唯一一个完全不需要人来解读的检查——一条命令、一个数字、一个明确的期望值 0。返回值可以直接翻译成 pass/fail，Agent 跑完就知道自己过没过。第 1 条要人判断「减少 17 行合不合理」，第 3 条要人肉眼比对两段文本，第 4 条要人看懂 diff 的形状，第 5 条压根不是个检查。只有第 2 条能自动判。

再说它为什么不够：它只防「没去干净」，不防「删多了」。`truncate -s 0 data/contacts.csv` 把文件清空，重复数照样是 0，这条检查照样绿。**做对了指标、做错了事**，说的就是这种情况。

所以正确做法是把第 2、3、4 条合成一个校验脚本，三条断言全过才退出 0：

```javascript
// scripts/check-dedupe.js
// 用法：node scripts/check-dedupe.js <原文件备份> <结果文件>
// 退出码 0 = 通过，1 = 不通过

const before = readRows(process.argv[2]);
const after = readRows(process.argv[3]);
const failures = [];

// 断言一：结果里没有重复邮箱
const emails = after.map((r) => r.email);
if (new Set(emails).size !== emails.length) {
  failures.push("结果文件里仍存在重复邮箱");
}

// 断言二：留下的是每个邮箱首次出现的那一行（防删错了那一条）
const expected = [];
const seen = new Set();
for (const row of before) {
  if (seen.has(row.email)) continue;
  seen.add(row.email);
  expected.push(row);
}
if (JSON.stringify(expected) !== JSON.stringify(after)) {
  failures.push("保留的行与「首次出现」的期望不一致");
}

// 断言三：行数刚好等于去重后的期望条数（防多删或少删）
if (after.length !== expected.length) {
  failures.push(`行数不符：期望 ${expected.length}，实际 ${after.length}`);
}

if (failures.length > 0) {
  console.error(failures.join("\n"));
  process.exit(1);
}
console.log("check-dedupe: 通过");
```

注意断言二其实已经蕴含了断言一和断言三——但把三条分开报，Agent 拿到的失败信息更具体，改起来方向更明确。给检查加上「说清楚哪儿错了」的能力，跟检查本身一样重要。

有了这个脚本，任务描述就可以写成：「去重前先把原文件备份成 `data/contacts.csv.bak`；去重完之后跑 `node scripts/check-dedupe.js data/contacts.csv.bak data/contacts.csv`，退出码不是 0 就继续改，直到它通过为止。」这时候 Agent 干活、跑检查、读结果、迭代到通过，整个过程不需要你在场[^S4]。

剩下的第 5 条（可回滚）建议放在脚本之外、由你的 harness 代码在跑任务前无条件做一次——备份这种事不该依赖模型记得做。

<!-- hint -->

破坏性写回是这道题的暗礁。「重复行没了」这个结果，用 `truncate -s 0` 把文件清空也能达到。你的清单挡不挡得住这种「指标达成、事情做错」？先按这个方向想想还缺哪一条。

<!-- hint -->

挑「能让循环自己闭合」的那一条时，标准只有一个：**Agent 跑完这条检查之后，能不能不问人就知道自己过没过。** 凡是需要你肉眼比对两段文本、或者需要你判断「这个数字合不合理」的，都不算。另外想一想，如果没有哪一条单独够格，能不能把几条合成一个脚本，让它们一起给出一个退出码。

## 小结

- Claude 在工作**看起来**做完的时候就会停下来。没有一个它自己能跑的检查时，「看起来做完了」是它唯一拿得到的信号，这时验证这份活儿落到了你头上——每一个错误都得等你发现[^S4]。
- 官方文档给这个空档起了名字：trust-then-verify gap——产出一份看起来可信、但不处理边缘情况的实现。配套的修法后半句同样重要：**验证不了的就别上线**[^S4]。
- 断言和证据的分界线是「能不能被第二个人原样重跑一遍」。让 Agent 交证据——测试输出、跑了哪条命令以及它返回了什么、结果的截图——而不是口头宣称成功；审证据比你自己重跑一遍快，而且对你没在旁边看着的会话同样管用[^S4]。
- Agent 是非确定性系统：相同起始条件下也可能产出不一样的响应[^S3]，即使提示词完全相同，两次运行的决策也不确定[^S2]。于是传统评估「给定输入 X 走路径 Y 产出输出 Z」的假设失效[^S2]——相同起点可以走出完全不同但都合法的路径[^S2]。
- 错误在 Agent 系统里是复利的：一步失败会让它转去探索一条完全不同的轨迹，结果变得没法预测[^S2]。自主性带来更高的成本和复利式错误，所以需要在沙箱环境里充分测试并配上护栏[^S1]。
- 出路是给它一个能跑的检查。有了能产出 pass 或 fail 的东西，循环就能自己闭合：干活、跑检查、读结果、迭代到通过[^S4]。检查可以是测试套件、构建退出码、linter、跟固定样本 diff 的脚本、或者跟设计稿比对的截图[^S4]。
- 执行过程中让 Agent 每一步都从环境里拿到真实反馈（工具结果、代码执行结果）来评估进展，而不是从自己的推理里拿[^S1]。
- 模型可能连续跑很多轮，你对它的决策必须有某种程度的信任[^S1]——但这份信任得有来源。
- 别给每件小事都套上整套验收机制。复杂度只有在带来可证明的改进时才值得加[^S1]；先看这个任务会不会重复跑、出错的代价谁承担、你现在手动验它花多少时间。
- 最划算的一步往往是：项目里那套测试、那个 lint 命令、那个构建脚本你早就有了，只是没接给 Agent。
