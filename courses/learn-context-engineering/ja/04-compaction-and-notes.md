## 1つのウィンドウに収まらないタスク

まずは、遠からず出会う場面から始めましょう。本シリーズのコース7「Agent Harness Fundamentals: Loops and Control」で自分の手で書いたハーネスを、デバッグタスクに向けます。並行実行時にだけ現れる競合状態の修正です。エージェントはファイルを読み、テストを走らせ、コードを編集し、またテストを走らせる。40 ターンあまり経ってもタスクは終わらず、メッセージ履歴は 10 万トークンを超えて膨らみ、ウィンドウは埋まりかけています。

コース7の4つの制御バルブ（最大ターン数、予算、アイドル空転検知、承認バルブ）はここでは役に立ちません。それらが司るのは「ループを暴走させない」ことですが、ループの挙動自体は正常です。タスクそのものが単に長いだけなのです。これは事故ではなく、ループの本性です。"An agent running in a loop generates more and more data that could be relevant for the next turn of inference"[^S1] — ツール出力、途中の結論、失敗した試行が、すべてメッセージ履歴に積み上がっていきます。

そしてウィンドウはタダではありません。大量のコンテキストを解析するモデルは "attention budget" から引き出しており、"Every new token introduced depletes this budget by some amount."[^S1] トークンが積み上がるほど、モデルの正確な想起能力は落ちます。"as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"[^S1] — 崖ではなく緩やかな下り坂ですが、下り坂であることに変わりはありません。だからこそ "context, therefore, must be treated as a finite resource with diminishing marginal returns."[^S1] Claude Code のベストプラクティス文書はもっと率直です。"Claude's context window fills up fast, and performance degrades as it fills"、そして "The context window is the most important resource to manage."[^S4]

1つのウィンドウに収まりきらないほどタスクが長くなったとき、武器は2つあります。コンパクションと構造化ノートです。このレッスンでは両方を通しで扱います。

## コンパクション: 要約して、新しいウィンドウを開く

コンパクションは名前のとおりです。"taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window."[^S1] 最後の部分に注目してください。要約を古い会話に押し戻して詰め込み続けるのではありません。再初期化するのです。古いウィンドウは丸ごと捨てられ、新しいウィンドウはシステムプロンプトとサマリーだけを携えて身軽に出発します。

実装は聞こえほど大げさではありません。"passing the message history to the model to summarize and compress the most critical details."[^S1] つまりコンパクションそれ自体が、追加のモデル呼び出し1回です。コードにするとおおよそ次のようになります（`formatHistory` はメッセージ配列を読める平文に連結するだけで、実装は省略します）。

```javascript
const COMPACT_INSTRUCTION = `以下はエージェントのこれまでの作業ログ全体です。このタスクを引き継いで
続行する、まっさらな新しいセッションのための引き継ぎサマリーに圧縮してください。サマリーには
必ず次を残してください:
1. すでに下したアーキテクチャ上の決定と、その理由
2. まだ解決していない問題（バグ、エラー、行き詰まり）と、調査がどこまで進んだか
3. すでに加えた変更の重要な実装詳細（どのファイルのどの関数を、なぜ変更したか）
次のものは捨てるか、1行の結論に縮めてかまいません:
- 冗長なツール出力（同じファイルを何度も読んだ生の戻り値や、同じテストの再実行）
- 後で破棄された途中試行の一部始終
`;

async function compact(client, messages) {
  const resp = await client.messages.create({
    model: "claude-sonnet-5",
    max_tokens: 2000,
    messages: [{
      role: "user",
      content: COMPACT_INSTRUCTION + "\n\n" + formatHistory(messages),
    }],
  });
  const summary = resp.content[0].text;
  // 再初期化: 新しいウィンドウの履歴はこのサマリーだけ（ハーネスはシステムプロンプトをそのまま保持する）
  return [{
    role: "user",
    content: "以下はこれまでの作業の引き継ぎサマリーです。ここから続けてください:\n\n" + summary,
  }];
}
```

これをコース7のループに継ぎ足すのに必要な発想は1つだけです。各ターンの先頭でメッセージ履歴のトークン使用量を確認し、上限に近づいたら `compact()` を呼んで `messages` 配列を戻り値で丸ごと置き換えます。実際にこれをハーネスへ組み込む方法 — トリガー閾値をどう決めるか、コンパクションが失敗したらどうするか — はレッスン6の実践材料です。ここでは仕組みを押さえておけば十分です。

## コンパクションの勘所: 何を残し、何を捨てるか

コンパクションで難しいのは「どう要約するか」ではなく「何を残し、何を捨てるか」です。方向自体ははっきりしています。"preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs."[^S1]

なぜこのトレードオフなのでしょうか。エージェントが新しいウィンドウで「目を覚ます」場面を想像してください。そのサマリーがエージェントの記憶のすべてです。圧縮の方向を間違えたときのコストは具体的です。たとえば要約指示に「会話内容を簡潔に要約してください」としか書かなかったとします。モデルは「`orders/service.js` に未完了の競合状態がある」を何気なく落としてしまう。エージェントは「完了」と記された記録だけを見て目を覚まし、仕事は終わったと宣言するか、すでに直した箇所をつつき回すかのどちらかになります。たった1回のコンパクションで、40 ターン分の作業が脱線するのです。

逆向きに見れば、冗長なツール出力こそ最も太い削り代です。1回の grep が 200 行のマッチを返しても、有用なシグナルは次のステップの結論「`updateStatus` 関数に絞り込んだ」にすでに取り込まれています。生の 200 行が残り続けても、アテンション予算を燃やすだけで、次の一手の判断価値はほとんど増えません。[^S1]

実務的なセルフチェックがあります。要約指示を書いたら、実際の長い会話を1回コンパクションにかけ、サマリーだけを見て3つの質問に答えてみてください。「次に何をすべきか」「どの決定が確定しているか」「どの穴がまだ埋まっていないか」。3つとも澄んだ答えが出れば、その指示の keep/drop ルールは合格です。どれか1つでも空白になるなら、その keep ルールを書き足しに戻ってください。

## 製品でのコンパクション: 自動コンパクションと /clear

毎日使っているツールに、出来合いの参照実装があります。Claude Code は "automatically compacts conversation history when you approach context limits, which preserves important code and decisions while freeing space"[^S4] — 上で手書きした `compact()` と同じ仕組みで、発動条件と keep/drop ルールを製品側が用意してくれているだけです。

ただしコンパクションだけが選択肢ではありません。**無関係な**新しいタスクに切り替えるなら、古いコンテキストは役に立たないどころか有害です。"Long sessions with irrelevant context can reduce performance."[^S4] そういうときドキュメントはこう言います。"Run /clear between unrelated tasks to reset the context window entirely"[^S4] — 要約もせず、保存もせず、まるごとリセットです。理屈は単純で、コンパクションはモデル呼び出しを1回消費し、keep/drop の判断を誤るリスクを抱えます。無関係なタスクなら、いっそクリアするほうが安上がりで綺麗です。コンパクションが受け持つのは「同じタスクがまだ終わっていない」、`/clear` が受け持つのは「これから別のことをする」です。

この文書にはもう1行、手元に置く価値のある一文があります。"A clean session with a better prompt almost always outperforms a long session with accumulated corrections."[^S4] 言い換えれば、セッションの履歴が「違う、やり直して」「まだ間違っている」で主に埋まっているとき、その履歴が次の一手にもたらす価値はおそらく負です。セッションを開き直し、学んだことを新しいプロンプトに直接焼き込むほうが、荷物をすべて引きずり続けるより勝ることが多いのです。

## 構造化ノート: 重要な状態をウィンドウの外に書く

コンパクションには生まれつきの弱点が1つあります。受け身であることです。ウィンドウが埋まりかけるまで待ってから振り返って要約するので、何が生き残るかはその瞬間の判断にすべてかかっており、判断は失敗しうるものです。情報が新鮮なうちに残しておく方法はないのでしょうか。

あります。しかも単純です。"the agent regularly writes notes persisted to memory outside of the context window."[^S1] "Like Claude Code creating a to-do list, or your custom agent maintaining a NOTES.md file."[^S1] 冒頭の競合状態のタスクをもう一度取り上げると、合格点のノートはおおよそこうなります。

```markdown
# NOTES.md — 注文サービスの競合状態を修正

## 決定事項
- テストフレームワーク: vitest に切り替え（ターン3で決定、理由: 既存のテストフィクスチャが依存しているため）

## 未解決
- orders/service.js の updateStatus に競合状態あり:
  同じ注文を変更する2つの並行リクエストで、後の書き込みが先の書き込みを潰す
- 試したこと: プロセス内ミューテックス -> 単一インスタンスでは動作、複数インスタンス構成では失敗

## 次のステップ
- データベースレベルの楽観的ロックを試す（orders に version フィールドを追加）
```

配線の仕方はコース7で学んだとおりです。エージェントにファイル書き込みツールを与え、システムプロンプトに要件を1つ足します。「重要な決定を下したとき、新しい問題を見つけたとき、1つの段階を終えたときは、まず `NOTES.md` を更新してから続行すること」。これ以降、ウィンドウ内の重要な状態は、ウィンドウの外に控えの写しを持ちます。ウィンドウがどうコンパクションされようと再起動されようと、ノートはディスクに残り、新しいウィンドウが最初にすることはそれを読み戻すことです。

この手はコーディングタスク専用ではありません。"Claude playing Pokémon demonstrates how memory transforms agent capabilities in non-coding domains."[^S1] Anthropic のマルチエージェントリサーチシステムも、長時間タスクに同じことをしています。"agents summarize completed work phases and store essential information in external memory."[^S3]

## 役割分担: コンパクションは保険、ノートは日常

2つの武器を並べると、役割分担がはっきりします。コンパクションは受動的です。ウィンドウが上限に近づいたときに発動し、そのタイミングは選べず、しかも損失をともないます。何が生き残るかはその瞬間の keep/drop 判断次第です。ノートは能動的です。重要な状態が生まれたその場で書き、内容は無損失で、コストは毎回数行のファイル書き込みだけです。一言でいえば、ノートは日常業務、コンパクションは保険です。

2つは衝突しません。互いを補強します。ノートを丁寧に書くほど、コンパクションが何かを落としたときの被害は軽くなります。サマリーが細部を取りこぼしても、ノートにはまだ残っています。逆向きに見れば、コンパクションという保険があるからこそ、ノートは網羅的である必要がなく、「新しいウィンドウで目を覚ましたエージェントが必ず知っておくべき」いくつかの区分だけで済みます。

分量の感覚も大事です。すべてのタスクがこの仕掛けに見合うわけではありません。Anthropic の指針は "you should consider adding complexity only when it demonstrably improves outcomes."[^S2] 動詞に注目してください。*consider*（検討する）です。禁止ではなく、天秤にかける姿勢です。10 ターンで終わるタスクにとって、コンパクションもノートも余った部品です。最も単純なループから始め、実際に天井にぶつかってから足してください。

最後に境界を2つ。このレッスンが扱わない答えを探して時間を無駄にしないために。

- ノートファイルの**セッションをまたぐ**永続化 — どう整理するか、新しいセッションでどう復元するか、長期的にどう保守するか — は本シリーズのコース5「エージェントメモリと状態」の主題です。このレッスンが気にするのは、1つの長時間タスクの中でノートがウィンドウの負荷をどう軽くするか、それだけです。
- 長時間タスクの扱いには、実は3手あります。"compaction, structured note-taking, and multi-agent architectures,"[^S1] いずれもエージェントに "maintain coherence, context, and goal-directed behavior over sequences of actions"[^S1] させることを狙ったものです。最初の2つは終わりました。3つ目 — きれいなウィンドウを持つサブエージェントにタスクを分割する — はレッスン5です。

### レベル1: 1回のコンパクションの要約指示を書く

あなたのデバッグエージェントは 40 ターンあまり走り、メッセージ履歴にはいくつもの種類が混ざっています。序盤の vitest に切り替えるという選択、途中で見つかったがまだ直っていない競合バグ、同じファイルを読んだツール出力が数十回分、そして最後に修正した2つの関数の重要な実装詳細です。ウィンドウはもうすぐ満杯で、ハーネスはまもなくコンパクションを発動します。モデルに渡す要約指示を書き（英語でかまいません）、さらにその指示とは別に、対応する「keep リスト」と「drop リスト」を挙げてください。

<!-- rubric -->
- 要約指示が、次を残すよう明示的に求めている: 未解決の競合バグと調査の進捗、アーキテクチャ上の決定（vitest への切り替え）とその理由、すでに変更した関数の重要な実装詳細
- 要約指示が、次を捨てるか1行の結論に縮めるよう明示的に求めている: 冗長なファイル読み取り出力など、繰り返されたツールの戻り値
- サマリーの用途が新しいウィンドウの再初期化（新しい会話の冒頭コンテキスト）であり、古い会話への追記ではないことを、指示が説明している

<!-- answer -->
合格点の要約指示:

「以下はデバッグエージェントの作業ログ全体です。このタスクを引き継いで続行する、まっさらな新しいセッションのための引き継ぎサマリーに圧縮してください。サマリーには必ず次を残してください。第1に、下したアーキテクチャ上の決定とその理由（例: テストフレームワークの選択）。第2に、まだ解決していないバグと現在の調査の手がかり。第3に、すでに加えた変更の重要な実装詳細（どの関数を、なぜそのように変更したか）。捨てるか1行の結論に縮めてよいもの: 冗長なファイル読み取りの生の戻り値、後で破棄された途中試行の一部始終。」

keep リスト: 未修正の競合バグと調査が止まった地点、「vitest への切り替え」という決定とその理由、変更した2つの関数の名前・変更内容・動機。  
drop リスト: 数十回分の繰り返されたファイル読み取り出力（有用な結論はすでに決定に反映済み）、破棄された試行のやり取り全体。

使い方の注記: このサマリーは古い会話に押し戻すのではなく、新しいウィンドウの再初期化に使います。新しいウィンドウはシステムプロンプトとこのサマリーだけを携え、エージェントはサマリーから続行します。[^S1]

<!-- hint -->
まず自問してください。「新しいウィンドウで目を覚ましたエージェントが、作業を続けるために最低限知っていなければならないことは何か」。その答えを逆算して keep リストにします。

<!-- hint -->
冗長と無用は同じではありません。それらのツール出力は当時は有用でしたが、結論がすでに後続の決定記録に落ちているなら、原文は捨ててかまいません。

### レベル2: 「コンパクション後の記憶喪失」を診断する

ある人がハーネス用にこの「コンパクション」関数を書き、ウィンドウが満杯に近づいたときに呼び出しました。

```javascript
function compact(messages, keepLast = 10) {
  // ウィンドウが満杯間近: 最初のメッセージと直近 10 件を残し、残りは捨てる
  return [messages[0], ...messages.slice(-keepLast)];
}
```

組み込んだあと、エージェントはターン45でコンパクションを発動しました。そこであなたは2つの症状を観察します。1つ目、ターン47で「テストフレームワークは node:test か vitest か」という、ターン3で vitest と決着済みの問題を蒸し返し始めたこと。2つ目、ターン5に記録された未解決の競合バグに一度も触れず、数ターン後にタスク完了を宣言したこと。両方の症状の原因を説明し、2層の修正を示してください。

<!-- rubric -->
- この `compact()` が要約ではなく純粋な切り捨てであることを指摘している: 最初のメッセージと直近 10 件だけを残し、ターン3の決定とターン5のバグ記録を物理的に削除している。コンパクション後、これらの情報はコンテキストに存在しないため、エージェントは決着済みの決定を蒸し返し、未完了のバグを想起する手段を持たない
- 第1層の修正: 切り捨てをモデルによる要約に置き換える。メッセージ履歴をモデルに渡して圧縮させ、アーキテクチャ上の決定・未解決のバグ・重要な実装詳細を残して冗長なツール出力を捨てるよう指示で明示し、そのサマリーから新しいウィンドウを再初期化する
- 第2層の修正: 構造化ノートを追加する。エージェントにファイル書き込みツールを与え、決定を下したときや問題を見つけたときにウィンドウ外の `NOTES.md` を更新させ、コンパクションや再起動のあとにノートを読んで状態を復元する。これにより重要な状態がコンパクション時点の判断に依存しなくなる

<!-- answer -->
原因: この `compact()` は「要約」を一切していません。切り捨てです。最初のメッセージ（通常はタスク記述）と直近 10 件を残し、間の 30 ターンあまりを一塊で捨てています。vitest を確定したターン3のメッセージと、競合バグを記録したターン5のメッセージは、どちらも破棄ゾーンに落ちます。情報は圧縮されたのではなく物理的に削除されたので、エージェントの次の推論では、これらのメッセージは初めから存在しなかったのと同じです。決定の記録がなければテストフレームワークの選択を蒸し返すのは自然ですし、バグの記録がなければ「未完了の作業がある」証拠は見えないので、数ターン後に完了を宣言するのはまったく理にかなっています。

修正は2層です。第1層、切り捨てを本物のコンパクションに置き換えます。捨てようとしているメッセージ履歴をモデルに渡して要約させ、すでに下したアーキテクチャ上の決定、まだ解決していないバグ、重要な実装詳細を残し、繰り返されたツール出力を捨てるよう指示で明示的に求め、そのサマリーから新しいウィンドウを再初期化します。[^S1] こうすればターン3とターン5の情報は要約の形で生き延びます。第2層、保険として構造化ノートを追加します。エージェントにファイル書き込みツールを与え、決定を固めたときや問題を見つけたときにウィンドウ外の `NOTES.md` を更新させます。[^S1] コンパクションや再起動のあとは、まずノートを読みます。こうすれば1回の要約の判断が失敗しても、重要な状態にはディスク上に無損失の控えが残ります。

<!-- hint -->
「切り捨て」と「要約」を対比してください。切り捨てはメッセージを丸ごと落とし、要約は細部を落として結論を残します。自問してください。このコンパクションのあと、ターン3とターン5のあの2つのメッセージはまだコンテキストにありますか。

<!-- hint -->
重要な状態が、捨てられる前にすでにウィンドウの外へ書き出されていたなら、コンパクションが何かを落としても致命傷になるでしょうか。ここから第2層の修正へ考えを進めてください。

## まとめ

- コンパクション = 会話がウィンドウの上限に近づいたときに "passing the message history to the model to summarize and compress the most critical details"[^S1] し、そのサマリーから "reinitiating a new context window"[^S1] すること。古い会話への追記ではなく、再初期化です
- コンパクションの勘所は残すか捨てるかの選択にあります。"preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs"[^S1]。圧縮の方向を間違えると、エージェントは自分が何をしていたか忘れて目を覚まします
- Claude Code は "automatically compacts conversation history when you approach context limits, which preserves important code and decisions"[^S4]。無関係なタスクの間では `/clear` で丸ごとリセットします。"A clean session with a better prompt almost always outperforms a long session with accumulated corrections"[^S4]
- 構造化ノート: "the agent regularly writes notes persisted to memory outside of the context window"（to-do リスト、`NOTES.md`）[^S1]。コンパクションは受動的な保険で損失をともない、ノートは能動的な外部化で書きながら残します
- 長時間タスクの3手は "compaction, structured note-taking, and multi-agent architectures"[^S1]。最初の2つは手中にあり、3つ目はレッスン5です。ノートのセッションをまたぐ永続化は本シリーズのコース5「エージェントメモリと状態」の主題です
