## AI가 정답은 맞혔지만 추론은 틀렸을 때

AI에게 수학 문장제를 물었더니 '42'라고 답합니다. 확인해 보니 답은 맞습니다. 그런데 비슷한 문제로 바꿔 넣으면 답이 틀리게 나옵니다. 무슨 일이 벌어진 걸까요? 모델이 찍었을 수도 있고, 망가진 추론 경로를 따라갔는데 우연히 맞는 숫자에 도착했을 수도 있습니다.

여러 단계의 추론이 필요한 작업(수학 문제, 논리 퍼즐, 복잡한 분석)에서는 AI에게 추론 단계를 보여 주게 하는 편이 답을 곧장 물어보는 것보다 신뢰할 만합니다[^S5][^S10]. 이것이 chain-of-thought(CoT) 프롬프팅의 핵심 아이디어입니다. 결론을 실제로 검증할 수 있는 중간 단계로 쪼개는 것입니다.

## Chain-of-Thought이란

**Chain-of-thought(CoT) 프롬프팅**은 모델이 최종 답을 내놓기 전에 중간 추론 단계를 펼쳐 놓게 하는 기법입니다[^S5]. 연구의 표현을 빌리면, chain-of-thought 프롬프팅은 "enables complex reasoning capabilities through intermediate reasoning steps"(중간 추론 단계를 통해 복잡한 추론 능력을 이끌어냅니다)[^S5]. 직관은 단순합니다. "Chain of Thought prompting encourages the model to think through the problem in a step-by-step manner, which is supposed to mimic how humans break down complex problems"(Chain of Thought 프롬프팅은 사람이 복잡한 문제를 쪼개는 방식을 흉내 내도록, 모델이 문제를 단계별로 사고하게 이끕니다)[^S10]. 수학 문제를 풀려고 연습장에 식과 중간 결과를 적어 나가는 것과 똑같은 일입니다.

두 접근을 비교해 보겠습니다.

### 답을 곧장 내놓기(에러가 나기 쉬움)

❌ **CoT 없이**:
```
문제: 어느 카페가 오전에 커피 23잔, 정오에 17잔, 오후에는 오전의 두 배를 팔았다. 하루 전체로는 몇 잔을 팔았을까?

답:
```

AI는 이렇게만 출력할 수 있습니다:
```
86잔
```

답이 틀렸을 때 어느 단계에서 어긋났는지 알 길이 없습니다.

### 추론 단계 보여 주기(더 신뢰할 만함)

✅ **CoT 적용**:
```
문제: 어느 카페가 오전에 커피 23잔, 정오에 17잔, 오후에는 오전의 두 배를 팔았다. 하루 전체로는 몇 잔을 팔았을까?

Let's think step by step:
```

AI 출력:
```
Let's think step by step:

1. 오전 판매량: 23잔
2. 정오 판매량: 17잔
3. 오후는 오전의 두 배: 23 × 2 = 46잔
4. 하루 합계: 23 + 17 + 46 = 86잔

답: 86잔
```

모든 단계가 눈에 보이므로, 하나가 틀렸다면 바로 짚어내 프롬프트를 고칠 수 있습니다.

연구에 따르면 여러 단계의 추론이 필요한 작업에서 CoT는 정확도를 상당히 끌어올립니다[^S5]. 어떤 작업에서는 CoT에 풀이가 담긴 시연을 곁들이면 정확도가 최대 28.2% 더 올라갑니다[^S10].

## CoT를 쓰는 두 가지 방법

### 방법 1: Zero-Shot CoT(가장 간단함)

프롬프트 끝에 한 줄을 덧붙입니다. "**let's think step by step**"[^S5][^S10].

```
문제: 5명이 5일 걸려 끝내는 프로젝트가 있다면, 10명은 며칠이 걸릴까?

Let's think step by step:
```

이 한 줄이 모델의 단계별 추론 모드를 켭니다. 예시를 하나도 주지 않아도 모델이 알아서 문제를 쪼갭니다.

### 방법 2: Few-Shot CoT(더 통제하기 좋음)

추론 과정 전체가 담긴 예시를 한두 개 제공합니다[^S5][^S10].

```
예시:
문제: 자동차가 시속 60km로 달린다. 3시간 동안 얼마나 갈까?
추론:
- 속도 = 60km/h
- 시간 = 3시간
- 거리 = 속도 × 시간 = 60 × 3 = 180km
답: 180km

이제 이 문제를 풀어 봐:
문제: 자동차가 시속 80km로 2.5시간을 달리고, 이어서 시속 60km로 1시간을 더 달린다. 전체 이동 거리는 얼마일까?
추론:
```

예시가 추론 형식과 단계를 얼마나 자세히 적어야 하는지를 보여 주고, 모델은 그 스타일을 따라 합니다.

## CoT에 맞는 작업

CoT는 여러 단계의 추론이 필요한 작업에 가장 잘 맞습니다[^S10]:

✅ **수학·논리 추론**
- 문장제
- 비와 비율 계산
- 여러 단계에 걸친 수식 유도

✅ **인과 분석**
- 'X는 왜 Y를 일으키는가?'
- '이 버그의 근본 원인은 무엇인가?'

✅ **계획과 의사결정**
- 'A를 먼저 해야 할까, B를 먼저 해야 할까?'
- '이 접근의 장단점은 무엇인가?'

✅ **코드 디버깅**
- '이 코드는 왜 실패하는가?'
- '성능 병목은 어느 단계인가?'

맞지 않는 경우:

❌ **단순 사실 조회**: 'Python은 언제 처음 공개되었나요?' — 추론이 필요 없습니다
❌ **창작 글쓰기**: 시, 소설 — 추론 단계가 창작의 흐름을 끊습니다
❌ **형식 변환**: JSON → CSV — 기계적인 작업이라 추론이 필요 없습니다

## 예제로 보기: CoT로 문제 분석하기

### 시나리오 1: 코드 성능 분석

**CoT 없이(믿을 수 없는 결론)**:
````
이 코드에 성능 문제가 있어?

```python
def find_duplicates(items):
    duplicates = []
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j] and items[i] not in duplicates:
                duplicates.append(items[i])
    return duplicates
```

답: 네, 성능 문제가 있습니다
````

결론만 있고 왜 그런지는 없습니다.

**CoT 적용(명확한 추론)**:
````
이 코드의 성능 문제를 분석해. 단계별로 설명해:
1. 반복문 구조 파악
2. 시간 복잡도 계산
3. 구체적인 병목 지점 지적
4. 최적화 방안 제안

```python
def find_duplicates(items):
    duplicates = []
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j] and items[i] not in duplicates:
                duplicates.append(items[i])
    return duplicates
```
````

AI가 보여 주는 것:
```
성능 분석:

1. 반복문 구조:
   - 바깥 반복문: 각 원소를 순회, O(n)
   - 안쪽 반복문: 각 원소마다 남은 원소를 순회, O(n)
   - 전체: 중첩 반복문, O(n²)

2. 시간 복잡도:
   - 주 반복문: O(n²)
   - `items[i] not in duplicates` 검사: 최악의 경우 O(m), 여기서 m은 지금까지 찾아낸 중복 원소의 개수
   - 총 복잡도: O(n² × m)

3. 성능 병목:
   - 중첩 반복문은 입력이 커지면(n > 1000) 매우 느려짐
   - 리스트를 훑는 `not in` 선형 탐색이 속도를 더 떨어뜨림

4. 최적화:
   - 중복 원소를 담을 때 리스트 대신 set을 쓰면 검사 비용이 O(m)에서 O(1)로 떨어짐
   - 또는 Counter로 두 번 이상 등장하는 원소를 한 번에 모두 찾으면 O(n)으로 떨어짐
```

모든 추론 단계를 검증할 수 있으므로, 하나가 틀렸다면 즉시 눈에 띕니다.

### 시나리오 2: 논리 퍼즐

**문제**:
```
A, B, C 세 사람이 대회에 나갔다. 알려진 사실은 다음과 같다:
- A는 1등이 아니다
- B는 꼴찌가 아니다
- C는 1등도 꼴찌도 아니다

각자의 등수는 어떻게 될까?

Let's reason step by step:
```

**AI 출력**:
```
Let's reason step by step:

1. C의 조건에서 출발합니다:
   - C는 1등도 아니고 꼴찌도 아니다
   - 따라서 C는 2등이어야 한다

2. A와 B를 확정합니다:
   - A는 1등이 아니다
   - B는 꼴찌가 아니다
   - C가 이미 2등이므로 A와 B에게는 1등과 3등이 남는다

3. 남은 등수를 배정합니다:
   - A는 1등이 아니므로 A는 3등이다
   - B는 꼴찌(3등)가 아니므로 B는 1등이다

답: B가 1등, C가 2등, A가 3등
```

이렇게 단계별 소거 과정을 펼쳐 놓으면 논리에 빈틈이 없는지 훨씬 쉽게 확인할 수 있습니다.

## 자주 쓰는 CoT 패턴

### 패턴 1: 문제 분해

복잡한 문제를 몇 개의 하위 문제로 쪼갭니다.

```
문제: 어떤 소프트웨어 프로젝트에 엔지니어가 5명 있고 각자 하루 6시간씩 일하며, 120 인일의 작업이 필요하다. 엔지니어를 8명으로 늘리면 며칠 더 일찍 끝낼 수 있을까?

단계별로 계산해 보자:
1. 현재 구성으로는 며칠이 걸리는가?
2. 인원을 늘리면 며칠이 걸리는가?
3. 며칠 더 빨라지는가?
```

### 패턴 2: 가설 검증

가설을 나열한 뒤 하나씩 확인합니다.

```
이 코드에서 "TypeError: unsupported operand type(s)"가 발생한다. 가능한 원인은 무엇일까?

가능한 원인을 하나씩 확인해 보자:
1. 연산자 양쪽 변수의 타입을 확인
2. 연산에 None 값이 끼어들지 않았는지 확인
3. 문자열과 숫자를 섞어 쓰고 있지는 않은지 확인
```

### 패턴 3: 양쪽 근거 따져 보기

찬성과 반대 근거를 나열한 뒤 결론에 이릅니다.

```
마이크로서비스 아키텍처를 써야 할까, 모놀리스를 써야 할까?

두 관점에서 분석해 보자:

마이크로서비스를 택할 이유:
1. ...
2. ...

모놀리스를 택할 이유:
1. ...
2. ...

종합 판단:
현재 팀 규모와 프로젝트 복잡도를 고려하면, ...를 권한다.
```

## CoT의 한계

CoT는 만병통치약이 아닙니다. 몇 가지 한계가 있습니다.

**1. 길이와 시간이 늘어납니다**

추론 단계를 보여 주면 출력이 길어지고, 토큰을 더 쓰고, 응답도 더 오래 걸립니다.

**들일 만할 때**: 복잡한 작업이라면 토큰을 2~3배 더 써서 정확도를 얻는 편이 충분히 남는 장사입니다.
**그렇지 않을 때**: 단순한 작업('오늘이 무슨 요일이지')에서는 추론 단계가 순전히 낭비입니다.

**2. 추론 단계 자체가 틀릴 수 있습니다**

AI가 보여 주는 단계는 그럴듯해 보여도 논리에 구멍이 있을 수 있습니다. 추론이 옳은지는 여전히 직접 확인해야 합니다.

CoT의 가치는 에러를 눈에 보이게 만든다는 데 있습니다. AI가 곧장 답할 때 에러는 블랙박스 안에 숨지만, 단계를 드러내면 에러가 어느 단계에선가 모습을 드러내므로 찾아내고 고치기 쉬워집니다.

**3. 직관에 기대는 작업에는 맞지 않습니다**

어떤 작업(창작 글쓰기, 예술 평가)은 전체적인 감각에 기대기 때문에, 억지로 단계로 쪼개면 전체가 무너집니다.

## 정리

Chain-of-thought 프롬프팅은 AI가 곧장 답으로 건너뛰는 대신 추론 단계를 보여 주게 한다. 프롬프트에 "let's think step by step"을 덧붙이거나 추론이 담긴 예시를 제공하면, 여러 단계의 추론이 필요한 작업에서 정확도를 크게 끌어올릴 수 있다.

CoT는 수학 추론, 논리 분석, 인과 추론, 복잡한 의사결정 — 여러 단계의 사고가 필요한 모든 것에 잘 맞는다. 추론을 눈에 보이고 검증 가능하게 만든다. 출력 길이가 늘어나기는 하지만, 복잡한 작업에서는 얻는 것이 비용을 훨씬 앞선다.

다음 레슨에서는 프롬프트를 디버깅하고 개선하는 법을 다룹니다. AI의 출력이 기대와 맞지 않을 때 문제를 체계적으로 찾아내 고치는 방법입니다.

## 💻 연습

### 레벨 1: Zero-Shot CoT 적용하기

"let's think step by step" 기법을 사용해 AI에게 아래 문제를 풀게 하세요:

**문제**: 어떤 팀에 8명이 있고 각자 하루 6시간씩 일합니다. 프로젝트에는 240 인시의 작업이 필요합니다. 팀이 12명으로 늘어나면 며칠 더 일찍 끝낼 수 있을까요?

전체 프롬프트("let's think step by step" 포함)를 작성하고, AI가 어떤 중간 단계를 보여줄지 예측하세요.

<!-- rubric -->
- 프롬프트에 "let's think step by step" 또는 비슷한 신호를 넣었다
- 문제 서술이 명확하고 빠짐이 없다
- 예측한 추론 단계가 논리적으로 옳다
- 추론 단계가 핵심 계산을 모두 담았다(현재 구성의 소요 일수, 새 구성의 소요 일수, 그 차이)
- 이 문제가 CoT에 잘 맞는 이유를 짚어냈다
<!-- answer -->
**프롬프트**:
```
어떤 팀에 8명이 있고 각자 하루 6시간씩 일한다. 프로젝트에는 240 인시의 작업이 필요하다. 팀이 12명으로 늘어나면 며칠 더 일찍 끝낼 수 있을까?

Let's think step by step:
```

**예측한 추론 단계**:
```
Let's think step by step:

1. 현재 팀의 하루 산출량 계산:
   - 8명 × 6시간/인/일 = 48 인시/일

2. 현재 구성의 소요 일수 계산:
   - 240 인시 ÷ 48 인시/일 = 5일

3. 확대된 팀의 하루 산출량 계산:
   - 12명 × 6시간/인/일 = 72 인시/일

4. 새 구성의 소요 일수 계산:
   - 240 인시 ÷ 72 인시/일 = 3.33일(약 3.4일)

5. 단축되는 일수 계산:
   - 5일 − 3.33일 = 1.67일(약 1.7일, 즉 1일 17시간)

답: 프로젝트를 약 1.7일 더 일찍 끝낼 수 있습니다.
```

**CoT에 맞는 이유**:
- 각 단계가 다음 단계로 이어지는 여러 단계의 계산입니다
- 곧장 답하면 계산을 틀리거나 단계를 건너뛰기 쉽습니다
- 단계를 보여 주면 계산을 하나씩 확인할 수 있습니다
- 답이 어긋났을 때 어느 단계가 잘못됐는지 빠르게 짚어낼 수 있습니다

<!-- hint -->
이런 유형의 문제에서 핵심은 현재 상태를 먼저 계산하고, 변화 후 상태를 계산한 다음, 그 차이를 구하는 것입니다. 추론 단계를 예측할 때도 그 순서대로 계산을 하나씩 나열하세요.
<!-- hint -->
Zero-shot CoT는 "let's think step by step" 한 줄을 덧붙이는 것이 전부이며, 예시는 필요 없습니다. 이 기법으로 AI에게 추론을 설명하게 해 보세요.

### 레벨 2: Few-Shot CoT 프롬프트 설계하기

시나리오: AI가 코드의 시간 복잡도를 판단하고 그 근거를 설명하게 해야 합니다.

전체 추론 단계를 보여 주는 예시 2개(하나는 O(n), 하나는 O(n²))로 few-shot CoT 프롬프트를 설계하세요.

<!-- rubric -->
- 두 예시 코드 모두 구조가 명확하고 복잡도 판단이 정확하다
- 각 예시의 추론 단계가 완결되어 있다: 반복문 파악 → 각 층의 복잡도 계산 → 총 복잡도로 합산
- 추론 단계가 일관된 형식을 쓴다
- 예시가 서로 다른 유형을 포괄한다(단일 반복문 vs 중첩 반복문)
- 프롬프트가 작업과 출력 형식을 명시했다
<!-- answer -->
**Few-Shot CoT 프롬프트**:

````
코드의 시간 복잡도를 분석하고 추론 단계를 보여 줘.

예시 1:
코드:
```python
def find_max(arr):
    max_val = arr[0]
    for num in arr:
        if num > max_val:
            max_val = num
    return max_val
```

추론:
1. 반복문 구조 파악: 배열을 순회하는 for 반복문 하나
2. 반복 횟수: n개의 원소를 방문하며, 각 원소는 한 번씩 접근
3. 반복문 본문 연산: 비교와 대입, 둘 다 O(1) 상수 시간
4. 총 복잡도: O(n) × O(1) = O(n)

결론: 시간 복잡도는 O(n)입니다

---

예시 2:
코드:
```python
def find_duplicates(arr):
    duplicates = []
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            if arr[i] == arr[j]:
                duplicates.append(arr[i])
    return duplicates
```

추론:
1. 반복문 구조 파악: 중첩된 for 반복문 두 개
2. 바깥 반복문: n개의 원소를 순회
3. 안쪽 반복문: 각 i에 대해 (n-i-1)개의 원소를 순회
4. 총 반복 횟수: (n-1) + (n-2) + ... + 1 = n(n-1)/2 ≈ n²/2
5. 반복문 본문 연산: 비교와 append, 둘 다 O(1)
6. 총 복잡도: O(n²) × O(1) = O(n²)

결론: 시간 복잡도는 O(n²)입니다

---

이제 이 코드를 분석해:
코드:
```python
[코드 붙여넣기]
```

추론:
````

**이 프롬프트가 통하는 이유**:
1. **예시 간 대비가 뚜렷함**: O(n)과 O(n²)를 가르는 것은 반복문의 중첩 여부입니다
2. **추론 단계가 표준화됨**: 구조 파악 → 반복 횟수 세기 → 연산 분석 → 결론 도출
3. **형식이 일관됨**: 두 예시 모두 번호 매긴 단계라는 같은 형식을 씁니다
4. **각 단계를 충분히 설명함**: '이건 O(n)이다'에서 그치지 않고 왜 O(n)인지를 밝힙니다
5. **열린 채로 끝냄**: '추론:'이 AI에게 추론 과정을 출력하라는 신호를 줍니다

<!-- hint -->
Few-shot CoT의 핵심은 예시가 답만 주는 것이 아니라, 문제에서 답에 이르는 사고의 모든 단계를 보여 주는 것입니다. 사람에게 이 작업을 가르친다고 상상해 보세요. 어떻게 쪼개서 설명하겠습니까?
<!-- hint -->
추론 단계를 설계할 때는 각 단계가 반드시 필요한지(건너뛰면 이해가 불완전해지는지), 그리고 검증 가능한지(그 단계만 따로 확인할 수 있는지)를 확인하세요.
