# 第 03 课：Few-shot Learning：通过示例引导 AI

## 当文字描述不如示例清楚

你想让 AI 用特定的格式输出数据——比如"提取文章中的关键信息，按 JSON 格式输出"。你在 prompt 里写了半天 JSON 的字段名、数据类型、嵌套结构……AI 还是输出了一个跟你预期不一样的格式。

换个方式：别描述格式了，**直接给 AI 看 2-3 个标准示例**。它一看就明白你要什么样的输出，第一次就能输出正确格式。这就是 few-shot learning（少样本学习）的威力——示例比文字更清晰[^S11]。

## 什么是 Few-shot Learning

**Few-shot learning** 是一种 prompt 技术，通过在 prompt 中提供少量示例（通常 2-5 个）来引导 AI 理解你想要的模式[^S4][^S11]。AI 会从这些示例中学习输入输出的关系、格式、风格，然后应用到新的输入上。

对比三种方式：

- **Zero-shot**（零样本）：不给示例，只给指令[^S15]
- **One-shot**（单样本）：给 1 个示例
- **Few-shot**（少样本）：给 2-5 个示例[^S4]

### Zero-shot：只有指令

❌ **Zero-shot prompt**：
```
将下面的用户评论分类为"正面"、"负面"或"中性"。

评论：这个产品用起来还行，但价格有点贵。
分类：
```

AI 可能输出：
- "中性"（合理）
- "负面"（因为提到"贵"）
- "正面但有保留"（自己发明了类别）

没有示例，AI 只能根据自己的理解来判断边界情况。

### Few-shot：给出示例

✅ **Few-shot prompt**：
```
将用户评论分类为"正面"、"负面"或"中性"。

示例：

评论：这个产品质量很好，非常满意！
分类：正面

评论：完全不能用，浪费钱。
分类：负面

评论：功能还可以，但客服响应慢。
分类：中性

现在分类这条评论：

评论：这个产品用起来还行，但价格有点贵。
分类：
```

AI 看到示例后，理解了：
- "正面"是完全满意的情况
- "负面"是严重不满
- "中性"是有好有坏的混合评价
- 输出格式是单个词，不加解释

所以它会输出"中性"，因为这条评论跟第三个示例的模式一致。

## Few-shot 的工作原理

Few-shot learning 利用了大语言模型的**上下文学习**（in-context learning）能力[^S4]。模型不需要重新训练，只需要在当前对话中看到几个示例，就能推断出规律并应用。

模型从示例中学到三类信息：

1. **输入输出的映射关系**：什么样的输入对应什么样的输出
2. **输出的格式和风格**：是简短回答还是详细解释、是 JSON 还是纯文本
3. **边界情况的判断标准**：模糊情况应该怎么分类

**关键发现**：研究表明，示例的**格式**和**多样性**比示例的正确性更重要[^S4]。即使示例中的标签有一些错误，只要格式一致、覆盖了不同类型的输入，AI 仍然能学到有用的模式。

## 设计高质量示例的原则

不是随便给几个示例就行，示例的质量直接影响 AI 的输出[^S11]。

### 原则 1：至少 2 个，通常不超过 5 个

- **1 个示例**（one-shot）有时不够——AI 可能认为那是特例
- **2-3 个示例**通常足以让 AI 理解模式
- **4-5 个示例**用于更复杂的任务或边界情况多的任务
- **超过 5 个**收益递减，还会多占不少 token

从 2 个开始，如果效果不好再加到 3-4 个[^S11]。

### 原则 2：示例要有代表性和多样性

示例应该覆盖任务中可能出现的不同类型——也就是示例多样性[^S4]。

❌ **示例缺少多样性**：
```
示例 1：iPhone 15 Pro → 手机
示例 2：iPhone 14 → 手机
示例 3：iPhone 13 → 手机

现在分类：MacBook Pro
```

所有示例都是手机，AI 没见过其他电子产品的例子，可能不知道怎么处理。

✅ **示例有多样性**：
```
示例 1：iPhone 15 Pro → 手机
示例 2：MacBook Air → 笔记本电脑
示例 3：AirPods Pro → 耳机

现在分类：iPad Pro
```

覆盖了不同品类，AI 能学到更通用的分类逻辑。

### 原则 3：示例的格式要完全一致

格式一致性是 few-shot 成功的关键[^S4]。

❌ **格式不一致**：
```
示例 1：
输入：天气真好
输出：正面

示例 2：
"这个电影太无聊了" --> 负面情绪

示例 3：还行吧 → 中性
```

格式乱七八糟，AI 不知道该输出"正面"、"正面情绪"还是别的。

✅ **格式一致**：
```
示例 1：
输入：天气真好
输出：正面

示例 2：
输入：这个电影太无聊了
输出：负面

示例 3：
输入：还行吧
输出：中性
```

清晰统一，AI 知道输出应该是单个形容词。

### 原则 4：包含边界情况和易混淆的例子

如果任务有模糊地带，示例中要包含[^S11]。

**场景：判断代码注释是否有用**

❌ **只有明显的例子**：
```
示例 1：
代码：x = x + 1  # 加 1
判断：无用（注释只是重复代码）

示例 2：
代码：result = calculate_tax(income, deductions)  # 计算应纳税额
判断：有用（解释了业务含义）
```

✅ **包含边界情况**：
```
示例 1：
代码：x = x + 1  # 加 1
判断：无用（注释只是重复代码）

示例 2：
代码：result = calculate_tax(income, deductions)  # 计算应纳税额
判断：有用（解释了业务含义）

示例 3：
代码：time.sleep(2)  # 等待 API 限流重置
判断：有用（解释了为什么等待，不是显而易见的）

示例 4：
代码：users = users.filter(active=True)  # 筛选活跃用户
判断：无用（方法名已经很清楚了）
```

第 3、4 个示例帮助 AI 理解边界：不是所有"解释代码做什么"的注释都有用，关键是代码本身是否已经清楚表达了意图。

## 实战示例：用 Few-shot 提取结构化数据

任务场景最常见的场景是从非结构化文本中提取结构化数据。

### 任务：从招聘信息中提取关键字段

**Zero-shot 版本（效果不稳定）**：
```
从下面的招聘信息中提取：职位名称、薪资范围、工作地点、经验要求。
用 JSON 格式输出。

招聘信息：我们正在寻找一位资深 Python 开发工程师，坐标北京，3-5 年经验，月薪 20-30k。
```

AI 可能输出各种格式：
```json
{"职位": "Python开发", "薪资": "20k-30k", ...}
```
或者
```json
{"job": "资深 Python 开发工程师", "salary": "20-30k/月", ...}
```

字段名、格式、单位都不统一。

**Few-shot 版本（格式稳定）**：
```
从招聘信息中提取关键字段，按以下 JSON 格式输出。

示例 1：
输入：招聘前端工程师，上海，2-3年经验，年薪30-40万
输出：
{
  "position": "前端工程师",
  "location": "上海",
  "experience": "2-3年",
  "salary": "30-40万/年"
}

示例 2：
输入：急招 Java 后端，深圳南山，要求5年以上经验，月薪25k-35k
输出：
{
  "position": "Java 后端",
  "location": "深圳南山",
  "experience": "5年以上",
  "salary": "25-35k/月"
}

示例 3：
输入：数据分析师，远程，不限经验，时薪200-300元
输出：
{
  "position": "数据分析师",
  "location": "远程",
  "experience": "不限",
  "salary": "200-300元/小时"
}

现在处理这条：
输入：我们正在寻找一位资深 Python 开发工程师，坐标北京，3-5 年经验，月薪 20-30k。
输出：
```

示例覆盖了三种薪资单位（年薪、月薪、时薪）和三种工作地点类型（城市、城市+区、远程），AI 学到了：
- 字段名用英文
- 保留原文中的薪资单位
- 提取地点时保留详细信息
- "不限"也是一种有效的经验要求

## Few-shot 的常见陷阱

### 陷阱 1：示例太少，覆盖不全

只给 1 个示例，AI 看到的是个例，不是规律。

**解决**：至少 2 个，最好 3 个。

### 陷阱 2：示例之间格式不一致

一会儿用箭头 →，一会儿用冒号 :，一会儿分多行。

**解决**：确定一种格式，所有示例严格遵守。

### 陷阱 3：示例都是简单情况，没有边界案例

真实数据有噪音、有歧义、有缺失，示例只展示理想情况，AI 遇到边界案例就不知所措。

**解决**：至少 1 个示例应该包含边界情况（比如缺失某个字段、有歧义的表述）。

### 陷阱 4：用了太多示例

超过 5 个示例，收益很小，反而多耗 token，拉长响应时间。

**解决**：从 2-3 个开始，不够再加，很少需要超过 5 个。

## 何时使用 Few-shot

Few-shot 最适合这些场景：

✅ **格式转换任务**：非结构化文本 → JSON、Markdown、CSV
✅ **分类任务**：情感分析、主题分类、意图识别
✅ **风格模仿**：学习特定的写作风格、代码风格
✅ **复杂规则难以用文字描述**：比如"什么样的注释是无用的"

不适合的场景：

❌ **任务本身很简单**："把这段文字翻译成英文"，不需要示例
❌ **每个输入都很独特**：创意写作、头脑风暴，示例反而限制了发挥
❌ **需要外部知识**：问"2024 年世界杯冠军是谁"，示例帮不上忙

判断标准：如果你给一个人类同事演示 2-3 个例子后，他就能明白该怎么做，那就适合用 few-shot。

## 小结

Few-shot learning 通过 2-5 个示例让 AI 理解你想要的模式，比文字描述更清晰。高质量示例的标准是：数量适中（2-5 个）、有代表性和多样性、格式完全一致、包含边界情况。

Few-shot 最适合格式转换、分类、风格模仿等任务。设计示例时，从 2 个开始，确保覆盖不同类型的输入，所有示例用同一种格式。

### Level 1：设计高质量示例

任务：让 AI 将用户反馈分类为"功能请求"、"Bug 报告"、"使用疑问"三类。

请设计 3 个 few-shot 示例，覆盖不同情况并保持格式一致。

<!-- rubric -->
- 三个示例分别代表三种不同类别
- 示例包含了容易混淆的边界情况（如"功能不work"可能是 bug 也可能是不会用）
- 所有示例格式完全一致（相同的结构、相同的标记方式）
- 示例贴近真实用户反馈的表达方式（不是理想化的简短句子）
- 每个示例的分类理由清晰，能帮助 AI 理解判断标准
<!-- answer -->
**示例设计**：

```
将用户反馈分类为：功能请求 / Bug 报告 / 使用疑问

示例 1：
反馈：希望能支持批量导出数据到 Excel，现在只能一条条复制太麻烦了。
分类：功能请求

示例 2：
反馈：点击"保存"按钮后页面卡住不动，等了 5 分钟也没反应，刷新后发现数据没保存上。
分类：Bug 报告

示例 3：
反馈：我找不到在哪里修改账户邮箱，试了个人设置和账户管理都没看到这个选项。
分类：使用疑问

现在分类这条反馈：
反馈：[粘贴用户反馈]
分类：
```

**为什么这些示例有效**：
1. **多样性**：三个示例各不相同，覆盖了三种类别
2. **边界清晰**：
   - 示例 1 明确说"希望能"，是功能请求
   - 示例 2 描述了具体错误（卡住、没保存），是 bug
   - 示例 3 说"找不到"，是使用疑问而不是功能缺失
3. **格式一致**：都用"反馈：[内容] / 分类：[类别]"格式
4. **真实表达**：不是"我想要新功能"这种简单句，而是用户的真实表达方式

<!-- hint -->
设计示例时，先想：什么情况最容易分错？比如"找不到某功能"是使用问题还是功能缺失？用一个示例明确这个边界。
<!-- hint -->
检查你的三个示例是否格式完全一致：相同的字段顺序、相同的标点符号、相同的换行方式。AI 会严格模仿示例的格式。

### Level 2：优化现有 few-shot prompt

下面是一个效果不好的 few-shot prompt，请找出问题并改进：

```
提取产品评论中的优点和缺点，输出 JSON。

示例：
"质量不错" -> {"pros": ["quality"], "cons": []}
"太贵了，而且物流慢" -> {"pros": [], "cons": ["expensive", "slow delivery"]}

现在处理：[评论内容]
```

问题：AI 的输出不稳定，有时字段名是中文，有时优点用形容词（"good"）而不是具体点（"quality"）。

<!-- rubric -->
- 识别出至少 3 个导致输出不稳定的问题
- 改进后的示例格式完全一致且清晰
- 示例覆盖了复杂情况（有优点有缺点、多个优缺点）
- 明确了字段命名和内容风格的规范
- 增加了必要的说明或约束
<!-- answer -->
**问题识别**：
1. **示例太简单**：第一个示例只有一句话，没展示如何从复杂评论中提取多个点
2. **没有统一规范**：示例中"quality"、"expensive"的抽象程度不一致（一个是名词、一个是形容词）
3. **示例数量不够**：只有 2 个，不足以建立稳定模式
4. **缺少边界情况**：没有展示"既有优点又有缺点"的复杂情况

**改进后的 prompt**：

```
从产品评论中提取优点和缺点，输出 JSON 格式。

字段说明：
- pros：优点列表，用简短名词短语（如"物流快"、"包装好"），不用形容词（不要"好"、"不错"）
- cons：缺点列表，格式同上

示例 1：
输入：质量很好，做工精细，用了一周没问题。
输出：
{
  "pros": ["质量好", "做工精细", "稳定性好"],
  "cons": []
}

示例 2：
输入：价格偏高，而且物流等了一个星期才到，不过产品本身还不错。
输出：
{
  "pros": ["产品质量好"],
  "cons": ["价格高", "物流慢"]
}

示例 3：
输入：功能太少，只能做基本操作，高级功能都要付费才能用。
输出：
{
  "pros": [],
  "cons": ["功能少", "高级功能收费"]
}

现在处理：
输入：[评论内容]
输出：
```

**改进点**：
1. 增加了字段说明，明确了用"名词短语"而不是形容词
2. 三个示例覆盖了三种情况：只有优点、有优有缺、只有缺点
3. 示例更复杂，展示了如何从长句中提取多个点
4. 格式完全一致：都有"输入："和"输出："标记，JSON 缩进统一
5. 输出前有"输入："提示符，明确了任务的开始

<!-- hint -->
当 few-shot 效果不稳定时，首先检查：(1) 示例格式是否一致？(2) 示例是否太简单？(3) 是否覆盖了边界情况？
<!-- hint -->
如果 AI 输出的字段名或内容风格不稳定，在 prompt 开头加一段"字段说明"或"输出规范"，明确你要的格式。示例展示形式，规范说明标准。
