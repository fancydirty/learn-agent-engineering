# レッスン4: 思考の連鎖: AIに推論プロセスを見せる

> 学習目標:
> - 思考の連鎖（chain-of-thought）がどう機能し、なぜ有効かを理解する
> - "let's think step by step"でAIの推論を誘導する方法を学ぶ
> - どのタスクがCoTに適しているかを見極める
>
> 前提: [<< レッスン3: Few-Shot学習](./03-few-shot-learning.md) | 次: [レッスン5 >>](./05-debugging-prompts.md)

## AIが正しい答えを出すが、推論が間違っている場合

数学の文章題をAIに聞くと「42」と答えが返ってきた。確認すると答えは正しい。しかし似た問題に変えると答えが間違ってしまう。何が起きたのか？モデルが推測したか、たまたま正しい数字にたどり着いた壊れた推論パスを辿っただけかもしれない。

複数ステップの推論を必要とするタスク（数学の問題、論理パズル、複雑な分析）では、AIに推論ステップを示させる方が直接答えを求めるよりも信頼性が高い[^S5][^S10]。これが思考の連鎖（CoT）プロンプティングの核心的なアイデアである：結論を実際にチェックできる中間ステップに分解する。

## 思考の連鎖とは

**思考の連鎖（CoT）プロンプティング**は、最終的な答えを出す前にモデルに中間推論ステップを示させる技術である[^S5]。研究の言葉を借りれば、思考の連鎖プロンプティングは "enables complex reasoning capabilities through intermediate reasoning steps"（中間推論ステップを通じて複雑な推論能力を可能にする）[^S5]。直感はシンプルだ："Chain of Thought prompting encourages the model to think through the problem in a step-by-step manner, which is supposed to mimic how humans break down complex problems"（思考の連鎖プロンプティングは、人間が複雑な問題をどう分解するかを模倣するように、モデルに段階的に問題を考え抜かせる）[^S10]。数学の問題を解くために紙に式と中間結果を書き出すのと同じことだ。

2つのアプローチを比較してみよう：

### 直接答える（エラーが起きやすい）

❌ **CoTなし**:
```
問題: あるコーヒーショップは朝に23杯、正午に17杯、午後に朝の2倍の量のコーヒーを売った。その日全体で何杯売ったか？

答え:
```

AIはこう出力するかもしれない：
```
86杯
```

答えが間違っていても、どのステップがずれたのか分からない。

### 推論ステップを示す（より信頼できる）

✅ **CoTあり**:
```
問題: あるコーヒーショップは朝に23杯、正午に17杯、午後に朝の2倍の量のコーヒーを売った。その日全体で何杯売ったか？

Let's think step by step:
```

AIの出力：
```
Let's think step by step:

1. 朝の売上: 23杯
2. 正午の売上: 17杯
3. 午後は朝の2倍: 23 × 2 = 46杯
4. 1日の合計: 23 + 17 + 46 = 86杯

答え: 86杯
```

すべてのステップが可視化されているので、1つが間違っていてもすぐに見つけてプロンプトを修正できる。

研究によると、複数ステップの推論を含むタスクでは、CoTが精度を大幅に向上させる[^S5]。一部のタスクでは、CoTと実例付きデモンストレーションを組み合わせることで、精度がさらに最大28.2%向上する[^S10]。

## CoTを使う2つの方法

### 方法1: ゼロショットCoT（最もシンプル）

プロンプトの最後に1行追加するだけ："**let's think step by step**"（段階的に考えよう）[^S5][^S10]。

```
問題: 5人の作業員が5日かかってプロジェクトを終えるとき、10人の作業員なら何日かかるか？

Let's think step by step:
```

この1行だけでモデルの段階的推論モードが発動する。例を提供する必要はなく、モデルが自分で問題を分解する。

### 方法2: Few-Shot CoT（より制御可能）

完全な推論プロセスを含む1～2つの例を与える[^S5][^S10]。

```
例:
問題: 車が時速60kmで走る。3時間でどれだけ進むか？
推論:
- 速度 = 60 km/h
- 時間 = 3時間
- 距離 = 速度 × 時間 = 60 × 3 = 180 km
答え: 180 km

では、この問題を解いてください:
問題: 車が時速80kmで2.5時間走り、その後時速60kmでさらに1時間走る。合計でどれだけ進むか？
推論:
```

例が推論フォーマットとステップの詳細度を示し、モデルがそのスタイルを真似る。

## どのタスクがCoTに適しているか

CoTは複数ステップの推論を必要とするタスクに最適である[^S10]：

✅ **数学と論理推論**
- 文章題
- 比率と比例の計算
- 複数ステップの式の導出

✅ **因果分析**
- 「なぜXがYを引き起こすのか？」
- 「このバグの根本原因は何か？」

✅ **計画と意思決定**
- 「AとB、どちらを先にやるべきか？」
- 「このアプローチの長所と短所は？」

✅ **コードデバッグ**
- 「なぜこのコードが失敗するのか？」
- 「どのステップがパフォーマンスのボトルネックか？」

適さない場面：

❌ **単純な事実検索**: 「Pythonはいつ最初にリリースされたか？」— 推論不要
❌ **創作**: 詩、物語 — 推論ステップが創造的な流れを壊す
❌ **フォーマット変換**: JSON → CSV — 機械的な操作、推論不要

## 実例：CoTで問題を分析する

### シナリオ1: コードパフォーマンス分析

**CoTなし（信頼できない結論）**:
````
このコードにパフォーマンスの問題があるか？

```python
def find_duplicates(items):
    duplicates = []
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j] and items[i] not in duplicates:
                duplicates.append(items[i])
    return duplicates
```

答え: はい、パフォーマンスの問題があります
````

結論だけで、理由がない。

**CoTあり（明確な推論）**:
````
このコードのパフォーマンス問題を分析してください。段階的に説明してください:
1. ループ構造を特定する
2. 時間計算量を計算する
3. 具体的なボトルネックを指摘する
4. 最適化を提案する

```python
def find_duplicates(items):
    duplicates = []
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j] and items[i] not in duplicates:
                duplicates.append(items[i])
    return duplicates
```
````

AIが示す：
```
パフォーマンス分析:

1. ループ構造:
   - 外側のループ: 各要素を反復、O(n)
   - 内側のループ: 各要素について残りの要素を反復、O(n)
   - 全体: ネストされたループ、O(n²)

2. 時間計算量:
   - メインループ: O(n²)
   - `items[i] not in duplicates`チェック: 最悪ケースでO(m)、mはこれまで見つかった重複の数
   - 合計計算量: O(n² × m)

3. パフォーマンスのボトルネック:
   - ネストされたループが大きな入力（n > 1000）で非常に遅くなる
   - リストに対する`not in`の線形スキャンがさらに遅くする

4. 最適化:
   - リストの代わりにsetを使って重複を保存し、チェックをO(m)からO(1)に削減
   - またはCounterを使ってすべての2回以上出現する要素を1回のパスで見つけ、O(n)に削減
```

すべての推論ステップがチェック可能なので、1つが間違っていてもすぐに分かる。

### シナリオ2: 論理パズル

**問題**:
```
3人 — A、B、C — がコンテストに参加する。分かっていること:
- Aは1位ではない
- Bは最下位ではない
- Cは1位でも最下位でもない

順位はどうなるか？

Let's reason step by step:
```

**AIの出力**:
```
Let's reason step by step:

1. Cの条件から始める:
   - Cは1位でも最下位でもない
   - したがってCは2位でなければならない

2. AとBを固定する:
   - Aは1位ではない
   - Bは最下位ではない
   - Cはすでに2位なので、1位と3位がAとBに残る

3. 残りの順位を割り当てる:
   - Aは1位ではないので、Aは3位
   - Bは最下位（3位）ではないので、Bは1位

答え: B 1位、C 2位、A 3位
```

この段階的な消去法を示すことで、論理が完璧かどうかをチェックしやすくなる。

## よくあるCoTパターン

### パターン1: 問題の分解

複雑な問題をいくつかのサブ問題に分解する。

```
問題: あるソフトウェアプロジェクトには5人のエンジニアがいて、各自1日6時間働き、120人日の作業が必要。8人のエンジニアに拡大すると、何日早く完了できるか？

Let's compute step by step:
1. 現在の体制で何日かかるか？
2. 人を追加した後は何日か？
3. 何日早くなるか？
```

### パターン2: 仮説検証

仮説をリストアップし、1つずつチェックする。

```
このコードが"TypeError: unsupported operand type(s)"をスローする。考えられる原因は？

Let's check the possible causes one by one:
1. 演算子の両側の変数の型をチェックする
2. 演算にNone値が関与していないかチェックする
3. 文字列と数値が混在していないかチェックする
```

### パターン3: 両面から議論

賛成と反対の理由をリストアップし、結論を出す。

```
マイクロサービスアーキテクチャとモノリスのどちらを使うべきか？

Let's analyze it from two angles:

マイクロサービスの理由:
1. ...
2. ...

モノリスの理由:
1. ...
2. ...

総合判断:
現在のチームサイズとプロジェクトの複雑さに基づき、...を推奨します
```

## CoTの限界

CoTは万能薬ではない。いくつかの限界がある：

**1. 長さと時間が増える**

推論ステップを示すと出力が長くなり、より多くのトークンを消費し、応答時間が長くなる。

**価値がある場合**: 複雑なタスクでは、精度を得るために2～3倍のトークンを使うのは良いトレードオフ。
**価値がない場合**: 単純なタスク（「今日は何曜日か」）では、推論ステップは純粋な無駄。

**2. 推論ステップ自体が間違っている可能性がある**

AIが示すステップは合理的に見えても、論理に穴がある可能性がある。推論が正しいかどうかを依然としてチェックする必要がある。

CoTの価値は、エラーを可視化することだ。AIが直接答える場合、エラーはブラックボックスに隠れる。ステップが示されると、エラーはあるステップで表面化し、見つけて修正しやすくなる。

**3. 直感に頼るタスクには適さない**

一部のタスク（創作、芸術の評価）は全体的な感覚に依存しており、ステップに強制すると全体が壊れる。

## まとめ

思考の連鎖プロンプティングは、AIに直接答えにジャンプするのではなく推論ステップを示させる。プロンプトに "let's think step by step" を追加するか、推論を含む例を提供することで、複数ステップの推論タスクでの精度を大幅に向上させることができる。

CoTは数学推論、論理分析、因果推論、複雑な意思決定 — 複数の思考ステップを必要とするすべてに適している。推論を可視化してチェック可能にする。出力の長さは増えるが、複雑なタスクでは見返りがコストをはるかに上回る。

次のレッスンでは、プロンプトをデバッグして改善する方法を扱う：AIの出力が期待と一致しないとき、どのように体系的に問題を見つけて修正するか。

## 💻 演習

### レベル1: ゼロショットCoTを適用する

"let's think step by step" 技術を使って、以下の問題をAIに解かせる：

**問題**: あるチームには8人がいて、各自1日6時間働く。プロジェクトには240人時間の作業が必要。チームが12人に成長すると、何日早く完了できるか？

完全なプロンプト（"let's think step by step" を含む）を書き、AIがどの中間ステップを示すか予測しなさい。

<!-- rubric -->
- プロンプトに "let's think step by step" または類似のキューが含まれている
- 問題文が明確で完全
- 予測された推論ステップが論理的に正しい
- 推論ステップが重要な計算をカバーしている（現在の体制で必要な日数、新しい体制で必要な日数、差分）
- この問題がCoTに適している理由を特定している
<!-- answer -->
**プロンプト**:
```
あるチームには8人がいて、各自1日6時間働く。プロジェクトには240人時間の作業が必要。チームが12人に成長すると、何日早く完了できるか？

Let's think step by step:
```

**予測される推論ステップ**:
```
Let's think step by step:

1. 現在のチームの1日の出力を計算:
   - 8人 × 6時間/人/日 = 48人時間/日

2. 現在の体制で必要な日数を計算:
   - 240人時間 ÷ 48人時間/日 = 5日

3. 拡大したチームの1日の出力を計算:
   - 12人 × 6時間/人/日 = 72人時間/日

4. 新しい体制で必要な日数を計算:
   - 240人時間 ÷ 72人時間/日 = 3.33日（約3.4日）

5. 節約できる日数を計算:
   - 5日 − 3.33日 = 1.67日（約1.7日、つまり1日と17時間）

答え: プロジェクトは約1.7日早く完了できる。
```

**CoTに適している理由**:
- 各ステップが次に渡される複数ステップの計算
- 直接答えると誤算やステップの飛ばしが起きやすい
- ステップを示すことで各計算をチェックできる
- 答えがずれていても、どのステップが間違ったか素早く特定できる

<!-- hint -->
この種の問題の鍵：まず現在の状態を計算し、次に変更後の状態、そして差分。推論ステップを予測するときは、各計算をその順序でリストアップする。
<!-- hint -->
ゼロショットCoTは1行追加するだけ、"let's think step by step" — 例は不要。この技術を使ってAIに推論を説明させてみよう。

### レベル2: Few-Shot CoTプロンプトを設計する

シナリオ: コードの時間計算量を判断し、推論を説明するAIが必要。

完全な推論ステップを示す2つの例（1つはO(n)、1つはO(n²)）を含むFew-Shot CoTプロンプトを設計しなさい。

<!-- rubric -->
- 両方の例のコードスニペットが明確な構造を持ち、計算量の判断が正しい
- 各例の推論ステップが完全：ループを特定 → 各レベルの計算量を計算 → 合計計算量に結合
- 推論ステップが一貫したフォーマットを使用
- 例が異なるタイプをカバー（単一ループ vs ネストされたループ）
- プロンプトがタスクと出力フォーマットを述べている
<!-- answer -->
**Few-Shot CoTプロンプト**:

````
コードの時間計算量を分析し、推論ステップを示してください。

例1:
コード:
```python
def find_max(arr):
    max_val = arr[0]
    for num in arr:
        if num > max_val:
            max_val = num
    return max_val
```

推論:
1. ループ構造を特定: 配列に対する1つのforループ
2. 反復回数: n要素を訪問、各要素に1回アクセス
3. ループ本体の操作: 比較と代入、両方ともO(1)定数時間
4. 合計計算量: O(n) × O(1) = O(n)

結論: 時間計算量はO(n)

---

例2:
コード:
```python
def find_duplicates(arr):
    duplicates = []
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            if arr[i] == arr[j]:
                duplicates.append(arr[i])
    return duplicates
```

推論:
1. ループ構造を特定: 2つのネストされたforループ
2. 外側のループ: n要素を反復
3. 内側のループ: 各iについて、(n-i-1)要素を反復
4. 合計反復回数: (n-1) + (n-2) + ... + 1 = n(n-1)/2 ≈ n²/2
5. ループ本体の操作: 比較とappend、両方ともO(1)
6. 合計計算量: O(n²) × O(1) = O(n²)

結論: 時間計算量はO(n²)

---

では、このコードを分析してください:
コード:
```python
[コードを貼り付け]
```

推論:
````

**このプロンプトが機能する理由**:
1. **例間の明確な対比**: O(n)とO(n²)の違いはループがネストされているかどうか
2. **標準化された推論ステップ**: 構造を特定 → 反復を数える → 操作を分析 → 結論に到達
3. **一貫したフォーマット**: 両方の例が同じ番号付きステップフォーマットを使用
4. **各ステップが十分に説明されている**: ただ「これはO(n)」ではなく、なぜO(n)なのか
