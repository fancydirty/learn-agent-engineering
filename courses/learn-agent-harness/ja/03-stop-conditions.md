# レッスン3: 停止条件: エージェントはいつ手を引くべきか

> 学習目標:
> - モデルが自分で `end_turn` を返すのに任せるだけではループを終わらせるのに足りない理由を説明し、その緊張をはっきり言う: モデルを信頼しなければならないが、そのモデルは多数のターンにわたって動き続けうる
> - 骨組みのループに最大ターン数のハードなゲートを足し、そのカウンタがループの外にあるときだけ機能する理由を説明する
> - ハードストップ（上限での強制停止）とソフトストップ / サスペンド（人間を待つ、再開可能）を区別し、あるエージェントが止まらなければならない条件を列挙する
>
> 前提: レッスン2を読み、`stop_reason` が駆動する `while` ループを書けて、`end_turn` が返ってきたときにループが自然に終わることを知っていること | 前: [レッスン2 <<](./02-the-core-loop.md) | 次: [レッスン4 >>](./04-loop-failure-modes.md)

## モデルが自分で切り上げるのを当てにしない

レッスン2の骨組みのループが止まる理由はただ1つです: あるラウンドでモデルがツールを要求しなくなり、`stop_reason` が `tool_use` から `end_turn` に変わり、`while` 条件が偽になって、ループが自然に終わる[^S2]。言い換えれば、もう1回転するかどうかの判断は、完全にモデルに委ねられています——モデルが「言うことは言った」と告げたときにループが止まるわけです。

たいていの場合それでうまくいきますが、誰が判断しているのかははっきりさせておきましょう。エージェントとは定義上、モデルが自身のプロセスと自身のツールの使い方を動的に指揮するシステムであり[^S1]、いつ切り上げるかもその一部です。自律性こそがエージェントを有用にしているものですが、同じコインの裏側はこれです: "The autonomous nature of agents means higher costs, and the potential for compounding errors."（エージェントの自律的な性質は、より高いコストと、エラーが積み重なる可能性を意味する）[^S1] そしてここで最も重要な一文: "The LLM will potentially operate for many turns, and you must have some level of trust in its decision-making."（LLMは多数のターンにわたって動作する可能性があり、その意思決定にある程度の信頼を置かなければならない）[^S1]

腰を据えて考えるべき言葉は*信頼*です。信頼は、モデルを無監督で放置することと同じではありません。モデルがどこかのステップで詰まったり、ツールが返してきたものに引きずられて脱線したりして、そのまま `end_turn` を返してこなくなったら、`stop_reason` しか見ていないループは、あなたの代わりに焦れてくれたりはしません。ラウンドを重ねながら、モデルに付き合って回り続けます——あなたが書いた `while` 条件のどこにも「もう十分に回った」と書かれていないからです。ですから、モデルによる自己終了だけでは足りません。モデルの気分を待たない、ホストが決める停止条件が必要です。

## まずはループにハードなゲートを: 最大ターン数

すべての中で最も基本的な停止条件は、Anthropicのエンジニアリングガイダンスにそのまま名指しされています: "it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control."（制御を保つために、停止条件（最大反復回数など）を含めることもよくある）[^S1] コードに翻訳すれば、ループが何回まで回ってよいかの上限です。

レッスン2の骨組みに対して、変更はわずかです:

```javascript
// tools は毎ラウンド同行させるツール定義の一覧
const MAX_TURNS = 10;              // ハードなゲート: ループは最大10回まで回してよい
const messages = [{ role: "user", content: userInput }];
let turns = 0;                     // ラウンドをまたいで積み上げられるよう、カウンタはループの外に置く

let response = await callModel({ tools, messages });

while (response.stop_reason === "tool_use") {
  // このラウンドを始める前にゲートを確認する: 上限なら、ハードに停止してこれ以上リクエストを送らない
  if (turns >= MAX_TURNS) {
    return { stopped: "max_turns", turns, last: response };
  }
  turns += 1;

  messages.push({ role: "assistant", content: response.content });

  const toolUseBlocks = response.content.filter((b) => b.type === "tool_use");
  const toolResults = await Promise.all(
    toolUseBlocks.map(async (block) => ({
      type: "tool_result",
      tool_use_id: block.id,
      content: await executeTool(block.name, block.input),
    }))
  );
  messages.push({ role: "user", content: toolResults });

  response = await callModel({ tools, messages });
}

// ループの出口は2つ: 上の早期 return か、stop_reason が tool_use でなくなるか
return { stopped: "end_turn", turns, last: response };
```

ここで重みを担っているのは2つです。第一に、`let turns = 0` はループの**外**で宣言されています。ラウンドをまたいで生き残り、1回ずつ足し上げていく必要があります。そうでなければゲートは何周したのかを知りようがありません。これをループ本体の中に移すと、レベル2の演習が解体するまさにその罠になります。第二に、ゲートはモデルが**なぜ**まだツールを要求しているのかを気にしません——詰まっている、堂々巡りしている、ツールの出力に引きずられて脱線している、どれであろうと問いません。周回数が上限に達したら、ホストは停止し、これ以上リクエストを送らず、制御を自分の側に取り戻します。

これが**ハードストップ**です: 境界で無条件に停止し、ループはそこで終わりです。これは、モデルが「終わった」と判断する `end_turn` によるソフトな終了とは別物です——一方はあなたが設定した上限、もう一方はモデル自身の判断です。`MAX_TURNS` をどれだけ大きくすべきかに定石はなく、そのタスクにおおよそ何ラウンド必要かに依存することに注意してください。ここでの10は仮置きの値です。大事なのは、ゲートが存在し、暴走したループを実際に止められることです。

## ハードストップの先にあるもう1種類: 人間を待つために止まる

最大ターン数のようなゲートには共通する性質があります: そこに達したら道は終わりで、ループは終了し、自動では続きません。しかし停止条件はそれだけではありません。同じ記事はもう1つを名指ししています: "Agents can then pause for human feedback at checkpoints or when encountering blockers."（そのうえでエージェントは、チェックポイントで、あるいは障害にぶつかったときに、人間のフィードバックを待って一時停止できる）[^S1] これはハードストップとは別の生き物であり、切り分けておく価値があります:

- **ハードストップ**: 上限で停止し、ループは完全に終了、何も自動的には続きません。最大ターン数も予算の使い切りもここに属します。**終端状態**です。
- **ソフトストップ / サスペンド**: ループがチェックポイントで意図的に停止し、制御を人間に渡し、その人が答えたらまさにその地点から再開できます。終わりではなく、**再開可能な一時停止**です。

コードの上では、違いは何を返すかに現れます。ハードストップは最終的な結果を返します——ここで終わりました、と。ソフトストップは状態を保存しなければなりません: 再開できる形で現場のスナップショットを返し、現在の `messages` と、止まった時点で保留になっているアクションを一緒に引き渡します。そうすれば、人間が対処し終えたあと、そのスナップショットだけで続きを進められます:

```javascript
while (response.stop_reason === "tool_use") {
  if (turns >= MAX_TURNS) {
    return { stopped: "max_turns", turns, last: response };   // ハードストップ: 終端
  }

  const block = response.content.find((b) => b.type === "tool_use");
  if (needsHumanApproval(block)) {
    // ソフトストップ / サスペンド: 終わりではなく一時停止。ここから再開できるよう現場ごと引き渡す
    return { paused: "awaiting_human", pending: block, messages, turns };
  }

  // ...それ以外は通常どおりツールを実行し、履歴に追記し、次のリクエストを送る
}
```

ソフトストップの典型的なケースは、モデルの次の一手が取り返しのつかないもの——データベースを落とす、メールを一斉送信する、注文を確定する——であり、実行される前に人間に見てほしい場合か、あるいはモデル自身が詰まっていて追加の情報が必要だと報告してくる場合です。今はハードストップとソフトストップの線を引ければ十分です。`needsHumanApproval` が実際にどう判断するのか、そして人間が答えたあとループがそのスナップショットからどう再開するのかは、人間をループに残すことを扱うレッスン5の主題です。

## フレームワーク: まず「どんな条件で止まらなければならないか」を問う

ハードストップとソフトストップが手元にあると、エージェントの設計に便利な初手ができます。ループを書き始める前に、1つの問いに答えておくのです: **これはどんな条件で止まらなければならないか？** 答えを書き出してみると、たいていは次の4つに落ち着きます:

1. **タスクが完了した**——モデルが `end_turn` を返す。4つの中で最もソフトで、モデルが判断するものであり、本当に完了したのか、途中で諦めたのかは、あなたが確かめる必要があります。
2. **ターン数の上限**——ハードストップ。上で見た `MAX_TURNS` のゲートであり、ループが走り出して自分を御せなくなる最悪ケースを捕まえます。
3. **人間の判断が必要な障害**——ソフトストップ / サスペンドであり、人間のフィードバックを待って一時停止します[^S1]。取り返しのつかない操作か、モデルが明示的に行き詰まりを報告したことがきっかけになります。
4. **予算の使い切り**——ハードストップ。トークン、支出、経過時間のうち、最初に上限に達したものがループを止めます。詳細（どう数えるか、どこに計測を入れるか）はレッスン4に譲ります。

この4つを並べると、見えてくるものがあります: 停止の判断は、すべてがモデルにあるわけではありません。1番はモデルのもの、2番と4番はホストのもの（モデルがどう考えていようと、その印で止まります）、そして3番は共有です。レッスン2のあの骨組みのループは1番だけを実装し、残り3つを落としていました——このレッスンでは最も基本的なハードなゲートである2番を足し、3番と4番はそれぞれレッスン5とレッスン4で入ってきます。

このフレームワークの価値は、4項目を暗記することではありません。習慣を作ることです: ループを書く前に「止まらなければならない」条件を明示的に数え上げる。どうせモデルが止まるだろうという既定の前提の下に埋もれさせておくのではなく。

## 停止条件は安価な保険であって、過剰設計ではない

こうしたゲートは単純なループを複雑にする、と不満を漏らす人もいるかもしれません。そこでAnthropicが繰り返し立ち返る原則が出てきます: "you should consider adding complexity only when it demonstrably improves outcomes."（結果が明らかに改善される場合にのみ、複雑さを追加することを検討すべきである）[^S1] この一文はたいてい、凝った仕掛けを積み上げるのを思いとどまらせるために引用されますが、停止条件については逆方向を指します——通してよい、と言うのです。

計算してみれば明らかです。最大ターン数のカウンタは、ループの外の宣言1つと中の比較1つ、コードにして数行です。それが防ぐもの——止まらずに回り続けるループ、制御を離れて上っていくコスト、操作されたり壊れたりした出力に基づいて取られる取り返しのつかないアクション——のほうが、はるかに高くつきます。エージェントの自律性はすでに、より高いコストと積み重なるエラーの可能性を伴っており[^S1]、停止条件はそのリスクをまっすぐ狙った最も安価なブレーキです。

ですから停止条件は、結果が明らかに改善される場合にのみ足すべき類いの複雑さ[^S1]ではありません——その基準を最初から満たしています。最悪ケースの境界を「無制限」から「有制限」に圧縮することは、それ自体が検証可能な結果の改善です。これは自律的なループを「走らせてみようと思える」ものにする最も基本的な制御であって、飾りの追加物ではありません。

### レベル1: エージェントの停止条件を数え上げる

あなたは「CIを自動で直す」エージェントを設計しています。失敗したパイプラインを引き取り、次のツールを持っています: `read_logs`（ログを読む）、`edit_file`（コードを変更する）、`run_tests`（テストを実行する）、`push`（リモートにプッシュし、新しいCIの実行をトリガーする）。目標はテストをグリーンにすることです。これについて次に答えてください:

1. このエージェントが止まらなければならない条件を、少なくとも4つ挙げてください。
2. それぞれについて、**ハードストップ**か**ソフトストップ / サスペンド**かを示し、停止の判断がモデルのものか、ホストのものか、その両方かを述べてください。
3. `push`（リモートにプッシュし、他の人にも見えるCIの実行をトリガーする）を、人間の承認を待つソフトストップとして設計しますか。理由を1行で述べてください。

<!-- rubric -->
- 停止条件が少なくとも4つ挙げられており、4つのカテゴリ（タスク完了 / ターン数の上限 / 人間の判断が必要な障害 / 予算の使い切り）の大部分をカバーしている
- 各条件がハードかソフトかに正しく分類され、誰が判断するかについて妥当な判定が付いている（タスク完了→モデル、ターン数と予算→ホスト、障害系→共有）
- `push` について理由付きの明確な立場が示されている: 外部から見え、比較的コストの高いアクションであり、承認を待つソフトストップに向いていると認識している

<!-- answer -->
1. 4つ（以上）の停止条件:
   - **テストがグリーン / タスク完了**——モデルが直ったと判断し、`end_turn` を返す。
   - **ターン数の上限**——たとえば「コードを直す→テストを実行する」を何ラウンド繰り返してもグリーンにならず、`MAX_TURNS` に達して強制的に停止する。
   - **リモートへのプッシュ（`push`）の直前**——停止して承認を待つ。このステップは外部から見え、他の人にも見えるCIの実行をトリガーするからです。
   - **予算の使い切り**——累積のトークン / 支出 / 経過時間が上限に達して停止する（詳細はレッスン4）。
   - （任意）**モデルが障害を報告する**——たとえば自分では取得できない権限や認証情報が必要だと判断し、人間のためにサスペンドする。
2. 分類と判断の主体:
   - タスク完了: **ソフトな終了**、判断は**モデル**（`end_turn` を返す）。
   - ターン数の上限: **ハードストップ**、判断は**ホスト**（モデルが何を望もうと、その印で止まる）。
   - 予算の使い切り: **ハードストップ**、判断は**ホスト**。
   - `push` 前の承認と、モデルによる障害の報告: **ソフトストップ / サスペンド**、**共有**（ホストがチェックポイントを置き、人間が続けるかどうかを決める）。
3. はい。`push` は変更をリモートに送り、他の人にも見えるCIの実行を起動します——外部から見え、巻き戻すのにコストがかかるアクションであり、ソフトストップに向いています: プッシュの前でループを止め、人間が変更を見て通すかどうかを決める。モデルに最後まで自分でプッシュさせるのではなく。

<!-- hint -->
本文の4つに戻ってください: タスク完了、ターン数の上限、人間の判断が必要な障害、予算の使い切り。それぞれをこのCI修復のシナリオに当てはめ、どの具体的なステップに対応するかを見てください。

<!-- hint -->
ハードストップとソフトストップを見分けるには、1つの問いを立ててください: 止まったあと、中断した地点から続きを進められるか？ 続けられず、そこで終わりならハードストップです。人間が答えたら再開できるならソフトストップです。

### レベル2: なぜこの最大ターン数のゲートは何も捕まえなかったのか

同僚がループに最大ターン数の安全装置を付けたいと考え、以下のバージョンを書きました。ツール呼び出しが1〜2回で済むタスクで試したところ「問題なさそう」に見えました。しかし、モデルが `end_turn` を返さずに同じツールを何度も呼び続ける状態に陥ったとき、このゲートは何も捕まえられず、ループは暴走し続けました。根本原因を突き止めて修正してください。

```javascript
async function runAgent(userInput, tools) {
  const MAX_TURNS = 10;
  const messages = [{ role: "user", content: userInput }];
  let response = await callModel({ tools, messages });

  while (response.stop_reason === "tool_use") {
    let turns = 0;                       // 暴走したループを捕まえるつもり
    if (turns >= MAX_TURNS) {
      return { stopped: "max_turns", response };
    }
    turns += 1;

    const block = response.content.find((b) => b.type === "tool_use");
    const result = await executeTool(block.name, block.input);
    messages.push({ role: "assistant", content: response.content });
    messages.push({
      role: "user",
      content: [{ type: "tool_result", tool_use_id: block.id, content: result }],
    });

    response = await callModel({ tools, messages });
  }
  return response;
}
```

<!-- rubric -->
- 根本原因を正確に指摘している: `let turns = 0` がループ本体の中で宣言されており、毎ラウンド0にリセットされ、`turns >= MAX_TURNS` は決して真にならず、ゲートはデッドコードである
- これがレッスン2の無限ループとどう違うかを説明している: ここでは `response` は再代入されており、モデル自身の `end_turn` でループは止まりうる。だからこそ「短いタスクでは問題なさそうに見える」のだが、暴走を捕まえるはずの最大ターン数の歯止めは一度も働いていない
- 修正を示している: `let turns = 0;` を `while` の上に移す（カウンタの状態はラウンドをまたいで積み上がる必要がある）。`turns += 1` はループ本体の中に残す

<!-- answer -->
根本原因: **カウンタ `turns` がループ本体の中で宣言されていること。** `let turns = 0` は毎ラウンドの先頭で再び実行されるので、`turns` は1周ごとに0にリセットされます。`turns += 1` で1になり、次のラウンドでまた0に戻るので、判定 `turns >= MAX_TURNS`（10）が真になることはありえません。ゲートは最初から最後までデッドコードです——停止条件が機能するのは、その状態がラウンドをまたいで積み上がるからであり、`let` 宣言のスコープはその波括弧の対で終わるので、持ち越せません。

なぜ「短いタスクでは問題なさそうに見える」のか: このコードはレッスン2の無限ループとは違います。あちらのバグは `response` の再代入を忘れていたことで、ループはそもそも抜けられませんでした。ここでは `response` は再代入されており、どこかのラウンドでモデルが `end_turn` を返せばループは正常に止まります。ですからモデルが行儀よく1〜2ラウンドで切り上げている限り、ゲートが不活性であることに気づきません——単に出番がなかっただけです。しかしモデルが `end_turn` を返すことを拒み、回り始めた瞬間、あると思っていた安全装置は最初から配線されていなかったことがわかり、ループは変わらず暴走します。

修正——カウンタをループの外に移し、ラウンドをまたいで積み上がるようにします:

```javascript
async function runAgent(userInput, tools) {
  const MAX_TURNS = 10;
  const messages = [{ role: "user", content: userInput }];
  let turns = 0;                         // 外に移動: 何かを止めるには、状態がラウンドをまたいで生きている必要がある
  let response = await callModel({ tools, messages });

  while (response.stop_reason === "tool_use") {
    if (turns >= MAX_TURNS) {
      return { stopped: "max_turns", response };
    }
    turns += 1;

    const block = response.content.find((b) => b.type === "tool_use");
    const result = await executeTool(block.name, block.input);
    messages.push({ role: "assistant", content: response.content });
    messages.push({
      role: "user",
      content: [{ type: "tool_result", tool_use_id: block.id, content: result }],
    });

    response = await callModel({ tools, messages });
  }
  return response;
}
```

<!-- hint -->
停止条件がループを押しとどめられるのは、その状態がラウンドをまたいで積み上がるときだけです。`turns` を宣言している行を見てください: 2ラウンド目の先頭で、1ラウンド目が足した分をまだ覚えているでしょうか。

<!-- hint -->
`let` で宣言された変数は、それが置かれた波括弧の対にスコープが限られます。今 `turns` は `while` の本体の中にいるので、毎ラウンド新品の `let turns = 0` が実行されます。

## まとめ

- ループは `end_turn` で自然に終わりますが、それはモデル自身の判断です。その意思決定にはある程度の信頼を置くことしかできず、モデルは多数のターンにわたって動作しうるので、モデルの自己終了だけに頼るのでは足りません[^S1]
- 最も基本的なハードなゲートは最大ターン数です: 制御を保つために最大反復回数のような明示的な停止条件を含めることは、よくある方法です[^S1]。カウンタはラウンドをまたいで積み上がるようループの**外**に置く必要があり、本体の中に移すと何も止めないデッドコードになります
- ハードストップの先にはソフトストップ / サスペンドがあります: チェックポイントで、あるいは障害にぶつかったときに、人間のフィードバックを待って一時停止するものです[^S1]——終端状態ではなく、現場のスナップショットから続きを進められる再開可能な一時停止です
- エージェントを設計するときは、まずどんな条件で止まらなければならないかを問うてください: タスク完了（`end_turn`、モデルの判断）、ターン数の上限（ハードストップ、ホストの判断）、人間の判断が必要な障害（ソフトストップ、共有）、予算の使い切り（ハードストップ、レッスン4で扱います）
- 停止条件は見返りの大きい安価な制御です: 自律性はすでにより高いコストと積み重なるエラーをもたらしており[^S1]、最大ターン数のゲートはまさにその最悪ケースを捕まえます。結果が明らかに改善される場合にのみ複雑さを足すという原則[^S1]に照らしても、これは最初から基準を満たしています——無制限を有制限に圧縮することは、検証可能な改善です
