> 学習目標:

## 最初の4つのレッスンはループ自体を管理した。このレッスンは人を入れる

ここまでで、あなたの手の中のループは走り、止まり、その下にフォールバックを備えています。レッスン3が明示的な停止条件を与え、レッスン4がデッドループと空回りを見分けて予算を燃やし尽くさない方法を教えました。これらの制御には共通点があります: 最初から最後まで、ハーネスがループと1対1で格闘しているだけで、誰も割って入っていません。

現実のエージェントが、誰にも見られずに最後まで走り切ることはめったにありません。タスクの途中で、全部を取りやめたくなるかもしれません — 方向がまるきり間違っているので、これ以上使わないでほしい。プロセスを止めずに目標だけ変えたくなるかもしれません: 「リファクタリングはやめて、まず本番のあのバグを見つけて直して」。あるいは、ある1つのステップだけは危険なので、実行される前に自分の目で見てうなずきたい。これらはどれもモデルが自分で決められることではなく、レッスン3と4の自動的な停止やフォールバックも届きません — これらは**人**がループの外側から手を伸ばして行うことです。このレッスンはその層を扱います: 人間はどうやってループの途中に介入するのか、そしてその介入のコードはどこに置くべきなのか。

## ループが自律的であるほど、人間によるゲートが要る

まず1つ片づけましょう: ループを自分で走らせるためにあれだけ手を尽くしたのに、なぜ人を戻すのでしょうか。

答えは「自律的」という言葉の裏側に隠れています。エージェントとは、ループの中でモデルが次に何をするか、どのツールを使うかを自分で決めるシステムです。その自律性こそが有用さの理由であり、そして危険さの理由でもあります。セキュリティの世界には、このリスクを指す名前があります: 過剰なエージェンシー（excessive agency）です。OWASP はこう述べています: "Excessive Agency is the vulnerability that enables damaging actions to be performed in response to unexpected, ambiguous, or manipulated outputs from an LLM, regardless of what is causing the LLM to malfunction."[^S4]（過剰なエージェンシーとは、LLM の誤動作の原因が何であれ、予期しない・曖昧な・操作された LLM の出力に反応して有害なアクションが実行されてしまう脆弱性である。）

この一文をループの上に重ねると、具体的になります。あるターンで、モデルはツールの返り値を読み違えるかもしれませんし、ユーザーの曖昧な一文を取り違えるかもしれませんし、読んだ Web ページに埋め込まれた悪意ある指示に引きずられるかもしれません。レッスン4の暴走モードが壊したのは、ループの*リズム*でした — 止まらない、その場で空回りする。ここで壊れるのはループの*アクション*です: 実際にやってはいけないことをやってしまいました。そしてループが持つ権限と自律性が大きいほど、たった1つの誤った判断がもたらす損害は大きくなります。だからハーネス自身の自動的なゲート — 停止条件、フォールバック — に加えて、誤りを取り消せない少数の地点には、もう1つのゲート、**人間**のゲートが必要です。アクションが着地する前に、人が「ちょっと待て」と言える機会を与えるためです。

これは自動化への不信ではありません。認識です。モデルは長い連続したターンにわたって走りうるのであり、Anthropic のガイダンスが言うとおりです: "The LLM will potentially operate for many turns, and you must have some level of trust in its decision-making."[^S1]（LLM は多くのターンにわたって動作しうるので、その意思決定をある程度は信頼しなければならない。）ただし信頼は、道中ずっと自由にさせることと同じではありません。信頼はほとんどのステップを自力で歩かせるためのものであり、人間のゲートは、曲がり方を間違えたら取り消せない少数の交差点を見張ります。

## 3種類の介入: 中断、操舵、承認

ループへ手を伸ばすことは、いつも「止めさせる」だけではありません。その後ループがどうなるかで分けると、3つの手があり、それぞれ切り込む地点も、変えるものも違います。

**中断 — ループ全体を取りやめる。** 3つの中でいちばん身も蓋もない手です: モデルがこのターンで何をしたがっていようと、ループは終了し、それ以上リクエストは出ません。レッスン3の停止条件に似ていますが、違いは引き金を引くのが誰かです。停止条件は、あらかじめ決めたルールによってハーネスが自分で手を引くこと。中断は、ループの外の人が手で停止を押すことです。方向がまるごと間違っていて、続けてもトークンを燃やすだけだと見て取れたときに使います。中断のあと、ループは終わりです — 「その後」はありません。

**操舵 — 目標を変える、あるいは新しい指示を渡し、そのまま走らせ続ける。** これは何も終了させません。会話に人間の新しいメッセージを押し込み、モデルが次に傾ける先を変え、ループはその指示を持って進みます。たとえばエージェントがあるモジュールのリファクタリングを黙々と進めているときに、もっと緊急な本番バグを見つけたとします。プロセスを再起動せずに、こう放り込めます: 「リファクタリングは中断して、まずログインエンドポイントの 500 を突き止めて直して」。操舵が変えるのはループの*目標*であって、ループが生き延びるかどうかではありません。

**承認 — 1つのステップに青信号を出す。うなずきがなければ、アクションもない。** 最初の2つはループ全体に作用します。承認は特定の1つのアクションに作用します: ループが高インパクトな操作にたどり着くと停止し、「これからこれをやります」と提示し、人がイエスと言った場合にだけ実行します — ノーならスキップまたはキャンセルします。これは実のところ、非常に規律ある一時停止にすぎません: "Agents can then pause for human feedback at checkpoints or when encountering blockers."[^S1]（エージェントはチェックポイントで、あるいは障害に突き当たったときに、人間のフィードバックを待って一時停止できる。）承認とはそのチェックポイントを、危険なアクションのちょうど手前に正確に留めたものです。承認が通れば、ループは通常のリズムに戻ります。3つの中でいちばん日常的でもあり、常時オンにしておくのに最も向いています。

3つを取り違えないための1行: 中断はループが**生きるか**を決め、操舵はループが**どこを向くか**を決め、承認は**1つのアクション**が通るかを決めます。レッスン6の最小ハーネスは、承認が実際にコードとして書き込まれる場所です。

## 承認弁をループに書き込む: アクションが着地する前に止める

3つのうち、ハーネスのコードに宿る必要が最も強いのは承認です。中断と操舵はたいてい、人がターミナルに何か打ち込めば起動できます。承認は、ハーネスが正しい場所で能動的に止まって待つ形でなければなりません。省けば、ループは単に危険なことをやってのけます。

過剰なエージェンシーに対して OWASP が挙げる緩和策の一つは、こうです: "Utilise human-in-the-loop control to require a human to approve high-impact actions before they are taken."[^S4]（ヒューマン・イン・ザ・ループの制御を用い、高インパクトなアクションが実行される前に人間が承認することを必須にせよ。）この一文の順序に注目してください — 実行される**前に**承認する。承認が先、実行が後であって、先に実行してあとから署名を集めるのではありません。弁を物理的にどこへ置くかについて、この標準は幅を残しています: "This may be implemented in a downstream system (outside the scope of the LLM application) or within the LLM extension itself."[^S4]（これは下流のシステム（LLM アプリケーションの範囲外）で実装してもよいし、LLM の拡張自体の中で実装してもよい。）これを私たちのループに落とすと、自然な置き場所はツールのディスパッチです — 高インパクトと印を付けたツールが実際に呼ばれる直前に、一時停止を挿し込みます。

コードでは、ツールを実行する行の手前に置いた分岐になります:

```javascript
// ループ本体の中、このターンの tool_use ブロックを手にした後、何かを実行する前
for (const block of toolUseBlocks) {
  if (isHighImpact(block.name)) {
    // 何をしようとしているかを提示する: ツール名 + 引数
    const decision = await askHuman(block.name, block.input);
    if (decision !== "approve") {
      // うなずきなし: 実行しない。「拒否された」を tool_result として返し、モデルに考え直させる
      results.push({
        type: "tool_result",
        tool_use_id: block.id,
        content: "人間がこの操作を拒否しました。再試行せず、別の方法を探してください。",
        is_error: true,
      });
      continue; // 肝心の行: この下の実際の実行をスキップする
    }
  }
  // 低インパクト、または承認済み: 通常どおり実行する
  const output = await executeTool(block.name, block.input);
  results.push({ type: "tool_result", tool_use_id: block.id, content: output });
}
```

3か所を見ておく価値があります。第一に、チェックは `executeTool` の**前**にあります — 一時停止はアクションが着地する前に起きなければならず、人間を待っているあいだ、危険な操作はまだ実行されていない必要があります。第二に、拒否は黙ってスキップされるのではなく、`is_error` を立てた `tool_result` を返します（レッスン2のあのフィールドを覚えていますか？）。そうすればモデルはこの経路が塞がれていることを学び、次のターンに同じアクションをもう一度提案する代わりに別の方法を探しにいきます。第三に、`isHighImpact` は高インパクトな操作だけを止めます — ファイルを読む、ログを確認する、といった無害な動きはそのまま通します。そうしないと1ステップごとに人間のうなずきが必要になり、エージェントは高価な手動ツールへ成り下がります。

## ゲートの置き場所: アクションが不可逆になる前であって、後ではない

あの承認弁が機能するのは、ひとえに正しい場所に立っているからです。この節では、その配置のルールだけを取り出します。このレッスンの中で最も逆に覚えられやすく、逆にしたときの代償が最も大きいものだからです。

ルールは一文です: **承認の一時停止は、アクションが不可逆になる前に置く。後ではない。** この考えには、以前のコース「エージェントツール呼び出し: エージェントに実際に行動させる」ですでに出会っています — アクションの影響範囲が大きく、取り消しが利かないほど、その確認点は早い位置になければなりません。ループに落とすとこうなります: チェックは `executeTool` の1行上に置き、人間を待っているあいだ破壊的なアクションはまだ起きていない状態にします。下へ動かせば、あなたが反応するころにはテーブルは削除され、メールは全員に送られ、本番設定はすでに変更済みです — そしてログがどれほど精密でも、やったことは残骸を写真に撮ることだけです。

「不可逆」をどう見分けるか。反実仮想のテストを自分に課してください: このアクションが実行されて、それが間違っていたら、1手で取り消せるか。安く巻き戻せるもの — 一時ファイルを書く、内部の下書きを保存する — にはゲートは不要か、あってもごく緩いもので構いません。取り消せない、あるいは莫大なコストでしか取り消せないもの — データベースの削除、送金、外部への公開、本番設定の変更 — には早い位置にゲートが必要で、しかも「先に承認、それから実行」でなければなりません。これはレッスン4ときれいにつながります: あちらはループがリソースを燃やし尽くすのを防ぐ話で、こちらはループが取り消せないことをやるのを防ぐ話です。前者はリズムの暴走、後者はアクションの暴走であり、どちらも「手遅れ」が来る前にゲートを置く必要があります。

たいてい見落とされる細部が1つ: ゲートは、アクションが実際に着地する場所にいちばん近いステップに置きます。テーブルの削除がいくつもの手を経るとしましょう — モデルが提案し、ハーネスがディスパッチし、`drop_table` が呼ばれる。「モデルが提案する」ステップに承認を置くだけでは足りません。提案そのものは何の損害も与えないからです。レッスン1が言ったとおり、"The model never executes anything on its own."[^S2]（モデルは自分では何も実行しない。）損害は最後の `executeTool` の呼び出しに宿ります。ゲートを実行側へできるだけ寄せておけば、モデルは何度でも考えを変え、引数を練り直せます — それらはすべて、まだ誰も傷つかないゲートのこちら側で起きます。

## レッスン6が3つを1つのループにどうまとめるか

このレッスンを前のレッスンと並べると、ハーネスの制御は一式そろいます: レッスン3の**停止条件**（頃合いになったら自動で手を引く）、レッスン4の**暴走のフォールバック**（デッドループと空回りを見つけ、予算を燃やし尽くさない）、そしてこのレッスンの**ヒューマン・イン・ザ・ループの承認**（危険なアクションが着地する前の手動ゲート）です。3つから1つを選ぶものではありません。同じループの上に積み重なる3つの層です — 停止条件はどれだけ長く走るかを、フォールバックは進路を外れたときどうするかを、承認はこの1手をそもそも実行させるかを司ります。

レッスン6では、この3つを1つの走る最小ハーネスに溶接します: ターン数上限つきの while ループ、空回り検知、そして高インパクトな操作への承認弁。このレッスンの `isHighImpact` の分岐、レッスン3のカウンター、レッスン4の進捗チェックが、1つのループ本体の中で互いに衝突せずそれぞれの位置に収まる様子を、そこで見ることになります。このレッスンでは、2つを握っておけば十分です: 3つの介入がそれぞれ何を変えるのか、そして承認のゲートは引き返せない地点の手前に立たなければならない、ということです。

## 💻 演習

### レベル1: 3つの介入手をラベル付けする

デプロイエージェントが「ビルド → テスト → 本番リリース」のパイプラインを自動で走らせています。以下は、オンコールのエンジニアが別々のタイミングで行った3つのことです。それぞれについて、**中断**・**操舵**・**承認**のどれかを判定し、その理由を述べてください（ループを終了させたのか、ループの目標を変えたのか、1つのアクションに青信号を出したのか）。

1. エージェントが「本番リリース」ステップの直前で止まります。画面にプロンプトが出ます: 「v2.3.1 を本番にリリースしようとしています。確認しますか？」。エンジニアはバージョン番号にちらりと目をやり、「確認」をクリックし、エージェントはリリースを進めます。
2. エージェントが、毎回失敗するテストを再試行し続けています。エンジニアはこの道は行き止まりだと判断して停止を押し、パイプライン全体が終了してプロセスが抜けます。
3. エージェントがまだテストを走らせているところに、エンジニアがメッセージを差し込みます: 「2.3.1 は出さないで — 顧客が欲しいのは 2.3.0 だから、そのバージョンに切り替えて続けて」。エージェントは新しいバージョン番号で進みます。

<!-- rubric -->
- 3つが承認・中断・操舵として正しくラベル付けされている
- それぞれの判断が分かれ目に着地している: 1つのアクションを変えるのか、ループの生死を変えるのか、ループの向きを変えるのか
- 項目1の鍵が「高インパクトなリリースのアクションが実行される前に一時停止が起き、人間のうなずきを待ってから続行している」ことだと特定できている

1. **承認。** ループは終了しておらず、目標も変わっていません。エンジニアは「本番リリース」という1つの高インパクトなアクションに青信号を出しただけです。ここで効いているのは順序です: 一時停止はリリースが実際に実行される前に起き、「確認」が返ってきて初めて続行しています — それがまさに、ヒューマン・イン・ザ・ループの承認における「承認が先、実行が後」の姿です。
2. **中断。** エンジニアが作用したのはループの生死です: パイプライン全体が取りやめられ、プロセスが抜け、「その後」はありません。停止条件に似ていますが、引き金はあらかじめ決めたルールでハーネスが自動的に手を引いたのではなく、ループの外の人が手で停止を押したことです。
3. **操舵。** ループは一度も止まっていません。エンジニアは会話に新しい指示を押し込み、ループが次に傾ける先（別のバージョン番号）を変え、エージェントは新しい目標を持って進みました。これは向きの話であって、生死の話でも、1つのステップへの青信号でもありません。

<!-- hint -->
まず1つ問うてください: これが起きた後、ループはまだ走っていますか。完全に止まっているなら中断です。まだ走っているなら、変わったのが「ループ全体の目標」なのか「特定の1つのアクションを起こすべきか」なのかを見ます。

<!-- hint -->
項目1と2はどちらもリリースとテストのまわりに集まっていて、混ざりやすいです。違いは結末です: 一方はステップに青信号を出したあともループが続き（承認）、もう一方はループそのものを終わらせます（中断）。

### レベル2: 承認弁を正しい位置に置く

以下のループ本体は、外部にメールを送れるエージェントに人間の承認を足そうとしていますが、書き方に問題があります: 人間に尋ねるころには、メールはすでに送信済みです。配置の何が問題で、それが何を招くかを指摘し、承認弁を正しい位置へ移してください。

```javascript
for (const block of toolUseBlocks) {
  const output = await executeTool(block.name, block.input);
  results.push({ type: "tool_result", tool_use_id: block.id, content: output });

  if (block.name === "send_external_email") {
    const decision = await askHuman(block.name, block.input);
    if (decision !== "approve") {
      console.log("人間はこのメールを承認しませんでした"); // しかしメールはもう出ていった
    }
  }
}
```

<!-- rubric -->
- 根本の問題を突き止めている: `askHuman` が `executeTool` の後にあるため、人間に尋ねる前にメールが出てしまい、承認が何も止められない事後の記録に成り下がっている
- 帰結を説明している: `send_external_email` は不可逆な外部アクションなので、事後に「ノー」と言っても取り戻せず、ゲートは名ばかりになる
- 修正では「高インパクトか + 承認待ち」のブロック全体を `executeTool` の前へ移し、承認されなければ実行をスキップし、拒否をモデルに返している（たとえば `is_error` 付きの tool_result として）

<!-- answer -->
根本の問題: **承認弁が `executeTool` の後に立っていることです。** このコードは無条件にツールを実行し — その時点でメールはもう出ています — それから人間に尋ねます。つまり `askHuman` がしているのは、事後に誰かの意見を記録することだけです。`send_external_email` は不可逆な外部アクションであり、メールはいったん出れば呼び戻せず、「ノー」はすでに起きた事故を追認するだけです。アクションの着地より後に置かれたゲートは、ゲートがないのと同じです。

直し方: 「高インパクトかのチェック + 承認待ち」のブロック全体を実行の前へ移し、承認されなければ実行をスキップし、モデルが別の道を取れるように拒否を返します。

```javascript
for (const block of toolUseBlocks) {
  if (block.name === "send_external_email") {
    const decision = await askHuman(block.name, block.input); // 送信する前に尋ねる
    if (decision !== "approve") {
      results.push({
        type: "tool_result",
        tool_use_id: block.id,
        content: "人間がこのメールを拒否したため、送信していません。再試行せず、別の方法で対応してください。",
        is_error: true,
      });
      continue; // 肝心の行: この下の実際の実行をスキップし、メールが出ないようにする
    }
  }
  const output = await executeTool(block.name, block.input); // 低インパクトまたは承認済みの呼び出しだけがここへ来る
  results.push({ type: "tool_result", tool_use_id: block.id, content: output });
}
```

これで一時停止はメールが実際に出る前に起きます: うなずきがあれば送り、拒否されればまったく送らず、そのあいだモデルはこの経路が塞がれていることを学びます。

<!-- hint -->
2つの行の順序を見てください: `executeTool`（実際にメールを送る）と `askHuman`（人に尋ねる）。いまはどちらが先に走りますか。ヒューマン・イン・ザ・ループの承認は「承認が先、実行が後」を要求します — 順序が逆になっていないか確かめてください。

<!-- hint -->
順序をひっくり返すだけでは足りません — 承認が通らなかったとき、ツールは本当に**実行されない**必要があり（`continue` でスキップする）、拒否は `is_error` 付きの `tool_result` としてモデルに返すのが最善です。そうしないと、次のターンに同じメールをまた提案してくる可能性が高いからです。

## まとめ

- ループが自律的であるほど、要所には人間のゲートが要ります: 過剰なエージェンシーとは、予期しない・曖昧な・操作されたモデル出力が、取り消せない有害なアクションを引き起こしうるということです[^S4]。多くのターンにわたって動作しうるモデルを信頼すること[^S1]は自由にさせることと同じではなく、人間のゲートは曲がり方を間違えたら取り消せない少数の交差点を見張ります
- 3つの介入はそれぞれ別の層を司ります: **中断**はループの生死に作用し（ループの外から人が全体を取りやめる）、**操舵**は向きに作用し（新しい指示を押し込み、目標を変え、走らせ続ける）、**承認**は1つのアクションが通るかに作用します（危険な操作の前で止まってうなずきを待つ）。最後のものはまさに「チェックポイントで人間のフィードバックを待って一時停止する」[^S1]という考えを、高インパクトなアクションの手前に留めたものです
- ヒューマン・イン・ザ・ループの承認の鉄則は、承認が先、実行が後です: 高インパクトなアクションは、実行される前に人間が承認することを必須にし[^S4]、弁は下流のシステムに置いても、エージェントの拡張自体の中に置いてもかまいません[^S4]
- ゲートはアクションが不可逆になる前に置き、後には置きません: `executeTool` の上に座っていれば、人間を待つあいだ破壊的なアクションはまだ起きていません。実行の下へ動かせば、どれほど精密なログも事後の追跡でしかなく、すでに着地したものは何も止められません。「不可逆」を見分けるには反実仮想のテストを使ってください — 間違って実行されたら、1手で取り消せるか。
- このレッスンの承認、レッスン3の停止条件、レッスン4の暴走のフォールバックは、同じループの上に積み重なる3つの層であり、レッスン6ではそれらを溶接して走る最小ハーネスにします
