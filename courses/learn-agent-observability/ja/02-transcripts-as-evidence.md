# レッスン2: 一次証拠は自己申告ではなく、生のトランスクリプト

> 学習目標:
> - エージェントの自己申告が二次資料である理由を理解し、「省いたことのほうが書いたことより重要なことが多い」がトランスクリプトのどの箇所を具体的に指しているのかを知る
> - 生のトランスクリプトとして何が数えられるかを認識する: 1回の実行の各ツール呼び出しについてはツール名と完全なパラメータ、各ツールレスポンスについては完全な戻り値またはエラー。そして疑わしい振る舞いを「メッセージNのどのフィールドか」まで特定できる
> - 4つの問い（ツールが違う、パラメータが違う、呼び出しが足りない、レスポンスの扱いを誤った）を使ってトランスクリプトを分類の結論まで読み、どの問いを人間が答え、どの問いをプログラムに委ねるべきかを知る
>
> 前提: レッスン1を完了し、非決定性がどのように「再現してデバッグ」を壊すか、1つの症状の下にいくつもの区別できない原因が隠れうることを理解していること | 前: [レッスン1 <<](./01-why-you-cant-see-why.md) | 次: [レッスン3 >>](./03-logs-and-metrics.md)

## 「3つのソースを突き合わせました」

リサーチエージェントが実行を終え、サマリーを返してきます:

> 3つの権威あるソースを検索し、相互に突き合わせました。データは一致しています。

あなたはそれを信じます。文面はプロフェッショナルで、抑制が効いていて、しかも自分から手順を説明しています。結果を事業チームに送ります。

3週間後、クレームが届きます: あの数字がまるで違う、と。その実行の生のトランスクリプトを開き、メッセージを1つずつ読み進めます——成功した検索呼び出しは1回だけ。2回目の呼び出しはページ取得で、1行のタイムアウトエラーが返っていました。3回目の呼び出しは、そもそも行われていません。「突き合わせました」という言葉は、渡されたサマリーの中にしか存在しませんでした。

これはモデルが嘘をついたわけではありません——その文を書いたとき、参照できる「照合回数」などどこにもなかったのです。ただ、締めくくりとして適切に聞こえる続きを書いただけです。ただしコストは実在します: 自己申告を信じ、トランスクリプトを飛ばし、この実行が2ステップ目で壊れていたと知るのに3週間かかりました。

レッスン1の結論はこうでした: エージェントは実行ごとに非決定的で、「再現してブレークポイントを置く」という従来の直感はそのまま通用しなくなり、進む道は実行自身に証拠を残させることだ、と。このシリーズの第10コースでは、評価とスコアリングの文脈で「エージェントの自己申告は証拠として使えない」と触れるだけでした。このレッスンは、それを読み方のプロトコルにまで展開します。

## 自己申告は二次資料

エージェントが渡してくる自己申告——締めくくりのサマリー、思考の連鎖（モデルが答えを出す前に書く推論。以下 CoT と略します）、ツール実行後の自己評価——は、いずれも**自分自身について書いた文章**です。こうしたテキストには価値がありますが、「実際に何をしたか」との間には一枚の層が挟まっています。

この層のいちばん厄介なところは、間違ったことを書くことではなく、そもそも**書かない**ことです。Anthropicのツールエンジニアリングの記事は率直にこう述べています: エージェントがフィードバックや応答で省略したことのほうが、書いたことよりも重要な場合が多い。LLMは、思っていることを必ずしも口に出すとは限らない[^S3]。省略は誤りよりも厄介です——誤りなら矛盾に気づけるかもしれませんが、省略はその機会すら与えてくれません。先ほどの例では、「2つ目のソースの取得に失敗した」とは書かれていませんでした——ただ触れなかっただけで、欠けているものは自分から手を挙げてはくれません。

だから順序はこうです: 推論とフィードバック（CoT）を読むことは粗い部分を見つける助けになりますが、CoT に明示的に書かれていない振る舞いを捕まえるには、ツール呼び出しとツールレスポンスを含む生のトランスクリプトを見る必要があります[^S3]。CoT は手がかり、トランスクリプトが証拠です。これを逆にすると、「やったと言っているのだから、たぶんやったのだろう」という結論を繰り返し出すことになります。

実践としてはこうです: 自己申告の中の具体的な数字を1つずつ、トランスクリプトまで遡ってください。出どころが見つからず、トランスクリプト内の数字から導くこともできないなら、それはモデルが生成したものです。

## 「生のトランスクリプト」として何が数えられるか

「生のトランスクリプト」は新しい概念ではありません。このシリーズの第7コースで、あなたは自分の手で作っています: あの `messages` 配列です。ループが1周するごとに assistant のメッセージが追加され、続いてツール結果を載せた user のメッセージが追加されます。タスクが終わったとき、配列に積み上がっているものが、その実行の生のトランスクリプトです。

広げてみると、2種類のブロックが見えます。**`tool_use` ブロック**は、モデルがどのツールを呼ぶかを指定するもので、ツール名と、モデルが生成した完全なパラメータオブジェクトを含みます。**`tool_result` ブロック**は、ハーネスが実際にツールを走らせたあとに返すもので、成功時は完全な戻り値、失敗時はエラーの内容とエラーフラグです。この2つのブロックは対で読まなければなりません: `tool_use` だけを見れば、それが何を**しようとしたか**しかわかりません。`tool_result` だけを見れば、環境が何を**返したか**しかわかりません。

なぜこれらが証拠になりうるのか。Anthropicのエージェントパターンの記事は、エージェント自身の視点から説明しています: 実行中、エージェントは進捗を評価するために、各ステップで環境から "ground truth"（ツール呼び出しの結果やコード実行の結果など、環境が返す事実）を得る必要がある[^S2]。同じデータの束が、あなたにも使えます——エージェントはこれで自分がどこにいるかを判断し、あなたも同じもので判断するのです。

同じ記事は設計原則も示しています: エージェントの計画ステップを明示的に見せることで、透明性を優先せよ[^S2]。これはしばしば UI への推奨として受け取られますが、デバッグにとっての含意はもっと具体的です——**ツール境界に着地しない行動は、トランスクリプトに何の痕跡も残さない**。モデルが「頭の中で2つのデータセットを比較する」ことは痕跡を残しませんが、`diff` ツールを呼べば残ります。何かを監査可能にしたいなら、それをツール境界まで押し出す必要があります。

## 人手のレビューは、評価が取りこぼすものを捕まえる

ここでこう聞きたくなる人がいるでしょう: 第10コースで評価セットを作ったばかりではないか。スコアを回して終わりにすればいいのでは。なぜ人間がメッセージを1つずつめくる必要があるのか。

評価セットが捕まえるのは、あなたがすでに思いついた失敗だけだからです。人手による評価は、自動化が取りこぼすものを捕まえます。エージェントをテストする人間は、評価が見逃すエッジケースを見つけます。そこには、珍しいクエリに対する幻覚的な回答、システムの障害、そしてソース選択の微妙な偏りが含まれます[^S1]。3つ目のカテゴリは詳しく見る価値があります: Anthropicのマルチエージェントリサーチシステムでは、初期のエージェントが、学術PDFや個人ブログのように権威はあるがランクの低いソースよりも、SEO最適化されたコンテンツファームを一貫して選んでいることに、人間のテスターが気づきました[^S1]。

この偏りは評価ではほとんど見えません: 回答が必ずしも間違っているわけではなく——コンテンツファームも正しい事実をコピーします——スコアは良いままです。それが書かれている場所はただ1つ: トランスクリプトの中に並ぶ、実際に選ばれたURLの列です。

ツールの層にも同種の例があります。Claudeのウェブ検索ツールをローンチしたとき、チームは Claude がツールの `query` パラメータに不必要に 2025 を付け足しており、検索結果に偏りが生じて性能が落ちていることを突き止めました。修正はツールの説明を改善して Claude を正しい方向へ導くことでした[^S3]。このバグはクラッシュもせず、エラーも投げず、タイムアウトもしません。ツールは毎回、正当な検索結果とともに成功で返ります。メトリクスは「性能が落ちた」までは教えてくれるかもしれませんが、「`query` に `2025` が入っているから落ちた」と指を差すには、パラメータを1行ずつ読む必要があります。

## トランスクリプトは人間だけが読むものではない

前のセクションは誤解を招きやすい書き方でした: トランスクリプトを読む＝人間の目で1行ずつ、ではありません。トランスクリプトは構造化されたテキストであり、モデルはそれを読むのが非常に得意です。ツールエンジニアリングの記事は、ほとんど身も蓋もない方法を示しています: 評価用エージェントのトランスクリプトを単に連結して、Claude Code に貼り付けるだけ。Claude はトランスクリプトの分析の専門家であり、大量のツールを一度にリファクタリングできます——たとえば、新しい変更が入ったときにツールの実装と説明が自己整合を保つようにする、といったことです[^S3]。

「トランスクリプトを読む」ことのボトルネックは知性ではなく、根気です。だから分担ははっきりしています: モデルは総なめのスキャンが得意で、トランスクリプトの束を容疑者リストに圧縮できます。人間は質的な判断が得意で、抜き出されたサンプルが本当に問題と言えるかを決められます。

## 他人のトランスクリプト形式は、その内部実装

トランスクリプトがそれほど重要なら、既存の製品がディスクに書き出している出来合いのトランスクリプトをそのまま読めばいいのでは。Claude Code を例に取ると、セッションのトランスクリプトを `~/.claude/projects/*/*.jsonl` ファイルに永続化しています[^S4]。理想的に見えます: 1メッセージ1行の、出来合いの、構造化された生のトランスクリプト。

しかし公式ドキュメントはすぐ後に警告を付けています: トランスクリプトのエントリ形式は Claude Code の内部仕様であり、バージョン間で変わる。したがってこれらのフィールドで結合するパイプラインは、どのリリースでも壊れうる。結合は安定した契約ではなく、バージョン固有のものとして扱うこと[^S4]。フックのドキュメントは2つ目の注意を加えています: フックが受け取るトランスクリプトファイルは**非同期に書かれる**ためメモリ上の会話に遅れることがあり、フックが発火した時点では、そのターンの最新のメッセージがまだ含まれていない場合があります[^S5]。

どちらも同じ教訓です: 他人の形式はあなたの管理下になく、書き込みのタイミングもあなたの管理下にありません。読むことはできますし、トラブルシューティングに使うこともできますが、その上にあなたの可観測性を建てることはできません。結論: **自分のハーネスは、自分のトランスクリプトを書く必要があります**。そのトランスクリプトのフィールドをどう設計するかはレッスン3、第7コースで書いたハーネスへの組み込みはレッスン6で扱います。

## トランスクリプトを読むための4つの問い

トランスクリプトを開いたとき、どこから手を付けるか。ツールエンジニアリングの記事が、出来合いの分類を用意してくれています: エージェントは、間違ったツールを呼ぶかもしれないし、正しいツールを間違ったパラメータで呼ぶかもしれないし、呼び出しが少なすぎるかもしれないし、ツールのレスポンスを誤って処理するかもしれない[^S3]。この4つはもともとツール設計についての話ですが、読み方のチェックリストとして非常によく機能します。それぞれが、トランスクリプトの中に指し示すべき固有の場所を持っているからです:

**問い1: ツールが違う。** 各 `tool_use` ブロックの `name` フィールドを見ます。目の前のタスクと、直前のツールレスポンスに突き合わせます。判断基準は「もっと適切なツールがそこにあったのに、使われなかったか」です。

**問い2: ツールは正しいが、パラメータが違う。** `tool_use` ブロックの `input` フィールドを、キーごとに見ます。先ほどの例——検索語に `2025` を付け足す——はこの問いに属します。パラメータは長く、しかももっともらしく見えるので、最も飛ばされやすい問いです。**自分で正誤を独立に判断できるキー**に絞って見てください: 日付、パス、ID、範囲の上下限、単位。

**問い3: 呼び出しが足りない。** この問いの証拠は**不在**なので、最も読み取りにくいものです。見つけ方は、「次の呼び出しがあるべきだったのに、なかった」箇所を探すことです: リトライのないエラー、5件返ってきた検索のうち1件しか取得していない、2つのソースが必要なタスクなのにトランスクリプトには成功した往復が1回しかない。不在は自分から飛び出してはくれません——タスクの要件をテンプレートにして、数えるしかありません。

**問い4: ツールレスポンスの扱いを誤った。** 各 `tool_result` の直後の assistant メッセージを見て、「次に言っていることは、いま受け取ったものと整合しているか」を問います。エラーを成功として扱う、返ってきた期間Aのデータを期間Bとして使う、戻り値が明示的に「結果は切り詰められました」と言っているのにエージェントが全体として受け取る——いずれもこの問いに属します。これはエラーメッセージの書き方にも直結します: ツールがエラーを発生させたとき、不透明なエラーコードやトレースバックではなく、具体的で実行可能な改善策を明確に伝えるように、エラー応答をプロンプトエンジニアリングできます[^S3]。エージェントが同じ種類のエラーを繰り返し読み違えているのを見たら、まずそのエラー自身が何と言っているかを確認してください。

## 比例配分: すべてのトランスクリプトを人手で1行ずつ読む必要はない

トランスクリプトを人手で読むのは**高価な**行為です: 数十メッセージある1回の実行を丁寧に読むと、たっぷり10分以上かかります。それを100実行分に掛ければ、誰も追いつけません。だから人手の読みは2箇所に置きます。1つは**抜き取り確認**です: 定期的に何本かの実行をランダムに選んで通読する。特定のバグを狩るためではなく、「普段どう動いているか」の直感を較正するためです——SEOコンテンツファームのような偏りは、まさに「バグを狩らずに読んでいる」ときに偶然ぶつかるものです。2つ目は**新しい問題の性質を掴むこと**です: 見慣れない症状にぶつかったとき、最初の何回かは人手で読まなければなりません。まだ何を探せばいいかがわかっていないからです。どのフィールドに現れるかが分かる程度まで読み込めたら、あとはプログラムに引き渡します。

日常の物量はプログラムによる読みが担います: ログのフィールドをどう設計するかはレッスン3、散らばった記録を1回の実行に相関させる方法はレッスン4です。そこまで来ると、人手の読みの入り口は「メトリクスで怪しい実行を数本まで絞り込み、それからトランスクリプトを開いて子細に見る」に変わります。まず証拠が存在して、初めて効率よく読む話ができます——このレッスンが扱ったのは、その前半です。

4つの問いそれぞれについて結論を出してください。各問いについて、証拠がどこにあるか——どのメッセージの、どのフィールドか——と、なぜそのフィールドがその結論を支えるのかを明確に書いてください。このトランスクリプトに支える証拠がない問いについては、無理に当てはめず「証拠なし」と明示してください。

<!-- rubric -->

- 4つの問いすべてに結論があり、「ツールが違う」は「このトランスクリプトには証拠なし」と明示されていること。[6] での `get_filing` への切り替えをこの問いに押し込んではいけない
- すべての問題が「メッセージ番号＋フィールドパス」（例: `[6].content[1].input.fiscal_year`）で特定されていること。「数字をでっち上げた」という一文だけで済ませていない
- 「128.4億ドルはでっち上げだ」と判定する根拠が、「このトランスクリプトのどの `tool_result` にもこの数字が含まれていない」であること。「本当の数字はこれではないと知っている」ではない

<!-- answer -->

**問い1: ツールが違う——このトランスクリプトには証拠なし。** 3回の呼び出しのツール選択はいずれも妥当です: ソースを見つけるための `web_search`（[2]）、URLがすでに得られているPDFを取得するための `fetch_page`（[4]）、開示データを取得するための `get_filing`（[6]）。[6] は誤判定しやすいところです——[5] のタイムアウトのあとにツールを切り替えていますが、ツールを切り替えたことは、間違ったツールに切り替えたことを意味しません。開示データの取得に `get_filing` は妥当で、問題はパラメータのほう、つまり問い2に属します。

**問い2: ツールは正しいが、パラメータが違う——証拠あり。** 証拠の位置: `[6].content[1].input.fiscal_year` の値が `2015` ですが、[1] のタスクが求めているのは FY2025 です。会計年度は、まさに独立に正誤を判断できる種類のキーです。裏づけの証拠は `[7].content[0].content.period` の値 `"FY2015Q3"`——ツールは渡された年度どおりにデータを取得しており、「パラメータは間違っていたがツール側が寛容に補正した」という可能性を排除できます。`[7].content[0].content.revenue_usd_millions` は `2130`、つまり21.3億ドルで、[6] と [8] が挙げる128.4億ドルとは6倍のずれがあります。

**問い3: 呼び出しが足りない——証拠あり。** [1] のタスク要件をテンプレートにして数えます: タスクは「独立した2つのソースで突き合わせる」ことを求めていますが、このトランスクリプト全体で FY2025 のデータを取得できた成功した往復は**ゼロ**です。欠けている箇所は2つ: [5] はタイムアウトエラー（`is_error: true`）ですが、トランスクリプトに2回目の `fetch_page` はありません——リトライがゼロ。そして [3] には rank 2 と rank 3 のURLがまだ残っており、一度も取得されていません。すぐ使えるフォールバックでした。

**問い4: ツールレスポンスの扱いを誤った——2箇所に証拠あり。** 1つ目: `[5].content[0].is_error` は `true`、content は `TimeoutError` ですが、直後の `[6].content[0].text` は「公式の決算資料により、クラウド事業の売上は128.4億ドルであることを確認しました」と断言しています。取得の失敗が成功として扱われました。しかも 128.4 という数字は、[3]、[5]、[7] の3つの `tool_result` のどこにも現れません——[3] にはタイトルとURLしかなく、[5] はエラー文字列、[7] は 2130 を返しています。この数字はモデルが生成したものでしかありえません。判断基準に注意してください: 「正しい数字を自分が知っているから」ではなく、「トランスクリプトにその出どころがないから」です。仮に128.4億ドルがたまたま正しかったとしても、このステップはでっち上げのままです。2つ目: `[7].content[0].content.period` は `"FY2015Q3"` と明示しているのに、`[8].content[0].text` はそれを FY2025 の2つ目のソースとして扱い、「両方のソースは一致しています」と主張しています。

**[8] のサマリーには、トランスクリプトの裏づけがない主張が3つあります:** 「公式の決算資料を検索し（て取得し）た」（[5] はタイムアウトで、そのページは一度も取得されていない）、「両方のソースは一致している」（21.3億ドル対128.4億ドル）、「前年同期比31%増」（3つの `tool_result` のどこにも前年同期のデータはない）。最も洗練されて聞こえる部分こそ、トランスクリプトの裏づけが最も薄い部分です。

<!-- hint -->

順番どおりに読まないでください。すべての `tool_result` をリストに書き出し、各項目について3つだけ記録します: 誰が呼んだか、成功か失敗か、戻り値にどんな数字が現れたか。それから [8] のサマリーの数字を1つずつリストに戻して出どころを探します。見つからないものが、最初の問題です。

<!-- hint -->

`is_error: true` の行にぶつかったら、「エラーが出た」とだけ記録して先に進まないでください。本当の情報は**その直後の assistant メッセージ**にあります——エラーのあとエージェントが最初に何をするかは、しばしば問い3（リトライすべきだったのにしなかった）と問い4（エラーを成功として扱った）の現場を同時に兼ねています。

### レベル2: 完了サマリーの各文に真偽の印を付ける

以下はデータ処理エージェントの完了サマリーで、5つの文から成ります。その下に、同じ実行の実行サマリーが続きます。

> ① data/2026-w33.csv の4127件すべてを staging_w33 にインポートしました。
> ② インポート前に列ごとにフィールド型を検証し、フォーマットの問題はありませんでした。
> ③ amount が null の不正データ63件を除去しました。
> ④ 全工程はエラーなく完了しました。
> ⑤ 今週のレポートは先週と同じ集計基準を使っています。

```text
run_id: r-8841    ツール呼び出し6回

1  read_file   {"path": "data/2026-w33.csv"}
             → ok      4128 rows / 1.9 MB
2  run_sql     {"sql": "CREATE TABLE staging_w33 (day date, dept text, amount numeric)"}
             → ok
3  run_sql     {"sql": "COPY staging_w33 FROM 'data/2026-w33.csv' CSV HEADER"}
             → ok      4127 rows copied
4  run_sql     {"sql": "SELECT count(*) FROM staging_w33 WHERE amount IS NULL"}
             → ok      63
5  run_sql     {"sql": "DELETE FROM staging_w33 WHERE amount IS NULL"}
             → error   permission denied for table staging_w33
6  write_file  {"path": "reports/w33.md", "bytes": 2147}
             → ok
```

5つの文それぞれに、**トランスクリプトが裏づける** / **トランスクリプトが否定する** / **トランスクリプトに対応なし** のいずれかの印を付けてください。各文について、判断の理由と、何番の呼び出しを指しているかを書いてください。さらに「対応なし」と印を付けた文については、もう1つ書いてください: 次の実行で検証可能にするには、どんな可観測性を追加する必要があるか。

<!-- rubric -->

- 5つの文すべてに印が付いており、「トランスクリプトが否定する」2文の証拠がどちらも呼び出し5の `permission denied` を指していること
- 「対応なし」と判断する際、トランスクリプトの中で**最も近い**証拠がどれで、それでもなぜ主張を確証するには不十分なのかを述べていること。「トランスクリプトに書かれていない」だけで済ませていない
- 「対応なし」の2文それぞれに、ツール境界に着地する補完策の提案があること——痕跡を残す新しい呼び出しを足す、または既存の呼び出しの input／戻り値にフィールドを足す——であって、「サマリーでエージェントにもっと説明させる」ではない

<!-- answer -->

**① ——トランスクリプトが裏づける。** 呼び出し3が `4127 rows copied` を返しており、数字が直接一致します。呼び出し1は4128行を返しており、差分の1行はまさに `CSV HEADER` が消費したヘッダです。両者が相互に裏づけ合っています。5つの文のうち、ツールレスポンスで直接検証できる唯一の文です。

**② ——トランスクリプトに対応なし。** 6つの呼び出しのどれも検証の行為ではありません: 呼び出し1はファイルを読んだだけで、返したのは行数とバイト数であり、列名すら含みません。呼び出し2から5はテーブル作成、インポート、カウント、削除。呼び出し6はファイル書き込みです。

トランスクリプトの中で最も近い証拠は2つあり、どちらも不十分です。呼び出し2の CREATE TABLE の DDL は確かに `day date, dept text, amount numeric` を宣言していますが、DDL が宣言するのは**投入先テーブルの構造**であって、**元データの検証**ではありません。呼び出し3の COPY が成功したことは、全行が宣言された型に変換できたことを意味しますが、それはインポートの副次的な効果であって、「インポート前に列ごとに検証した」という行為ではありません。しかも「フォーマットの問題はなかった」ことの証明にもなりません——呼び出し4がすぐに amount の null を63件見つけています。直接の裏づけも直接の否定もなく、この行為があったかどうかはトランスクリプトからは判断できません。

**追加すべき可観測性:** 検証をモデルの頭の中からツール境界へ移すため、明示的な調査用の呼び出しを追加します——`run_sql` による検査クエリでも、`profile_csv` のようなツールでも構いません。各列について、非 null の行数、目的の型に変換できる行数、変換できない行の行番号のサンプルを返すようにします。その input も戻り値もトランスクリプトに着地するので、次回はこの文を `tool_result` に直接突き合わせて判断できます。追加したあともエージェント自身の言葉でしか確認できないなら、それは何も追加していないのと同じです。

**③ ——トランスクリプトが否定する。** 63 は確かに呼び出し4から来ているので前半には根拠があります。しかし呼び出し5の DELETE は `error permission denied for table staging_w33` を返しており、実行されていません。そのあとにリトライもなく、カウントの取り直しもありません。この文は、検査で見つかった実在の数字を、成功しなかった行為に縫い合わせています。だからこそ、特に信憑性が高く聞こえます。

**④ ——トランスクリプトが否定する。** 呼び出し5が `error permission denied` を明示的に返しています。証拠は1つで足ります。

③ と ④ はどちらも呼び出し5を指していますが、誤りの種類は違います: ③ はやっていないことをやったと主張し、④ は起きたことを起きなかったと主張しています。後者のほうが危険です——誰もトランスクリプトを読まない限り、この権限の問題は毎週63行のデータを静かに素通りさせ続けます。

**⑤ ——トランスクリプトに対応なし。** この実行は先週の成果物に一切触れていません: 先週のレポートも読まず、基準の設定も読まず、履歴テーブルにも問い合わせていません。最も近い証拠は呼び出し6の `write_file` が2147バイトを書き込みに成功したことですが、これはレポートが書かれたことしか証明しません。かといって否定とも言えません——基準が変わったとトランスクリプトのどこも言っていないからです。ただ検証しようのない文なのです。

**追加すべき可観測性:** 「先週の基準」を、この実行が実際に読むものにします: 先週のレポートまたは基準の設定に対する `read_file` を追加し、その戻り値をトランスクリプトに着地させます。同時に、`write_file` の input に基準の出所を示す識別子——設定ファイルのパスと内容のハッシュなど——を持たせます。「先週と同じ」は、そこで評価的な一文から、2つの実行の間で比較できるフィールドへと姿を変えます。ハッシュが一致すれば、同じです。

**5つの文の内訳そのものが1つの結論です**: 1つが裏づけられ、2つが否定され、2つが検証不能——にもかかわらず、どれも同じだけ自信たっぷりに読めます。自己申告は、自信のない箇所で声を落としてはくれません。

<!-- hint -->

文ごとに判断するときは、問いの順序を固定してください: まず「これを**直接否定する**証拠がトランスクリプトにあるか」を問う。あれば否定。なければ次に「**直接裏づける**証拠があるか」を問う。あれば裏づけ。どちらもなければ対応なし。順序を逆にすると、周辺的な証拠（CREATE TABLE の DDL、成功した write_file）を裏づけと読み違えたことに、自分でも気づけない可能性が高くなります。

<!-- hint -->

補完策が十分かどうかを試す基準は一文で書けます: 変更後、次の実行で同じこの文が、**たった1つの `tool_use` または `tool_result` だけで**真偽を判断できるか。まだエージェント自身の言葉に頼るなら、あるいはまだ誰かが手でデータベースを確認しに行く必要があるなら、それは補完できていません。

## まとめ

- エージェントの自己申告は二次資料です: エージェントがフィードバックや応答で省略したことのほうが、書いたことよりも重要な場合が多く、LLMは思っていることを必ずしも口に出すとは限りません[^S3]。そして欠けているものは、サマリーの中で手を挙げてはくれません
- CoT を読むことで粗い部分は見つかりますが、CoT に明示的に書かれていない振る舞いを捕まえるには、ツール呼び出しとツールレスポンスを含む生のトランスクリプトを見る必要があります[^S3]——CoT は手がかり、トランスクリプトが証拠です
- 生のトランスクリプトとは、このシリーズの第7コースのあの `messages` 配列に積み上がるものです。それが証拠になりうるのは、ツールの結果やコード実行が、各ステップで環境が与える ground truth だからです[^S2]。公式のガイダンスは「エージェントの計画ステップを明示的に見せることで透明性を優先せよ」とも述べています[^S2]——裏返して読めば、それがこのレッスンの系です: ツール境界に着地しない行動は、痕跡を残しません
- 人手による評価は自動化が取りこぼすものを捕まえます: 評価が見逃すエッジケース——珍しいクエリに対する幻覚的な回答、システムの障害、ソース選択の微妙な偏り[^S1]。現実の例が、初期のエージェントが学術PDFや個人ブログよりもSEO最適化されたコンテンツファームを一貫して選んでいたことです[^S1]——この種の偏りは、トランスクリプトに着地したとき、実際に選ばれたURLの列として現れます。ツール層のバグもパラメータに宿ります: Claude はかつて検索ツールの `query` パラメータに不必要に `2025` を付け足しており、結果に偏りが生じて性能が落ちました。修正はツールの説明の改善でした[^S3]
- トランスクリプトは人間だけが読むものではありません: 評価用エージェントのトランスクリプトを単に連結して Claude Code に貼り付ける。Claude はトランスクリプトの分析の専門家であり、大量のツールを一度にリファクタリングできます——たとえばツールの実装と説明の自己整合を保つように[^S3]。トランスクリプトを読むための4つの問いは、ツールが違う、ツールは正しいがパラメータが違う、呼び出しが足りない、ツールレスポンスの扱いを誤った、です[^S3]
- 他人のトランスクリプト形式は、その内部実装です。Claude Code はセッションのトランスクリプトを `~/.claude/projects/*/*.jsonl` に書きます[^S4]が、公式ドキュメントはこの形式が Claude Code の内部仕様でありバージョン間で変わると明言しており、これらのフィールドで結合するパイプラインはどのリリースでも壊れうるため、バージョン固有のものとして扱うべきです[^S4]。フックが受け取るトランスクリプトファイルも非同期に書かれ、メモリ上の会話に遅れることがあります[^S5]。だから自分のハーネスは自分のトランスクリプトを書く必要があります——フィールドの設計はレッスン3、実装はレッスン6です
