# 第 1 课：为什么你说不清它哪儿错了

> 学习目标：
> - 说清一个用户可见的症状底下，为什么会压着好几个从外面看完全不可区分的原因
> - 讲明白非确定性怎么让「复现一次再打断点」这套传统调试直觉失去着力点
> - 认出 Agent 系统里错误的几种形态：级联、轨迹改道、跨轮次复利、多 Agent 的涌现
>
> 前置要求：完成本系列前 10 门课，能手写以 `stop_reason` 驱动的 harness 循环，知道评测跑道只给你 pass/fail | 下一课 [第 2 课 >>](./02-transcripts-as-evidence.md)

## 一个说不清的周二下午

你的内部研究 Agent 上线两周了。周二下午，运营同事转来一条用户反馈：

> 我让它查我们去年的定价方案，它回我说没找到。可那份文档明明就在知识库里，我自己两秒钟就翻到了。

你打开这条会话，屏幕上只有两样东西：用户的那句问题，和 Agent 最后回的那句「我没有检索到相关资料」。中间到底发生了什么，你手里一个字都没有。

于是你开始猜。

是它把搜索词起坏了？比如把用户那句大白话原样丢进检索，搜了一长串自然语言而不是几个关键词。还是搜到了但挑来源时挑歪了？返回八条结果，它偏偏读了最不相关的那两条，然后判断「没有」。又或者，那次检索工具压根就报了错，而 Agent 把报错读成了「这个方向没有资料」，接着往下走了？

这三个猜测，从用户那一侧看长得一模一样：Agent 找不到明明就在那儿的信息。

这不是你一个人的处境。Anthropic 团队复盘他们的多 Agent 研究系统时记下过同一件事：用户会报告 Agent「找不到明显的信息」，而他们看不出为什么——是 Agent 用了糟糕的搜索词？挑了差的来源？还是撞上了工具故障[^S1]。同样三个问题，答不上来。

## 评测跑道只回答「挂没挂」

你的第一反应大概是打开上一门课（本系列第 10 门）建的那套东西：终态判分、验证器、评测集。这是对的第一步。你把这条真实的用户问题加进评测集，配上一句判据「回答里必须引用到那份定价文档」，跑一遍。

结果是一行红字：`fail`。

这行红字有用——它把一条主观抱怨变成了可复跑、可回归的判定。但它答不了你现在真正想问的那个问题：为什么。判分器看的是终态，终态是「没引到」；至于这个「没引到」是搜索词造成的、来源选择造成的，还是工具报错被当成空结果吞掉了，判分器不关心，也没有能力关心。它站在跑道终点，只负责举牌。

这门课要补的就是中间那一段。用一句本课自己的说法：

> **验证告诉你挂没挂，可观测性告诉你为什么。**

这句话不是哪份官方文档的原话，是本课程用来串起后面五节的框架，背后有两条真实经验撑着。一条来自那个多 Agent 系统的复盘：把全链路 tracing 上到生产之后，他们才终于能诊断 Agent 为什么失败，并系统性地修问题[^S1]。另一条来自工具工程那边：把评测 Agent 留下的原始记录交给模型去分析，可以帮你探究 Agent 为什么调、或者为什么不调某个工具[^S3]。两句话指的是同一件事——只有让过程留下痕迹，「为什么」才有地方可问。

## 「复现一下再打断点」为什么在这儿失灵

先把词说清楚。**确定性**系统的意思是：给它同样的输入，它每次产出同样的输出。**非确定性**系统则相反——Agent 就是这类系统，即便起始条件完全相同，它也可能生成不同的响应[^S3]。

这一条把传统调试的地基抽掉了。Agent 做的是动态决策，两次运行之间是非确定的，即便提示词一模一样也是如此，调试因此变难[^S1]。传统的评估方式还默认了一个假设：给定输入 X，系统应当沿路径 Y 产生输出 Z。多 Agent 系统不这么工作——即便起点完全相同，Agent 也可能走上完全不同、但同样成立的路径去达成目标[^S1]。

具体长什么样：

```text
同一个问题，同一版提示词，两次运行

运行 A                              运行 B
1 search("2024 定价方案")            1 search("pricing plan 2024 内部文档")
2 read_doc(doc_17)                  2 search("定价 归档")
3 回答（引用 doc_17）                3 read_doc(doc_09)
                                    4 read_doc(doc_17)
                                    5 回答（引用 doc_17 与 doc_09）
```

两条路径都不算错，终态也都能算通过。可如果出事的是运行 A 的第 2 步，你重跑十次跑出九个运行 B，那九次都帮不上忙。

断点也一样悬空。断点挂在代码行上，前提是「第二次执行会走到这一行、且带着同样的上下文」。而 Agent 出岔子的地方常常根本不在你的代码里，它在模型的某一次决策上；就算你想停，你也不知道该停在第几轮——这次第 3 轮出岔，下次可能第 11 轮才出，也可能压根不出。

你可能会想到把采样温度调低，或者把工具返回录下来回放。这些工程手段确实能减少一部分抖动，本课后面也不反对你用。但它们改变的是你实验室里的那次运行，不是线上出事的那一次——线上那一次已经过去了，它唯一留下的东西就是记录。

Anthropic 团队给的做法是另一个思路。他们的说法叫「像你的 Agent 一样思考」：用系统里一模一样的提示词和工具搭出模拟环境，然后一步一步地看 Agent 干活。这立刻暴露出了几种失败模式——已经拿到足够结果却还在继续、搜索词写得过于冗长、选错了工具[^S1]。

重点在哪儿：不是「复现出同一次」，而是「看得见每一步」。这是可观测性和传统调试分岔的地方。

## Agent 出的错，形状也不一样

就算你接受了「得靠记录」，还有一层要理解：Agent 系统里的错误，形态跟传统 bug 不是一回事。

传统软件里，一个 bug 可能破坏某个功能、拖慢性能，或者引发一次宕机。而在 Agent 系统里，微小的改动会级联成很大的行为变化，这让「为需要在长时间运行中维护状态的复杂 Agent 写代码」变得异常困难[^S1]。

具体到一次运行里，最典型的形态是**轨迹改道**。错误在 Agent 系统里会复利，对传统软件而言只是小问题的东西，足以让 Agent 彻底跑偏：一步失败就可能让 Agent 转去探索一条完全不同的轨迹，最后给出不可预测的结果[^S1]。

```text
第 3 轮 search 超时，工具返回 "Error: upstream timeout"
        ↓
Agent 把它读成「这个方向没资料」
        ↓
换了一个完全不同的检索方向
        ↓
后面 12 轮全长在这条错分支上
        ↓
终态：一份看着挺完整、来源全是旁枝末节的报告
```

注意这条链的第一环有多小：一次超时。在传统服务里它可能只是一条重试日志，在这里它改写了后面十二轮的内容，而终态那份报告不报错、不崩溃，读起来还挺流畅。

第二个形态是**跨轮次复利**。Agent 是有状态的，错误会复利：它们可以跑很长时间，在很多次工具调用之间维持状态，所以你需要能持久地执行、并在过程中处理错误[^S1]。这也是为什么出错之后不能简单地从头再来——重启既昂贵又让用户难受，所以他们做成了能从出错的位置恢复[^S1]。对你的意义很直接：出错时那份状态没被记下来，「从哪儿恢复」这个问题就无从答起。

第三个形态要到多 Agent 系统里才看得见：**涌现行为**。多 Agent 系统会出现没被专门编程过的涌现行为——对主 Agent 的一个小改动，可能不可预测地改变子代理的行为方式；把这件事做对，靠的是理解交互模式，而不只是单个 Agent 的行为[^S1]。

这几种形态合起来是什么样子，那个团队的早期版本给过很直白的答案：早期的 Agent 会犯这类错——为一个简单查询孵出 50 个子代理、为并不存在的来源无休止地扫网、用过量的相互更新把彼此带偏[^S1]。

这三种错误有个共同点：站在外面看，终态都可能只是「回答质量不太行」。你分不出是哪一种。

## 抽象层会遮住证据

还有一层麻烦不来自模型，来自你的工具链。

Agent 框架让人容易起步，它们简化了调用 LLM、定义和解析工具、把调用串起来这些底层活儿。但它们往往制造出额外的抽象层，遮住底层的提示词与响应，让这些东西更难调试[^S2]。给开发者的建议因此是：先直接用 LLM API 开始，很多模式几行代码就能写出来；如果确实要用框架，得确保你理解底层的代码，因为对水面之下的错误假设是客户出问题的常见来源[^S2]。（这篇文章自己标注了其中对工具生态的描述已经过时，所以这里取的是原则部分，不当作现在的选型建议。）

这一条对你来说其实是好消息。你在本系列第 7 门课手写过 harness 循环，那层抽象你没有：

```javascript
while (response.stop_reason === "tool_use") {
  messages.push({ role: "assistant", content: response.content });
  // 这一行里跑掉的东西: 工具名、参数、返回体、耗时、报没报错
  const toolResults = await runToolUses(response.content);
  messages.push({ role: "user", content: toolResults });
  response = await client.messages.create({ model, max_tokens, tools, messages });
  // 这一行里跑掉的东西: 这是第几次请求、花了多久、耗了多少 token、停在什么 stop_reason
}
```

证据全在这个循环里流过，一次不落，问题只在于流过之后就没了。你没有遮挡，但也没有留存——从事后要证据的角度看，这两者一样难受。

所以本课的判断是：调试 Agent 的难，一半来自非确定性这个客观事实，另一半来自「本来能记下来的东西没记」。前一半改不了，后一半在你手里。

## 出路：接下来五课给你什么

那个多 Agent 系统的团队把这件事放在了和提示词、工具设计同一档的位置上：把这事做对，靠的是仔细的提示词与工具设计、扎实的启发式规则、可观测性，以及紧凑的反馈回路[^S1]。复盘里还有一句更直白的——他们把重心放在了一个由可观测性和测试用例构成的快速迭代回路上[^S1]。

注意「测试用例」这半句：可观测性不是来替代评测跑道的，它俩是一副挑子的两头。评测告诉你这次挂没挂、改完有没有变好；观测告诉你这次为什么挂、该动哪一处。

后面五节课按这个顺序推进：

- **第 2 课** 先立地基：原始记录是第一手证据，Agent 的自述不算数——它省略掉的往往比写出来的更要紧。
- **第 3 课** 把每一步变成数据：结构化日志和指标。同一组指标，上一门课拿来判分，这门课拿来诊断。
- **第 4 课** 把散落的记录串成一棵树：一条提示词触发的所有模型请求与工具执行读成一个整体，子代理的调用嵌进父级。
- **第 5 课** 在循环的生命周期关口安探头，走一遍非确定性下的定位流程：从一堆记录里找到第一处分岔。
- **第 6 课** 动手：给你在本系列第 7 门课写的那个 harness 装上一整层观测，从「说不清」的症状追到具体哪一步出的岔子。

本课只点名不展开：记录怎么读是第 2 课的事，指标怎么设计是第 3 课，trace 是什么结构是第 4 课。

## 分寸：什么时候不用上全套

不是每个 Agent 都需要这一整套。一次性的小脚本——跑一遍、看一眼、跑完就删——给它配日志、指标和 trace 是纯粹的浪费。

判断标准不复杂：**观测投入应该跟「出事之后你得花多久说清楚为什么」成正比。** 自己跑、自己看、错了重来成本为零的，不用记；给别人用的、跑得久的、错了要花半天翻聊天记录的，从第一天就该记。

有一条线跟规模无关：只要 Agent 能动手——写文件、发请求、花钱——就别省测试。Agent 的自主性意味着更高的成本，以及错误复合的可能，所以建议在沙箱环境里做广泛测试，并配上合适的护栏[^S2]。

至于怎么知道自己做对了：跟任何 LLM 功能一样，成功的关键在于测量表现、并对实现做迭代[^S2]。而测量的前提是有东西可测——这就绕回了这门课要解决的事。

### Level 1：一个症状，三个说不清的原因

不用写代码。下面是三条线上会遇到的症状，都只给了用户那一侧看得见的信息：

1. Agent 交出的调研报告里引用了一个文件名 `docs/pricing-2024.md`，但仓库里根本没有这个文件。
2. 同一个归档任务，昨天跑了 12 轮就结束，今天跑到第 47 轮才停下，结果看起来差不多。
3. 用户问「帮我查一下这个报错在我们代码库里出现过几次」，Agent 回了一大段关于这个报错含义的科普。

对每一条症状：

- 列出**至少三个**从外面看彼此不可区分的候选原因；
- 对每个候选原因，写出「要确认是它、排除另外两个，我需要看到什么证据」。

证据要说到字段一级。「看日志」不算答案。

<!-- rubric -->

- 每条症状都写出了至少三个候选原因，且落在不同环节（模型的决策、工具的输入与输出、harness 的控制流或上下文处理），而不是同一个原因换三种说法。
- 每个候选原因都配了一条具体到「看哪一轮、哪条记录的哪个字段」的证据，而不是「看看日志」这种没有指向的答案。
- 每条症状都说清了：只有最终输出时，这几个原因为什么彼此不可区分——也就是解释了过程证据非留不可的理由。

<!-- answer -->

**症状一：报告引用了不存在的文件名**

- 模型决策环节：检索工具返回的都是真实文件，模型在写报告时把文件名记串了，或者按命名习惯编了一个。证据——把那次运行里所有 `read_file` / `read_doc` 的参数列出来，看这个文件名有没有作为参数出现过。一次都没出现过，说明它是在生成阶段被造出来的。
- 工具输入输出环节：检索工具确实返回了这个名字，因为索引是三周前建的，文件后来被改名或删掉了。证据——看那一轮 `search` 的返回体原文，里面是不是带着这个文件名。
- 控制流环节：读文件时工具报了「不存在」，但 harness 把异常吞了，只往 `tool_result` 里塞了空字符串，模型于是照着上一轮的假设接着写。证据——看那一轮 `tool_result` 的内容是不是空的、有没有带错误标记。
- 为什么不可区分：三条路的终态都是同一份报告、同一个假文件名，没有任何字段能分开它们。

**症状二：12 轮变 47 轮**

- 模型决策环节：今天的检索结果更零碎，模型反复换措辞试探。证据——把每一轮 `tool_use` 的工具名和参数列出来，看是不是同一个工具被换着词调了十几次。
- 工具输入输出环节：某个工具的分页大小或返回上限今天变了，一次拿不完只好多拿几次。证据——比对两天里同一工具的返回体大小与调用次数。
- 控制流环节：某一步失败之后 Agent 换了分支重来了一遍，前半段活干了两次。证据——把两次运行按轮次对齐，找**第一处**不一样的步骤，只看那一轮的工具返回。
- 为什么不可区分：终态都是「任务完成了，多花了点时间」。轮数只是个总量，不告诉你多出来的 35 轮长在哪一段。

**症状三：答非所问**

- 模型决策环节：模型把「出现过几次」理解成了「这是什么意思」。证据——看第一轮它有没有调检索工具，还是直接开始生成回答。
- 工具输入输出环节：检索工具报错或返回空，模型退回到用自己的参数知识作答。证据——那一轮 `tool_result` 的内容和错误标记。
- 上下文环节：这轮之前的历史被截断或压缩过，用户那句限定语「在我们代码库里」在真正发出去的消息里已经不在了。证据——看那次请求实际发出的 `messages`，而不是你以为发出的那份。
- 为什么不可区分：三种情况下用户收到的都是一段「不对题但读着挺顺」的文字。要分辨，得同时看「送进去的是什么」和「拿回来的是什么」。

<!-- hint -->

先给自己准备三个抽屉：模型的决策、工具的输入与输出、harness 的控制流与上下文处理。同一个症状往往在每个抽屉里都能找到一个说得通的原因。三个原因全落在同一个抽屉里，说明还没跳出第一反应。

<!-- hint -->

写证据时强迫自己说到字段一级：不是「看日志」，而是「看那一轮 `tool_result` 的内容、以及它有没有被标成错误」。说不到字段，就说明你还没想清楚该往记录里留什么——这正是第 2、3 课要动手做的事。

### Level 2：把传统调试流程逐步拆了

不用写代码。下面是每个后端工程师都熟的四步调试流程：

```text
1 复现       在本地用同样的输入把 bug 跑出来
2 打断点     停在可疑的那一行
3 单步       一行一行往下走，看变量什么时候变得不对
4 修复并确认  改完再跑一次，绿了就算修好
```

对每一步，回答两个问题：

- 它在 Agent 上为什么失灵？把原因落到具体机制上（非确定性、轨迹改道、证据被遮住或压根没留）。
- 它在 Agent 世界里的对应替代是什么？只需要写出方向——「要拿到什么证据、按什么维度组织」——具体实现是后面几课的事。

<!-- rubric -->

- 四步全都逐一处理了，每一步既写了失灵的原因、也写了对应的替代方向，包括最容易被跳过的第 4 步「修复并确认」。
- 失灵原因落到了具体机制上（两次运行之间的非确定性、一步失败导致整条轨迹改道、抽象层或缺记录让证据看不见），而不是笼统一句「因为模型不确定」。
- 替代方向说的是「要拿到什么证据、按什么维度把它们组织起来」，而不是「装某个观测产品」；只给方向、不展开实现细节，也算合格。

<!-- answer -->

**第 1 步 复现**

失灵原因：Agent 在两次运行之间是非确定的，即便提示词一模一样也是如此；就算起点完全相同，它也可能走上完全不同、但同样成立的路径。你在本地跑十次，很可能都不是出事那次走的路。

替代方向：放弃「再来一次」这个目标，改成让出事的那一次自己把过程留下来。要拿到的证据是那一次完整的模型请求与工具往返——这是第 2 课的内容。

**第 2 步 打断点**

失灵原因：断点挂在代码行上，可 Agent 出岔子的地方常常不在你的代码里，而在模型的一次决策上；而且循环可能几十轮，你不知道该停在第几轮。如果你还用了一个把提示词与响应包在抽象层底下的框架，连该看哪一行都定位不了。

替代方向：把「停在一行」换成「每一步都记一条」，事后按关联 ID 把属于同一次提示的记录过滤出来。探头具体挂在循环的哪些关口上，是第 3 课和第 5 课的内容。

**第 3 步 单步**

失灵原因：单步默认状态变化是局部、可预期的。但 Agent 是有状态的，错误会复利，一步失败就能让整条轨迹改道。你手工单步走出来的第 5 步，跟出事那次的第 5 步很可能不是同一件事。

替代方向：不要把一次运行读成一条线性的命令序列，读成一棵树——一条提示词触发的所有模型请求与工具执行归到一起，子代理的活动嵌进父级。要找的不是「哪一行错了」，而是**第一处分岔**：从哪一步开始，这次运行和成功的那次不一样了。树怎么建是第 4 课的内容，找分岔的流程在第 5 课。

**第 4 步 修复并确认**

失灵原因：跑一次绿了不能说明修好了，因为下一次可能走另一条路；而且微小的改动会级联成很大的行为变化，你在主 Agent 上的一点调整可能不可预测地改变子代理。只看这一条 case 变绿，容易把「这次刚好没走到那条分支」当成「修好了」。

替代方向：改完之后回到评测集上批量跑（本系列第 10 门课那套东西），同时看观测数据里的行为分布有没有跟着动——工具调用次数、轮数、报错率。评测回答「整体有没有变好」，观测回答「变好的原因是不是我以为的那个」。

<!-- hint -->

传统四步里，每一步都偷偷依赖一个前提：复现依赖「同样输入必然走同样路径」，断点依赖「问题在某一行代码里」，单步依赖「状态变化是局部的」，确认依赖「通过一次就算通过」。先把这四个前提原样写出来，再逐个问它在 Agent 上还成不成立。

<!-- hint -->

替代方向不用写成实现方案。「需要一份按轮次对齐的完整往返记录」就是合格答案，「需要能把同一条提示词触发的所有请求归到一起」也是。具体怎么落地是后面几课的事，这题只考你能不能把需求说清楚。

## 小结

- 一个用户可见的症状底下，常常压着好几个从外面完全不可区分的原因。用户报告 Agent「找不到明显的信息」时，你没法判断是搜索词差、来源挑得烂，还是撞上了工具故障[^S1]。
- 评测跑道回答的是「挂没挂」。本课用一句自己的提法把分工说清楚：验证告诉你挂没挂，可观测性告诉你为什么。支撑它的是两条真实经验——上了全链路 tracing 才能诊断失败并系统性地修[^S1]，以及读原始记录能帮你探究 Agent 为什么调或不调某个工具[^S3]。
- 「复现再打断点」失灵，是因为 Agent 做动态决策、两次运行之间非确定，即便提示词相同也一样[^S1]；确定性系统给相同输入产出相同输出，Agent 这类非确定性系统不保证这一点[^S3]。传统评估那套「输入 X 走路径 Y 出输出 Z」的假设也不成立，相同起点可以走出完全不同但都成立的路径[^S1]。
- Agent 的错误形态和传统 bug 不同：传统软件里 bug 破坏一个功能，Agent 系统里微小改动会级联成很大的行为变化[^S1]；一步失败就能让 Agent 转去探索完全不同的轨迹[^S1]；Agent 有状态、错误会复利，所以要能持久执行并沿途处理错误[^S1]；多 Agent 还有涌现行为，对主 Agent 的小改动会不可预测地改变子代理，要理解的是交互模式而非单体[^S1]。早期版本闹出过为简单查询孵 50 个子代理、为不存在的来源无休止扫网、用过量更新互相干扰这类事[^S1]。
- 抽象层会把证据挡住：框架常常制造额外的抽象层，遮住底层的提示词与响应，让它们更难调试[^S2]；建议直接从 LLM API 起步，用框架也要理解水面之下的代码[^S2]。你手写的 harness 没有这层遮挡，但也没有留存。
- 出路是把观测和紧凑的反馈回路当成一等要求[^S1]，落成一个由可观测性和测试用例构成的快速迭代回路[^S1]。后面五课依次是：原始记录、日志与指标、trace、hooks 与定位流程、动手实装。
- 分寸：一次性小脚本不必背全套。但只要 Agent 能动手，就在沙箱里做广泛测试并配上护栏[^S2]；判断做没做对，靠的是测量表现、对实现做迭代[^S2]。
