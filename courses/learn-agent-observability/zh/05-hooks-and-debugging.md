# 第 5 课：在关口安探头：hooks 与定位流程

> 学习目标：
> - 说清 hooks 是什么：在 Agent 生命周期固定点自动执行的用户自定义处理器，分「每会话一次 / 每轮一次 / 循环内每次工具调用」三种节奏，并能为一个观测需求挑对事件、写对 matcher、指出该用载荷里的哪些字段
> - 避开两个真会咬人的坑：hook 子进程拿不到 harness 的 OTel 导出配置，以及转录文件异步写入、hook 触发时可能还不含最近的消息
> - 用一条五步流程在非确定性下定位问题：按 prompt id 收窄、找第一处分岔、用一模一样的输入重放观察、反复压同一个组件、修复后从出错处恢复
>
> 前置要求：读完第 1–4 课（非确定性与「说不清」、原始记录作为第一手证据、结构化日志与指标、trace 树与遥测管道的陷阱） | 上一课 [第 4 课 <<](./04-tracing.md) | 下一课 [第 6 课 >>](./06-build-observability.md)

## 你想在工具执行前后各记一笔

第 3 课教你在自己的 harness 里给每次工具调用记一条结构化日志，第 4 课教你把这些记录串成一棵 trace 树。那是你写的循环，源码在手上，想在哪儿插一行 `log()` 就在哪儿插。可现在生产上跑的是 Claude Code——你没有它的 `runToolUses`。你要的东西并不复杂：工具执行之前记一笔（它打算用什么参数），执行之后再记一笔（它拿到了什么）。但插桩点在别人的进程里。

产品早想到了这件事，答案叫 hooks。

**hooks 是在 Claude Code 生命周期的特定点自动执行的用户自定义命令、HTTP 端点或 LLM 提示**[^S5]。翻成大白话：你在配置里声明「某某时刻，帮我执行这个脚本」，Claude Code 跑到那个时刻就执行它。而且不是空手来的——当一个事件触发、并且 matcher 命中时，Claude Code 会把这个事件的 JSON 上下文交给你的处理器[^S5]。

本系列第 7 门课里，你在 harness 循环中写过一个审批阀——遇到 HIGH_IMPACT 的工具，执行前停下来等人确认。那是你手搓的一个拦截点。hooks 做的是同一件事，但把「循环里有哪些值得停一下的位置」整理成了一份具名清单，每个位置的载荷固定、可依赖。对可观测性来说，这份清单的价值不在于「能改行为」，而在于**能不改行为地看**。

## 三种节奏：会话、轮、工具调用

事件分三种节奏[^S5]：

- **每会话一次**：`SessionStart` 和 `SessionEnd`
- **每轮一次**：`UserPromptSubmit`、`Stop` 和 `StopFailure`（从名字推断，`StopFailure` 对应轮次没能正常收尾的那条出口——官方引文只给了节奏归类，具体语义以你手上的参考页为准）
- **循环内每次工具调用**：`PreToolUse` 和 `PostToolUse`

对照本系列第 7 门课讲的循环解剖，三层立刻就对上了：

```text
SessionStart                       ← 会话开始（整个 runAgent 启动）
  UserPromptSubmit                 ← 一轮开始（用户提交提示）
    while (stop_reason === "tool_use") {
       ... 模型请求 ...
       PreToolUse                  ← 循环体内，参数已生成、还没执行
       ... 工具执行 ...
       PostToolUse                 ← 循环体内，工具执行完了
    }
  Stop / StopFailure               ← 一轮结束
SessionEnd                         ← 会话结束
```

选错节奏会得到很难解释的数：想统计「一次任务用了多少次工具」，插在每轮的关口上只能拿到零。挑事件之前先问一句：我要数的东西，一次会话里发生几次？

一个细节值得单拎出来：`SessionStart` 在新开会话时触发，**恢复已有会话时也触发**[^S5]。本系列第 9 门课讲过 `--resume`，从循环角度那不是「新开始」，但它同样会敲响 `SessionStart`。写「会话开始时初始化一份新日志」的人，第一次遇到 resume 就会把上一段记录覆盖掉。

## 观测用得上的关口细节

**`PreToolUse` 运行在 Claude 已经创建好工具参数之后、处理这次工具调用之前**[^S5]。这个夹缝很关键：参数已经定型（你能看到模型到底打算用什么参数），但工具还没跑。第 2 课讲过一个真实案例——官方发现 Claude 会往搜索工具的 query 参数里多余地追加 `2025`，把结果带偏[^S3]。这类毛病的证据就长在 `PreToolUse` 能看到的那份参数里。

**`PostToolUse` 在工具已经成功执行之后触发，输入里同时包含 `tool_input`（发给工具的参数）和 `tool_response`（工具返回的结果）**[^S5]。一次触发就给你一条完整的调用记录，不用自己把「哪次请求配哪次响应」拼回去。第 2 课强调过的原则——完整往返才是第一手证据[^S3]——在这里是一个字段对一个字段直接拿到的。注意它的触发条件是「已经成功执行」[^S5]；想覆盖参数生成了、但执行没成功的情况，得把 `PreToolUse` 一起配上，用两边的记录做差。

**matcher 怎么写**：想让一个钩子在任何工具完成后都跑，省略 `matcher` 或者设成 `"*"` 就行[^S5]。观测场景要的正是这种一钩全记——你不知道哪个工具会出问题，所以哪个都记。

**处理器怎么收发数据**：命令钩子通过 stdin 接收 JSON 数据，通过退出码、stdout 和 stderr 传回结果[^S5]。所以一个最小的观测处理器就是「从 stdin 读一段 JSON，挑几个字段追加进文件，退出码 0」，没有任何魔法。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "*",
        "hooks": [
          { "type": "command", "command": "node ~/.claude/obs/record-tool-call.mjs" }
        ]
      }
    ]
  }
}
```

```javascript
#!/usr/bin/env node
// record-tool-call.mjs —— PostToolUse 处理器
// 从 stdin 收一段 JSON，抄成一行 JSON Lines，退出码 0 表示一切正常
import { appendFileSync, mkdirSync } from "node:fs";

let raw = "";
process.stdin.setEncoding("utf8");
process.stdin.on("data", (chunk) => { raw += chunk; });
process.stdin.on("end", () => {
  const evt = JSON.parse(raw);
  const line = {
    ts: new Date().toISOString(),
    session_id: evt.session_id,
    prompt_id: evt.prompt_id,
    tool: evt.tool_name,
    input: evt.tool_input,       // 发给工具的参数
    response: evt.tool_response, // 工具返回的结果
  };
  mkdirSync("/tmp/agent-obs", { recursive: true });
  appendFileSync("/tmp/agent-obs/tool-calls.jsonl", JSON.stringify(line) + "\n");
  process.exit(0);
});
```

这就是第 3 课那份 JSON Lines 日志，只不过写日志的人从「你的 harness」换成了「你挂在别人循环上的一个小脚本」。配置项与字段名的确切写法以你手上这个版本的参考页为准。

**载荷里有耗时，但口径要看清**：载荷里带一个可选字段，是工具执行的毫秒数，**不含花在权限提示和 `PreToolUse` 钩子上的时间**[^S5]。后半截是重点：用户体感上的「这一步等了多久」包含等他点确认的那段，而这个数把它剔掉了。拿它回答「工具慢不慢」是对的，拿它回答「用户等了多久」会系统性偏小。第 4 课提过同一件事的另一个说法——工具 span 底下挂着两个子 span，一个是等权限决定的时间、一个是执行本身[^S4]，分开记正是因为这两段不该混。

**hook 自己也在 trace 里**：每个用户提示开启一个 `claude_code.interaction` 根 span，API 调用、工具调用和 hook 执行都记录成它的子节点[^S4]。观测手段本身也是被观测的对象。

## 两条会咬人的告诫

**第一条：hook 子进程不继承 OTEL_\* 导出变量。** 有一组变量是不被继承的——Claude Code 会从它派生的每一个子进程里移除 `OTEL_*` 导出变量，hooks 也不例外[^S5]。

这句话直接否掉一个非常自然的想法：「harness 那边已经把 endpoint、协议、认证头都配好了，我在 hook 里引一个 OTel SDK，环境变量顺手就能用。」——用不了。处理器进程启动时那些变量已经被剥掉了，数据要么发不出去，要么打到默认端点上石沉大海。更别指望有人喊一嗓子提醒你：第 4 课讲过，CLI 自己那套导出连失败都是静默的[^S6]，你在 hook 里自建的 exporter 默认也不会更吵——没数据到后端时，两边都安安静静。

能走的路有两条：一是 hook 自带一整套导出配置（在脚本里显式写 endpoint 和认证，不指望继承）；二是别在 hook 里发遥测，让它落一份结构化日志，靠 ID 在后端跟遥测对齐。第二条路有官方支撑：hook 载荷里那个标识当前正在处理的用户提示的 UUID，与 OpenTelemetry 事件上的 `prompt.id` 属性是同一个值，所以你能把 hook 的输出和同一次提示的遥测关联起来[^S5]。两边各写各的，最后用同一个 prompt id join——跟第 4 课「靠关联 ID 串成一棵树」是同一招，只是这次跨了两个数据源。

**第二条：转录文件是异步写的。** 载荷里会给你一个指向对话 JSON 的路径，但这个文件是异步写入的，可能落后于内存里的对话，所以 hook 触发时它可能还不包含当前这一轮最近的消息[^S5]。

坑人的地方在于它不报错，只给你旧数据。有人会想「载荷字段不够用，我直接读转录文件，那里什么都有」，结果是记录时好时坏地缺半截。**要 `tool_input` 和 `tool_response` 就用载荷里的字段**，那是 `PostToolUse` 明确保证会给你的[^S5]。转录适合事后回看，不适合在 hook 触发那一瞬间当实时数据源。

顺带一条跟你机器有关的提醒：命令钩子是以你的完整用户权限执行 shell 命令的，能修改、删除、访问你的用户账户能访问的任何文件，所以把任何 hook 命令加进配置之前，先审再装[^S5]。

## hook 自己不干活的时候

你挂了钩子，日志文件里空空如也。是没触发？matcher 没命中？还是脚本自己崩了？这时候要观测的对象变成了观测手段本身，第 4 课那个道理在这里又用一遍：探测器自己要先验证。

**hook 的执行细节——哪些钩子命中了、它们的退出码、完整的 stdout 和 stderr——都会写进 debug 日志文件**[^S5]。拿到它有两种方式：用 `claude --debug-file <path>` 写到你指定的位置，或者跑 `claude --debug`，然后去 `~/.claude/debug/<session-id>.txt` 读[^S5]。想看得更细，把 `CLAUDE_CODE_DEBUG_LOG_LEVEL` 设成 `verbose`，会多出一些日志行，比如 hook matcher 的计数[^S5]。

```text
排查顺序：日志文件是空的
 └─ debug 日志里有这个钩子的命中记录吗？
      没有  → matcher 写错了；先用省略 matcher 的版本确认能触发
      有    → 退出码是 0 吗？
               不是 → 读 stderr，多半是脚本路径、权限或 JSON 解析
               是   → 跑了但没写对地方；检查写入路径与目录是否存在
```

## 定位流程：非确定性下怎么查一个问题

前半课讲探头装在哪儿，后半课讲拿着这些数据怎么真的查出一个问题。

先把难处摆正。第 1 课说过：Agent 做的是动态决策，两次运行之间是非确定性的，即使给一模一样的提示词也一样，这让调试变难[^S1]。传统调试的第一步是「复现」，而这一步在这里不成立——你重跑一遍，它可能走一条完全不同、但同样合法的路。

下面这五步是**本课自己的编排**，不是哪家的官方方法论；但每一步踩的那块砖各自有出处。

### 第一步：收窄

在前四课攒下的记录里，先把范围缩到「这一次出问题的提示」上。第 4 课给过办法：**要追踪单条提示触发的全部活动，按某个具体的 `prompt.id` 值过滤你的事件**[^S4]。

这一步的意义不在技术，在心态。「Agent 出问题了」是个没法查的命题；「这一条 prompt id 底下的 11 条事件里有一条不对劲」是个能查的命题。

### 第二步：找第一处分岔

从头往后读，找**行为开始偏离预期的第一步**。为什么执着于「第一处」？因为一步失败会让 Agent 探索完全不同的轨迹，导向不可预测的结果[^S1]。你在末尾看到的那些荒唐（引用了不存在的文件、连着报错、绕远路），绝大多数是下游噪声。去修第 8 条事件，多半是在给第 4 条的错误擦屁股。

判断「偏离」有几个好用的形状[^S3]：调了不该调的工具、调了对的工具但参数不对、该调的工具调得太少、或者拿到工具响应之后处理错了。最后一种最难看出来，因为工具本身返回的是成功，日志上一片绿——错的是 Agent 对这个成功结果的理解。

### 第三步：重放观察

官方的做法是：为了理解提示词的效果，**用系统里一模一样的提示词和工具搭模拟环境，然后逐步观看 Agent 干活**；这个办法立刻暴露了几种失败模式——已经拿到足够结果了还继续往下找、搜索词写得过于啰嗦、选错了工具[^S1]。

「立刻暴露」四个字值得琢磨。同样这些毛病，在聚合指标里看不见（成功率还挺高），在事后日志里要一条条读才能察觉，但盯着它一步一步跑，人眼几秒钟就能看出「它明明已经够了还在搜」。重放时两件事要控住：输入必须是同一份（提示词、工具定义都不能顺手改），观察必须是逐步的。

### 第四步：反复压同一个组件

如果嫌疑落在某个工具身上，单跑几次很可能什么也看不出来——非确定性会让毛病时隐时现。

官方造过一个工具测试 Agent：给它一个有缺陷的 MCP 工具，它去试着用，然后重写工具描述来避开失败；**通过把这个工具测试几十次，这个 Agent 找出了关键的细节和 bug**[^S1]。

「几十次」是重点。一次运行藏得住的毛病，几十次会把它逼出来：某个边界输入下的返回形态特别、某句描述有歧义、某个错误文案让模型误判成「重试就好」。第 3 课的诊断读法在这里接得上——大量重复调用暗示分页或 token 上限参数需要调，大量参数无效的报错暗示工具描述该写清楚、该配例子[^S3]。顺带一句能省很多次往返的事：工具报错时把错误响应也当提示词来写，清楚说明具体该怎么改，而不是甩一串不透明的错误码或调用栈[^S3]。

### 第五步：修复后从出错处恢复

改完了，别习惯性地按「重新开始」。官方的说法很直接：错误发生时不能只是从头重启——重启既贵又让用户难受；他们建的系统是从 Agent 出错的那个位置恢复[^S1]。

本系列第 9 门课讲过恢复机制怎么做，那一课的场景是「任务被打断了怎么接着跑」。在调试里它是另一种用法：出错点之前的几十次工具调用是有效的、花过钱的、结果正确的，重跑一遍除了烧 token 什么也不多给你，还引入一堆新的非确定性，让你分不清「这次好了」是修对了还是运气好。

## 关于「复现」，说句诚实话

你可能在别处见过一套让 Agent 可复现的技法：固定随机种子、把 temperature 设成 0、录制真实的工具返回做回放桩。

这些做法在工程上确实有人用，本系列第 8–10 门课实战里那个桩 client 就是同一个路子——把一次真实运行的 `tool_result` 存下来，之后每次都返回同一份，工具这一侧就变成了确定的。用来验证「我改的这行代码有没有改坏解析逻辑」很好使。

但要说清两件事。第一，**这些技法没有任何一手来源背书**。上面五步流程的每一步我都给了出处，这一段我不给，因为确实没有。你在网上看到「官方推荐用 temperature 0 来复现 Agent 问题」之类的说法，让对方把链接发过来。

第二，它们能锁住的东西比听上去少。桩住工具返回锁住的是环境，模型这一侧仍然是非确定性的[^S1]。所以它把「两个变量都在动」变成了「只有一个变量在动」——这已经很有价值，但不是那种「同样输入必得同样输出」的复现。别拿它当保证，拿它当降噪。

## 什么问题值得走这套流程

五步走完是有成本的：收窄要查日志，重放要搭模拟，压组件要跑几十次。一个粗糙但够用的分法：

- **低频、无害的抖动**——比如某次多调了一次搜索，结果照样对。记在案，攒着。单看每一条都不值得查，攒到十几条之后往往能看出共同的模式，那时候再一次性查划算得多。
- **高影响的**——给出了错的事实、动了不该动的文件、卡死不返回。不管频率多低都立案，一次就够贵了。
- **复发的**——同一个形状的问题第三次出现，说明它不是运气，是结构问题。立案。

第 1 课那句话在这里是判断依据：一个用户可见的症状底下，压着好几个从外面看不可区分的内部原因[^S1]。你决定不查一个问题，等于接受「我不知道它是哪个原因」——对无害抖动这没关系，对高影响问题这就是在赌。

本课到此为止是纸上的。第 6 课把两半合起来动手：给本系列第 7 门课的 harness 装上一整层观测，然后拿一个「说不清」的症状从头追到底。

### Level 1：给三个观测需求配钩子

有三个观测需求。对每一个，写出：**挑哪个事件**、**matcher 怎么写**、**用载荷里的哪些字段**、以及**这个需求特有的坑是什么**。不需要写完整代码，配置片段和一两句说明就够。

1. 记录每次工具调用的完整参数与结果，落成 JSON Lines。
2. 统计每一轮（用户提交一次提示到这一轮结束）的耗时。
3. 会话恢复时，提醒用户「上次遗留了一个未完成的任务」。

<!-- rubric -->

**评分要点**

- 需求 1 选 `PostToolUse`，matcher 省略或 `"*"`，字段用载荷里的 `tool_input` 与 `tool_response`；坑答到「不要去读转录文件」并说出原因是异步写入、可能滞后。
- 需求 1 若额外指出「`PostToolUse` 只在成功执行后触发，要覆盖失败情况需搭配 `PreToolUse`」，加分。
- 需求 2 选每轮节奏的事件配对：`UserPromptSubmit` 记起点、`Stop` 记终点，并考虑到 `StopFailure` 这条异常出口；坑答到「不能把 `PostToolUse` 载荷里的执行毫秒数加总当轮耗时」，并说清那个数不含权限等待与 `PreToolUse` 的时间。
- 需求 3 选 `SessionStart`；坑答到「新开会话和恢复会话都会触发这个事件」，并给出区分两者的具体办法。
- 三问都答到「事件 + 字段 + 坑」三项才算完整，工具类需求（需求 1）还要多答一项 matcher；只写事件名不算。

<!-- answer -->

**需求 1**

- 事件 `PostToolUse`：工具成功执行之后触发，输入里同时带 `tool_input` 和 `tool_response`，一次触发就是一条完整往返记录，不用自己配对。
- matcher 省略或写 `"*"`——观测要的就是一钩全记，你事先不知道哪个工具会出问题。
- 字段：`tool_name`、`tool_input`、`tool_response`，外加会话标识和 prompt id。带 prompt id 是因为它跟遥测事件上的 `prompt.id` 是同一个值，之后能 join。
- 坑：**别为了「拿更全的上下文」去读载荷给的转录文件路径**。转录异步写入、可能落后于内存里的对话，hook 触发那一刻它可能还不包含当前轮最近的消息，你会得到时好时坏的残缺记录，而且不报错。
- 补充：`PostToolUse` 的前提是「成功执行」。还关心「参数生成了但没跑成」，就再配一个通配的 `PreToolUse` 记下参数，两边做差捞出没走到 `PostToolUse` 的调用。

**需求 2**

- 事件是一对，都在「每轮一次」的节奏上：`UserPromptSubmit` 落起点时间戳，`Stop` 落终点并算差值。`StopFailure` 也要挂同一个处理器，否则异常结束的轮次永远没有终点，起点记录一直悬着。
- 这几个事件不针对工具，不需要工具通配。
- 字段：把起点写进一个以 prompt id 为键的临时文件，终点用同一个 prompt id 取回做差。用 prompt id 而不是会话标识，因为一次会话里有很多轮。
- 坑：**别把 `PostToolUse` 载荷里的执行毫秒数加总当轮耗时**。那个字段的口径是工具执行时间，明确不含花在权限提示和 `PreToolUse` 钩子上的时间，而且模型请求时间压根不在里面。这么算会系统性偏小，越是需要人点确认的工作流偏得越多。

**需求 3**

- 事件 `SessionStart`（提醒的时机）加 `SessionEnd`（记录遗留状态的时机），两个都在「每会话一次」的节奏上。字段用会话标识，把「谁遗留的」对上号。
- 坑：**`SessionStart` 在新开会话和恢复已有会话时都会触发**。不加区分地弹提醒，用户每次全新开会话都会被告知「你有未完成任务」，很快就没人看了。
- 区分办法（不依赖任何具体字段名的稳妥版）：让 `SessionEnd` 判断这次结束时有没有留下未完成的活儿，有就往一个以会话标识命名的快照文件里写一份；`SessionStart` 只做一件事——找有没有对应的快照，找到才提醒，读完就删。全新会话找不到快照，自然不响。顺便还解决了另一个问题：判断「未完成」需要的信息在会话结束那一刻最全。
- 相关的坑：写成「`SessionStart` 时初始化一份新的空日志」的处理器，第一次遇到恢复会话就会把上一段记录清掉。

<!-- hint -->

提示：先给三个需求各自定位到节奏。问自己「这件事一次会话里发生几次」——每次工具调用一次？每轮一次？整个会话一次？节奏定了，事件基本就定了。

<!-- hint -->

提示：三个坑分别藏在三处细节里——第一个跟「转录文件什么时候被写」有关；第二个跟「那个毫秒数把什么排除在外了」有关；第三个跟「这个事件除了新建会话还在什么时候触发」有关。三处本课前半部分都明确写过。

### Level 2：一份病例，走一遍五步

**症状**：用户报告「它给我的汇总报告里引用了根本不存在的文件」。

你按这条提示的 prompt id 过滤，拿到下面这段事件摘要（原始提示是「读一下 reports/ 目录，把本季度三份周报的结论汇总给我」）：

```text
prompt.id = 8f2c1a94-...   （同一条用户提示触发的事件摘要，按时间排序；
                            input/response 就是 hook 载荷里的 tool_input/tool_response，此处为排版缩写；
                            tool_decision 每次调用都有一条，摘要里只保留 #3 一条示意）

#1   user_prompt     prompt_length=27
#2   llm_request     dur=1840ms  stop_reason=tool_use
#3   tool_decision   tool=list_files   decision=allow（在允许列表内，无人工等待）
#4   tool_result     tool=list_files   input={"path":"reports/"}
                     response={"entries":[]}   success=true   dur=12ms
#5   llm_request     dur=2210ms  stop_reason=tool_use
#6   tool_result     tool=read_file    input={"path":"reports/2026-Q2-week03.md"}
                     success=false   error="ENOENT: no such file or directory"
#7   llm_request     dur=1990ms  stop_reason=tool_use
#8   tool_result     tool=read_file    input={"path":"reports/q2-summary.md"}
                     success=false   error="ENOENT: no such file or directory"
#9   llm_request     dur=2400ms  stop_reason=tool_use
#10  tool_result     tool=search_notes input={"query":"Q2 周报 结论 2026"}
                     response={"hits":[3 条与本项目无关的旧笔记]}   success=true
#11  llm_request     dur=5100ms  stop_reason=end_turn
#12  最终回答        「根据 reports/2026-Q2-week03.md 与 reports/q2-summary.md
                     两份周报，本季度……」
```

不用写代码。按五步流程回答四个问题：

1. **第一处分岔是哪一条事件？** 指到具体编号，并说清为什么它前面那几条不算、后面那几条只是下游。
2. **重放观察怎么做？** 用哪一份输入、盯着看什么。
3. **「反复压同一个组件」在这里压的是什么？** 说清压的对象和要观察的现象。
4. **修好之后从哪里恢复？** 说清恢复点和为什么不从 #1 重跑。

<!-- rubric -->

**评分要点**

- 第一处分岔指到 **#5**（Agent 拿到空目录之后仍然生成了一次 `read_file` 调用），或指到「#4 与 #5 之间那个决策」并说明最早的可观察证据落在 #6 的 `tool_input` 上。只指 #6 或 #12 判为「指到了下游」。
- 必须说清 **#4 不算分岔**：`list_files` 返回 `success=true`、耗时 12ms，工具本身工作正常，错的是 Agent 对空结果的处理。
- 必须说清 **#6/#8/#10 是下游**：一步失败会让轨迹整体改道，后面这几步是在给 #5 的判断擦屁股。
- 重放答案要包含两个约束：输入用一模一样的提示词与工具定义；观察是逐步的，重点看模型拿到空 `entries` 之后的第一反应。
- 「反复压同一组件」要指向 `list_files`（空结果的返回形态与工具描述），而不是笼统地说「多跑几次看看」；要给出压的维度（不同路径形态）和要看的现象（模型每次怎么解读空结果）。
- 恢复点答 **#4 之后、#5 之前**，并给出不从 #1 重跑的理由：#1–#4 结果正确、重跑白烧 token，且会引入新的非确定性、分不清「这次好了」是修对了还是运气好。
- 四问都答到才算完整。答案与事件序列自相矛盾（例如说 `list_files` 报错了）判为不通过。

<!-- answer -->

**1. 第一处分岔：#5。**

#4 的 `list_files` 返回 `{"entries": []}`、`success=true`、12ms——这一步工具干得没毛病，它诚实地报告了「这个路径下没有条目」。真正开始偏离的是 #5：Agent 拿到一个空目录之后，正确的行为是停下来告诉用户「reports/ 下面没有文件，请确认路径」，但它生成了一次 `read_file` 调用，参数是 `reports/2026-Q2-week03.md`。

最早能在记录上看见这个分岔的地方是 **#6 的 `tool_input`**——那个路径从未出现在此前任何一条 `tool_response` 里。这是一条可以机器化检查的判据：后续调用或报告里出现的文件名，能不能在之前的工具响应中找到出处；找不到就是凭空来的。

前面几条为什么不算：#2 判断该列目录，合理；#3 是权限放行，没有人工等待；#4 工具正常。后面几条为什么是下游：#6 和 #8 的两次 ENOENT、#9 转去 `search_notes`、#10 捞回三条不相关的旧笔记、#12 把编出来的文件名写进报告——全是在 #5 那个错误前提上继续往前推。修 #6（比如把 ENOENT 的文案写得更友好）不解决问题，因为 #5 压根就不该发生。

分岔属于哪一类：不是「调了不该调的工具」，也不是「工具报错了」，而是**拿到工具响应之后处理错了**——这类最难在监控上发现，因为出问题的那一步在日志上是绿的。

**2. 重放观察。**

用一模一样的提示词和一模一样的工具定义搭一个模拟，逐步观看它干活。两个约束不能松：输入原样照搬，不能顺手「改清楚点」，否则你观察的就不是原来那个系统了；观察要一步一步看，不能一次跑完只看最终报告——分岔那一步的信息全在中间。

盯什么：**模型拿到空 `entries` 之后的第一个动作**。把 #4 的响应固定成 `{"entries": []}` 喂回去，看它是停下来报告空目录，还是往下编。如果几次重放里表现不一，说明这是个概率性行为，得靠第四步把频率量出来。这一步大概率还会顺带暴露别的毛病——#10 那条 query 里的「2026」就跟官方那个真实案例撞了脸（往搜索词里多余地追加年份、把结果带偏），整条 query 也偏啰嗦。

**3. 反复压的是 `list_files`。**

压的对象不是整个 Agent，是这一个工具在空结果这个边界上的表现，具体两样东西：

- **返回形态**：`{"entries": []}` 对模型来说信息量太低。同样是空，可以返回得更明确，比如区分「路径存在但没有条目」和「路径不存在」，让模型知道该报告哪一种。
- **工具描述**：有没有说清空结果意味着什么、拿到空结果之后应该做什么。

方法是把这个工具反复用几十次，覆盖不同的路径形态：不存在的、存在但为空的、有内容的、权限不足的，每种跑很多次，看模型每一次怎么解读返回值、多大比例会往下编文件名。几十次的意义就在这儿——单跑三五次，「有时候会编」这个毛病可能一次都不出现。官方那个工具测试 Agent 就是这么用的。

如果压测显示模型在 ENOENT 之后倾向于换个名字再试，那 `read_file` 的错误文案也该一起改——错误响应可以当提示词来写，明确告诉它「这个路径不存在，请先列目录确认，不要猜测文件名」，比甩一个 `ENOENT` 有用。

**4. 从 #4 之后恢复。**

恢复点是 **#4 的 `tool_result` 已经进了上下文、#5 还没发生**的那个位置。换上改好的返回形态与描述，从这里重新走一步，看它这次是不是停下来报告空目录。

不从 #1 重跑有两条理由。一是浪费：#1–#4 的结果完全正确，重跑只是把同样的目录再列一次。二是更要紧的——重跑会把非确定性重新放进来。模型可能这次连 `list_files` 都不调，那你就没法判断「这次没编文件名」是因为你修对了，还是因为它刚好走了另一条路。从 #4 之后恢复，把变量锁在了你要验证的那一步上。

<!-- hint -->

提示：从后往前读这段事件，你会先看到两次 ENOENT，很容易停在那儿。但 ENOENT 说明的是「这个文件不存在」——问题是，那两个文件名是从哪里来的？在事件序列里往回找它们的出处，找不到出处的地方就是分岔。

<!-- hint -->

提示：注意 #4 的 `success=true`。工具没有失败，它返回了一个正确的空结果。所以这个病例的分岔类型不是「工具报错」，而是「Agent 对一个正确的结果理解错了」——想清楚这一点，第三问该压什么就有方向了：压的是那个返回空结果的东西，不是那个报错的东西。

## 小结

- hooks 是在 Claude Code 生命周期特定点自动执行的用户自定义命令、HTTP 端点或 LLM 提示；事件触发且 matcher 命中时，Claude Code 把该事件的 JSON 上下文交给你的处理器[^S5]。
- 事件分三种节奏——每会话一次（`SessionStart`/`SessionEnd`）、每轮一次（`UserPromptSubmit`/`Stop`/`StopFailure`）、循环内每次工具调用（`PreToolUse`/`PostToolUse`）[^S5]。挑事件之前先定节奏。`SessionStart` 在恢复会话时也触发[^S5]。
- `PreToolUse` 跑在参数已生成、调用尚未处理之间；`PostToolUse` 在工具成功执行后触发，输入里同时带 `tool_input` 与 `tool_response`，一次触发给你一条完整的调用记录[^S5]。matcher 省略或设成 `"*"` 就是一钩全记[^S5]。
- 命令钩子从 stdin 收 JSON，用退出码、stdout 和 stderr 回话[^S5]；载荷里那个执行毫秒数不含权限提示和 `PreToolUse` 花掉的时间[^S5]，别拿它当用户等待时长。
- 两条负面结论：Claude Code 会从每个派生的子进程（包括 hooks）里移除 `OTEL_*` 导出变量[^S5]，想在 hook 里发遥测得自带导出配置；载荷给的转录文件是异步写入的，hook 触发时可能还不含当前轮最近的消息[^S5]。命令钩子以你的完整用户权限执行，装之前先审[^S5]。
- hook 自己不干活时，去 debug 日志里看命中了哪些钩子、退出码和完整的 stdout/stderr，用 `--debug-file` 指定位置[^S5]；想看 matcher 计数就把日志级别设成 verbose[^S5]。hook 载荷里的 prompt id 与遥测事件上的 `prompt.id` 是同一个值，两边数据能对齐[^S5]。
- 定位流程五步（本课的编排）：按 `prompt.id` 过滤出这次提示触发的全部事件[^S4] → 找第一处分岔，因为一步失败会让整条轨迹改道[^S1] → 用一模一样的提示词和工具做模拟、逐步观看[^S1] → 把嫌疑组件反复用几十次把毛病逼出来[^S1] → 修好后从出错处恢复而不是从头重启[^S1]。
- 固定种子、temperature 0、录制回放工具返回这些技法没有一手来源背书，本课按工程实践口径介绍：它们锁住的是环境这一侧，模型仍然是非确定性的[^S1]，所以是降噪，不是复现保证。
- 不是每个问题都值得走全流程：低频无害的抖动记在案、攒成模式再查；高影响或复发的才立案深查。
