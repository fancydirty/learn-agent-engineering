## 되짚기: 서브에이전트가 못 보는 것은, 여러분이 적어 넣어 줘야 한다

레슨 2는 여기서 중요한 메커니즘 하나를 다뤘습니다. "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there."[^S3] (각 서브에이전트는 새롭고 격리된 컨텍스트 윈도로 시작한다. 여러분의 대화 기록도, 이미 호출한 스킬도, Claude가 이미 읽은 파일도 보지 못한다. Claude가 작업을 요약한 위임 메시지를 작성하면, 서브에이전트는 거기서부터 작업한다.) 이 레슨은 그것을 구체화합니다. 오케스트레이터 층위에서 사용자와 함께 짚어 온 모든 배경, 앞선 라운드에서 정리한 절충, 사용자가 지나가듯 던진 제약을 서브에이전트는 하나도 알지 못한다는 뜻입니다. 서브에이전트가 아는 것은 여러분이 이 하나의 위임 작업에 적어 넣은 말뿐입니다.

이것은 부드러운 알림이 아니라 단단한 제약입니다. **위임 프롬프트의 품질 상한이 서브에이전트 산출물의 품질 상한을 정합니다**. 프롬프트가 명시하지 않은 것은, 서브에이전트가 추측하거나, 건너뛰거나, 가정을 지어내 계속 진행합니다. 맞게 추측하면 운이 좋은 것이고, 틀리게 추측하면 그 하위 작업은 사실상 낭비됩니다.

## 자기완결성: 프롬프트가 홀로 전부를 말해야 한다

**자기완결성**: 위임 프롬프트를 읽고 나면, 서브에이전트는 자신이 무엇을 해야 하는지 정확히 알아내는 데 추가 배경이 필요하지 않습니다. 프롬프트가 자기완결적인지 가리는 간단한 시험이 있습니다. 그것만 따로 떼어내, 여러분과 오케스트레이터 사이의 모든 컨텍스트를 벗겨낸 채로, 차갑게 읽어 보세요. 그래도 작업 세부를 채우려면 *추측*해야 한다면, 그 프롬프트는 시험에 통과하지 못한 것입니다.

레슨 1의 세 클라우드 제공업체 가격 조사 예시를 봅시다. 오케스트레이터가 서브에이전트에게 "AWS 가격을 찾아봐"라고만 적힌 작업을 넘긴다면, 그 한 줄은 오케스트레이터 자신에게는 충분한 정보를 담고 있습니다. 오케스트레이터의 컨텍스트에는 여전히 "왜 이걸 찾는지", "그다음 무엇과 비교할지", "어떤 차원으로 비교하는지"의 배경이 남아 있기 때문입니다. 하지만 서브에이전트는 그중 무엇도 보지 못합니다. 서브에이전트가 받는 것은 "AWS 가격을 찾아봐"라는 외로운 한 줄이고, 추측하는 수밖에 없습니다. 어느 제품 카테고리의 가격? 현재 가격만, 아니면 지난 1년간의 변화까지? 찾고 나면 산출물은 어떤 모양이어야 하지? 추측 하나하나가 빗나갈 수 있는 도박입니다.

## 범위와 제약을 명시하라: 무엇을 할지, 무엇을 하지 말지, 어떤 출처를 쓸지

공식 가이드는 탄탄한 서브에이전트 작업 설명이 담아야 할 것을 나열합니다. "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information."[^S1] (각 서브에이전트에는 목표, 출력 형식, 쓸 도구와 출처에 대한 안내, 그리고 뚜렷한 작업 경계가 필요하다. 상세한 작업 설명이 없으면 에이전트들은 작업을 중복하고, 빈틈을 남기고, 필요한 정보를 찾지 못한다.)

그 목록을 풀어 봅시다. "목표"와 "출력 형식"은 파악하기 쉽습니다. 건너뛰기 쉬운 것은 마지막 한 쌍, 곧 **출처 안내**와 **작업 경계**입니다. 출처 안내는 서브에이전트에게 답을 어디서 찾을지 알려 줍니다. 공식 가격 페이지인지, 제3자 가격 비교 사이트인지, 아니면 둘 다이되 공식 페이지가 우선인지. 작업 경계는 서브에이전트에게 이번 실행은 이 조각만 다루니 그 너머로 뻗지 말라고 알려 줍니다. 현재 가격만, 과거 가격 변화는 안 됨. 주요 제품 라인만, 온갖 잘 알려지지 않은 서비스까지 열거하지 말 것. 이 둘을 놓치면 서브에이전트는 둘 중 한 방향으로 흐르기 쉽습니다. 실제로 원했던 정보를 놓치거나, 아니면 원한 것보다 훨씬 많이 가져와 아낄 수 있었던 도구 호출과 토큰을 태웁니다.

범위가 뚜렷한 자기완결적 작업 설명으로 다시 쓰면, 클라우드 제공업체 조사는 대략 이런 모양입니다.

```json
{
  "objective": "AWS 주력 컴퓨트 서비스(EC2)의 현재 가격 구조를 조사하되, 두 과금 모델인 온디맨드 인스턴스와 예약 인스턴스에 초점을 맞춘다",
  "scope": "지금 이 순간 유효한 가격만 조사하고, 과거 가격 변화는 다루지 않는다. 범용 및 컴퓨트 최적화 인스턴스 유형만 다루고, 모든 인스턴스 패밀리를 다룰 필요는 없다",

```

따로 떼어 놓고 봐도, 이 설명은 서브에이전트가 오케스트레이터가 내부적으로 논의한 무엇도 알지 못한 채로 "무엇을 찾고, 어디까지 밀고 갈지, 무엇을 내놓을지"를 정확히 판단하게 해 줍니다.

## 반례: 막연한 지시는 서브에이전트를 임기응변에 내맡긴다

범위와 경계를 명시하지 않으면 실제로 무엇이 어긋나는지 — 공식 팀이 실무에서 겪은 실제 사례를 주었습니다. "We started by allowing the lead agent to give simple, short instructions like 'research the semiconductor shortage,' but found these instructions often were vague enough that subagents misinterpreted the task or performed the exact same searches as other agents."[^S1] (우리는 리드 에이전트가 'research the semiconductor shortage' 같은 짧고 단순한 지시를 주는 것으로 시작했지만, 이런 지시는 흔히 충분히 막연해서 서브에이전트들이 작업을 오해하거나 다른 에이전트와 똑같은 검색을 수행한다는 것을 알게 되었다.)

"research the semiconductor shortage"는 작업을 넘기는 것처럼 읽히지만, 아무것도 못 박지 못합니다. 어느 기간에 걸쳐? 공급 측, 수요 측, 아니면 정책 영향에 초점? 어떤 형태로 내놓을지? 같은 막연한 지시를 받은 세 서브에이전트는 십중팔구 모두 "반도체 부족의 원인", 곧 가장 먼저 떠오르는 각도로 검색해 갈 것이고, 그 결과는 심하게 겹치는 세 뭉치의 조사가 되며, 정작 다뤄야 했던 각도(가령 하류 산업에 미친 영향, 또는 나라별 대응)는 손대지 않은 채 남습니다. 이것이 레슨 2의 "중복 작업" 문제의, 프롬프트 층위에서의 뿌리입니다. 서브에이전트가 말을 안 들어서가 아니라, 작업 설명 자체가 경계를 긋지 않았기 때문입니다.

## 하나의 문제 영역, 하나의 에이전트

프롬프트 하나를 명료하게 쓰는 것을 넘어, 여러 서브에이전트가 일을 어떻게 나누는지도 공식 실무에서 추려낼 수 있는 원칙을 따릅니다 — 공식 팀이 이름 붙인 적은 없고, 이 이름은 우리 것입니다: **하나의 문제 영역, 하나의 에이전트** — 각 서브에이전트는 하나의 서브에이전트가 무관한 여러 일을 한꺼번에 다루는 대신, 뚜렷이 경계 지어진 한 부류의 문제만 맡아야 합니다.

공식 시스템에는 직접적인 예가 있습니다. 그들은 전용 CitationAgent를 두었습니다. "a CitationAgent, which processes the documents and research report to identify specific locations for citations. This ensures all claims are properly attributed to their sources."[^S1] (문서와 조사 보고서를 처리해 인용이 들어갈 구체적 위치를 식별하는 CitationAgent다. 이는 모든 주장이 그 출처에 제대로 귀속되도록 보장한다.) 인용이 들어갈 자리를 찾는 것은 "어느 회사의 가격 전략을 조사하는" 것과는 완전히 다른 종류의 일입니다. 앞쪽은 확인하고 위치를 짚는 일이고, 뒤쪽은 검색하고 판단하는 일입니다. 둘 다 같은 서브에이전트에게 맡기면 그것은 완전히 다른 두 사고 방식을 오가야 하고, 두 목표를 함께 섬기려다 작업 설명이 길고 뒤엉켜져 하나를 위해 다른 하나를 소홀히 하기 쉽습니다. 초점 잡힌 두 서브에이전트로 나누면, 각자의 작업 설명이 단순하고 뚜렷이 경계 지어진 채로 남습니다 — 이는 레슨 1의 잣대와 통합니다. 독립적인 하위 작업으로 나뉠 수 있다면, 나눌 가치가 있습니다.

## 💻 연습

### 레벨 1: 막연한 지시를 비판하고 다시 쓰기

오케스트레이터가 서브에이전트에게 내린 위임 지시는 이렇습니다. "이 오픈소스 프로젝트의 최근 이슈를 좀 살펴보고 주목할 만한 것을 찾아봐." 이 지시에 어떤 요소가 빠져 있는지 짚고, 범위가 뚜렷한 자기완결적 작업 설명으로 다시 써 보세요(레슨 3 예시의 JSON 구조를 써도 되고 여러분만의 형식을 써도 되지만, 목표, 범위, 출처, 출력 형식이라는 네 요소 유형을 모두 담아야 합니다).

<!-- rubric -->
- 원래 지시에 빠진 구체적 요소를 짚는다(막연하게 "명확하지 않다"가 아니라)
- 다시 쓴 작업 설명이 목표, 범위, 출처, 출력 형식이라는 네 요소 유형을 모두 담는다
- 범위가 빈 형용사가 아니라 "무엇을 찾고 무엇을 안 찾을지"의 구체적 경계를 반영한다

<!-- answer -->
원래 지시에 빠진 요소: "최근"이 어느 기간을 뜻하는지 말하지 않는다. "주목할 만한"의 기준(스타 수인지, 논의 활발함인지, 버그인지)을 정의하지 않는다. 어떤 출처를 쓸지(이슈 목록 자체인지, 연결된 논의와 PR까지인지) 말하지 않는다. 어떤 형식으로 내놓을지 말하지 않는다.

다시 쓴 예시:

```json
{
  "objective": "이 오픈소스 프로젝트에서 지난 30일 내에 열린 이슈 중, bug 라벨이 붙고 댓글이 5개를 넘는 것을 찾는다",
  "scope": "지난 30일 내에 열린 이슈만 살펴보고, 더 오래된 과거 이슈는 다룰 필요가 없다. bug 라벨이 붙은 것만 살펴보고, 기능 요청 이슈는 무시한다",
  "sources": "이 프로젝트의 GitHub 저장소 이슈 목록과 각 이슈 아래 댓글을 진실의 출처로 삼는다",
  "output_format": "각 항목이 이슈 제목, 링크, 댓글 수를 담는 목록으로, 댓글 수가 많은 순으로 정렬하며 최대 10개까지"
}
```

<!-- hint -->
원래 지시에서 막연한 단어 — "최근", "주목할 만한" — 를 모두 동그라미 치는 것에서 출발하세요. 막연한 단어 뒤마다 여러분이 서브에이전트를 대신해 정해 줘야 할 판단 기준이 앉아 있습니다. 그 기준을 뚜렷이 적어 낸 다음에야 지시가 자기완결적이 됩니다.

<!-- hint -->
"출력 형식"은 빠뜨리기 쉽지만, 결과가 돌아왔을 때 오케스트레이터가 그것을 곧장 쓸 수 있는지를 좌우합니다. 서브에이전트의 답변을 받은 뒤 오케스트레이터가 다음에 무엇을 하는지 그려 보고, 거기서 거꾸로 서브에이전트가 무엇을 내놓아야 할지를 짚어 보세요.

### 레벨 2: 어느 위임이 "하나의 문제 영역, 하나의 에이전트"를 어기는지 판단하기

오케스트레이터가 이런 서브에이전트를 설계했습니다. "이 회사의 최근 투자 유치 소식을 조사하는 동시에, 나중에 카피를 쓸 때 팀이 참고하도록 회사 홈페이지의 카피 스타일을 요약하는 일을 맡는다." 이 설계가 타당한지 판단하고 이유를 설명하세요. 타당하지 않다면 더 합리적인 분할 방법을 제시하세요.

<!-- rubric -->
- 설계가 "하나의 문제 영역, 하나의 에이전트"에 맞는지 판단하고 이유를 설명한다
- 근거가 두 작업이 성질상 어떻게 다른지를 반영한다(그저 "어색하다"가 아니라)
- 제안한 분할(타당하지 않다고 판단한 경우)이 독립적인 서브에이전트로 뚜렷이 나뉜다

<!-- answer -->
타당하지 않으며, "하나의 문제 영역, 하나의 에이전트"를 어깁니다. 투자 유치 소식 조사는 "사실 데이터를 검색하고 검증하는" 부류의 일로, 출처가 권위 있는지와 숫자가 정확한지를 판단해야 합니다. 홈페이지 카피 스타일 요약은 "글의 어조를 읽고 뽑아내는" 부류의 일로, 언어 스타일에 대한 감각이 필요하고 숫자 정확성 검증과는 거의 무관합니다. 둘을 같은 작업 설명에 욱여넣으면 서브에이전트는 서로 다른 두 부류의 일을 오가야 하고, 두 목표를 담느라 작업 설명 자체가 더 길고 뒤엉켜져 하나에서 부족해지기 쉽습니다. 더 합리적인 분할은 두 서브에이전트를 두는 것입니다. 하나는 투자 유치 소식 검증 전담으로, 출력 형식은 투자 라운드·금액·날짜 같은 구조화된 데이터입니다. 다른 하나는 홈페이지 카피를 읽고 스타일 특징을 요약하는 전담으로, 출력 형식은 몇 가지 스타일 설명과 예시 문장입니다.

<!-- hint -->
두 가지가 같은 "문제 영역"인지 판단하려면 물어보세요. 두 작업이 같은 종류의 판단을 요구하는가? 숫자 정확성을 검증하는 것과 글 스타일을 요약하는 것은 분명히 서로 다른 기준을 요구합니다.

<!-- hint -->
이 레슨의 CitationAgent 예시와 견줘 보세요. 인용 위치를 찾는 것과 회사의 가격 전략을 조사하는 것은, 둘 다 결국 같은 조사 보고서를 섬기는데도, 서로 다른 종류의 일을 요구하기에 두 다른 서브에이전트로 나뉩니다.

## 정리

- 서브에이전트는 오케스트레이터의 대화 기록을 볼 수 없으며[^S3], 이는 위임 프롬프트가 **자기완결적**이어야 함을 뜻한다. 어떤 대화 배경과도 떨어져 홀로 읽혀도, 서브에이전트가 자신이 무엇을 해야 하는지 정확히 판단하기에 충분해야 한다
- 탄탄한 작업 설명은 목표, 출력 형식, 출처 안내, 그리고 뚜렷한 작업 경계를 담아야 한다. 이것들이 없으면 서브에이전트는 작업을 중복하고, 빈틈을 남기고, 필요한 정보를 찾지 못한다[^S1]
- 공식 실무 반례는 'research the semiconductor shortage' 같은 막연한 지시가 서브에이전트로 하여금 작업을 오해하거나 다른 서브에이전트와 똑같은 검색을 돌리게 만든다는 것을 증명한다[^S1] — 범위와 경계는 선택이 아니라 중복 작업을 피하는 열쇠다
- **하나의 문제 영역, 하나의 에이전트**(이 레슨이 공식 실무에서 추려낸 것): 각 서브에이전트는 뚜렷이 경계 지어진 한 부류의 문제만 맡아야 하며, 인용 위치를 다룰 전용 CitationAgent를 두듯이 성질이 다른 일을 서로 다른 서브에이전트로 나눠[^S1] 각 작업 설명이 단순하고 초점 잡힌 채로 남게 한다
- 위임 프롬프트가 충분히 좋은지 판단하는 시험은 간단하다. 그것을 따로 떼어 한 번 읽고, 서브에이전트가 작업 세부를 채우려면 추측해야 하는지 보라
