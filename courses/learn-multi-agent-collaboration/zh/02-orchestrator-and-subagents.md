# 第 2 课：编排者与子代理：扇出与汇总

> 学习目标：
> - 说清楚编排者-子代理架构里，编排者和子代理各自负责什么
> - 解释「上下文隔离」具体隔离的是什么，为什么它能缓解上一课讲的上下文污染和注意力稀释
> - 说明为什么子代理应该只把结论回传给编排者，而不是把自己积累的全部思考过程都塞回去
>
> 前置要求：完成第 1 课，理解「多 Agent 系统」的定义和适用边界 | 上一课 [第 1 课 <<](./01-why-multiple-agents.md) | 下一课 [第 3 课 >>](./03-writing-prompts-for-delegation.md)

## 编排者：拆任务、派工、等结果

上一课判断出「调研三家云服务商定价」这类任务适合拆给多个 Agent，但没细讲这个「拆」具体怎么运作。常见的一种结构叫**编排者-子代理**架构：官方定义是「一个中心 LLM 动态地拆解任务、把任务委派给多个工作 LLM、再把它们的结果整合起来」。[^S2]

这句定义里有三个动作，分别对应编排者要做的三件事：**拆解**——把一个大任务判断出能拆成哪几块；**委派**——把每一块连同必要的背景，交给一个子代理去做；**整合**——等子代理们都返回结果后，把这些结果合成最终答案。编排者自己不下场去读云服务商的定价页面，它的工作是判断怎么分工、分给谁、以及最后怎么把几份结果拼成一份说得通的答案。

## 子代理：拿到一个任务，在自己的上下文里独立完成

子代理这一侧，运作方式和编排者很不一样。官方说得很明确：「每个子代理都从一个全新、独立的上下文窗口开始。它看不到你的对话历史、你已经调用过的技能、以及已经读过的文件。」[^S3] 也就是说，子代理不知道你一开始跟编排者说了什么、编排者内部是怎么权衡「要不要拆」「拆成几份」的，它能看到的只有编排者交给它的这一份任务说明。

这一点看起来像是限制，其实正是上一课那两个问题的解药。子代理的上下文里没有编排者的完整对话历史，自然也就没有编排者在别处踩过的坑、看到过的无关信息——**上下文隔离**：把每个 Agent 的工作范围限定在一个独立的上下文窗口内，一个 Agent 里发生的上下文污染，不会传染到另一个 Agent 里。子代理手上只有自己那一份任务要处理的资料，不用同时兼顾三家公司的全部内容，注意力稀释的压力也跟着降下来。至于怎么把一份任务说明写得足够清楚、让子代理不用看到对话历史也能独立把活干好，下一课会具体讲。

## 扇出：把任务拆开，同时派给几个子代理

回到调研三家云服务商定价的例子。编排者拆解出「查第一家」「查第二家」「查第三家」三块任务之后，不是排队一个一个做，而是同时把这三块任务派发出去——官方系统里的做法正是如此：主导 Agent 并行启动 3 到 5 个子代理，而不是串行一个个来[^S1]。这个「同时往外派」的动作就叫**扇出**：编排者把拆好的几块子任务，并行分发给对应数量的子代理，让它们各自独立、同时开始工作，而不是等第一个子代理做完了再派第二个。

扇出带来的好处很直接：三个子代理并行工作，总耗时接近做完一份调研的时间，而不是三份调研时间的总和——官方系统在引入这类并行化改进后，复杂查询的调研耗时最多缩短了 90%[^S1]。但扇出不是把任务硬切成几份就完事——切法本身有讲究，比如三家公司天然独立，切三份很自然；如果换成「审查一份 20 页的合同」，条款之间可能互相引用、互相制约，切法不当反而会让子代理各自缺失关键上下文，做出前后矛盾的判断。判断怎么切、切多细，仍然要回到上一课的判断标准：切出来的每一块，是不是真的能独立处理、不依赖其他块的中间结果。

## 汇总：收拢结果，不是简单拼接

三个子代理各自查完自己那一家公司的定价，把结果交回来之后，编排者要做的不是把三段文字原样拼在一起。子代理返回的是各自视角下的调研结论，编排者要做的是**汇总**：把几份独立产出的结果放在一起比较、消解掉可能存在的重复或矛盾之处、按最终要交付的形式重新组织，写出一份读起来是一个整体、而不是三段拼接痕迹很重的文档。

官方文档在讲子代理顺序接力时提到：「每个子代理完成自己的任务后，把结果返回给 Claude，Claude 再把相关的上下文传给下一个子代理。」[^S3] 由此可以看出，汇总不一定是「等所有子代理都交卷、编排者一次性收齐再处理」这么简单——有些场景下，前一个子代理的结果本身就是后一个子代理任务说明的一部分，编排者在扇出和汇总之间来回切换，直到所有子任务都有了结果。

结果的传递路径也不一定非要经过编排者中转。当子代理产出的内容本身体量很大、又需要被原样保留时，官方提到过一种做法：「让子代理把输出直接写入文件系统，以此把『层层转述』的信息损耗降到最低——某些类型的结果可以绕过主协调者直接产出，这样既保真又省性能开销。」[^S1] 直接写文件系统这一步，本质上是在避免结果在「子代理→编排者→最终输出」这条链路上被转述、压缩、丢失细节。

## 结果只回传结论，不回传子代理的整个思考过程

子代理为了完成任务，中间可能读了很多页无关紧要的内容、试过几条走不通的思路、甚至犯过几次小错误又自己纠正回来。这些过程本身不需要——也不应该——原样塞回编排者的上下文里。编排者需要的是子代理最终站得住脚的结论，以及支撑这个结论的关键依据，而不是那段完整的、包含弯路的推理过程。

原因回到第 1 课讲过的道理：编排者自己也有一个上下文窗口，也会经历上下文污染和注意力稀释。官方文档对此有直接提醒：子代理完成后结果会返回主对话，多个子代理各自回传详细结果，会消耗可观的上下文[^S3]。如果三个子代理各自几千字的完整思考过程都原样塞回编排者，编排者反而在自己这一层重新遇到了当初想靠多 Agent 缓解的问题。**结果回传**应该只携带结论本身，把「怎么得出这个结论」的细节留在子代理自己已经用完、即将丢弃的上下文里。

这不代表所有委派场景都从零开始。官方文档里还提到一种特殊的子代理类型——**fork**：「fork 是一种继承了目前为止全部对话历史的子代理，而不是从零开始……fork 自己的工具调用仍然不会进入你的主对话，只有它的最终结果会被带回来，这样你的主上下文窗口能保持干净。」[^S3] 也就是说，即便一个子代理罕见地需要看到完整历史（比如需要基于此前的全部讨论做一次深度总结），它中间的思考过程依然不会原样进入编排者的上下文——「只回传结论」这条原则是稳定的，变的只是子代理起步时手上有没有历史背景。

## 换个说法：这套分工在别的框架里也是同一套逻辑

「编排者-子代理」不是某一家的专属说法。OpenAI 的 Agents SDK 文档里把同样的结构称为 **Manager 模式**：「一个中心管理者/编排者把专门的子代理当作工具来调用，并且始终掌控着整个对话。」[^S4] 换了个词——manager 对应编排者、agents-as-tools 对应子代理——描述的仍然是同一件事：一个中心节点负责拆任务、派工、掌控全局，具体执行交给专门的下级去做，下级做完把结果交回来，中心节点继续掌控接下来的走向。认出这套分工的本质，比记住某一家框架的具体术语更重要——你会在几乎所有多 Agent 框架的文档里看到这套逻辑的某种变体。

## 💻 练习

### Level 1：给一次代码审查任务画出编排者和子代理的分工

任务是：「审查一个开源项目最近 10 个 PR，找出其中改动了核心权限逻辑的 PR，为每一个这样的 PR 写一段风险说明。」请回答：

1. 编排者应该做哪些事？
2. 这个任务该怎么扇出——拆成几块、每块大概是什么？
3. 子代理完成后，应该往回传什么？编排者收到后要做的「汇总」具体是什么？

<!-- rubric -->
- 编排者的职责里体现了「拆解、委派、整合」，而不是编排者自己去读 PR
- 扇出方案给出了具体的拆分依据（比如按 PR 分组），而不是笼统说「分成几份」
- 说清楚了子代理该回传结论还是回传全部思考过程，以及汇总具体在做什么

<!-- answer -->
1. 编排者先拿到 10 个 PR 的列表，判断出这个任务能拆成「逐个检查 PR 是否改动了权限逻辑」这一层可以并行的子任务；把每个 PR（或几个 PR 一组）派给一个子代理去检查；等子代理们都返回结果后，把「确实改动了权限逻辑」的那几个 PR 的风险说明整理成一份统一的审查报告。
2. 可以按 PR 拆，比如每个子代理负责 2-3 个 PR，一共派出 4-5 个子代理并行检查；也可以更细，10 个 PR 各配一个子代理，具体粒度取决于每个 PR 改动的大小和检查所需要的上下文量。
3. 子代理应该只回传结论：这个 PR 有没有改动核心权限逻辑，如果有，风险说明是什么，以及支撑这个判断的关键代码位置，而不是把自己读过的整段 diff 和中间试错的思考过程都传回来。编排者收到后，「汇总」是把所有子代理确认「有风险」的 PR 挑出来，按风险说明的格式统一整理成一份报告，而不是把 10 段子代理的原始回复直接拼接。

<!-- hint -->
编排者「拆解、委派、整合」三个动作里，容易漏掉的是它自己不下场去读 PR 的具体内容——一旦编排者自己也去读了某个 PR 的完整 diff，它就在替子代理干活，这条分工线就模糊了。

<!-- hint -->
子代理该回传什么，可以反过来想：如果编排者收到的是每个子代理完整的思考过程，编排者自己的上下文会不会因此重新变得又长又杂？如果答案是会，说明该回传的只是结论。

### Level 2：找出这个编排设计里的问题

有人设计了这样一套编排者-子代理流程：「编排者一开始就把自己和用户的完整对话历史（包括几轮跟这次任务无关的闲聊）打包，作为背景信息发给每一个子代理，理由是『万一子代理需要用到什么背景，提前给它总比漏了强』。」找出这个设计的问题，并给出更合理的做法。

<!-- rubric -->
- 指出了问题所在，并且引用了本课讲过的具体原理（而不是笼统说「不好」）
- 说明了这个做法会带来什么具体后果
- 给出的改进方案体现了「按需提供、划清边界」的原则

<!-- answer -->
问题在于违背了子代理默认从全新、独立的上下文开始这一机制的初衷——把无关的闲聊内容也打包给每个子代理，等于人为地把编排者自己上下文里的无关信息，重新引入到每一个子代理的上下文里，这正是第 1 课讲的上下文污染，只是污染源从「Agent 自己搜到的错误信息」换成了「编排者好心塞进来的无关历史」。后果是子代理要多花注意力去分辨哪些是真正有用的背景、哪些是无关闲聊，注意力稀释的问题也跟着出现，而且这个「万一漏了什么」的顾虑本身也没有解决——真正需要的背景应该被明确写进任务说明里，而不是靠打包全部历史来「兜底」。更合理的做法是编排者只把这次任务真正需要的背景信息挑出来，明确写进发给子代理的任务说明里，用不到的历史一律不传。

<!-- hint -->
回想「子代理该不该看到完整对话历史」这道判断题——「万一需要」和「明确需要」是两回事，前者容易演变成把所有东西都塞进去，后者要求派工的人先想清楚这次任务到底需要什么背景。

<!-- hint -->
可以对照一下：如果这份「完整对话历史」本身就有几千字，塞给三个子代理，相当于编排者还没扇出，就已经先把上下文污染和注意力稀释的成本转嫁给了每一个子代理。

## 小结

- **编排者-子代理**架构里，一个中心 LLM 负责拆解任务、把子任务委派给多个工作 LLM、再把结果整合起来[^S2]，编排者自己不下场处理具体子任务的细节内容。
- 每个子代理默认从一个全新、独立的上下文窗口开始，看不到编排者的对话历史[^S3]——这就是**上下文隔离**，它是缓解上一课讲的上下文污染和注意力稀释的关键机制。
- **扇出**是把拆好的子任务并行分发给多个子代理同时处理；**汇总**不是简单拼接子代理的回复，而是比较、消解矛盾、按统一格式重新组织；结果传递也可以绕开编排者直接写入文件系统，以减少信息在转述过程中的损耗[^S1]。
- 子代理完成任务后，结果会返回给编排者[^S3]；回传的应该只是**结论**，而不是中间踩过的弯路、完整的思考过程——官方明确提醒，多个子代理各自回传详细结果会消耗可观的上下文[^S3]，编排者自己也会在这一层重新遇到上下文污染和注意力稀释。
- 「编排者-子代理」不是某一家框架的专属说法——OpenAI Agents SDK 把同样的结构称为 Manager 模式，一个中心管理者把子代理当作工具调用、并始终掌控对话[^S4]，认出这套分工背后的共同逻辑，比记住某个具体术语更重要。
