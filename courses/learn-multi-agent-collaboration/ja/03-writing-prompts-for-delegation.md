# レッスン3: 委任のためのプロンプトを書く

> 学習目標:
> - サブエージェントがあなたとオーケストレーターの会話を見ることに依存しない、自己完結型の委任プロンプトを書く
> - タスクの範囲、境界、どのソースを使うかを委任プロンプト自体の中で明示する
> - 「1つの問題領域、1つのエージェント」原則と、それを破るコストを説明する
>
> 前提: レッスン2を完了し、オーケストレーター・サブエージェントアーキテクチャとコンテキストの分離を理解している | 前: [レッスン2 <<](./02-orchestrator-and-subagents.md) | 次: [レッスン4 >>](./04-collaboration-patterns.md)

## 復習: サブエージェントが見られないものは、あなたがそのために書き込む必要がある

レッスン2はここで重要な1つのメカニズムをカバーしました: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there."（各サブエージェントは新鮮な、分離されたコンテキストウィンドウから始まる。それはあなたの会話履歴、あなたが既に呼び出したスキル、Claudeが既に読んだファイルを見ない。Claudeはタスクを要約した委任メッセージを作成し、サブエージェントはそこから作業する）[^S3]。このレッスンはそれを具体化します。つまり、オーケストレーターレベルでユーザーと話し合ったすべての背景、以前のラウンドで決着させたトレードオフ、ユーザーが何気なく投げ込んだ制約——サブエージェントはそれを何も知りません。サブエージェントが知っているのは、あなたがこの1つの委任タスクに書いた言葉だけです。

これは優しいリマインダーではなく、ハードな制約です: **委任プロンプトの品質の上限が、サブエージェントが生み出すものの品質の上限を設定します**。プロンプトが明示しないものは、サブエージェントは推測するか、スキップするか、または仮定を発明して進み続けます。正しく推測すれば運が良かった。間違って推測すれば、そのサブタスク全体が基本的に無駄になります。

## 自己完結型: プロンプトは全体を独自に言わなければならない

**自己完結型**: 委任プロンプトを読んだ後、サブエージェントは何をすべきかを正確に判断するために追加の背景を必要としません。プロンプトが自己完結型かどうかの簡単なテストがあります。それを単独で引き出し、あなたとオーケストレーターの間のすべてのコンテキストを取り除き、白紙から読みます。それでもタスクの詳細を埋めるために*推測*しなければならない場合、プロンプトはテストに失敗します。

3つのクラウドプロバイダーの価格調査というレッスン1の例を取り上げましょう。オーケストレーターがサブエージェントに「AWSの価格を調べる」とだけ言うタスクを渡すと、その1行はオーケストレーター自身には十分な情報を運びます——オーケストレーターのコンテキストには「なぜこれを調べているのか」「後で誰と比較するのか」「どの次元で比較するのか」の背景がまだ残っているからです。しかしサブエージェントはそれを何も見ることができません。それが受け取るのは1つの孤独な行、「AWSの価格を調べる」であり、推測するしかありません: どの製品カテゴリーの価格？現在の価格だけ、それとも過去1年間の変更？見つけたら成果物はどのように見えるべき？すべての推測は間違う可能性のある賭けです。

## 範囲と制約を明示する: 何をすべきか、何をすべきでないか、どのソースを使うか

公式ガイダンスは、堅実なサブエージェントタスク記述が含むべきものをリストしています: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information."（各サブエージェントは目的、出力フォーマット、使用するツールとソースのガイダンス、明確なタスク境界を必要とする。詳細なタスク記述がなければ、エージェントは作業を重複させ、ギャップを残し、必要な情報を見つけられない）[^S1]

そのリストを開いてみましょう。「目的」と「出力フォーマット」は理解しやすいです。スキップされるのは最後のペア——**ソースガイダンス**と**タスク境界**です。ソースガイダンスは、サブエージェントに答えをどこで探すべきかを伝えます: 公式の価格ページ、サードパーティの価格比較サイト、または両方で公式ページが優先される。タスク境界は、サブエージェントにこの実行はこのスライスだけをカバーし、それを超えて手を伸ばさないよう伝えます: 現在の価格のみ、過去の価格変更なし。主要な製品ラインのみ、あらゆる不明瞭なサービスをリストしない。この2つを見逃すと、サブエージェントは2つの方法のいずれかに漂う傾向があります。実際に欲しかった情報を見逃すか、または欲しかったよりもはるかに多くを取得し、節約できたツール呼び出しとトークンを消費します。

明確な範囲を持つ自己完結型のタスク記述として書き直すと、クラウドプロバイダー調査はおおよそ次のようになります:

```json
{
  "objective": "AWSの主要なコンピューティングサービス（EC2）の現在の価格構造を調査し、2つの課金モデルに焦点を当てる：オンデマンドインスタンスとリザーブドインスタンス",
  "scope": "現在有効な価格のみを調べる、過去の価格変更なし。汎用およびコンピューティング最適化インスタンスタイプのみをカバー、すべてのインスタンスファミリーをカバーする必要なし",
  "sources": "AWS公式価格ページを真実のソースとして使用。公式ページが十分に明確でない場合、公式のAWS価格計算機で補足してもよい",
  "output_format": "300語未満のテキスト要約で、以下をカバー：オンデマンドインスタンスの時間料金範囲、リザーブドインスタンスがオンデマンドに対して提供する割引、どの課金モデルがどのユースケースに適しているかについての1行の結論"
}
```

単独で引き出されたこの記述は、サブエージェントがオーケストレーターが内部で議論したことを何も知らずに、「何を調べるか、どこまで進めるか、何を提供するか」を正確に判断できるようにします。

## 反例: 曖昧な指示はサブエージェントに即興を強いる

範囲と境界を明示しない場合に実際に何が間違うか——公式チームは実践からの実例を示しました: "We started by allowing the lead agent to give simple, short instructions like 'research the semiconductor shortage,' but found these instructions often were vague enough that subagents misinterpreted the task or performed the exact same searches as other agents."（我々は、リードエージェントが「半導体不足を調査する」のような単純で短い指示を与えることから始めたが、これらの指示はしばしば十分に曖昧で、サブエージェントがタスクを誤解したり、他のエージェントとまったく同じ検索を実行したりすることがわかった）[^S1]

「半導体不足を調査する」はタスクを渡すように読めますが、何も固定していません——どの時間範囲で？供給側、需要側、または政策の影響に焦点を当てる？どの形式で提供される？同じ曖昧な指示を渡された3つのサブエージェントは、「半導体不足の原因」、最初に思い浮かぶ角度に向かって検索し、結果として3つの大きく重複する調査の塊が生じる可能性が非常に高く、実際にカバーが必要だった角度（例えば、川下産業への影響、または異なる国がどのように対応したか）は手つかずのままになります。これは、レッスン2からの「重複作業」問題のプロンプトレベルでの根源です——サブエージェントが聞かないのではなく、タスク記述自体が境界を引かなかったのです。

## 1つの問題領域、1つのエージェント

単一のプロンプトを明確に書くことを超えて、複数のサブエージェントが作業をどのように分割するかも、公式の実践から抽出できる原則に従います——公式チームはそれに名前を付けませんでした。この命名は我々のものです: **1つの問題領域、1つのエージェント**——各サブエージェントは、1つのサブエージェントが一度にいくつかの無関係なものを扱うのではなく、明確に境界された1つのクラスの問題だけを所有すべきです。

公式システムには直接的な例があります: 彼らは専用のCitationAgentを設定しました。"a CitationAgent, which processes the documents and research report to identify specific locations for citations. This ensures all claims are properly attributed to their sources."（CitationAgentは、文書と調査レポートを処理して引用の特定の場所を識別する。これにより、すべての主張がそのソースに適切に帰属される）[^S1]。引用がどこに行くかを見つけることは、「ある会社の価格戦略を調査する」とはまったく異なる種類の作業です——前者はチェックと位置特定、後者は検索と判断です。両方を同じサブエージェントに渡すと、それは2つのまったく異なる思考モードの間を行き来しなければならず、そのタスク記述は2つの目的を果たそうとして長く絡み合ったものになり、一方を他方のために軽視しやすくなります。2つの集中したサブエージェントに分割すると、それぞれのタスク記述は単純で明確に境界されたままです——これはレッスン1からの尺度を反映しています: 独立したサブタスクに分割できる場合、分割する価値があります。

## 💻 演習

### レベル1: 曖昧な指示を批評し、書き直す

オーケストレーターのサブエージェントへの委任指示は: 「このオープンソースプロジェクトの最近のissueを見て、注意を払う価値があるものを見つけてください」。この指示が欠いている要素を指摘し、明確な範囲を持つ自己完結型のタスク記述として書き直してください（レッスン3の例からのJSON構造、または自分のフォーマットを使用できますが、4つすべての要素タイプをカバーする必要があります: 目的、範囲、ソース、出力フォーマット）。

<!-- rubric -->
- 元の指示が欠いている特定の要素を指摘する（漠然と「十分明確ではない」と言うのではなく）
- 書き直されたタスク記述は4つすべての要素タイプをカバーする: 目的、範囲、ソース、出力フォーマット
- 範囲は空の形容詞ではなく、「何を調べるか、何をしないか」の具体的な境界を反映している

<!-- answer -->
元の指示が欠いている要素: 「最近」がどの時間範囲を意味するかを言っていない。「注意を払う価値がある」の基準を定義していない（スター数、ディスカッション活動、またはバグかどうかによって）。どのソースを使用するかを言っていない（issue リスト自体、またはリンクされたディスカッションとPRも）。どのフォーマットで提供するかを言っていない。

書き直しの例:

```json
{
  "objective": "このオープンソースプロジェクトで過去30日以内に開かれたissueから、5件を超えるコメントがあるバグとラベル付けされたものを見つける",
  "scope": "過去30日以内に開かれたissueのみを見る、古い過去のissueをカバーする必要なし。バグラベルがあるものだけを見る、機能リクエストのissueは無視する",
  "sources": "プロジェクトのGitHubリポジトリのissueリストと各issueの下のコメントを真実のソースとして使用する",
  "output_format": "各エントリがissueのタイトル、リンク、コメント数を含むリスト、コメント数の多い順に並べ替え、最大10エントリ"
}
```

<!-- hint -->
元の指示のすべての曖昧な単語に丸をつけることから始めます——「最近」、「注意を払う価値がある」。各曖昧な単語の背後には、サブエージェントの代わりに決定しなければならない判断基準があります。それらの基準を明確に書き出して初めて、指示は自己完結型になります。

<!-- hint -->
「出力フォーマット」は省略しやすいですが、それは、結果が戻ってきたときにオーケストレーターがそれを直接使用できるかどうかを決定します。オーケストレーターがサブエージェントの返答を受け取った後に次に何をするかを想像し、サブエージェントが何を提供すべきかに逆算します。

### レベル2: 委任が「1つの問題領域、1つのエージェント」を破るかどうかを判断する

オーケストレーターはこのサブエージェントを設計しました: 「この会社の最近の資金調達ニュースを調べ、同時に会社のホームページのコピースタイルを要約して、チームが後でコピーを書くときに参考にできるようにする」。この設計が健全かどうかを判断し、理由を説明してください。健全でない場合は、それを分割するより合理的な方法を示してください。

<!-- rubric -->
- 設計が「1つの問題領域、1つのエージェント」に適合するかどうかを判断し、理由を説明する
- 理由は、これら2つのタスクが性質上どのように異なるかを反映している（単に「違和感がある」と言うのではなく）
- 提案された分割（健全でないと判断された場合）は、独立したサブエージェントに明確に分離されている

<!-- answer -->
健全ではありません。「1つの問題領域、1つのエージェント」を破ります。資金調達ニュースを調べることは「事実データを検索して検証する」クラスの作業に分類され、ソースが権威的であるかどうか、数字が正確であるかどうかを判断する必要があります。ホームページのコピースタイルを要約することは「文章のトーンを読んで蒸留する」クラスの作業に分類され、言語スタイルへの感度が必要で、数値の正確性を検証することとはほとんど関係ありません。両方を同じタスク記述に詰め込むと、サブエージェントは2つの異なる作業モード間を切り替えなければならず、タスク記述自体は2つの目的をカバーすることからより長く絡み合ったものになり、そのうちの1つを軽視しやすくなります。より合理的な分割は、2つのサブエージェントを設定します: 1つは資金調達ニュースの検証専用で、出力フォーマットは資金調達ラウンド、金額、日付のような構造化データ。もう1つはホームページのコピーを読んでそのスタイル特性を要約することに専念し、出力フォーマットはいくつかのスタイル記述と例文です。

<!-- hint -->
2つのことが同じ「問題領域」であるかどうかを判断するには、次のように尋ねます: 2つのタスクは同じ種類の判断を求めますか？数値の正確性を検証することと文章スタイルを要約することは、明らかに異なる基準を求めます。

<!-- hint -->
このレッスンのCitationAgentの例と比較してください——引用の場所を見つけることと会社の価格戦略を調査することが2つの異なるサブエージェントに分割されるのは、両方が最終的に同じ調査レポートに役立つとしても、それらが異なる種類の作業を求めるためです。

## まとめ

- サブエージェントはオーケストレーターの会話履歴を見ることができません[^S3]。これは、委任プロンプトが**自己完結型**でなければならないことを意味します: 単独で読めて、会話の背景から離れても、サブエージェントが何をすべきかを正確に判断するのに十分です。
- 堅実なタスク記述は、目的、出力フォーマット、ソースガイダンス、明確なタスク境界を含まなければなりません。これらがなければ、サブエージェントは作業を重複させ、ギャップを残し、必要な情報を見つけられません[^S1]。
- 公式の実世界の反例は、「半導体不足を調査する」のような曖昧な指示がサブエージェントにタスクを誤解させたり、他のサブエージェントとまったく同じ検索を実行させたりすることを証明しています[^S1]——範囲と境界はオプションではなく、重複作業を避けるための鍵です。
- **1つの問題領域、1つのエージェント**（このレッスンの公式実践の抽出）: 各サブエージェントは、引用の場所を処理する専用のCitationAgentを設定するように、明確に境界された1つのクラスの問題だけを所有すべきであり、異なる性質の作業を異なるサブエージェントに分割します[^S1]。そうすることで、各タスク記述は単純で集中したままです。
- 委任プロンプトが十分に良いかどうかを判断するために、テストは単純です: それを単独で引き出して一度読み、サブエージェントがタスクの詳細を埋めるために推測しなければならないかどうかを見てください。
