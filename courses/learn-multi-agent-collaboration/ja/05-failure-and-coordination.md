# レッスン5: 失敗と調整

> 学習目標:
> - サブエージェントが「完了」と主張しても額面通りに受け取れない理由と、独立した検証方法が必要な理由を説明する
> - マルチエージェントコラボレーションにおける2つの一般的な失敗を認識する: 重複作業と矛盾する結果
> - 結果統合段階で、重複を排除する方法と矛盾する出力を処理する方法を知る
>
> 前提: レッスン4を完了し、3つのコラボレーションパターンとハンドオフを区別できること | 前: [レッスン4 <<](./04-collaboration-patterns.md) | 次: [レッスン6 >>](./06-build-a-review-pipeline.md)

2つのサブエージェントがそれぞれ同じクラウドプロバイダーのスタータープランを調査します。一方は月額\$20から始まると報告し、もう一方は\$25と言います。そして両方の出力は自信を持って「検証済み、エラーなし」とマークしています。前のレッスンはすべてマルチエージェントコラボレーションを立ち上げる方法をカバーしました。このレッスンは、それを構築した後でどこが壊れるかをカバーします。サブエージェントの自己報告ステータスは信頼できない、重複作業、矛盾する結果、そしてオーケストレーターがそれぞれについて何をすべきかです。

## サブエージェントが「完了」と言っても正しくやったという意味ではない

サブエージェントが結果を返すとき、通常「完了」や「検証済み、エラーなし」のような行を付け加えます。その声明は証拠ではありません。それは単にサブエージェント自身の出力についての自己要約であり、その要約は間違っている可能性があります。エージェントの動作についての公式の観察はまさにこれです。"Claude stops when the work looks done. Without a check it can run, \"looks done\" is the only signal available, and you become the verification loop: every mistake waits for you to notice it."[^S6] だから公式のアドバイスは "Have Claude show evidence rather than asserting success."[^S6] です。

公式ドキュメントはこれを trust-then-verify gap と呼んでいます。"The trust-then-verify gap. Claude produces a plausible-looking implementation that doesn't handle edge cases. Fix: Always provide verification (tests, scripts, screenshots). If you can't verify it, don't ship it."[^S6] そのアドバイスはコードを書くことについて書かれましたが、同じ論理は任意の委任に適用されます。サブエージェントが返すものはスムーズに読め、正しいフォーマットで、注意深く行われたように見えます。そしてそのすべては単に「もっともらしく見える」だけで、実際に正しいこととは同じではありません。オーケストレーターがサブエージェントの「完了」という言葉を額面通りに受け取り、出力を最終結果に直接つなぎ合わせると、検証を完全にスキップしたことになります。

## 検証方法: サブエージェントの出力に対してチェック可能な基準を設定する

「額面通りに受け取らない」と言うのは簡単です。難しいのは検証方法です。一度読んで「良さそうだ」と決めることは検証ではありません。それはまだ trust-then-verify gap の前半に留まっています。信頼できるアプローチは、最初に具体的でチェック可能な基準を定義し、次にサブエージェントの出力をそれに対して測定することです。

本番システムで使用されている1つの基準はこのように見えます。"We used an LLM judge that evaluated each output against criteria in a rubric: factual accuracy (do claims match sources?), citation accuracy (do the cited sources match the claims?), completeness (are all requested aspects covered?), source quality (did it use primary sources over lower-quality secondary sources?), and tool efficiency (did it use the right tools a reasonable number of times?)."[^S1] これらの5つの基準が共有するのは、それぞれが印象でスコアされるのではなく、具体的にチェックできるということです。事実の正確性は、サブエージェントが引用したソースに対して一行ずつチェックできます。完全性は、タスク記述にリストされたすべての要件に対してチェックし、それらがすべてカバーされたかどうかを確認できます。ツール効率は呼び出しログから直接読み取って、明らかに冗長または重複した呼び出しがあったかどうかを判断できます。

これを自分のコラボレーションセットアップに取り入れる場合、サブエージェントの出力を検証する最初のステップは「これは正しく見えるか」と尋ねることではなく、「このタスクについて、私は何を具体的にチェックできるか」と尋ねることです。それらをリストアップし、各項目に対して出力を測定します。

## 重複作業: 複数のサブエージェントが同じことをする

レッスン3では、十分に詳細でないタスク記述が、"misinterpreted the task or performed the exact same searches as other agents."[^S1] というサブエージェントにつながることをカバーしました。それが根本原因ですが、失敗は通常、結果が集約される瞬間にのみ表面化します。オーケストレーターは複数のサブエージェント出力を受け取り、そのうちの2つが大きく重複し、異なる言葉で同じことをカバーしていることを発見します。

重複作業はそれ自体が壊滅的なエラーではありません。コンテンツは間違っていません。異なる角度をカバーすべきだったトークンと呼び出しを無駄にしただけです。しかし、それはシグナルです。一部のサブエージェントのタスク境界が十分に明確に引かれておらず、この1つのバッチの結果を手動で重複排除して完了と呼ぶのではなく、派遣ステップからのタスク記述を確認するために戻る価値があります。重複作業を見つけたら、重複したコンテンツを削除するだけでなく、なぜ繰り返されたのかを理解する方がより価値があります。2つのタスク記述がスコープで重複していたか、サブエージェントがそれぞれ同じ最も明白な方向に漂ったかです。

## 矛盾する結果: 2つのサブエージェントが矛盾する結論に達する

重複作業よりも厄介なのは結果の衝突です。このレッスンを開始したシーンのように、2つのサブエージェントがそれぞれ独自の調査を行い、互いに矛盾する結論を返します。一方はスタータープランが月額\$20から始まると言い、もう一方は\$25と言います。「どちらかを選ぶ」か「差を分割する」ことでこれに対処することはできません。両方のアプローチは、間違った数値を最終結論として提供するリスクがあります。

結果の衝突に遭遇したとき、賢明な順序は、最初に各側が答えの基礎にしたものを見ることです。彼らは異なるソースを参照したか、一方はプロバイダーの現在のライブページを使用し、もう一方は誤ってキャッシュされた古いページを使用したか。基礎を追跡できる場合、通常どちらがより信頼できるかを判断し、信頼できないものを置き換えることができます。基礎そのものが誰が正しいかを解決できない場合、統合中に自分で判断を下さないでください。矛盾をそのまま人間のレビューのためにフラグするか、その1つの不一致点を検証するために特別に新しいサブエージェントを立ち上げます。結果の衝突が露呈する問題は、通常、重複作業よりも心配する価値があります。それは少なくとも1つのサブエージェント出力が間違っていることを意味し、それを処理せずに最終結果にドロップすると、未検証のエラーを「完了」の結論としてパッケージ化したことになります。

## 結果統合と重複排除: オーケストレーターがまとめるために行うこと

複数のサブエージェント出力を最終結果につなぎ合わせることは、それらを端から端まで連結することではありません。上記の問題のカテゴリーを再度実行することを意味します。マージする必要がある重複コンテンツはありますか、検証またはフラグする必要がある矛盾する結論はありますか、すべての主張が対応する基礎に遡ることができますか。最後のポイントは特に見落としやすいです。レッスン3「委任のためのプロンプトを書く」では、本番システムが専用のエージェントを設定したことに言及しました。"a CitationAgent, which processes the documents and research report to identify specific locations for citations. This ensures all claims are properly attributed to their sources."[^S1] と説明されています。同じ論理が統合段階にも当てはまります。複数のサブエージェント出力がプールされると、誤った帰属が起こりやすくなります。サブエージェントAが見つけたデータを、サブエージェントBが担当していた会社についての結論として書き上げることです。統合段階で各主張のソース帰属を検証することは、事実そのものが正確かどうかを検証することと同じくらい重要です。

重複排除、衝突の検証、ソース帰属のチェック。これら3つが一緒に「集約」ステップの本当の作業であり、レッスン2が警告したように、サブエージェントの生の返信を連結して完了と呼ぶことではありません。

## 💻 演習

### レベル1: 結果の衝突を処理する

2つのサブエージェントがそれぞれ企業の最近の資金調達ラウンドの金額を調査します。サブエージェントAはテクノロジーメディアのレポートに基づいて\$30ミリオンと言います。サブエージェントBは企業自身が公開したプレスリリースに基づいて\$35ミリオンと言います。この衝突をどう処理するか、最終結果をどう提示すべきかを説明してください。

<!-- rubric -->
- 単に「どちらかを選ぶ」か「差を分割する」だけで済ませない
- 各側の基礎を検証し、ソースの信頼性を判断する具体的な方法に言及する
- 最終結果をどう提示すべきかを説明する（基礎が誰が正しいかを解決できない場合に何をすべきかを含む）

<!-- answer -->
数値を選ぶか平均するだけではいけません。まず、各側のソースの信頼性を比較します。公式のプレスリリースは通常、第三者のメディア報道よりも権威があり、一次ソースに近いので、この場合サブエージェントBの\$35ミリオンの方が信頼できます。リリースの公開日と正確な文言を検証し、誤読がないことを確認し、\$35ミリオンを最終結果として使用できます。一方で、出力に「一部のメディアレポートの\$30ミリオンとは異なります。公式プレスリリースの数字が権威です」と注記し、衝突を静かにドロップして存在しないふりをするのではありません。2つのソースがほぼ同等に信頼でき、どちらがより信頼できるかを判断できない場合、統合段階で自分で判断を下すべきではありません。人間のレビューのために不一致をそのままフラグするか、検証するために別のサブエージェントを派遣します。

<!-- hint -->
まず尋ねます: 各サブエージェントは何に基づいて答えを出したか。ソースそのものが権威において異なり、それはしばしばどちらを信頼するかを判断するのに十分です。推測したり、ショートカットとして差を分割したりする必要はありません。

<!-- hint -->
ソースが本当に同等に信頼できる場合、選択を強制して間違った情報を提供するリスクを負うよりも、正直に衝突をフラグする方が安全です。

### レベル2: サブエージェントタスクの検証基準を書く

サブエージェントのタスクは次のとおりです。「先月の顧客フィードバックを読み、最も頻繁に言及された3つの問題を抽出する。」このレッスンの公式 LLM ルーブリック（事実の正確性、完全性など）のアプローチに従って、この特定のタスクに対して3〜4つのチェック可能な検証基準を書いてください。各基準は、正確に何をチェックするか、どうチェックするかを述べる必要があります。

<!-- rubric -->
- 3〜4つの基準を書き、それぞれが曖昧な「合理的に読めるか」という基準ではなく、具体的にチェック可能である
- 基準はこの特定のタスク（フィードバック問題の抽出）を反映しており、公式の例の研究レポート基準のコピーではない
- 各基準は、基準名だけでなく、チェック方法を説明する

<!-- answer -->
サンプル回答:

1. **抽出の正確性**: 元のフィードバックに対してスポットチェックを行い、リストされた3つの問題が実際に生のフィードバックで明示的に言及されていることを確認し、サブエージェント自身が要約または外挿したものではないことを確認します。
2. **ランキングの正確性**: これらの3つの問題が本当に言及数による上位3つであることを検証します。サブエージェントに各問題の具体的な言及数またはソース引用のリストも提供させて、ランキングが成立するかどうかをチェックできます。
3. **カバレッジの完全性**: サブエージェントが実際に先月のフィードバックすべてを読んだことを確認し、一部からのみ結論を出していないことを確認します。サブエージェントが処理したと報告する数をチェックするだけではいけません。それはまだ自己報告ステータスに依存しているからです。代わりに、その月のフィードバックからいくつかの項目をランダムにサンプリングし（最も早いものと最も遅いもののいくつかを含む）、それらのコンテンツがサブエージェントの分類またはカウントに現れるかどうかをチェックします。
4. **帰属の正確性**: 各問題の下に引用された元のフィードバックスニペットが本当にその問題の説明をサポートしているかをチェックし、1つのフィードバックを別の問題に誤って帰属させないようにします。

<!-- hint -->
このタスクの「事実の正確性」は次のようにマップされます: リストされた問題は元のテキストで本当に言及されているか、サブエージェントが作り上げたものではないか。ソースに対してスポットチェックする方法を理解することが、この基準の具体的なチェック方法です。

<!-- hint -->
このタスクの「完全性」は「要求されたすべての側面がカバーされているか」ではなく、「実際に要求されたフィードバックすべてを読んだか」です。サブエージェントがその一部だけを読んだ後に結論を急いでいないかを検証する方法を考えてください。

## まとめ

- サブエージェントが返すときの「完了」または「検証済み、エラーなし」は単なる自己報告で、証拠ではありません。実行できるチェックがなければ、"looks done" が利用可能な唯一のシグナルです[^S6]。公式ドキュメントは、Claude が "produces a plausible-looking implementation that doesn't handle edge cases" であることを明示しており、検証できない場合は出荷しないでください。[^S6]
- 検証は「うまく読める」で止まることはできません。特定のタスクに対してチェック可能な基準を定義します。公式の LLM ジャッジが使用したルーブリックのように、事実の正確性、引用の正確性、完全性、ソースの品質、ツール効率はそれぞれ一行ずつチェックできます。[^S1]
- **重複作業**は明確に引かれていないタスク境界の一般的な結果であり[^S1]、通常、結果が集約されるときにのみ表面化します。重複を見つけることは余分なコンテンツを削除するだけでなく、派遣ステップからのタスク記述を確認するために戻る価値があります。
- **矛盾する結果** — 2つのサブエージェントが矛盾する結論に達する — はランダムに1つを選ぶか差を分割することで処理できません。まず各側の基礎の信頼性を検証し、ランク付けできない場合は、人間のレビューのために衝突をそのままフラグします。
- 統合段階は3つのことを同時に行います。重複排除、衝突の検証、各主張のソース帰属が誤って帰属されていないかのチェック[^S1]です。それが「集約」ステップの本当の作業であり、サブエージェントの生の返信を連結するだけではありません。
