> - YAML 프론트매터의 필수 필드 파악하기
> - 실제로 작동하는 description 작성법 익히기
> - 지시문 섹션을 구성하는 방법 살펴보기
>

## 스킬 파일은 어떻게 생겼나

어떤 스킬을 열어 봐도 같은 모양입니다.[^S1]

```markdown
---
name: task-organizer
description: 어수선한 할 일 목록을 우선순위와 마감일에 따라 그룹으로 정리한다
---

# 태스크 정리 도구

정리되지 않은 작업 목록에서 구조화된 정보를 뽑아낸다.

## 입력 형식

다음 중 무엇이든 받는다:
- 일반 텍스트 목록
- Markdown 체크리스트
- 타임스탬프가 있는 대화 로그

## 단계

1. 각 작업의 핵심 내용을 추출한다
2. 마감일이 있다면 식별한다
3. 우선순위를 판단한다(긴급 / 중요 / 보통)
4. 마감일이 가까운 순으로 정렬한다

## 출력 형식

### 🔴 긴급(오늘 또는 내일 마감)
- [작업] - 마감 시각

### 🟡 중요(이번 주 마감)
- [작업] - 마감 시각

### ⚪ 보통(마감이 분명하지 않거나 더 나중)
- [작업]
```

**이 파일은 두 부분으로 이루어져 있습니다.**

1. **YAML 프론트매터**(`---` 마커 사이의 모든 내용): 이 스킬의 기본 정보를 Claude에게 알려 주는 메타데이터
2. **Markdown 지시문**(그 뒤의 모든 내용): Claude가 무엇을 해야 하는지 알려 주는 실제 지시

## YAML 프론트매터: Claude가 스킬을 찾아내는 방법

프론트매터는 파일 맨 위에 `---`로 감싸인 블록입니다. 여기에서 가장 중요한 두 가지를 Claude에게 알려 줍니다.[^S3][^S4]

### name: 스킬의 고유 식별자

```yaml
name: task-organizer
```

- **규칙**: 소문자, 숫자, 하이픈만 사용합니다. 공백은 안 됩니다.
- **역할**: name이 그대로 `/task-organizer` 같은 명령이 됩니다.
- **조언**: 설명적이고, 짧고, 한눈에 뜻이 통하는 이름으로 지으세요.

**좋은 이름:**
- `meeting-notes`
- `code-review`
- `changelog-generator`

**나쁜 이름:**
- `my-skill-1`(아무것도 알려 주지 않음)
- `super_amazing_task_helper`(너무 길고, 언더스코어는 쓸 수 없음)
- `taskOrganizer`(camelCase — 소문자와 하이픈이어야 함)

### description: 가장 중요한 필드

```yaml
description: 어수선한 할 일 목록을 우선순위와 마감일에 따라 그룹으로 정리한다
```

**이 한 문장이 세 가지를 결정합니다:**[^S6]

1. **Claude가 이 스킬을 스스로 읽어 들일지 여부**
2. **사용자가 스킬 목록에서 보게 되는 내용**
3. **Claude가 이 스킬을 무엇을 위한 것으로 이해할지**

그래서 파일 안의 그 무엇보다 공들여 쓸 가치가 있습니다.[^S6]

> "The description is the single most important field in your frontmatter. A bad description means your skill either never triggers or triggers on everything. The formula: What it does + When to use it + Key capabilities."

(description은 프론트매터에서 가장 중요한 필드입니다. 이것이 부실하면 스킬은 아예 발동하지 않거나 아무 데서나 발동합니다. 공식은 '무엇을 하는지 + 언제 쓰는지 + 주요 기능'입니다.)

**좋은 description:**
```yaml
description: 어수선한 할 일 목록을 우선순위와 마감일에 따라 그룹으로 정리한다. 구조화되지 않은 작업 목록이나 회의 액션 아이템에 사용한다
```

**나쁜 description:**
```yaml
description: 작업을 도와준다  # 너무 모호함 — Claude는 언제 꺼내 써야 할지 알 수 없다
description: 지능형 우선순위 분석을 갖춘 강력한 태스크 관리 도구  # 홍보 문구. 쓸모 있는 정보는 맨 뒤에 오거나 아예 없다
```

### 선택 필드(여기가 아니라 레슨 6에서 다룹니다)

- `model`: 사용할 모델을 고른다
- `allowed-tools`: 이 스킬이 건드릴 수 있는 도구를 제한한다
- `version`: 버전 번호

**첫 스킬에는 `name`과 `description`만 있으면 충분합니다.**[^S4]

## Markdown 지시문: Claude에게 방법을 알려 주기

프론트매터 뒤의 모든 내용은 Claude가 읽고 따르도록 쓰인 것입니다.[^S1]

**좋은 지시문에는 세 가지 공통점이 있습니다.**

### 1. 명확한 섹션

제목을 사용해 각 부분을 나눕니다.

```markdown
## 입력 형식
(어떤 종류의 입력을 받을지)

## 단계
(절차를 한 단계씩 명시)

## 출력 형식
(결과가 어떤 모습이어야 하는지)

## 엣지 케이스
(까다로운 경우를 어떻게 처리할지)
```

### 2. 구체적인 단계

**약한 방식:**
```markdown
1. 작업을 분석한다
2. 우선순위를 정한다
3. 결과를 출력한다
```

**강한 방식:**
```markdown
1. 작업 목록을 읽는다. 한 줄에 작업 하나
2. 작업 텍스트에서 날짜 키워드를 추출한다(오늘, 내일, 금요일, 2024-01-15 등)
3. 작업에 "긴급", "ASAP", "오늘 안에"가 들어 있으면 높은 우선순위로 표시한다
4. 마감일이 가까운 순으로 정렬한다
5. 긴급, 중요, 보통 세 그룹으로 출력한다
```

## 두 부분이 함께 작동하는 방식

**프론트매터는 발견하는 장치이고, 지시문은 실행을 안내하는 지침입니다.**[^S2][^S5]

1. 여러분이 `/task-organizer`를 입력하거나, 그냥 "이 작업들 좀 정리해 줘"라고 말한다
2. Claude가 프론트매터의 `name`과 `description`을 읽고, 이 스킬을 읽어 들일지 판단한다
3. 읽어 들이기로 했다면, Claude가 지시문 전체를 읽는다
4. Claude가 쓰인 그대로 단계를 밟아 나간다
5. 출력이 지시문에서 지정한 형식과 일치한다

**description이 좋아야만 하는 이유가 여기에 있습니다**. Claude가 이 스킬을 쓸지 말지 판단할 때 가진 유일한 근거이기 때문입니다.[^S6]

"작업을 도와준다"라고 쓰면 Claude는 어떤 상황에서 써야 할지 알지 못합니다. "어수선한 할 일 목록을 우선순위와 마감일에 따라 그룹으로 정리한다"라고 쓰면, 요청에 들어 있는 "정리", "할 일", "작업" 같은 말만으로도 이 스킬을 불러들이기에 충분합니다.

## 실제 예시: 코드 리뷰 스킬 뜯어보기

실제로 쓰이고 있는 스킬을 보겠습니다.

```markdown
---
name: code-review
description: 코드 변경 사항에서 팀 컨벤션 위반, 버그 가능성, 성능 문제를 검토한다
---

# 코드 리뷰 어시스턴트

## 리뷰 체크리스트

아래 항목을 하나씩 확인한다:

### 1. 컨벤션
- 변수 이름이 팀 컨벤션을 따르는가(camelCase, 의미 있는 이름)?
- 50줄이 넘는 함수가 있는가(분리를 고려)?
- 중복된 코드가 있는가(DRY)?

### 2. 버그 가능성
- 처리되지 않은 에러가 있는가(try-catch, 에러 반환값)?
- null 역참조 가능성이 있는가?
- SQL 인젝션 위험이 있는가(데이터베이스를 다루는 경우)?

### 3. 성능
- N+1 쿼리가 있는가?
- 불필요한 중첩 루프가 있는가?
- 캐싱할 수 있는 반복 연산이 있는가?

## 출력 형식

모든 문제에 대해 다음을 제시한다:
- **위치**: 파일 이름 + 줄 번호
- **문제**: 구체적으로 무엇이 잘못됐는지
- **제안**: 어떻게 고칠지

문제가 없으면 "✓ 코드 리뷰 통과"를 출력한다
```

**뜯어보면 이렇습니다.**

- **프론트매터의 description**: 무엇을 하는지(코드를 리뷰한다)와 무엇을 점검하는지(컨벤션, 버그, 성능)를 밝히고 있다
- **지시문은 세 개의 체크리스트로 나뉜다**: 컨벤션, 버그, 성능. 각각에 살펴볼 구체적인 항목이 있다
- **출력 형식이 명시되어 있다**: 모든 문제에는 위치, 문제, 제안이 반드시 따라붙어야 한다

이렇게 쓰인 스킬은 한 번에 제대로 동작합니다.

## 💻 연습

### 레벨 1: 망가진 프론트매터 고치기

이 프론트매터의 무엇이 문제이고, 어떻게 고치겠습니까?

```markdown
---
name: My Amazing Tool
description: 도구
---
```

<!-- rubric -->
- `name`의 문제를 짚어냈다(공백 불가, 소문자로, 하이픈 사용)
- `description`의 문제를 짚어냈다(너무 모호하고, 무엇을 하는지 말하지 않는다)
- 구체적인 개선안을 제시했다

<!-- answer -->
**문제점:**

1. `name`에 공백과 대문자가 들어 있다. `my-amazing-tool`로 바꿔야 하지만 — 그래도 이름 자체는 여전히 나쁘다. 이 스킬이 무엇을 하는지 아무것도 알려 주지 않기 때문이다
2. `description`이 "도구"뿐이다. 이 스킬이 무엇을 하는지, 언제 꺼내 써야 하는지 말하지 않는다

**더 나은 버전:**

```markdown
---
name: api-doc-generator
description: 코드 주석에서 API 문서를 생성한다. JSDoc과 Python docstring 형식을 지원한다
---
```

<!-- hint -->
명명 규칙으로 돌아가자: 소문자, 숫자, 하이픈

<!-- hint -->
description 공식으로 돌아가자: 무엇을 하는지 + 언제 쓰는지 + 주요 기능

### 레벨 2: 내 사례에 맞는 프론트매터 작성하기

레슨 1의 연습에서 찾은 작업을 가져와 그 프론트매터를 작성해 보세요.

<!-- rubric -->
- `name`이 명명 규칙을 따른다(소문자, 하이픈, 설명적)
- `description`이 무엇을 하는지, 언제 쓰는지, 주요 기능이 무엇인지를 담고 있다
- `description`이 한 문장에 들어가고, 대략 200자 미만이다

<!-- answer -->
레슨 1의 고객 피드백 작업을 바탕으로 한 예시입니다.

```markdown
---
name: feedback-classifier
description: Slack의 고객 피드백을 버그 리포트, 기능 요청, 사용법 질문으로 분류하고 각각에 우선순위를 태그한다. 매일 하는 피드백 정리에 사용한다
---
```

**왜 이것이 잘 작동하는가:**
- `name`이 설명적이다 — 보는 순간 무엇인지 알 수 있다
- `description`이 무엇을 하는지(피드백을 분류·정리한다), 무엇이 들어가는지(Slack의 고객 피드백), 무엇이 나오는지(카테고리와 우선순위), 언제 쓰는지(매일 하는 정리)를 담고 있다

<!-- hint -->
description이 좋은지 판단이 서지 않는다면 이렇게 자문해 보자. 요청에 담긴 어떤 말이 Claude로 하여금 이 스킬을 떠올리게 해야 하는가? 그 말들을 description에 넣자.

## 정리

- **SKILL.md는 두 부분**: YAML 프론트매터(메타데이터)와 Markdown 지시문(지시)
- **필수 프론트매터 필드**: `name`(소문자, 하이픈, 고유)과 `description`(자동 발동을 좌우한다)
- **description 공식**: 무엇을 하는지 + 언제 쓰는지 + 주요 기능
- **좋은 지시문의 세 가지 특징**: 명확한 섹션, 구체적인 단계, 잘 만든 예시
- **두 부분이 맞물리는 방식**: 프론트매터로 Claude가 스킬을 찾고, 지시문으로 Claude가 그것을 실행한다

다음 레슨에서는 아무것도 없는 상태에서 시작해 완전한 스킬 하나를 처음부터 끝까지 작성합니다.
