## 개인 스킬 vs 프로젝트 스킬

지금까지 만든 스킬은 모두 `~/.claude/skills/`에 들어갔습니다. 그것들은 개인 스킬입니다 — 오직 당신만 쓸 수 있습니다. [^S1]

그런데 팀에서는 보통 다른 것이 필요합니다.

- 모두가 같은 기준으로 코드를 리뷰하는 것
- 새로 합류한 사람이 저장소를 클론하면 곧바로 팀의 스킬을 갖게 되는 것
- 스킬의 개선이 아무도 파일을 복사해 나르지 않아도 모두에게 닿는 것

그것이 바로 **프로젝트 스킬**이 존재하는 이유입니다. [^S9]

### 둘은 어떻게 다른가

| 특성 | 개인 스킬 | 프로젝트 스킬 |
|-------|----------------|----------------|
| 위치 | `~/.claude/skills/` | `.claude/skills/` |
| 범위 | 당신의 모든 프로젝트 | 현재 프로젝트 |
| 버전 관리 | 필요 없음 | Git에 커밋 |
| 팀 공유 | 공유되지 않음 | 모두와 공유 |
| 전형적 용도 | 개인 습관, 범용 도구 | 프로젝트 컨벤션, 팀 프로세스 |

### 어느 쪽을 골라야 하나

**개인 스킬:** [^S9]

- 문서 형식 변환 (Markdown → Word)
- 당신이 개인적으로 선호하는 작업 정리 방식
- 자기만의 코드 스타일 취향
- 모든 프로젝트에서 쓰고 싶은 범용 도구

**프로젝트 스킬:**

- 팀의 코드 리뷰 기준
- 프로젝트의 커밋 메시지 형식
- 특정 프레임워크용 스캐폴딩
- 프로젝트의 배포 절차

## 프로젝트 스킬 만들기

### 1단계: 프로젝트 디렉터리에 만들기

프로젝트로 이동합니다.

````bash
cd ~/projects/my-app

# 프로젝트 스킬 디렉터리 생성
mkdir -p .claude/skills/commit-format

# SKILL.md 생성
cat > .claude/skills/commit-format/SKILL.md << 'EOF'
---
name: commit-format
description: 짧은 커밋 메시지를 type, scope, 상세 본문을 갖춘 팀 필수 형식으로 다시 쓴다
---

# 커밋 메시지 포맷팅

간결한 커밋 메시지를 팀이 합의한 형식으로 다시 쓴다.

## 팀 컨벤션

커밋 메시지 형식:
```
<type>(<scope>): <subject>

<body>
```

**Types:**
- feat: 새 기능
- fix: 버그 수정
- docs: 문서 변경
- style: 서식만 (동작 변경 없음)
- refactor: 구조 재정리
- test: 테스트 관련
- chore: 빌드 또는 툴링 변경

**Scopes:**
- api: API 레이어
- ui: 인터페이스
- db: 데이터베이스
- auth: 인증과 인가
- core: 핵심 로직

## 처리 단계

1. 원본 커밋 텍스트를 읽고 type과 scope를 정한다
2. 빠져 있는 맥락을 채운다 (왜 변경했는지, 무엇에 영향을 주는지)
3. 요구된 형식으로 출력한다

## 출력 형식

```
<type>(<scope>): <subject>

<body>
- 왜 변경했는지
- 어떤 기능이나 모듈에 영향을 주는지
- 관련 issue나 PR이 있다면
```

## 예시

**입력:** "그 로그인 버그 고침"

**출력:**
```
fix(auth): 로그인 페이지의 비밀번호 검증 수정

- 문제: 비밀번호에 특수문자가 들어가면 검증이 실패했다
- 원인: 정규식이 특수문자를 이스케이프하지 않았다
- 영향: 비밀번호에 특수문자가 있는 사용자가 로그인할 수 없었다
- 관련 issue: #123
```
EOF
````

### 2단계: Git에 커밋하기

```bash
git add .claude/skills/commit-format/
git commit -m "feat(tooling): add commit message formatting Skill"
git push
```

### 3단계: 팀원이 받아 가기

팀의 다른 사람들은 이렇게 합니다.

```bash
git pull
```

스킬이 곧바로 동작합니다. 따로 설정할 것은 없습니다. [^S1]

## Git으로 스킬 관리하기

프로젝트 스킬이 Git 안에 들어오면, Git이 할 수 있는 모든 것이 그대로 적용됩니다. [^S8]

### 버전 이력

```bash
# 스킬의 이력 보기
git log -- .claude/skills/commit-format/

# 이전 버전으로 되돌리기
git checkout abc123 -- .claude/skills/commit-format/

# 두 버전 비교하기
git diff main..feature-branch -- .claude/skills/
```

### 스킬 자체를 코드 리뷰하기

**스킬을 리뷰하는 일은 코드를 리뷰하는 일만큼 중요합니다.** [^S10]

누군가 새 스킬을 제출하거나 기존 스킬을 바꿀 때:

1. description이 명확한지 확인한다
2. 지시문이 충분히 구체적인지 확인한다
3. 실제로 의도대로 동작하는지 테스트한다
4. 이 프로젝트에 자리를 차지할 만한지 판단한다 (기존 스킬과 충돌하지는 않는가?)

**PR에서 스킬 파일을 리뷰할 때:**

```markdown
## 리뷰 체크리스트

- [ ] description이 무엇을 하는지와 언제 쓰는지를 담고 있다
- [ ] 지시문이 구체적이고 실행 가능하다
- [ ] 입력과 출력 예시가 포함되어 있다
- [ ] 최소 3가지 케이스로 테스트했다
- [ ] 기존 스킬과 중복되거나 충돌하지 않는다
```

### 브랜치 활용

**실험적인 스킬은 피처 브랜치에 둡니다.**

```bash
# 실험 브랜치 생성
git checkout -b experiment/ai-refactor-skill

# 실험용 스킬 추가
mkdir -p .claude/skills/ai-refactor
# ... SKILL.md 작성

# 커밋
git add .claude/skills/ai-refactor/
git commit -m "experiment: add AI-assisted refactoring Skill"

# 일주일 써 보고, 값어치를 하면 main에 병합
git checkout main
git merge experiment/ai-refactor-skill
```

## 오래가는 팀 관행

### 1. README에 문서화한다

스킬을 문서화하는 일은 간단합니다. 프로젝트 루트 README나 `.claude/README.md`에 목록을 적으면 됩니다. [^S10]

````markdown
## 사용 가능한 Claude 스킬

### commit-format
간결한 커밋 메시지를 팀 형식으로 다시 씁니다.

**사용법:** `/commit-format [원본 커밋 메시지]`

**예시:**
```
/commit-format 로그인 버그 고침
```

### code-review
코드 변경을 팀 기준에 비추어 리뷰합니다.

**사용법:** `/code-review`를 입력한 뒤 코드나 diff를 붙여넣습니다

**참고:** 리뷰 출력은 참고용입니다 — 중요한 변경에는 여전히 사람 리뷰어가 필요합니다
````

### 2. 네이밍을 합의한다

팀 전체가 하나의 네이밍 컨벤션에 합의합니다. [^S8]

**권장:**

- 하이픈: `commit-format`, `api-doc-gen`
- 동사-명사 또는 명사-동사: `format-commit`, `review-code`
- 짧고 분명하게: 두세 단어

**피할 것:**

- 숫자 접미사: `skill-1`, `helper-v2`
- 모호한 것: `tool`, `helper`, `utility`
- 프로젝트 약어에 숫자를 붙인 것: `proj-skill-3`

### 3. 주기적으로 솎아낸다

분기에 한 번씩 전체를 점검합니다. [^S8]

```bash
# 모든 프로젝트 스킬 나열
ls .claude/skills/

# 각각에 대해 물어본다:
# - 지난 3개월 동안 몇 번이나 썼는가?
# - 지금 팀의 일하는 방식에 여전히 맞는가?
# - 다른 스킬이 이것을 대체했는가?
```

**거의 쓰이지 않는 스킬은 개선하거나 삭제해야 합니다.** 쓰이지 않는 스킬이 쌓이면 Claude가 실제로 맞는 스킬을 찾기 어려워집니다.

### 4. 변경을 알린다

**이건 중요합니다:** 기존 스킬을 바꿨다면 팀 채널에 알립니다.

```
📢 스킬 업데이트: code-review

변경 사항:
- React Hooks 규칙 점검 추가
- 함수 길이 임계값 하향 (50줄 → 40줄)

영향:
- 전에는 통과하던 코드가 이제 지적될 수 있음
- 최근 PR을 다시 리뷰해 볼 만함

문의: @dana
```

## 스킬 조합하기

**스킬 조합이란 여러 스킬을 이어 붙여 더 큰 작업 하나를 처리하는 것입니다.** [^S1]

```
/commit-format 로그인 버그 고침

(Claude가 포맷팅된 커밋을 돌려준다)

/code-review

(방금 바꾼 코드를 붙여넣는다)
```

**또는 한 스킬 안에서 다른 스킬을 참조합니다.**

```markdown
## 단계

1. commit-format 스킬로 커밋 메시지를 포맷팅한다
2. code-review 스킬로 코드 변경을 점검한다
3. 두 결과를 합쳐 PR 설명을 만든다
```

바로 여기에서 스킬의 도달 범위가 생깁니다. 작고 목적이 하나뿐인 스킬들이 모여 더 큰 워크플로가 됩니다. Anthropic 엔지니어링 가이드는 이렇게 표현합니다. "Instead of building fragmented, custom-designed agents for each use case, anyone can now specialize their agents with composable capabilities." (각 유스케이스마다 파편화된 맞춤 에이전트를 만드는 대신, 이제 누구나 조합 가능한 능력으로 자기 에이전트를 전문화할 수 있다.) [^S3]

## 기본기를 넘어서: 다음은 어디로

이제 핵심 기술은 갖췄습니다. 여기서부터 살펴볼 만한 방향이 몇 가지 있습니다.

### 선택적 프론트매터 필드

이 코스에서는 `name`과 `description`만 썼습니다. 더 있습니다. [^S5]

- **`model`**: 이 스킬이 어느 모델에서 돌아갈지 (더 강한 추론이 필요할 때)
- **`allowed-tools`**: 스킬을 특정 도구로 제한
- **`disable-model-invocation`**: Claude가 자동으로 로드하지 못하게 해서 수동 전용으로 만들기

셋 중에서 `model`은 모델을 고르고, `allowed-tools`는 권한 경계를 긋고, `disable-model-invocation`은 자동 트리거를 끄고 수동 호출만 남깁니다.

**언제 쓰는가:**

- 비용이 큰 작업 (외부 API 호출) → `disable-model-invocation`으로 실수로 발동되지 않게
- 신중한 추론이 필요한 작업 → `model: claude-opus-4`
- 보안에 민감한 스킬 → `allowed-tools`로 건드릴 수 있는 범위 제한

**전체 필드 목록은 공식 문서에 있습니다:** https://code.claude.com/docs/en/skills [^S1]

### 스킬과 MCP 서버

**MCP(Model Context Protocol) 서버는 도구를 공급하고, 스킬은 워크플로 지식을 공급합니다.** [^S7]

예를 들면:

- MCP 서버가 `read_database` 도구를 노출한다
- 스킬이 그 도구를 써서 "월간 리포트 생성" 워크플로를 수행하는 법을 Claude에게 가르친다

이 둘을 합치면, 스킬은 Claude와 외부 시스템을 잇는 다리가 됩니다. [^S7]

### 커뮤니티 스킬

다른 사람들이 무엇을 만들었는지 보려면:

- GitHub에서 "claude skills"를 검색
- https://github.com/travisvn/awesome-claude-skills [^S1]

**남의 스킬을 실행하기 전에:**

- SKILL.md 전체를 읽고 무엇을 하는지 파악한다
- 프로덕션 코드가 아니라 임시 프로젝트에서 먼저 시험한다
- 위험할 만한 것을 살핀다 (스크립트 실행, 네트워크 접근, 파일 수정)

## 💻 연습

### 레벨 1: 첫 프로젝트 스킬 만들기

지금 작업 중인 프로젝트를 하나 골라 프로젝트 스킬을 추가합니다.

1. 프로젝트 디렉터리에 `.claude/skills/[skill-name]/`을 만든다
2. 그 프로젝트에 특화된 스킬을 쓴다 (커밋 형식, 배포 절차, 테스트 생성 등 맞는 것으로)
3. Git에 커밋한다
4. 프로젝트 README에 문서화한다

<!-- rubric -->
- 스킬 디렉터리가 프로젝트의 `.claude/skills/` 아래에 있음
- SKILL.md가 완전함 (프론트매터 + 지시문)
- Git에 커밋됨
- README에 사용법이 설명되어 있음

<!-- answer -->
예시 (배포 점검 스킬):

**만들기:**
```bash
cd ~/projects/my-web-app
mkdir -p .claude/skills/deploy-check
cat > .claude/skills/deploy-check/SKILL.md << 'EOF'
---
name: deploy-check
description: 환경 변수, 의존성 버전, 테스트 커버리지, 설정 파일을 검증하는 배포 전 체크리스트
---

# 배포 전 점검

## 점검 항목

### 1. 환경 변수
- 필요한 환경 변수가 모두 설정되어 있는가 (DATABASE_URL, API_KEY 등)
- 민감한 값이 소스에 하드코딩되어 있지는 않은가

### 2. 의존성
- package.json의 버전이 고정되어 있는가 (`^`나 `~` 없이)
- 알려진 취약점은 없는가 (`npm audit` 실행)

### 3. 테스트
- 단위 테스트 커버리지 80% 이상
- 핵심 경로의 통합 테스트가 통과하는가

### 4. 설정
- 프로덕션 설정이 올바른가
- 로그 레벨이 INFO 또는 ERROR인가 (DEBUG가 아니라)

## 출력 형식

### ✅ 통과
- [점검 항목]

### ❌ 실패 (배포 차단)
- [점검 항목] - [문제] - [수정 방법]

### ⚠️ 경고 (수정 권장, 차단하지는 않음)
- [점검 항목] - [문제]
EOF

git add .claude/skills/deploy-check/
git commit -m "feat(tooling): add pre-deploy check Skill"
```

**문서화하기 (프로젝트 README에):**
```markdown
## 배포 전 점검

`/deploy-check`를 실행해 배포 전 체크리스트를 전부 훑습니다.

**다루는 것:**
- 환경 변수 설정
- 의존성 보안
- 테스트 커버리지
- 프로덕션 설정

모든 점검을 통과한 뒤에만 프로덕션에 배포하세요.
```

### 레벨 2: 스킬 PR 리뷰하기

팀원이 새 스킬을 추가하는 PR을 열었습니다. 리뷰를 작성하세요.

**PR 내용:**
```markdown
---
name: helper
description: Helps process data
---

# Helper
```

**문제 1: 이름이 너무 모호하다**

`helper`는 이 스킬이 무엇을 하는지 아무것도 말해 주지 않습니다. 대신 설명적인 이름을 쓰세요.

**문제 2: description을 쓸 수가 없다**

'Helps process data'는 너무 넓어서, Claude가 이 스킬이 언제 해당되는지 판단할 방법이 없습니다.

다음을 밝혀야 합니다.

- 어떤 데이터인지 (사용자 입력? CSV 파일? API 응답?)
- 그것에 무엇을 하는지 (검증? 변환? 정제?)

**문제 3: 지시문에 세부가 전혀 없다**

'Read the data', 'Process it', 'Output the result' — 어느 것도 실행 가능하지 않습니다. 다음이 필요합니다.

- 입력 형식

- 최소 하나의 입출력 예시

## 정리

- **개인 스킬(`~/.claude/skills/`)은 자기 습관을 위한 것**이고, 프로젝트 스킬(`.claude/skills/`)은 팀으로 일하기 위한 것이다 [^S9]
- **프로젝트 스킬은 Git에 들어가고**, 팀원은 자동으로 받아 가며, 다른 파일과 똑같이 버전 관리하고 브랜치를 딸 수 있다
- **팀 관행**: 문서화하기, 네이밍 합의하기, 주기적으로 솎아내기, 변경 알리기
- **스킬은 조합된다**: 작고 목적이 하나뿐인 스킬들이 모여 더 큰 워크플로가 된다 [^S3]
- **다음 갈 곳**: 선택적 프론트매터 필드, MCP 서버 연동, 커뮤니티 스킬
