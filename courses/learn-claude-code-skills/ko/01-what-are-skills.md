## 매번 똑같은 절차를 설명하고 있다

여러분은 Claude Code로 회의록을 정리하고 있습니다. 이렇게 입력합니다. "이 회의 녹취록을 구조화된 항목으로 정리해 주세요. 결정 사항, 액션 아이템, 미결 사항으로 나누고, 액션 아이템마다 담당자와 마감일을 태그로 붙여 주세요."

Claude는 요청대로 해냅니다. 결과물도 좋습니다.

다음 날, 또 다른 회의가 있습니다. 여러분은 같은 내용을 다시 입력합니다.

사흘째, 나흘째. 회의가 끝날 때마다 같은 지시를 다시 내리고 있습니다. Claude는 매번 제대로 처리하지만, 매번 여러분이 처음부터 설명해야 합니다.[^S1]

**이것이 스킬이 해결하는 문제입니다**: 계속 설명하게 되는 워크플로를 재사용 가능한 지시로 패키징하는 것입니다. 한 번 작성해 두면 필요할 때마다 호출할 수 있습니다.[^S2]

## 스킬이란 무엇인가

**스킬은 특정 작업을 어떻게 처리할지 Claude에게 알려 주는 SKILL.md 파일이 담긴 디렉터리입니다.**[^S4]

Claude에게 건네는 작업 절차서라고 생각하면 됩니다. 단계를 명확하게 적어 두면 Claude가 그것을 보고 작업합니다. 설명을 처음부터 다시 할 필요가 없습니다.[^S3]

예를 들어 회의록 정리 스킬의 핵심은 다음과 같은 모습입니다.

```markdown
---
name: meeting-notes
description: 회의 녹음이나 녹취록을 결정 사항, 액션 아이템, 미결 사항으로 정리한다
---

# 회의록 정리

## 단계

1. 회의 내용(녹취록 또는 녹음 파일)을 읽는다
2. 실제로 내려진 결정 사항을 모두 뽑아내 한 줄에 하나씩 적는다
3. 모든 액션 아이템을 [작업] - 담당자 - 마감일 형식으로 뽑아낸다
4. 언급은 됐지만 결론이 나지 않은 것을 미결 사항으로 나열한다
5. 출력을 날짜순으로 정렬하되 마감일이 가까운 것을 앞에 둔다
```

이렇게 저장해 두면 `/meeting-notes`와 회의 내용을 입력하는 것만으로 Claude는 이미 무엇을 해야 하는지 알고 있습니다.[^S1]

## 어떤 상황이 스킬에 적합한가

**스킬에 적합한 상황에는 세 가지 공통점이 있습니다.**

1. **반복성**: 매주, 매일, 때로는 매시간 같은 일을 한다
2. **고정된 단계**: 매번 달라지지 않고 명확한 단계로 적어 낼 수 있다
3. **검증 가능성**: Claude가 제대로 했는지 판단할 수 있다

**대표적인 적합 사례:**

- 코드 리뷰(팀의 컨벤션에 비추어 작업물을 점검)
- 문서 형식 변환(특정 서식을 유지하면서 Markdown을 Word로)
- 로그 분석(에러 로그에서 의미 있는 신호를 추출)
- 테스트 케이스 생성(기능 설명을 테스트 시나리오로 변환)
- 커밋 메시지 정규화(무뚝뚝한 커밋을 팀이 합의한 형식으로 다시 작성)

**스킬에 적합하지 않은 상황:**

- 일회성 작업("이 페이지 레이아웃 설계하는 것 좀 도와줘" 같은 것)
- 매번 사람의 판단이 많이 필요한 작업
- 완전히 열려 있는 창작 작업

## 스킬이 동작하는 방식

스킬을 만들 때 여러분이 실제로 하는 일은 두 가지입니다.[^S5]

1. **YAML 프론트매터 작성**(파일 맨 위 `---`로 감싸인 부분). 이 스킬의 이름이 무엇이고 언제 사용해야 하는지를 Claude에게 알려 줍니다
2. **Markdown 지시문 작성**(프론트매터 뒤의 본문). 이 작업을 정확히 어떻게 수행할지를 Claude에게 알려 줍니다

**사용하는 방법은 두 가지입니다.**

- **수동 호출**: `/meeting-notes`를 입력하면 Claude가 해당 스킬의 지시문을 읽어 들여 실행합니다
- **자동 트리거**: "이 회의록 좀 정리해 줘"라고 말하면 Claude가 각 스킬의 description을 읽고 meeting-notes 스킬이 관련 있다고 판단해 스스로 읽어 들입니다[^S6]

자동 트리거는 description이 잘 작성되어 있을 때만 동작합니다. 이 내용은 레슨 2에서 자세히 다룹니다.

## 스킬이 놓이는 위치

**위치는 두 곳입니다.**[^S1]

- **개인 스킬**: `~/.claude/skills/` — 자신만 쓰며, 모든 프로젝트에서 사용할 수 있습니다
- **프로젝트 스킬**: `.claude/skills/` — 프로젝트 디렉터리에 보관되므로, 팀원이 저장소를 클론하면 함께 받게 됩니다

첫 스킬은 개인 스킬로 시작하세요. 몇 개 만들어 보고 실제로 쓸모 있다는 것이 확인되면, 가장 자주 쓰는 것을 프로젝트 디렉터리로 옮겨 팀과 공유하면 됩니다.

### 레벨 1: 첫 스킬 후보 찾기

지난 한 주의 업무를 돌아보고, Claude에게 최소 세 번은 설명한 작업을 하나 찾아보세요.

다음을 적어 보세요.
1. 그 작업은 무엇인가?
2. 단계가 고정되어 있는가?
3. Claude가 제대로 했는지 판단할 수 있는가?

- 다른 사람이 읽어도 무슨 일을 하는지 알 수 있을 만큼 작업 설명이 명확하다
- 단계가 고정되어 있는지 여부를 분명히 밝힌다

예시 답변:

**작업**: Slack 채널의 고객 피드백을 버그 리포트, 기능 요청, 사용법 질문으로 분류하기

**단계가 고정?**: 네. 항상 메시지를 읽고, 분류를 판단하고, 해당 항목으로 정리하고, 우선순위 태그를 붙이는 흐름입니다

**검증 가능?**: 네. 분류가 맞는지, 우선순위 태그가 타당한지 눈으로 확인할 수 있습니다

**스킬에 적합?**: 네. 반복성이 높고, 단계가 고정되어 있으며, 검증할 수 있습니다

## 정리

- **스킬은 반복되는 워크플로를 재사용 가능한 지시로 패키징**하므로, 매번 다시 설명할 필요가 없다
- **스킬에 적합한 상황**: 반복성, 고정된 단계, 검증 가능한 결과
- **스킬은 디렉터리와 SKILL.md 파일**이며, YAML 프론트매터와 Markdown 지시문을 담는다
- **사용법은 두 가지**: 수동 호출(`/skill-name`) 또는 자동 트리거(Claude가 description을 보고 판단)
- **위치는 두 곳**: 개인 스킬(`~/.claude/skills/`)과 프로젝트 스킬(`.claude/skills/`)
