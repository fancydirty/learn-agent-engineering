# 레슨 3: 실습: 첫 스킬 작성하기

> 학습 목표:
> - 스킬의 디렉터리 구조 만들기
> - 완전한 SKILL.md를 처음부터 작성하기
> - 점진적 공개 원칙 이해하기
> - 만든 스킬을 처음으로 호출해 보기
>
> 전제: [<< 레슨 2](./02-skill-anatomy.md) | 다음: [레슨 4 >>](./04-testing-debugging.md)

## 무엇을 만드는가

이번 레슨에서는 아무것도 없는 상태에서 실제로 쓸 수 있는 스킬 하나를 만듭니다. 바로 **태스크 정리 도구**입니다.

**하는 일:**
- 입력: 어수선하게 쌓인 할 일들(흩어진 텍스트, 스크린샷에서 뽑아낸 텍스트, 회의록)
- 출력: 우선순위와 마감일로 묶은 깔끔한 목록

**왜 이것을 고르는가:**
- 단순합니다 — 복잡한 로직이 앞을 가리지 않습니다
- 쓸모 있습니다 — 오늘부터 바로 쓸 수 있습니다
- 스킬 구조의 핵심 부분을 빠짐없이 다뤄 봅니다

## 1단계: 디렉터리와 파일 만들기

터미널을 열고 다음을 실행합니다.

```bash
# 개인 스킬 디렉터리 생성(아직 없다면)
mkdir -p ~/.claude/skills

# 스킬 디렉터리 생성
mkdir ~/.claude/skills/task-organizer

# SKILL.md 파일 생성
touch ~/.claude/skills/task-organizer/SKILL.md
```

**이제 디렉터리 구조는 다음과 같습니다.**

```
~/.claude/skills/
└── task-organizer/
    └── SKILL.md
```

평소 쓰는 텍스트 편집기(VS Code, Cursor 등 무엇이든)로 `SKILL.md`를 엽니다.

## 2단계: 프론트매터 작성하기

파일 맨 위의 메타데이터부터 시작합니다. [^S1]

```markdown
---
name: task-organizer
description: 할 일 항목을 정리해 우선순위와 마감일로 묶는다. 어수선한 작업 목록, 회의 액션 아이템, 프로젝트 백로그에 사용한다
---
```

**체크리스트:**
- ✓ `name`이 소문자와 하이픈으로 되어 있다
- ✓ `description`이 무엇을 하는지(할 일을 정리한다), 무엇을 입력으로 받는지(어수선한 목록), 언제 꺼내 쓰는지(회의 액션 아이템, 프로젝트 백로그)를 담고 있다

## 3단계: 제목과 소개 작성하기

프론트매터 뒤에 제목을 추가합니다.

```markdown
# 태스크 정리 도구

구조화되지 않은 텍스트에서 작업을 뽑아내, 우선순위와 마감일에 따라 구조화된 목록으로 정리한다.
```

**제목과 소개를 굳이 쓰는 이유:**
- 제목은 사람을 위한 것입니다 — 석 달 뒤에 이 파일을 다시 열어도 한눈에 용도가 떠오릅니다
- 소개는 Claude를 위한 것입니다 — `description`에 담을 자리가 없었던 세부 내용을 채워 줍니다

## 4단계: 입력 형식 정의하기

어떤 종류의 입력을 받을지 Claude에게 알려 줍니다. [^S5]

````markdown
## 입력 형식

다음 형태 중 무엇이든 작업 목록으로 받는다:

- 일반 텍스트 목록(한 줄에 작업 하나)
- Markdown 체크리스트(`- [ ] 작업 내용`)
- 시간 표시가 있는 메시지("내일까지 X 끝내야 함")
- 회의록에 묻혀 있는 액션 아이템

**입력 예시:**

```
분기 보고서 마무리하기
- [ ] PR #234 리뷰
내일까지 로그인 버그 고쳐야 함
금요일 전까지 데모 준비
문서 업데이트
```
````

**이 섹션이 해내는 일:**
- 이 스킬이 마주칠 수 있는 입력 형태를 빠짐없이 열거한다
- 구체적인 예시를 하나 제시해, 실제 입력이 어떤 모습인지 Claude가 알게 한다

## 5단계: 처리 단계 작성하기

여기가 지시문의 심장부이며, 구체적으로 써야 합니다. [^S5]

```markdown
## 처리 단계

다음을 순서대로 수행한다:

1. **작업 추출**
   - 각 줄 또는 각 목록 항목이 작업 하나
   - 체크박스 마커(`- [ ]` 또는 `- [x]`)를 제거
   - 작업의 핵심 설명을 유지

2. **시간 정보 식별**
   - 날짜를 나타내는 말을 찾는다: 오늘, 내일, 이번 주, 요일 이름(월요일, 금요일), 명시적 날짜(2024-01-15)
   - 마감을 나타내는 표현을 찾는다: "X까지", "마감 X", "X 전에"
   - 명시적인 시간이 없으면 "마감 없음"으로 표시

3. **우선순위 부여**
   - "긴급", "ASAP", "바로", "즉시"를 포함 → 긴급
   - "중요", "우선", "치명적"을 포함 → 중요
   - 오늘 또는 내일 마감 → 긴급
   - 이번 주 안에 마감 → 중요
   - 그 밖의 모든 것 → 보통

4. **정렬**
   - 같은 우선순위 안에서는 마감일이 가까운 순으로 정렬
   - 마감이 없는 작업은 해당 등급의 맨 뒤에 배치
```

**이렇게까지 자세히 쓰는 이유:**

Claude는 사람이 아니어서 "알아서 헤아려" 주지 않습니다. "우선순위를 부여한다"라고만 쓰면 어떤 기준을 적용해야 할지 알 수 없습니다. "'긴급'을 포함 → 긴급"이라고 쓰면 추측할 여지가 남지 않습니다. [^S2]

## 6단계: 출력 형식 정의하기

결과가 어떤 모습이어야 하는지 Claude에게 알려 줍니다.

```markdown
## 출력 형식

이 구조를 사용하고, 우선순위 표시는 이모지로 한다:

### 🔴 긴급(오늘 또는 내일)
- [작업] - 마감

### 🟡 중요(이번 주)
- [작업] - 마감

### ⚪ 보통
- [작업] - 마감(있는 경우)

**출력 예시:**

### 🔴 긴급
- 로그인 버그 수정 - 내일
- 분기 보고서 마무리 - 오늘

### 🟡 중요
- PR #234 리뷰 - 금요일
- 데모 준비 - 금요일

### ⚪ 보통
- 문서 업데이트 - 마감 없음
```

**예시가 가져다주는 것:**

예시를 한 번 본 뒤로는 배치, 기호, 서식이 확정됩니다. 이모지가 어디에 붙는지, 시간이 작업 앞에 오는지 뒤에 오는지 추측할 필요가 없습니다.

## 7단계: 엣지 케이스 처리하기

이례적인 경우를 어떻게 다룰지 명시합니다.

```markdown
## 참고 사항

- 입력이 비어 있거나 작업을 하나도 식별할 수 없으면 "유효한 작업을 찾지 못했습니다"를 출력한다
- 어떤 작업에도 시간 정보가 없으면 모두 보통에 넣는다
- 작업 설명이 길면(100자 초과) 앞의 80자만 남기고 "..."를 붙인다
- 이미 완료로 표시된 작업(`[x]`)은 건너뛴다
```

## 완성된 파일

이제 `SKILL.md`는 다음과 같은 모습이어야 합니다.

## 점진적 공개: 왜 모든 세부 사항을 처음부터 쓰지 않는가

이 스킬에는 다른 작업에 의존하는 작업이나, 서로 다른 사람에게 배정된 작업에 관한 이야기가 전혀 없다는 것을 눈치챘을지도 모릅니다. [^S2][^S5]

**의도한 것입니다.**

**점진적 공개란, 한꺼번에 모든 것을 쏟아붓는 대신 지금 당장 필요한 것만 Claude에게 주는 것입니다.** [^S2]

첫 버전은 핵심 작업만 합니다 — 추출하고, 분류하고, 정렬하는 것. 며칠 써 보고 담당자 배정이 정말로 필요하다고 느껴지면 그때 추가하면 됩니다.

**이렇게 해서 얻는 것:**
- 짧은 스킬 파일: 소비하는 컨텍스트가 줄고, 로딩이 빨라진다
- 단순한 로직: 잘못될 수 있는 경로가 적어진다
- 핵심 동작이 실제로 작동하는지 빠르게 확인할 수 있다

먼저 1번 버전을 굴러가게 만들고, 그다음 반복하세요. 좋은 스킬은 모두 그렇게 만들어집니다. [^S2]

```markdown
# 피드백 분류기

Slack 메시지에서 고객 피드백을 뽑아내, 유형과 우선순위에 따라 정리한다.

## 입력 형식

다음을 받는다:
- 내보내기 한 Slack 메시지(일반 텍스트)
- 고객 피드백 스크린샷에서 추출한 텍스트
- 손으로 복사해 붙여 넣은 메시지

## 처리 단계

1. **피드백 추출**
   - 각 메시지에서 핵심 문제나 요청을 식별
   - 주변의 잡담(인사, 감사 표현 등)은 걷어낸다

2. **유형 판단**
   - 오류, 크래시, 동작하지 않는 것을 설명 → 버그 리포트
   - 새로운 기능이나 더 나은 경험을 요청 → 기능 요청
   - 어떻게 하는지, 왜 그렇게 동작하는지를 질문 → 사용법 질문

3. **우선순위 태그**
   - 프로덕션에 영향을 주고, 업무를 막는다 → P0(최상위)
   - 일부 사용자에게 영향을 주고, 우회 방법이 있다 → P1
   - 다듬는 수준, 있으면 좋은 것 → P2

4. **핵심 세부 정보 추출**
   - 제품의 어느 부분과 관련 있는지
   - 어떤 사용자인지(언급된 경우)
   - 시간에 민감한 사안인지

## 출력 형식

### 버그 리포트
- [설명] - 우선순위 - 영역

### 기능 요청
- [요청] - 우선순위 - 영역

### 사용법 질문
- [질문] - 영역

## 참고 사항

- 한 메시지가 서로 다른 여러 문제를 제기하면 여러 항목으로 나눈다
- 우선순위가 분명하지 않으면 P1로 태그한다
- 원래 타임스탬프가 있으면 그대로 유지한다
```

단계가 충분히 구체적인지 확신이 서지 않는다면 자문해 보자. 이 작업을 한 번도 해 본 적 없는 동료가 이 파일을 한 줄씩 따라 했을 때 제대로 해낼까?

<!-- hint -->
첫 버전이 완벽할 필요는 없다. 핵심 흐름을 쓰고, 일단 굴러가게 만든 뒤, 세부 사항은 나중에 다듬자

### 레벨 2: 엣지 케이스 테스트하기

만든 스킬에 얌전하지 않은 입력을 넣어 보세요. 예를 들면 다음과 같습니다.
- 빈 입력
- 형식이 깨진 입력
- 특수 문자가 들어 있는 입력

무엇이 나오는지 보고 기록해 두세요. 다음 레슨에서 그 결과를 디버깅 연습에 사용합니다.

<!-- rubric -->
- 엣지 케이스를 최소 한 가지 테스트했다
- 입력과 실제 출력을 모두 기록했다
- 출력이 기대와 일치했는지 말할 수 있다

<!-- answer -->
테스트 예시:

**입력:** 빈 문자열

**기대:** "유효한 작업을 찾지 못했습니다"를 출력해야 한다

**실제 출력:** (Claude가 실제로 내놓은 것을 기록)

**기대와 일치:** (예 / 아니요 — 아니라면 어디에서 어긋났는지 적는다)

<!-- hint -->
고려할 만한 엣지 케이스: 빈 입력, 형식이 깨진 입력, 아주 긴 입력, 특수 문자, 극단적인 값

## 정리

- **스킬을 만드는 7단계**: 디렉터리 → 프론트매터 → 제목 → 입력 → 단계 → 출력 → 엣지 케이스
- **단계는 구체적이어야 한다**: "작업을 분석한다"가 아니라 "날짜를 나타내는 말을 찾는다: 오늘, 내일…"
- **예시가 중요하다**: 입력과 출력이 실제로 어떤 모습인지 Claude에게 보여 준다
- **점진적 공개**: 1번 버전은 핵심 작업만 한다 — 모든 세부 사항을 처음부터 쓰지 않는다
- **호출 방법**: `/skill-name` 뒤에 입력을 붙인다
