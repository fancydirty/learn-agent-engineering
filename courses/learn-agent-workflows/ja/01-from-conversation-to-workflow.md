# レッスン1: 会話からワークフローへ: オーケストレーションが存在する理由

> 学習目標:
> - 単一の会話とワークフローの根本的な違いを理解する
> - ワークフローに適したタスクの特性を認識する
> - ワークフローオーケストレーションの核心的価値を把握する
>
> 前提: Claude Codeや類似のAIツールを使用したことがある | 次: [レッスン2 >>](./02-workflow-building-blocks.md)

## エージェントが壁にぶつかる

Claude Codeに大規模なコードベースのリファクタリングを依頼します。「この5,000行のモノリスをマイクロサービスに分割して」

Claudeは作業を開始します。ファイルを読み、モジュールの境界を特定し、依存関係を抽出し、そしてファイル47あたりで、コンテキストウィンドウがいっぱいになります。以前の作業を忘れ、最初からやり直し、ループに陥ります。[^S3]

あるいは「すべてのオープンなPRをレビューして、今週のリリースノートを書いて」と依頼します。Claudeは一度に1つのPRしか処理できないため、手動で20回実行し、毎回フォーマットルールを再説明することになります。

これが単一の会話の上限です。1つの会話、1つのコンテキストウィンドウ、1つの推論チェーン。複雑なタスクに対して、このパターンは破綻します。[^S1]

## ワークフローとは何か

ワークフローは、複雑なタスクをステップに分解し、各ステップを新しいエージェントに委譲し、全体を自身で調整する実行可能なスクリプトです。[^S2]

主な違い:

| 次元 | 単一の会話 | ワークフロー |
|------|---------|--------|
| 制御フロー | エージェントが次に何をするかを決定 | スクリプトが次に何をするかを決定 |
| コンテキスト | すべての履歴が1つのウィンドウに存在 | 各ステップが独自のコンテキストを持つ |
| 並列性 | 順次実行 | 多数のエージェントを同時起動可能 |
| 再現性 | 実行ごとに異なる可能性 | 固定スクリプト、決定論的実行 |
| 適合するスケール | 小規模タスク（数ファイル） | 大規模タスク（数百ファイル、複数の検証段階） |

例えば、リファクタリングワークフローは次のようになります:

```javascript
// 疑似コード例
async function refactorWorkflow(codebase) {
  // ステップ1: すべてのモジュールを並列解析
  const modules = await Promise.all(
    codebase.files.map(file => 
      agent({ task: `${file}の責務と依存関係を解析` })
    )
  );
  
  // ステップ2: マイクロサービスの境界を提案
  const plan = await agent({ 
    task: '解析結果からマイクロサービスの境界を設計',
    context: modules 
  });
  
  // ステップ3: 各サービスを並列抽出
  const services = await Promise.all(
    plan.services.map(svc => 
      agent({ task: `${svc.name}サービスのコードを抽出` })
    )
  );
  
  // ステップ4: すべてのサービスのテストが通ることを検証
  return await agent({ 
    task: 'すべてのサービスのテストスイートを実行',
    context: services 
  });
}
```

スクリプトがループ、分岐、中間結果を保持し、Claudeのコンテキストは最終的な答えだけを見ます。オーケストレーションは決定論的で、各ステップ内の作業のみがモデル駆動です。[^S2]

## ワークフローが適合する場合

ワークフローに適したタスクを示す4つの特性:

1. **1つの会話が調整できる以上のエージェントが必要。** 単一の会話は3〜5個のサブエージェントを管理できます。それを超えると、ワークフローが必要です。
2. **オーケストレーションを読みやすく再利用可能なスクリプトとして成文化したい。** 一度書けば、いつでも再実行できます。
3. **タスクが明確なフェーズに分割される。** 解析、計画、実装、検証。
4. **並列実行やクロスチェックが必要。** 独立したサブタスク、敵対的検証、トーナメント式比較。

公式ドキュメントは明確に述べています: "Reach for a workflow when a task needs more agents than one conversation can coordinate, or when you want the orchestration codified as a script you can read and rerun."（1つの会話が調整できる以上のエージェントが必要なタスク、またはオーケストレーションを読み、再実行できるスクリプトとして成文化したい場合にワークフローを選択してください）[^S1]

典型的なシナリオ:

- **コードベース監査。** 500ファイルをスキャンし、セキュリティ問題をチェックするファイルごとに1エージェント、その後結果を集約。
- **大規模マイグレーション。** 200個のコンポーネントをVue 2からVue 3へ並列アップグレードし、最後に統合を検証。
- **クロスチェック研究。** 5つのエージェントに同じ質問を独立に調査させ、事実をクロスチェックし、一貫性レポートを生成。
- **多角的設計レビュー。** 設計を3つの角度（アーキテクチャ、パフォーマンス、コスト）から独立に評価し、その後マージ。[^S1]

ワークフローが間違ったツールである場合:

- 単一ファイルの編集やコードレビューなど、直接の会話で十分なシンプルなタスク。
- クリエイティブライティングやブレインストーミングのようなオープンエンドの作業。
- 多くの人間の判断が必要で、ステップに還元できないタスク。

## ワークフローの進化

ワークフローは突然現れたわけではありません。Claude Codeのオーケストレーション能力の第4段階です:[^S3]

**段階1: モノリシックエージェント**
```
┌─────────┐
│ Claude  │  1つのコンテキストウィンドウがすべてを実行:
└─────────┘  読み込み、計画、編集、テスト
```

**段階2: サブエージェントファンアウト（Agentツール）**
```
┌─────────┐
│ Claude  │──→ agent: "コードベースを検索"
│ (main)  │──→ agent: "これら40ファイルを読む"
└─────────┘  結果が親エージェントに返る
```

**段階3: エージェントチーム**
```
┌─────────┐    ┌─────────┐    ┌─────────┐
│ Planner │───→│ Coder   │───→│ Tester  │
└─────────┘    └─────────┘    └─────────┘
     各エージェントが独自の役割とコンテキストを保持
```

**段階4: ワークフローオーケストレーション**
```
    ┌─────────────────┐
    │ Workflow Script │  ループ、分岐、状態を保持
    └────────┬────────┘
         ┌───┴───┬───────┬───────┐
         ↓       ↓       ↓       ↓
    agent()  agent() agent() agent()
    各呼び出しが独立したサブエージェントを起動
```

ワークフローの核心的革新は制御フローの反転です: エージェントに「次に何をすべきか」を決めさせる代わりに、スクリプトが「次にどのエージェントを呼び出すか」を決定します。[^S2]

## オーケストレーションの本質

オーケストレーションは文字通りの意味です: "Orchestration is exactly what it sounds like: one score, many musicians. A script deciding it — for loop, if statement — is orchestration."（オーケストレーションはまさにその通りの意味です: 1つの楽譜、多数の演奏者。スクリプトがそれを決定する — forループ、if文 — それがオーケストレーションです）[^S3]

ワークフローにおいて:

- **楽譜** = あなたが書くJavaScript/TypeScriptスクリプト、その`for`ループ、`if`文、`Promise.all`呼び出し。
- **演奏者** = 各`agent()`呼び出しが起動するサブエージェント。
- **指揮者** = スクリプトの実行エンジン、楽譜に従ってエージェントを調整。

これがその区別を、それを命名したガイドの言葉で: "A normal agent decides the control flow as it goes. A workflow inverts that. You write the control flow as plain code, and each individual step is delegated to a fresh subagent."（通常のエージェントは進むにつれて制御フローを決定します。ワークフローはそれを反転させます。制御フローをプレーンなコードとして書き、個々のステップは新しいサブエージェントに委譲されます）

通常のエージェントは実行時に即興します: 「最初にAを実行し、その後BかCのどちらを実行するか決定」。ワークフローは制御フローをコードで固定します: 「A1〜A10を並列実行し、すべて完了したらBを実行。Bが`score > 0.8`を返せばCを実行、そうでなければD」。

決定論的オーケストレーションが得られるもの:

- **予測可能。** 同じ入力、同じ実行パス。
- **デバッグ可能。** どのステップが失敗したかが明白。
- **再実行可能。** スクリプトは`.claude/workflows/`に存在し、名前で呼び出せる。
- **スケーラブル。** 10エージェントから100エージェントへの移行は、ループカウントの変更だけ。[^S2]

## 最初のワークフローシナリオ: コードレビューパイプライン

実際のケースを見てみましょう。チームには15個のPRがレビュー待ちで、各PRには4つのチェックが必要です:

1. コードはスタイルガイドに従っているか？
2. 明らかなバグはないか？
3. テストカバレッジは十分か？
4. 関連ドキュメントは更新されたか？

単一の会話では、15回実行し、毎回手動でPRを切り替えます。

ワークフローでは:

```javascript
async function reviewPRsWorkflow(prList) {
  // フェーズ1: すべてのPRを並列レビュー
  const reviews = await Promise.all(
    prList.map(pr => 
      agent({
        task: `PR #${pr.number}をレビュー`,
        prompt: `コードスタイル、潜在的バグ、テスト、ドキュメントをチェック。
                 JSON出力: { style: score, bugs: [], 
                 coverage: number, docs: boolean }`
      })
    )
  );
  
  // フェーズ2: レポート集約
  return await agent({
    task: '週次レポート生成',
    prompt: `${reviews.length}個のPRのレビュー結果に基づいて、
             今週のコード品質レポートを作成し、
             問題を重大度順にソート`
  });
}
```

このワークフローが得られるもの:

- 15個のPRを並列レビュー、順次より15倍高速。
- 一貫したレビュー基準（すべてのPRが同じプロンプトを使用）。
- 毎週自動実行可能、手動ステップなし。
- スクリプトはGitにコミットされ、チーム全体で共有される。

## 💻 演習

### レベル1: 最初のワークフローシナリオを見つける

過去1週間の作業を振り返り、反復的なタスクを見つけ、それがワークフローに適合するか判断してください:

**基準:**
- 多数の類似した入力を処理する必要がある（多数のファイル、多数のデータソース、多数のサービス）
- 明確なフェーズがある（抽出、変換、検証、出力）
- プロセスが毎回同じ方法で実行されることを望む
- 部分的または完全に並列実行可能

**記述内容:**
1. タスクを1文で
2. 現在どのように実行しているか
3. ワークフローを使用した場合、どのフェーズに分割されるか
4. どれだけの時間を節約できると予想するか

<!-- rubric -->
シナリオが明確に記述され、フェーズが合理的（3〜5個）で、並列実行がどこで役立つかを指摘でき、時間見積もりに根拠がある（例: 「10ファイルを順次処理すると今日は30分かかる。並列では5分を期待」）。

<!-- answer -->
回答例 — タスク: 複数のマイクロサービスの変更履歴を生成。現在: 各サービスのGitコミットを手動で読み、ドキュメントにコピー。ワークフローフェーズ: (1) 各サービスのコミット履歴を並列取得、(2) コミットをユーザー可読な変更記述に並列変換、(3) 統一フォーマットでリリースノートにまとめる、(4) 前バージョンと比較したハイライトサマリーを生成。期待: 45分から8分に短縮、ステップ1と2で8サービスを並列処理できるため。

<!-- hint -->
多数の類似オブジェクトに同じ操作を行うタスクから始めてください。ファイルのバッチ処理、APIのバッチ呼び出し、レポートのバッチ生成など。

<!-- hint -->
優れたワークフローシナリオは通常、ファンアウト、処理、集約の形状を持っています: タスクを多数のエージェントに分散し、各自がスライスを処理し、結果をマージします。

### レベル2: 単一の会話とワークフローを比較

次の2つのシナリオの1つを選び、なぜ一方が単一の会話に適し、もう一方がワークフローに適するかを説明してください:

**シナリオA:** 明確なロジックを持つ50行の関数のバグを修正する。

**シナリオB:** 30個のコンポーネントのUIライブラリをMaterial-UI v4からv5にアップグレードする。

判断と理由を記述してください（各シナリオ2〜3文）。

<!-- rubric -->
シナリオAが単一の会話に適し（小規模タスク、管理可能なコンテキスト、並列性不要）、シナリオBがワークフローに適する（大規模、分解可能、並列化可能）ことを正しく識別。定義を繰り返すだけでなく「なぜ」を説明。具体的なワークフローの利点（並列性、一貫性、反復可能性）を挙げる。

<!-- answer -->
シナリオAは単一の会話に適合します。1つの関数のバグ修正は範囲が小さく、50行は1つのコンテキストウィンドウに完全に読み込まれ、エージェントは分解する必要なく、直接読み、理解し、修正し、検証できます。シナリオBはワークフローに適合します。30個のコンポーネントは1つの会話が効率的に管理できる範囲を超え、コンポーネントは通常独立しているため、並列にアップグレードでき（コンポーネントごとに1エージェント）、その後統合テストを実行して検証できます。ワークフローはすべてのコンポーネントが同じアップグレードルールを使用することを保証し、見落としを防ぎます。

<!-- hint -->
自問してください: 人がこれら2つのタスクを実行する場合、シナリオAは10分で座って完了する種類のものか、それとも数日、チェックリスト、段階的ステップを要する大きな仕事か？

<!-- hint -->
シナリオBのキーワードは「30個のコンポーネント」です。数が10を超えたら、ワークフローを検討してください。タスクが「N個のオブジェクトに同じ操作を実行」と説明できる場合、ワークフローはほぼ常により良い選択です。
