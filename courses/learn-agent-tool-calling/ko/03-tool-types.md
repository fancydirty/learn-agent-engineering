# 레슨 3: 흔한 도구 다섯 유형: 읽기, 쓰기, 실행, 검색, 호출

> 학습 목표:
> - 흔한 도구를 피해 규모에 따라 다섯 유형으로 나누고, 각각의 전형적인 시그니처 짚어 내기
> - 명령 실행 도구가 왜 나머지 넷과 다른 위험 등급에 놓이는지 설명하기
> - 검색 도구가 왜 파일 전체가 아니라 일치하는 스니펫을 반환하는지 설명하기

## 표에서 시작한다

| 도구 | 전형적인 입력 | 반환하는 것 | 잘못됐을 때 최악의 경우 |
|---|---|---|---|
| 파일 읽기 | `path` | 파일 내용(문자열) | 읽으면 안 되는 파일을 읽어 정보가 새어 나간다 |
| 파일 쓰기 | `path`, `content` | 성공/실패 상태 | 아직 저장하지 않은 작업물을 덮어쓴다 |
| 명령 실행 | `command` | stdout/stderr/종료 코드 | 데이터베이스를 날리고, 요청을 보내고, 오염된 패키지를 설치한다 — 되돌릴 수 없다 |
| 검색 | `query`, `path` | 일치 위치 목록 + 스니펫 | 너무 많이 반환해 컨텍스트를 날려 버리거나, 핵심 결과를 놓친다 |
| 외부 API 호출 | 구조화된 파라미터(서비스마다 다름) | JSON/에러 객체 | 남의 돈을 쓰고, 엉뚱한 메시지를 보내고, 낡은 데이터를 가져온다 |

이 표를 정렬하는 기준은 무엇일까요? 알파벳 순서가 아닙니다. '호출 한 번이 얼마나 넓은 범위의 피해를 일으킬 수 있는가', 즉 그 호출의 **영향 반경(blast radius)**입니다. 읽기 전용 도구의 영향 반경은 사실상 0입니다. 엉뚱한 파일을 읽어도 이번 대화 한 턴이 어긋날 뿐입니다. 파일 쓰기는 기존 내용을 덮어쓸 수 있습니다. 명령 실행은 시스템 전체에 무슨 짓이든 할 수 있습니다. 유형을 하나씩 짚어 가다 보면, '무엇을 할 수 있는가'를 넘어 각 유형만 걸려 넘어지는 함정이 하나씩 있다는 것을 보게 됩니다.

## 읽기: 가장 안전하지만 위험이 0은 아니다

파일 읽기 도구의 시그니처는 대개 이렇게 생겼습니다.

```json
{
  "name": "read_file",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": { "type": "string", "description": "파일의 절대 경로" },
      "offset": { "type": "integer", "description": "읽기를 시작할 줄 번호(선택)" },
      "limit": { "type": "integer", "description": "읽을 최대 줄 수(선택)" }
    },
    "required": ["path"]
  }
}
```

반환값은 파일 내용 그 자체이고, 나중에 모델이 참조할 수 있도록 대개 줄 번호가 붙습니다.

```
1  export function add(a, b) {
2    return a + b;
3  }
```

파일을 읽는 것은 어떤 상태도 바꾸지 않습니다. 모델이 엉뚱한 것을 읽거나 너무 많이 읽어도, 최악의 결과는 이번 한 턴에 관련 없는 내용이 섞이는 정도입니다. 게다가 모델은 잘못 읽었다는 것을 알아채고 다시 읽는 편입니다. '가장 안전한' 유형이라 부르는 이유가 그것입니다. 위험이 없다는 뜻이 아니라, 위험이 이 대화의 경계를 벗어나지 못한다는 뜻입니다.

진짜 위험은 **애초에 건드려서는 안 되는 파일을 읽는 것**입니다. 에이전트에게 `~/.ssh/id_rsa`나 프로젝트의 `.env`를 읽을 권한이 있다면, "이 디렉터리에 뭐가 있는지 보여 줘" 같은 순진해 보이는 요청 하나가 비밀 키를 글자 그대로 대화 컨텍스트로 끌어올릴 수 있습니다. 그 시점부터, 그 컨텍스트가 모델에 의해 출력되거나, 로그에 기록되거나, 이후의 '외부 API 호출' 도구에 실려 나가는 순간 유출은 이미 벌어진 것입니다. 파일 읽기 도구가 '읽기 전용이니 그냥 열쇠를 다 넘겨도 된다'가 아니라 거의 언제나 경로 허용 목록이나 샌드박스와 함께 다니는 이유입니다. 그런 경계를 어떻게 세우는지는 레슨 5에서 자세히 다룹니다.

## 쓰기: 결과가 더 이상 대칭이 아닌 지점

파일 쓰기 도구는 읽기보다 파라미터가 하나 많고, 안전장치는 하나 적습니다.

```json
{
  "name": "write_file",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": { "type": "string" },
      "content": { "type": "string" }
    },
    "required": ["path", "content"]
  }
}
```

반환값은 대개 단순한 상태값뿐입니다.

```json
{ "success": true, "bytesWritten": 842 }
```

문제는 반환값이 아니라 호출 그 자체입니다. 읽기가 잘못되면 다시 읽으면 되고 달라진 것은 없습니다. 쓰기가 잘못되면 — 예를 들어 모델이 `path`를 잘못 채웠거나 `content`에 있어야 할 내용의 절반이 빠졌다면 — 원본 파일의 내용은 이미 덮어써졌고, 버전 관리나 백업이 없는 한 되돌릴 수 없습니다. 이것이 '읽기 도구와 쓰기 도구의 비대칭'입니다. 두 호출의 생김새는 거의 같지만(`path`에 파라미터 몇 개), 한쪽은 마음껏 재시도할 수 있고 다른 쪽은 호출할 때마다 도박을 겁니다.

그래서 책임 있는 쓰기 도구는 보호 장치를 한 겹 덧댑니다. 예를 들어 편집하기 전에 그 파일을 먼저 읽었을 것을 요구하거나(모델이 기억에 의존해 편집하는 것을 막기 위해), 맨숭맨숭한 '성공' 대신 이전 내용과 새 내용의 diff를 반환해 호출자(호스트 애플리케이션)가 실제로 디스크에 반영되기 전에 변경을 보여 줄 기회를 갖게 합니다. 여기서 다룰 초점은 아닙니다. 레슨 4에서 인터페이스 설계를 다루며 펼쳐 보겠습니다.

## 실행: 그 자체로 하나의 위험 등급

명령 실행 도구는 다섯 중 시그니처가 가장 밋밋해 보입니다.

```json
{
  "name": "bash",
  "input_schema": {
    "type": "object",
    "properties": {
      "command": { "type": "string", "description": "실행할 셸 명령" }
    },
    "required": ["command"]
  }
}
```

문자열 하나가 들어가고, stdout과 stderr, 종료 코드가 나옵니다.

```json
{
  "stdout": "3 files changed, 12 insertions(+)\n",
  "stderr": "",
  "exit_code": 0
}
```

함정은 이 `command` 필드가 본질적으로 열려 있는 입구라는 데 있습니다. '이 파일을 지운다'거나 '이 줄을 읽는다' 같은, 스키마로 경계가 그어진 특정 동작이 아니라 임의의 셸 스크립트입니다. `rm -rf`, 데이터를 외부 서버로 실어 보내는 `curl`, 오염된 패키지를 끌어오는 `npm install` — 전부 그 문자열 하나 안에 들어갑니다. 나머지 네 유형(읽기, 쓰기, 검색, API 호출)은 시그니처를 어떻게 설계하든 파라미터 구조가 할 수 있는 일을 제한합니다. 명령 실행 도구의 능력 경계는 운영체제 전체의 능력 경계입니다. 그래서 별도 등급인 것입니다. '조금 더 위험하다'가 아니라, 위험의 자릿수가 다릅니다.

바로 그 때문에 공식 문서는 이 유형만을 위해 운영체제 수준의 격리를 설계합니다. 파일 시스템 접근과 네트워크 접근은 별개의 두 샌드박스 계층이고, 모델이 프롬프트 인젝션에 조종당해 위험한 명령을 기어이 실행하려 들더라도 OS 경계는 그와 무관하게 버팁니다. 모델이 협조할 '의사'가 있는지에 기대지 않습니다[^S16]. 밝혀 둔 동기는 직설적입니다. 프롬프트 인젝션이 성공하더라도 그 영향이 온전히 갇혀 샌드박스를 벗어나지 못하게 하는 것이 목표입니다[^S17]. 그 격리를 어떻게 설정하는지는 레슨 5에서 다룹니다. 지금은 하나만 붙잡아 두세요. ## 검색: 세상 전부가 아니라 위치를 돌려준다

검색 도구(예를 들어 코드베이스 전체에서 키워드나 정규식을 찾는 도구)는 시그니처에 '얼마나 돌려줄지 제한하는' 파라미터를 함께 두는 경우가 많습니다.

```json
{
  "name": "search_code",
  "input_schema": {
    "type": "object",
    "properties": {
      "pattern": { "type": "string" },
      "path": { "type": "string", "description": "검색을 특정 디렉터리로 한정(선택)" },
      "max_results": { "type": "integer", "default": 20 }
    },
    "required": ["pattern"]
  }
}
```

반환값은 파일 자체가 아니라 '일치가 어디에 있고 그 주변이 어떻게 생겼는지'입니다.

```json
{
  "matches": [
    { "file": "src/auth/login.ts", "line": 42, "snippet": "  if (!user.verified) {" },
    { "file": "src/auth/session.ts", "line": 17, "snippet": "export function verifyToken(token) {" }
  ],
  "total_matches": 2
}
```

이 도구가 일치한 파일의 전체 내용을 그대로 밀어 넣는다면 문제가 둘 생깁니다. 첫째는 토큰 문제입니다. 검색 한 번에 50개 파일이 걸리고 각각 수백 줄이라면, 그것이 전부 컨텍스트에 쏟아지고, 이 도구 호출 하나가 이번 턴의 입력 예산을 통째로 먹어 치워 모델이 이어서 일할 여지가 남지 않습니다[^S9]. 도구 description을 잘 쓰고 입력과 출력의 경계를 통제하는 것 자체가 도구를 쓸 만하게 만드는 기본 요건이기도 합니다[^S8]. 둘째 문제가 더 중요합니다. 검색의 요점은 '관련 있을 만한 것을 전부 읽어 두기'가 아니라 '모델이 다음에 어디를 봐야 할지 알아내도록 돕기'입니다. 일치 위치와 짧은 문맥 스니펫을 돌려주면, 모델이 그 스니펫을 읽고 스스로 판단합니다. "이 결과 중 두 번째가 내가 찾던 것 같으니, 그 파일의 전체 내용을 따로 읽어 보자." 검색 도구와 읽기 도구가 함께 일하는 방식이 이것입니다. 검색이 범위를 좁히고, 읽기가 세부를 가져옵니다. '파일 전체'가 아니라 '일치 위치'를 반환하는 것이야말로, 쓸모 있을지 모를 것을 한 번에 쏟아붓는 대신 모델이 필요로 하는 다음 단서를 주는 일입니다.

## 외부 API 호출: 실패는 예외가 아니라 일상이다

앞의 네 유형은 대체로 로컬 시스템 안에 머뭅니다. 외부 API 호출은 다릅니다. 네트워크를 건너, 여러분이 통제하지 못하는 서비스로 갑니다.

```json
{
  "name": "send_slack_message",
  "input_schema": {
    "type": "object",
    "properties": {
      "channel": { "type": "string" },
      "text": { "type": "string" }
    },
    "required": ["channel", "text"]
  }
}
```

정상 반환은 이렇게 생겼습니다.

```json
{ "ok": true, "ts": "1735689600.000200" }
```

하지만 외부 서비스는 요청량을 제한하고, 타임아웃을 내고, 권한이 없다며 요청을 거절하고, 여러분이 호출하는 사이에 인터페이스를 바꾸기도 합니다. 이런 것들은 '예상치 못한 상황'이 아니라 이 유형의 정상 운영 조건입니다. 이 도구가 쓸 만한지를 실제로 가르는 것은 '잘 돌아갈 때 무엇을 반환하는가'가 아니라 '실패할 때 무엇을 반환하는가'입니다.

```json
{ "ok": false, "error": "rate_limited", "retry_after": 30 }
```

이 에러 메시지는 여러분을 위한 것이 아니라 모델을 위한 것입니다. 다음에 재시도할지 전략을 바꿀지는 모델이 그 `error` 필드를 읽을 수 있느냐에 달려 있습니다. MCP 명세는 이것을 프로토콜에 그대로 적어 두었습니다. 클라이언트는 도구 실행 에러를 언어 모델에 제공해, 모델이 스스로 바로잡고 다시 시도할 기회를 갖게 해야 한다는 것입니다[^S11]. 다시 말해, 429를 조용히 삼키고 '호출 실패'만 돌려주는 도구는 모델에게서 스스로 고칠 기회를 빼앗는 것이고, `retry_after` 같은 구체적인 정보를 실어 돌려주는 도구가 '실패'를 정상적인 작업 흐름의 일부로 설계한 것입니다.

외부 API 호출 유형은 위험을 한 겹 더 끌고 옵니다. 이 에이전트가 비공개 데이터를 읽을 수 있으면서 동시에 신뢰할 수 없는 콘텐츠(예: 사용자가 붙여 넣은 웹 텍스트 덩어리)에 노출되어 있고, 게다가 바깥으로 메시지나 요청을 보낼 수도 있다면, 이 셋이 합쳐진 것이 보안 연구에서 "lethal trifecta"(치명적 3요소)라고 부르는 것입니다. 공격자는 여러분의 시스템에 침입할 필요가 없습니다. 에이전트가 읽을 콘텐츠에 지시를 숨겨 두고, 에이전트가 스스로 비공개 데이터를 실어 내게 하면 됩니다[^S19]. 이 주제는 레슨 5에서 따로 펼칩니다. 지금은 이것만 알아 두세요. 외부 API 호출은 그 사슬의 마지막이자 가장 결정적인 고리입니다. 데이터가 실제로 여러분의 시스템을 빠져나가는 출구이기 때문입니다.

## 💻 연습

### 레벨 1: 도구의 반환값 고르기

아래는 도구 호출 결과의 초안 셋이고, 각각 문제가 있습니다. 그 문제가 어느 유형의 도구에 속하는지(읽기/쓰기/실행/검색/API 호출) 밝히고, 그 설계가 왜 어울리지 않는지 설명한 뒤, 어떻게 고칠지 제시해 보세요.

1. `search_code`가 반환: `{ "content": "<파일 50개의 전체 소스를 이어 붙인 것, 총 8000줄>" }`
2. `write_file`이 반환: `{ "success": true }` (diff도, 이전 내용 정보도 없음)
3. `send_email`이 실패 시 반환: `{ "error": "failed" }`

<!-- rubric -->
- 세 문제 모두 이 레슨에서 다룬 함정에 대응된다(검색이 토큰을 아끼지 않음, 쓰기 도구가 변경을 검토할 방법을 주지 않음, API 호출 실패가 행동 가능한 정보를 주지 않음)
- 고치는 방법이 두루뭉술한 '더 낫게 하자'가 아니라 필드 수준까지 구체적이다
- '이것이 더 올바르다'가 아니라 '모델이 왜 이 정보를 필요로 하는가'를 말할 수 있다

<!-- answer -->
1. 검색 도구의 문제입니다. 일치한 파일의 전체 내용을 한 번에 밀어 넣으면 '범위 좁히기'와 '세부 읽기'가 한 단계로 합쳐지고, 8000줄은 이번 턴의 컨텍스트를 날려 버립니다. `{ "matches": [{ "file": "...", "line": 42, "snippet": "..." }] }`처럼 일치 위치와 짧은 스니펫만 반환하고, 전체 내용이 필요할 때 모델이 스스로 `read_file`을 다시 호출하게 해야 합니다.
2. 쓰기 도구의 문제입니다. 불리언 하나만 돌려주면 호출자는 이번 덮어쓰기가 무엇을 얼마나 바꿨는지, 이전에는 어떤 모습이었는지 알 길이 없고, 문제가 생겨도 대조하거나 되돌릴 근거가 없습니다. 이전 내용과 새 내용의 diff를, 적어도 변경 전 바이트 수나 해시를 실어 비교할 수 있게 해야 합니다.
3. 외부 API 호출의 문제입니다. `"failed"`는 다음에 무엇을 할지 — 재시도할지, 수신자를 바꿀지, 사용자에게 보고할지 — 모델에게 아무것도 알려 주지 않습니다. `{ "ok": false, "error": "invalid_recipient", "detail": "주소 형식이 잘못됨" }`처럼, 모델이 다음 수를 판단할 수 있는 구체적인 에러 유형이어야 합니다.

<!-- hint -->
이 레슨의 표로 돌아가 보세요. 각 유형의 '잘못됐을 때 최악의 경우' 열이 바로 그 유형의 가장 전형적인 함정입니다. 문제를 먼저 유형에 대응시킨 다음 고칠 방법을 생각하세요.

<!-- hint -->
이 반환값을 받은 모델이라고 상상해 보세요. 배경 지식 없이 이 JSON만 있습니다. 다음에 무엇을 할지 정할 수 있습니까? 정할 수 없다면 그 반환값에는 핵심 정보가 빠져 있는 것입니다.

### 레벨 2: 새 시나리오의 도구 유형 고르고 시그니처 설계하기

에이전트에 도구를 붙여야 합니다. 이 에이전트는 서드파티 물류 API의 배송 상태를 주기적으로 확인하고, 상태가 '이상'으로 바뀌면 운송장 번호와 사유를 로컬 `alerts.log` 파일에 기록합니다.

이 작업에는 사실 도구 유형이 하나 이상 관여합니다. 다음을 작성해 보세요.

1. 이 레슨의 다섯 유형 중 어느 것이 필요합니까? 각각 무엇을 맡습니까?
2. '외부 API를 호출해 배송 상태를 조회하는' 도구의 JSON `input_schema`를 작성하되, 운송장 번호 파라미터는 최소한 포함하세요(인터페이스 설계의 체계적인 이야기는 다음 레슨입니다. 여기서는 이 레슨에 나온 시그니처 형식을 흉내 내면 됩니다)
3. 이 도구의 조회가 실패할 때(운송장 번호가 없음, 요청 타임아웃) 반환값은 어떤 모습이어야 합니까?

<!-- rubric -->
- 최소 두 유형을 올바르게 짚는다(상태 조회를 위한 외부 API 호출 + 이상을 기록하기 위한 파일 쓰기. 어떻게 구성하느냐에 따라 파일 읽기도 포함될 수 있다)
- input_schema가 `type: object`, `properties`, `required` 기본 필드를 담고 있고, 파라미터 이름이 합리적이다
- 실패 반환이 '운송장 번호가 없음'과 '요청 타임아웃'을 뭉뚱그린 하나의 `error`가 아니라 서로 다른 두 종류의 실패로 구분한다

<!-- answer -->
1. 최소 두 유형입니다. 외부 API 호출(물류 상태 조회)은 최신 상태를 가져오는 일을 맡고, 파일 쓰기(alerts.log에 기록)는 상태가 이상일 때 디스크에 쓰는 일을 맡습니다. 중복 제거까지 하고 싶다면(같은 이상을 두 번 기록하지 않기), 이 운송장 번호에 대한 기록이 alerts.log에 이미 있는지 먼저 확인하기 위해 파일 읽기도 필요할 수 있습니다.
2. 참고 시그니처:

```json
{
  "name": "check_shipment_status",
  "input_schema": {
    "type": "object",
    "properties": {
      "tracking_number": { "type": "string", "description": "운송장 번호" }
    },
    "required": ["tracking_number"]
  }
}
```

3. 참고 실패 반환: `{ "ok": false, "error": "not_found", "detail": "운송장 번호가 존재하지 않음" }`과 `{ "ok": false, "error": "timeout", "retry_after": 10 }`은 서로 다른 `error` 값이어야 합니다. 모델은 `not_found`를 보면 재시도를 멈추고 사용자에게 보고해야 하고, `timeout`을 봤을 때만 `retry_after`가 알려 주는 시간 뒤에 재시도해야 합니다.

<!-- hint -->
먼저 작업을 '상태 조회'와 '이상 기록'이라는 두 동작으로 쪼갠 다음, 각각을 이 레슨의 표에 대조해 어느 유형에 속하는지 정하세요.

<!-- hint -->
'운송장 번호가 존재하지 않음'과 '요청 타임아웃'은 모델에게 완전히 다른 신호입니다. 하나는 재시도를 포기하라는 뜻이고, 다른 하나는 나중에 다시 시도하라는 뜻입니다. 반환값이 둘을 같은 `error` 필드의 같은 값으로 뭉뚱그리면 모델은 어느 쪽으로 움직여야 할지 알 수 없습니다.

## 정리

- 다섯 유형의 위험은 고르게 퍼져 있지 않다. 파일 읽기의 결과가 가장 가볍고, 파일 쓰기부터 되돌릴 수 없어지기 시작하며, 명령 실행의 영향 반경은 운영체제 전체와 같고, 검색과 외부 API 호출은 각자 별개의 함정을 지닌다
- 읽기 도구와 쓰기 도구의 핵심 차이는 **안전하게 재시도할 수 있는가**다. 잘못 읽으면 다시 읽으면 되지만, 잘못 쓰면 원본 내용이 영영 사라질 수 있다
- 명령 실행 도구가 OS 수준 샌드박스라는 방벽을 필요로 하는 것은, 그 `command` 파라미터가 나머지 넷처럼 스키마 구조로 묶이지 않은 열린 문자열이기 때문이다[^S16][^S17]
- 검색 도구가 파일 전체가 아니라 일치 위치와 스니펫을 반환하는 것은, 첫째로 토큰을 아끼기 위해서이고, 둘째로 '위치 찾기'와 '세부 읽기'를 갈라 모델이 이어 갈 단서를 건네기 위해서다[^S9]
- 외부 API 호출 도구는 실패 정보(에러 유형, 재시도 가능 여부)를 삼키지 말고 모델에게 그대로 실어 보내야 한다. 이 유형에서 실패는 예외가 아니라 일상이다[^S11]

다음 레슨에서는 이 다섯 유형의 '시그니처'를 뜯어봅니다. 모델이 한 번에 제대로 호출하도록 좋은 도구 이름, description, 파라미터 스키마, 반환값을 어떻게 쓸 것인가입니다.
