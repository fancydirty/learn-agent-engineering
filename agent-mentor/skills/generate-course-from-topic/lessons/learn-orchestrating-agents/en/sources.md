## S1 — Anthropic: How we built our multi-agent research system
URL: https://www.anthropic.com/engineering/multi-agent-research-system
- authority: official-docs
- supports: The orchestrator-worker architecture that Lessons 2 and 3 teach; the measured token multiple and eval gain in Lesson 1; the documented delegation failures (duplicated work, vague instructions, 50 subagents for a simple query) in Lesson 2; the subagent return-channel shape and the filesystem escape hatch in Lesson 3; the synchronous fan-out bottleneck and the compounding-error argument in Lesson 4.
- key-fact: On the architecture: "Our Research system uses a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." On why it works: "The essence of search is compression: distilling insights from a vast corpus. Subagents facilitate compression by operating in parallel with their own context windows, exploring different aspects of the question simultaneously before condensing the most important tokens for the lead research agent." On the measured gain: "We found that a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval." On what explains it: "three factors explained 95% of the performance variance in the BrowseComp evaluation... We found that token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors." On the cost: "in practice, these architectures burn through tokens fast. In our data, agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats. For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance." On the boundary: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today. For instance, most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time. We've found that multi-agent systems excel at valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools." On delegation: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." On the observed duplication: "one subagent explored the 2021 automotive chip crisis while 2 others duplicated work investigating current 2025 supply chains, without an effective division of labor." On early coordination failures: "Early agents made errors like spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates." On sizing: "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities." On parallelism: "the lead agent spins up 3-5 subagents in parallel rather than serially; (2) the subagents use 3+ tools in parallel. These changes cut research time by up to 90% for complex queries." On errors: "In agentic systems, minor changes cascade into large behavioral changes... Without effective mitigations, minor system failures can be catastrophic for agents. When errors occur, we can't just restart from the beginning: restarts are expensive and frustrating for users. Instead, we built systems that can resume from where the agent was when the errors occurred." On the blocking shape: "Currently, our lead agents execute subagents synchronously, waiting for each set of subagents to complete before proceeding. This simplifies coordination, but creates bottlenecks in the information flow between agents. For instance, the lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent to finish searching." On the filesystem pattern: "Subagent output to a filesystem to minimize the 'game of telephone.' Direct subagent outputs can bypass the main coordinator for certain types of results, improving both fidelity and performance... Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator. This prevents information loss during multi-stage processing." Published 2025-06-13; the numbers are from Anthropic's own internal evals on a research product, not an independent benchmark.

## S2 — Anthropic: Building effective agents
URL: https://www.anthropic.com/engineering/building-effective-agents
- authority: official-docs
- supports: Lesson 1's default position that the simplest structure wins until something forces complexity, and Lesson 2's distinction between a pre-planned parallel split and an orchestrator that decides the split at run time.
- key-fact: The core recommendation: "When building applications with LLMs, we recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all. Agentic systems often trade latency and cost for better task performance, and you should consider when this tradeoff makes sense." On the two shapes: parallelization is "Breaking a task into independent subtasks run in parallel," and it "is effective when the divided subtasks can be parallelized for speed, or when multiple perspectives or attempts are needed for higher confidence results." The orchestrator variant: "In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results. This workflow is well-suited for complex tasks where you can't predict the subtasks needed... Whereas it's topographically similar, the key difference from parallelization is its flexibility—subtasks aren't pre-defined, but determined by the orchestrator based on the specific input." Published 2024-12-19. This is the oldest source in the course and is cited only for durable design positions, never for what any current system does.

## S3 — Cognition: Don't Build Multi-Agents
URL: https://cognition.com/blog/dont-build-multi-agents
- authority: blog
- supports: Lesson 1's counterargument against decomposition by default, and Lesson 5's mechanism for why a synthesiser inherits conflicts it cannot see.
- key-fact: The two principles: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results." On the tempting architecture: an agent that "breaks its work down into multiple parts, starts subagents to work on those parts, combines those results in the end... This is a tempting architecture, especially if you work in a domain of tasks with several parallel components to it. However, it is very fragile." The worked failure: a "build a Flappy Bird clone" task split into a background subtask and a bird subtask, where "subagent 1 actually mistook your subtask and started building a background that looks like Super Mario Bros... Now the final agent is left with the undesirable task of combining these two miscommunications." On why copying the task down does not fix it: "in a real production system, the conversation is most likely multi-turn, the agent probably had to make some tool calls to decide how to break down the task, and any number of details could have consequences on the interpretation of the task." On the second failure even with shared context: "you might end up with a bird and background with completely different visual styles. Subagent 1 and subagent 2 cannot not see what the other was doing and so their work ends up being inconsistent with each other. The actions subagent 1 took and the actions subagent 2 took were based on conflicting assumptions not prescribed upfront." The recommendation: "The simplest way to follow the principles is to just use a single-threaded linear agent." On compression: introducing a model "whose key purpose is to compress a history of actions & conversation into key details, events, and decisions. This is hard to get right... Depending on the domain, you might even consider fine-tuning a smaller model (this is in fact something we've done at Cognition)." Written by Walden Yan, published 2025-06-12. This is a vendor engineering blog arguing a position, not a measurement; the course cites it for its stated mechanism and says so in the lesson.

## S4 — Why Do Multi-Agent LLM Systems Fail? (MAST)
URL: https://arxiv.org/abs/2503.13657
- authority: authoritative-guide
- supports: Lesson 1's claim that multi-agent gains are frequently small and failures are structural rather than model-limited; the named failure modes in Lessons 2 and 4; Lesson 5's claim that adding a verification step is one of the interventions with a measured effect.
- key-fact: The framing: "Despite enthusiasm for Multi-Agent LLM Systems (MAS), their performance gains on popular benchmarks are often minimal." The dataset and method: "We introduce MAST-Data, a comprehensive dataset of 1600+ annotated traces collected across 7 popular MAS frameworks... We develop MAST through rigorous analysis of 150 traces, guided closely by expert human annotators and validated by high inter-annotator agreement (kappa = 0.88). This process identifies 14 unique modes, clustered into 3 categories: (i) system design issues, (ii) inter-agent misalignment, and (iii) task verification." The prevalence figures, stated as "the prevalence of each failure mode and category as observed in our analysis of 1642 MAS execution traces": step repetition (FM-1.3) 15.7%, mismatch between reasoning and action (FM-2.6) 13.2%, not recognizing task completion (FM-1.5) 12.4%, disobeying task specification (FM-1.1) 11.8%, incorrect verification (FM-3.3) 9.1%, no or incomplete verification (FM-3.2) 8.2%, task derailment (FM-2.3) 7.4%, proceeding on wrong assumptions instead of asking (FM-2.2) 6.8%, premature termination (FM-3.1) 6.2%, context loss (FM-1.4) 2.8%, conversation reset (FM-2.1) 2.2%, ignoring other agents' input (FM-2.5) 1.9%, disobeying role specification (FM-1.2) 1.5%, information withholding (FM-2.4) 0.85%. On verification quality: "many existing verifiers perform only superficial checks, despite being prompted to perform thorough verification, such as checking if the code compiles or if there are leftover TODO comments." The intervention: "adding a high-level task objective verification step to ChatDev yields a +15.6% improvement in task success on ProgramDev." A second intervention: "a straightforward system workflow adjustment ensuring the CEO had the final say contributed to a +9.4% increase in overall task success rate." The stated limits: "Although first step interventions lead to performance gains, not all failure modes are resolved, and task completion rates still remain low." The systems studied are open-source research frameworks (MetaGPT, ChatDev, HyperAgent, OpenManus, AppWorld, Magentic, AG2) on GPT-4-era and Claude-3-era models, so the percentages describe that population and not any current commercial product. Cemri, Pan, Yang, Agrawal, Chopra, Tiwari, Keutzer, Parameswaran, Klein, Ramchandran, Zaharia, Gonzalez, Stoica. Submitted 2025-03-17, last revised 2025-10-26; published in the NeurIPS 2025 Datasets and Benchmarks track.

## S5 — Anthropic: Building a C compiler with a team of parallel Claudes
URL: https://www.anthropic.com/engineering/building-c-compiler
- authority: official-docs
- supports: Lesson 4's central claim that parallelism is bounded by whether the work actually splits, with a first-party account of sixteen agents colliding on one indivisible task and the fix that made the work divisible; Lesson 2's evidence for role specialisation; Lesson 5's warning about trusting a green test suite as proof of completion.
- key-fact: The setup: "I tasked 16 agents with writing a Rust-based C compiler, from scratch, capable of compiling the Linux kernel. Over nearly 2,000 Claude Code sessions and \$20,000 in API costs, the agent team produced a 100,000-line compiler that can build Linux 6.9 on x86, ARM, and RISC-V." The coordination mechanism: "Claude takes a 'lock' on a task by writing a text file to current_tasks/... If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one." Notably absent: "I haven't yet implemented any other method for communication between agents, nor do I enforce any process for managing high-level goals. I don't use an orchestration agent." The collision: "When there are many distinct failing tests, parallelization is trivial: each agent picks a different failing test to work on... But when agents started to compile the Linux kernel, they got stuck. Unlike a test suite with hundreds of independent tests, compiling the Linux kernel is one giant task. Every agent would hit the same bug, fix that bug, and then overwrite each other's changes. Having 16 agents running didn't help because each was stuck solving the same task." The repair: using GCC "as an online known-good compiler oracle to compare against. I wrote a new test harness that randomly compiled most of the kernel using GCC, and only the remaining files with Claude's C Compiler... This let each agent work in parallel, fixing different bugs in different files." On verifiers: "it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." On specialisation: "I tasked one agent with coalescing any duplicate code it found. I put another in charge of improving the performance of the compiler itself, and a third I made responsible for outputting efficient compiled code." On the risk: "For autonomous systems, it is easy to see tests pass and assume the job is done, when this is rarely the case." Written by Nicholas Carlini; published 2026-02-05. This is one researcher's prototype on one project, reported as engineering observation rather than a controlled comparison.

## S6 — Anthropic: Harness design for long-running application development
URL: https://www.anthropic.com/engineering/harness-design-long-running-apps
- authority: official-docs
- supports: Lesson 5's core mechanism — that separating the agent doing the work from the agent judging it is what makes a synthesis checkable, and that the separation alone is not enough; Lesson 1's rule that a component earns its place only while the task sits beyond what one agent does reliably.
- key-fact: On self-evaluation: "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre. This problem is particularly pronounced for subjective tasks like design, where there is no binary check equivalent to a verifiable software test." On the repair and its limits: "Separating the agent doing the work from the agent judging it proves to be a strong lever to address this issue. The separation doesn't immediately eliminate that leniency on its own; the evaluator is still an LLM that is inclined to be generous towards LLM-generated outputs. But tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work, and once that external feedback exists, the generator has something concrete to iterate against." On tuning it: "Out of the box, Claude is a poor QA agent. In early runs, I watched it identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway. It also tended to test superficially." On the contract: "Before each sprint, the generator and evaluator negotiated a sprint contract: agreeing on what 'done' looked like for that chunk of work before any code was written." On communication: "Communication was handled via files: one agent would write a file, another agent would read it and respond either within that file or with a new file that the previous agent would read in turn." On cost: a solo run took 20 minutes and \$9, the full harness 6 hours and \$200 — "The harness was over 20x more expensive, but the difference in output quality was immediately apparent," with the solo run's central feature broken. On when the extra agent is worth it: "the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." On maintenance: "every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing, both because they may be incorrect, and because they can quickly go stale as models improve." Written by Prithvi Rajasekaran; published 2026-03-24. These are single runs on one prompt each, not repeated trials.

## S7 — Claude Code documentation: Create custom subagents
URL: https://code.claude.com/docs/en/sub-agents
- authority: official-docs
- supports: Lesson 3's mechanism for what crosses the worker boundary in each direction and why only a summary returns; Lesson 2's statement that a worker's inheritance is a delegation message; Lesson 4's note on the latency a cold worker adds.
- key-fact: "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions." On the inbound side: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there." On the outbound side: "the subagent does that work in its own context and returns only the summary." On the strongest use: "One of the most effective uses for subagents is isolating operations that produce large amounts of output. Running tests, fetching documentation, or processing log files can consume significant context." On parallel dispatch, the documented example prompt is "Research the authentication, database, and API modules in parallel using separate subagents," and the page notes that "For tasks that need sustained parallelism or exceed your context window, agent teams give each worker its own independent context." On the cost of a cold start: "Latency matters. A subagent that isn't a fork starts fresh and may need time to gather context." On nesting: "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation. At the depth limit, Claude Code withholds the `Agent` tool from every subagent except a fork... Only the top-level subagent's summary returns to you." Retrieved 2026-08-23; this page is versioned rather than dated, and every mechanism on it is one vendor's product surface.

## S8 — Claude Code documentation: Orchestrate teams of Claude Code sessions
URL: https://code.claude.com/docs/en/agent-teams
- authority: official-docs
- supports: Lesson 2's distinction between workers that report to a lead and peers that talk to each other; Lesson 4's evidence that coordination overhead and dependency structure decide which shape fits, and that real orchestration systems ship with unresolved coordination limitations.
- key-fact: "Agent teams let you coordinate multiple Claude Code instances working together. One session acts as the team lead, coordinating work, assigning tasks, and synthesizing results. Teammates work independently, each in its own context window, and communicate directly with each other." On fit: "Agent teams are most effective for tasks where parallel exploration adds real value," with the strongest cases listed as research and review, new modules or features where "teammates can each own a separate piece without stepping on each other," debugging competing hypotheses, and cross-layer changes. On the cost: "Agent teams add coordination overhead and use significantly more tokens than a single session. They work best when teammates can operate independently. For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." The comparison table records subagents as "Own context window; results return to the caller," "Main agent manages all work," best for "Focused tasks where only the result matters," with "Lower" token cost; and teams as "Own context window; fully independent," "Self-coordination through messages, plus a shared task list," best for "Complex work requiring discussion and collaboration," with "Higher: each teammate is a separate Claude instance." Documented limitations include "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks," "No nested teams," and "Lead is fixed." The page describes agent teams as of v2.1.178 and states they are "experimental and disabled by default." Retrieved 2026-08-23.

## S9 — OpenAI Codex documentation: Subagents
URL: https://learn.chatgpt.com/docs/agent-configuration/subagents
- authority: official-docs
- supports: Lesson 1's cross-vendor confirmation that parallel workers cost more tokens than one run; Lesson 4's read-heavy-first rule and the write-contention warning; Lesson 2's three-part specification for a dispatch instruction.
- key-fact: On the shape: ChatGPT Work and Codex "can run subagent workflows by spawning specialized agents in parallel and then collecting their results in one response." On cost: "Subagent workflows consume more tokens than comparable single-agent runs because each subagent does its own model and tool work." On what to delegate: "As a starting point, use parallel agents for read-heavy tasks such as exploration, tests, triage, and summarization. Be more careful with parallel write-heavy workflows, because agents editing code at once can create conflicts and increase coordination overhead." The documented example: "Review this branch with parallel subagents. Spawn one subagent for security risks, one for test gaps, and one for maintainability. Wait for all three, then summarize the findings by category with file references." On the returned shape: "Return summaries from subagents instead of raw intermediate output." Retrieved 2026-08-23 from the canonical `developers.openai.com/codex/subagents` path, which serves this URL; the page is versioned rather than dated.

## S10 — Claude API documentation: Rate limits
URL: https://platform.claude.com/docs/en/api/rate-limits
- authority: official-docs
- supports: Lesson 4's mechanism for why parallel workers contend even when their tasks are independent — the limit is organisation-wide and replenishes continuously, so concurrency, not task structure, is what exhausts it.
- key-fact: "Limits are set at the organization level." On the shape of the limit: "The API uses the token bucket algorithm to do rate limiting. This means that your capacity is continuously replenished up to your maximum limit, rather than being reset at fixed intervals." On bursts: "You might hit rate limits over shorter time intervals. For instance, a rate of 60 requests per minute (RPM) might be enforced as 1 request per second. Short bursts of requests can exceed the limit and trigger rate limit errors." On sudden concurrency: "You might also encounter 429 errors because of acceleration limits on the API if your organization has a sharp increase in usage. To avoid hitting acceleration limits, ramp up your traffic gradually and maintain consistent usage patterns." On the signal: exceeding a limit returns "a 429 error describing which rate limit was exceeded, along with a `retry-after` header indicating how long to wait." Retrieved 2026-08-23; this page describes one vendor's API and the specific tier numbers on it change, so the course cites only the mechanism.

- authority: official-docs

## S12 — Simon Willison: Embracing the parallel coding agent lifestyle
URL: https://simonwillison.net/2025/Oct/5/parallel-coding-agents/
- authority: blog
- supports: Lesson 4's claim that the binding constraint on a fan-out is usually the human reviewing its output rather than the machine producing it, and Lesson 1's observation that the tasks worth parallelising first are the ones that produce no code you must review.
- key-fact: "I was pretty skeptical about this at first. AI-generated code needs to be reviewed, which means the natural bottleneck on all of this is how fast I can review the results. It's tough keeping up with just a single LLM given how fast they can churn things out, where's the benefit from running more than one at a time if it just leaves me further behind?" And the resolution: "I can only focus on reviewing and landing one significant change at a time, but I'm finding an increasing number of tasks that can still be fired off in parallel without adding too much cognitive overhead to my primary work." The categories he names are research ("Research tasks answer questions or provide recommendations without making modifications to a project that you plan to keep"), small maintenance tasks, and "carefully specified and directed actual work," of which he notes: "Code that started from your own specification is a lot less effort to review." Published 2025-10-05. A practitioner's personal weblog reporting his own workflow, not a measurement; the course cites it for the framing of the bottleneck, which its own reasoning supports.

## S13 — From Single to Multi: How LLMs Hallucinate in Multi-Document Summarization
URL: https://arxiv.org/abs/2410.13961
- authority: authoritative-guide
- supports: Lesson 5's central claim that a synthesis pass over several sources is itself a place where content gets invented, including content about material that was never there — which is exactly the position a synthesiser reading several worker reports sits in.
- key-fact: "When evaluating 5 LLMs on our benchmarks, we observe that on average, up to 75% of the content in LLM-generated summary is hallucinated, with hallucinations more likely to occur towards the end of the summaries. Moreover, when summarizing non-existent topic-related information, gpt-3.5-turbo and GPT-4o still generate summaries about 79.35% and 44% of the time, raising concerns about their tendency to fabricate content." On the character of the errors: "Subsequent manual analysis of 700+ insights reveals that, albeit faithful to the input, a large fraction of insights is overly generic or inconsistent with the instructions." On repairs: "we investigate the efficacy of simple post-hoc baselines in mitigating hallucinations but find them only moderately effective." The 75% figure is the upper bound across models and conditions on two purpose-built news and conversation benchmarks, not a typical rate for arbitrary summarisation, and the models tested are the GPT-3.5/GPT-4o generation. Belem and five co-authors; submitted 2024-10-17, revised 2025-04-26; Findings of NAACL 2025.

## S14 — On Positional Bias of Faithfulness for Long-form Summarization
URL: https://arxiv.org/abs/2410.23609
- authority: authoritative-guide
- supports: Lesson 5's warning against fixing a synthesis problem by adding another merging layer — the measured result is that restructuring the merge hurt faithfulness rather than helping it, and that where a report sits in the pile changes how faithfully it is represented.
- key-fact: "Analyzing LLM-generated summaries across six datasets, we find a 'U-shaped' trend in faithfulness, where LLMs faithfully summarize the beginning and end of documents but neglect middle content. Perturbing document order similarly reveals models are less faithful when important documents are placed in the middle of the input." On mitigations: "we experiment with different generation techniques to reduce positional bias and find that prompting techniques effectively direct model attention to specific positions, whereas more sophisticated approaches offer limited improvements." The paper's own summary of the finding is blunter: "Performing methods that changes the input structure (i.e., hierarchical merging or incremental updating) hurts faithfulness." On why incremental updating fails: "the method maintains only a working summary cache and updates it solely based on the next document, leading to a pronounced recency bias... it ultimately replaces one positional bias, i.e., lost-in-the-middle, with another, i.e., recency bias." The experiments are on long-form document summarisation with GPT-4o-era models, so the U-shape is the durable finding to carry, not the per-dataset numbers. Wan and three co-authors; submitted 2024-10-31, revised 2025-07-06; NAACL 2025.

## S15 — Anthropic: Quantifying infrastructure noise in agentic coding evals
URL: https://www.anthropic.com/engineering/infrastructure-noise
- authority: official-docs
- supports: Lesson 4's claim that the environment an agent runs in is part of the system rather than a neutral container, and that concurrency and load conditions move outcomes by amounts large enough to be mistaken for a difference in the work itself.
- key-fact: "Infrastructure configuration can swing agentic coding benchmarks by several percentage points—sometimes more than the leaderboard gap between top models. In internal experiments, the gap between the most- and least-resourced setups on Terminal-Bench 2.0 was 6 percentage points (p < 0.01)." On why: "Agentic coding evals are different: models are given a full environment where they write programs, run tests, install dependencies, and iterate over multiple turns. The runtime is no longer a passive container, but an integral component of the problem-solving process. Two agents with different resource budgets and time limits aren't taking the same test." On the mechanism at the tight end: "When these are set to the same value, there's zero headroom for transient spikes: a momentary memory fluctuation can OOM-kill a container that would otherwise have succeeded." Infra error rates went "from 5.8% at strict enforcement to 0.5% when uncapped." And on load: "We have observed anecdotally, for instance, that pass rates fluctuate with time of day, likely because API latency varies with traffic patterns and incidents. We have not formally quantified this effect, but it illustrates a larger point: the boundary between 'model capability' and 'infrastructure behavior' is blurrier than a single benchmark score suggests." Written by Gian Segato; published 2026-02-05. The time-of-day observation is explicitly marked as anecdotal by its authors and the course repeats that qualification.
