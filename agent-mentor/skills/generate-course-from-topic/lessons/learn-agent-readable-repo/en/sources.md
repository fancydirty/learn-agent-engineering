## S1 — AGENTS.md — the format's own site and FAQ
URL: https://agents.md/
- authority: official-docs
- supports: Supports Lesson 1's definition of the format and its README boundary, Lesson 3's nearest-file precedence rule and the nested-monorepo pattern, Lesson 5's conflict-resolution answer, and the course's governance and adoption claims.
- key-fact: The site's own headline: "A simple, open format for guiding coding agents, used by over 60k open-source projects." On the boundary against a README: "README.md files are for humans: quick starts, project descriptions, and contribution guidelines. AGENTS.md complements this by containing the extra, sometimes detailed context coding agents need: build steps, tests, and conventions that might clutter a README or aren't relevant to human contributors." On what to include: "Project overview / Build and test commands / Code style guidelines / Testing instructions / Security considerations," plus "Commit messages or pull request guidelines, security gotchas, large datasets, deployment steps: anything you'd tell a new teammate belongs here too." On nesting: "Place another AGENTS.md inside each package. Agents automatically read the nearest file in the directory tree, so the closest one takes precedence and every subproject can ship tailored instructions. For example, at time of writing the main OpenAI repo has 88 AGENTS.md files." FAQ, on required fields: "No. AGENTS.md is just standard Markdown. Use any headings you like; the agent simply parses the text you provide." FAQ, on conflicts: "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything." FAQ, on commands: "Yes—if you list them. The agent will attempt to execute relevant programmatic checks and fix failures before finishing the task." On governance: "AGENTS.md is now stewarded by the Agentic AI Foundation under the Linux Foundation." Site fetched 2026-08-23; the page footer reads "Copyright © AGENTS.md a Series of LF Projects, LLC". The "60k+" adoption figure and the "88 AGENTS.md files" example are the site's own self-reported counts with no method stated, and the site itself qualifies the second with "at time of writing" — the course cites both as the format's own claims, dated, not as independently measured counts.

## S2 — AAIF: Measuring AGENTS.md — what five runs show that one doesn't
URL: https://aaif.io/blog/measuring-agents-md-what-five-runs-show-that-one-doesn-t
- authority: authoritative-guide
- supports: Supports Lesson 6's central method — that a single before/after run cannot tell you whether an instruction file changed behaviour, and that the observable win shows up in the tail rather than the average — and supplies Lesson 4's concrete-versus-aspirational contrast and Lesson 1's guidance-not-enforcement boundary.
- key-fact: The setup, in the author's words: "I ran a controlled test on a real repository: teamxray, a VS Code extension with a normal amount of repo-specific texture, npm not pnpm, a specific pretest chain, a postinstall patch script, generated files that shouldn't be touched. Two identical clones. One got a twelve-line AGENTS.md. One didn't. Same coding agent, GitHub Copilot CLI in non-interactive mode... Same prompt, same starting commit, five runs per condition." On why one run was not enough: "My first attempt to measure this, one run per condition, told me the wrong thing. On the harder task, the AGENTS.md run looked 44% slower and 41% more expensive for identical output. Clean numbers. Wrong conclusion. Agent wall-clock time and token counts are noisy enough per run that a single comparison can point the wrong direction and still look convincing." The medians: "On the ambiguous task, it cut wall time 27%, credits 24%, and produced diffs 26% smaller, because the file's single instruction to keep changes scoped removed defensive code nobody asked for. On the multi-file task, the median win was smaller, 9 to 10%, but the more useful finding was in the tail: two of five runs without AGENTS.md wasted time re-orienting in the repo or running an unrequested production build at the end. Every run with AGENTS.md skipped both." On the guardrails specifically: "None of the runs, with or without the file, touched the protected postinstall script or webpack config, so the guardrails weren't the reason for the win. The context was." On writing style: "'Follow best practices' gives an agent nothing to act on. 'Run npm run lint after any source change' and 'do not edit files in dist/' give it commands, paths, and boundaries." On enforcement: "AGENTS.md is guidance, not enforcement... It can tell an agent not to touch a file. It can't guarantee that. Real enforcement still belongs to CI, branch protection, and sandboxed execution." The author's own stated limit: "My results are one data point, gathered on one repo with one agent." Andrea Griffiths, published 2026-07-22 on the Agentic AI Foundation blog. AAIF stewards the format, so this is the steward's own evidence for its value; the course cites it for the measurement method and the size of effect on one repository, not as a general expected gain.

## S3 — OpenAI Codex: Custom instructions with AGENTS.md
URL: https://learn.chatgpt.com/docs/agent-configuration/agents-md
- authority: official-docs
- supports: Supports Lesson 3's worked mechanism for how a chain of instruction files is assembled and why "closest wins" is implemented as concatenation order rather than replacement, Lesson 2's size-cap consequence, and Lesson 6's command for asking a tool which instruction files it actually loaded.
- key-fact: On timing: "Codex reads AGENTS.md files before doing any work." On chain construction: "Codex builds an instruction chain when it starts (once per run; in the TUI this usually means once per launched session)." The discovery order: "Global scope: In your Codex home directory (defaults to ~/.codex...), Codex reads AGENTS.override.md if it exists. Otherwise, Codex reads AGENTS.md. Codex uses only the first non-empty file at this level. Project scope: Starting at the project root (typically the Git root), Codex walks down to your current working directory... In each directory along the path, it checks for AGENTS.override.md, then AGENTS.md, then any fallback names in project_doc_fallback_filenames. Codex includes at most one file per directory. Merge order: Codex concatenates files from the root down, joining them with blank lines. Files closer to your current directory override earlier guidance because they appear later in the combined prompt." On the cap: "Codex skips empty files and stops adding files once the combined size reaches the limit defined by project_doc_max_bytes (32 KiB by default)... Raise the limit or split instructions across nested directories when you hit the cap." On verification: "codex --ask-for-approval never 'Summarize the current instructions.'" with the expected result "Codex quotes the items from ~/.codex/AGENTS.md before proposing work"; and "codex --cd services/payments --ask-for-approval never 'List the instruction sources you loaded.'" with "Expected: Codex reports the global file first, the repository root AGENTS.md second, and the payments override last." Fetched 2026-08-23 as raw markdown; developers.openai.com/codex/guides/agents-md 308-redirects to this learn.chatgpt.com path, and appending .md to either returns raw markdown. Discovery order, the override filename, and the 32 KiB default are product surface and the most version-sensitive facts in this course.

## S4 — Amp owner's manual: AGENTS.md
URL: https://ampcode.com/manual
- authority: official-docs
- supports: Supports Lesson 3's claim that "nearest file wins" is a family of resolution rules rather than one rule — Amp loads parent files always and subtree files on demand — and supplies Lesson 1's evidence that a second tool reads the same filename with different mechanics, plus Lesson 3's path-scoped alternative to deeper nesting.
- key-fact: On what the file is for: "Amp looks in AGENTS.md files for guidance on codebase structure, build/test commands, and conventions." On loading: "AGENTS.md files in the current working directory (or editor workspace roots) and parent directories (up to \$HOME) are always included. Subtree AGENTS.md files are included when the agent reads a file in the subtree." On other filenames: "If no AGENTS.md exists in a directory, but a file named AGENT.md (without an S) or CLAUDE.md does exist, that file will be included." On monorepo structure: "In a large repository with multiple subprojects, we recommend keeping the top-level AGENTS.md general and creating more specific AGENTS.md files in subtrees for each subproject." On inspecting the loaded set: "To see the agent files that Amp is using, select agents-md list from the command palette." On path-scoped guidance: "To provide guidance that only applies when working with certain files, you can specify globs in YAML front matter of mentioned files"; "Mentioned files with globs will only be included if Amp has read a file matching any of the globs." On migration: "From Claude Code: mv CLAUDE.md AGENTS.md && ln -s AGENTS.md CLAUDE.md, and repeat for subtree CLAUDE.md files." Fetched 2026-08-23. Tool-specific loading rules are a dated snapshot.

## S5 — Claude Code documentation: How Claude remembers your project
URL: https://code.claude.com/docs/en/memory
- authority: official-docs
- supports: Supports Lesson 1's boundary between a repo instruction file and a Skill, Lesson 2's size guidance and the reason instruction files cost context on every session, Lesson 3's concatenation-and-order resolution model, and Lesson 5's mechanism for what a tool does when two of your own rules contradict each other.
- key-fact: On the filename: "Claude Code reads CLAUDE.md, not AGENTS.md. If your repository already uses AGENTS.md for other coding agents, create a CLAUDE.md that imports it so both tools read the same instructions without duplicating them" — via a `@AGENTS.md` import or "ln -s AGENTS.md CLAUDE.md". On the nature of the file: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead. The more specific and concise your instructions, the more consistently Claude follows them." On size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." On specificity, with its own examples: "'Use 2-space indentation' instead of 'Format code properly'"; "'Run `npm test` before committing' instead of 'Test your changes'"; "'API handlers live in `src/api/handlers/`' instead of 'Keep files organized'." On contradictions: "if two rules contradict each other, Claude may pick one arbitrarily. Review your CLAUDE.md files, nested CLAUDE.md files in subdirectories, and .claude/rules/ periodically to remove outdated or conflicting instructions." On load order: "All discovered files are concatenated into context rather than overriding each other. Across the directory tree, content is ordered from the filesystem root down to your working directory... so instructions closer to where you launched Claude are read last." On subdirectories: "Claude also discovers CLAUDE.md and CLAUDE.local.md files in subdirectories under your current working directory. Instead of loading them at launch, they are included when Claude reads files in those subdirectories." On the Skill boundary: "Keep it to facts Claude should hold in every session: build commands, conventions, project layout, 'always do X' rules. If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." On when to add: "Claude makes the same mistake a second time"; "A new teammate would need the same context to be productive." On verifying the load: "run /context in a session and check the list under Memory files." Fetched 2026-08-23 as raw markdown from the canonical docs path. Filenames, flags, and version numbers on this page are product surface and go stale fast.

## S6 — How Many Instructions Can LLMs Follow at Once? (IFScale)
URL: https://arxiv.org/abs/2507.11538
- authority: authoritative-guide
- supports: Supports Lesson 2's central claim that instruction adherence degrades as instruction count rises, and that the degradation is not uniform — it has distinct shapes and a measured bias toward instructions that appear earlier in the list.
- key-fact: "We introduce IFScale, a simple benchmark of 500 keyword-inclusion instructions for a business report writing task to measure how instruction-following performance degrades as instruction density increases. We evaluate 20 state-of-the-art models across seven major providers and find that even the best frontier models only achieve 68% accuracy at the max density of 500 instructions. Our analysis reveals model size and reasoning capability to correlate with 3 distinct performance degradation patterns, bias towards earlier instructions, and distinct categories of instruction-following errors." The three named patterns: "(1) threshold decay—near-perfect performance until a critical density, then rising variance and decreased adherence...(2) linear decay...and (3) exponential decay," with the last "showing steep performance drops after minimal instruction densities before asymptotically approaching consistent low-performance baselines" and levelling "around similar accuracy floors (7-15%)." On the primacy measurement: "We compute primacy effects as the ratio of error rates in the final third of instructions to error rates in the first third of instructions. A ratio greater than 1.0 indicates that later instructions are more likely to be violated." Design: densities from 10 to 500 in steps of 10, five random seeds per level, graded by regex keyword matching. Daniel Jaroslawicz, Brendan Whiting, Parth Shah, Karime Maamari (Distyl AI); arXiv preprint submitted 2025-07-15, not peer-reviewed. The task is single-turn keyword inclusion in a business report, not repository work, and the models evaluated are the mid-2025 generation — the course carries the shape of the finding (adherence falls with count; earlier instructions survive better) and explicitly not the percentages as an expectation for any current agent reading an AGENTS.md.

## S7 — Control Illusion: The Failure of Instruction Hierarchies in Large Language Models (AAAI-26)
URL: https://arxiv.org/abs/2502.15851
- authority: authoritative-guide
- supports: Supports Lesson 5's core claim that a declared priority ordering is not a mechanism that enforces itself, that models rarely announce a conflict they are resolving, and that a stated hierarchy competes against the model's own biases toward particular kinds of instruction.
- key-fact: "Our experiments across six state-of-the-art LLMs reveal that models struggle with consistent instruction prioritization, even for simple formatting conflicts. We find that the widely-adopted system/user prompt separation fails to establish a reliable instruction hierarchy, and models exhibit strong inherent biases toward certain constraint types regardless of their priority designation." The measured gap: "all models demonstrate strong performance (ranging from 74.8–90.8%) when following individual constraints without conflicts," but "Most models show dramatically lower performance (9.6–45.8% average R1) when handling conflicting constraints." On explicitly stating the priority: "Even for the emphasized separation configuration, where priority is explicitly stated, the obedience rate remains far from reliable priority control (GPT4o with 63.8% average R1 performs the best on simple instructions, and Claude 3.5 Sonnet with 47.5% performs the best on rich-context instructions)." On silence: "models rarely acknowledge the existence of conflicting instructions in their responses, and even when they do recognize conflicts, they frequently fail to maintain proper instruction hierarchies." On bias: "Bias magnitudes often exceed 0.5, indicating a clear default tendency toward certain constraints," and "models have better priority control over categorical constraints (e.g., case, language) than constraints requiring reasoning along a continuous scale." Yilin Geng, Haonan Li, Honglin Mu, Xudong Han, Timothy Baldwin, Omri Abend, Eduard Hovy, Lea Frermann; peer-reviewed, accepted to the AAAI-26 Main Technical Track, published in Proceedings of the AAAI Conference on Artificial Intelligence 40(36): 30816-30824, 2026; arXiv v1 2025-02-21, v4 2025-12-04. The conflicts tested are deliberately minimal formatting constraints (capitalisation, length, language) placed in system versus user messages on the 2025-generation models — not repository instruction files. The course carries the mechanism, states the setting, and does not present the percentages as rates for AGENTS.md conflicts.

## S8 — Anthropic: Building effective AI agents
URL: https://www.anthropic.com/engineering/building-effective-agents
- authority: official-docs
- supports: Supports Lesson 4's design principle that instructions written for a model deserve the same care as an interface written for a person, and that the test of a written instruction is whether acting on it requires no guesswork.
- key-fact: On the interface framing: "One rule of thumb is to think about how much effort goes into human-computer interfaces (HCI), and plan to invest just as much effort in creating good agent-computer interfaces (ACI)." The test to apply: "Put yourself in the model's shoes. Is it obvious how to use this tool, based on the description and parameters, or would you need to think carefully about it? If so, then it's probably also true for the model." On what a good definition contains: "A good tool definition often includes example usage, edge cases, input format requirements, and clear boundaries from other tools... Think of this as writing a great docstring for a junior developer on your team." On removing ambiguity by construction: "Poka-yoke your tools. Change the arguments so that it is harder to make mistakes... we found that the model would make mistakes with tools using relative filepaths after the agent had moved out of the root directory. To fix this, we changed the tool to always require absolute filepaths—and we found that the model used this method flawlessly." Erik S. and Barry Zhang; published 2024-12-19, page re-read 2026-08-23. Written about tool definitions rather than repository instruction files; the course applies the principle by analogy and says so in the lesson text.

## S9 — GitHub Docs: Adding repository custom instructions for GitHub Copilot
URL: https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions
- authority: official-docs
- supports: Supports Lesson 3's claim that nearest-file precedence is the shared rule across independent vendors, and Lesson 5's distinction between an instruction file and a path-scoped rule as two different ways to narrow scope.
- key-fact: "Agent instructions are used by AI agents. You can create one or more AGENTS.md files, stored anywhere within the repository. When Copilot is working, the nearest AGENTS.md file in the directory tree will take precedence." On the alternative filenames: "Alternatively, you can use a single CLAUDE.md or GEMINI.md file stored in the root of the repository." On the separate path-scoped mechanism: "Path-specific custom instructions apply to requests made in the context of files that match a specified path. These are specified in one or more NAME.instructions.md files within or below the .github/instructions directory in the repository. If the path you specify matches a file that Copilot is working on, and a repository-wide custom instructions file also exists, then the instructions from both files are used." Fetched 2026-08-23. Which Copilot surfaces honour which file is product surface and changes; the course cites this as a dated snapshot of one vendor's resolution rule.

## S10 — Cursor docs: Rules
URL: https://cursor.com/docs/rules
- authority: official-docs
- supports: Supports Lesson 2's length guidance from a second independent vendor, Lesson 4's rule against copying whole style guides into an instruction file, and Lesson 1's boundary between plain repo context and a structured rule system.
- key-fact: On AGENTS.md support: "AGENTS.md is a simple markdown file for defining agent instructions. Place it in your project root as an alternative to .cursor/rules for straightforward use cases. Unlike Project Rules, AGENTS.md is a plain markdown file without metadata or complex configurations." On scope: "Cursor supports AGENTS.md in the project root and subdirectories." On what rules are for: "Large language models don't retain memory between completions. Rules provide persistent, reusable context at the prompt level. When applied, rule contents are included at the start of the model context." Under "Best practices": "Good rules are focused, actionable, and scoped. Keep rules under 500 lines. Split large rules into multiple, composable rules. Provide concrete examples or referenced files. Avoid vague guidance. Write rules like clear internal docs. Reference files instead of copying their contents—this keeps rules short and prevents them from becoming stale as code changes." Under "What to avoid in rules": "Copying entire style guides: Use a linter instead. Agent already knows common style conventions." Fetched 2026-08-23. The 500-line figure is this vendor's own recommendation for its own rule files, not a measured threshold and not a property of the AGENTS.md format.
