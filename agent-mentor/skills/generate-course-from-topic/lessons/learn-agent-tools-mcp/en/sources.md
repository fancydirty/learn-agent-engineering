## S1 — MCP specification: Versioning and Compatibility
URL: https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning
- authority: official-docs
- supports: Establishes which protocol revision this course is written against, how revisions are named and marked, and how a client and server agree on a version now that there is no handshake — the version boundary stamped on every volatile fact in this course.
- key-fact: "The Model Context Protocol uses string-based version identifiers following the format `YYYY-MM-DD`, to indicate the last date backwards incompatible changes were made." Revisions are marked Draft, Current, or Final, and the page states: "The **current** protocol version is [**2026-07-28**]." On negotiation without a handshake: "Every request declares the protocol version it is using via the `io.modelcontextprotocol/protocolVersion` key in its `_meta` field, and the server accepts or rejects each request independently... If the server does not support the requested version, it responds with an `UnsupportedProtocolVersionError` listing the versions it does support." On discovery: "Clients that want to select a version up front can call `server/discover`, a mandatory RPC that returns the server's supported protocol versions, capabilities, and identity in a single request. Calling it is optional." Fetched 2026-08-23; `https://modelcontextprotocol.io/specification/versioning` 307-redirects to this canonical docs path. This page is the course's answer to "is 2026-07-28 still current?" and is the first thing a reader should re-check.

## S2 — MCP specification 2026-07-28: Key Changes (changelog)
URL: https://modelcontextprotocol.io/specification/2026-07-28/changelog
- authority: official-docs
- supports: Supports Lesson 3's account of what the 2026-07-28 revision removed and added — statelessness, the dropped handshake, `server/discover`, the removal of session identity — and Lesson 5's claim that Tasks moved out of the core into an official extension.
- key-fact: On sessions: "Remove protocol-level sessions and the `Mcp-Session-Id` header from the Streamable HTTP transport. List endpoints (`tools/list`, `resources/list`, `prompts/list`) no longer vary per-connection. Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments." On the handshake: "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request now carries its protocol version and client capabilities in `_meta`." On discovery: "Add `server/discover`: servers MUST implement this RPC to advertise their supported protocol versions, capabilities, and identity." On Tasks: "Move experimental tasks out of the core protocol and into an official extension (`io.modelcontextprotocol/tasks`). The redesigned extension replaces the blocking `tasks/result` method with polling via `tasks/get` and a new `tasks/update` for client-to-server input." On extensions: "Add `extensions` field to `ClientCapabilities` and `ServerCapabilities` to support optional extensions beyond the core protocol." On stream loss: "Remove SSE stream resumability and message redelivery... A broken response stream loses the in-flight request; clients **MUST** re-issue it as a new request with a new request ID." Deprecations in this revision include Roots, Sampling and Logging, and the OAuth 2.0 Dynamic Client Registration mechanism. Fetched 2026-08-23. This page is scoped to one revision; a later revision publishes its own changelog.

## S4 — MCP specification 2026-07-28: Architecture
URL: https://modelcontextprotocol.io/specification/2026-07-28/architecture
- authority: official-docs
- supports: Supports Lesson 2's entire model — the host/client/server split, the 1:1 client-server relationship, what each role is responsible for — and the isolation design principle that Lesson 6 builds its trust boundary on.
- key-fact: "The Model Context Protocol (MCP) follows a client-host-server architecture where each host can run multiple client instances. MCP is a stateless protocol: every request is self-contained and carries its own protocol version and capabilities." On the host: it "Creates and manages multiple client instances," "Controls client connection permissions and lifecycle," "Enforces security policies and consent requirements," and "Handles user authorization decisions." On clients: "Each client is created by the host and communicates with exactly one server... A host application creates and manages multiple clients, with each client having a 1:1 relationship with a particular server." On servers: they "Expose resources, tools and prompts via MCP primitives" and "Can be local processes or remote services." Design principle 3, quoted in full in Lesson 2: "Servers should not be able to read the whole conversation, nor 'see into' other servers — Servers receive only necessary contextual information; Full conversation history stays with the host; Each server maintains isolation; Cross-server interactions are controlled by the host; Host process enforces security boundaries." Fetched 2026-08-23.

## S5 — MCP specification 2026-07-28: Base Protocol overview
URL: https://modelcontextprotocol.io/specification/2026-07-28/basic/index
- authority: official-docs
- supports: Supports Lesson 3's normative statement of what statelessness requires of a server, the required per-request `_meta` fields, and the rule that cross-request state must be an explicit identifier — the mechanism Lesson 5's handles and task IDs both rest on.
- key-fact: "The Model Context Protocol (MCP) is a **stateless protocol**: all the information needed to process a request is contained in the request itself. A server processes each request independently; no state should be inferred from previous requests, even those on the same connection or stream." The normative list: "Servers **MUST NOT** rely on prior requests over the same connection to establish context (e.g., capabilities, protocol version, client identity)"; "Servers **SHOULD NOT** require that a client reuse the same connection or process to perform related operations"; "State that needs to span multiple requests (e.g., long-running tasks, application-level handles) **MUST** be referenced by an explicit identifier the client passes on each request." And the note: "an open connection, such as a STDIO process, is not a conversation or session." Required per-request `_meta` fields are `io.modelcontextprotocol/protocolVersion` (required) and `io.modelcontextprotocol/clientCapabilities` (required), with `clientInfo` optional but SHOULD-included; "A request missing any required field is malformed; the server **MUST** reject it with JSON-RPC error code `-32602`." On identity fields: "`clientInfo` and `serverInfo` are self-reported by the sender and are not verified by the protocol... Implementations **SHOULD NOT** rely on them for security decisions." Fetched 2026-08-23.

## S6 — MCP specification 2026-07-28: Tools
URL: https://modelcontextprotocol.io/specification/2026-07-28/server/tools
- authority: official-docs
- supports: Supports Lesson 4's account of what a tool definition actually contains and what the model sees, Lesson 4's two-channel error model, Lesson 5's stateful-handle pattern, and the human-in-the-loop and untrusted-annotation warnings that Lesson 6 turns into a permission rule.
- key-fact: On control: "Tools in MCP are designed to be **model-controlled**, meaning that the language model can discover and invoke tools automatically based on its contextual understanding and the user's prompts." The trust warning: "For trust & safety and security, there **SHOULD** always be a human in the loop with the ability to deny tool invocations," with applications SHOULD "Present confirmation prompts to the user for operations, to ensure a human is in the loop." A tool definition carries `name`, optional `title`, `description` ("Human-readable description of functionality"), `inputSchema` ("JSON Schema defining expected parameters", which "**MUST** be a valid JSON Schema object"), optional `outputSchema`, optional `icons`, and optional `annotations`. On annotations: "For trust & safety and security, clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers." On errors, the two mechanisms: protocol errors are "issues with the request structure itself that models are less likely to be able to fix," while tool execution errors "contain actionable feedback that language models can use to self-correct and retry with adjusted parameters" and are "reported in tool results with `isError: true`"; "Clients **SHOULD** provide tool execution errors to language models to enable self-correction." On stateful tools (marked non-normative): "MCP has no protocol-level session, so a server cannot rely on implicit per-connection state to relate one tool call to the next. Servers that need to maintain state across calls... should do so by returning an explicit handle from a creation tool and accepting that handle as an argument on subsequent calls," and "The model is responsible for carrying `basket_id` forward." Client security duties include "Prompt for user confirmation on sensitive operations" and "Show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration." Fetched 2026-08-23.

## S7 — MCP: Security Best Practices
URL: https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices
- authority: official-docs
- supports: Supports Lesson 6's named attack classes — state handle hijacking, token passthrough, local server compromise — and the normative mitigations the course turns into reader-side checks.
- key-fact: On handles: "MCP is stateless and has no protocol-level sessions. Servers that need state spanning multiple requests mint an explicit handle... State handle hijacking is an attack vector where an unauthorized party obtains or guesses such a handle and uses it to access or modify another user's state." Mitigation: "MCP servers that implement authorization **MUST** verify all inbound requests. MCP servers **MUST NOT** treat possession of a state handle as authentication," and servers "**SHOULD** bind handles server-side to the authenticated user." On token passthrough: it is "an anti-pattern where an MCP server accepts tokens from an MCP client without validating that the tokens were properly issued *to the MCP server*," and the rule is absolute: "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." On local servers: "Local MCP servers are binaries that are downloaded and executed on the same machine as the MCP client," carrying risks of "Arbitrary code execution. Attackers can execute any command with MCP client privileges" and "No visibility. Users have no insight into what commands are being executed." The client duty: "If an MCP client supports one-click local MCP server configuration, it **MUST** implement proper consent mechanisms prior to executing commands," showing "the exact command that will be executed, without truncation." Also documented: the confused deputy problem, SSRF against OAuth metadata URLs, and scope minimization ("Minimal initial scope set... containing only low-risk discovery/read operations"). Fetched 2026-08-23.

## S8 — MCP Extensions Overview
URL: https://modelcontextprotocol.io/extensions/overview
- authority: official-docs
- supports: Supports Lesson 3's boundary between the core protocol and everything negotiated on top of it, and Lesson 5's explanation of why a capability a reader's client lacks simply will not be available.
- key-fact: "MCP extensions are optional additions to the specification that define capabilities beyond the core protocol." Naming: "Extensions are identified using a unique *extension identifier* with the format: `{vendor-prefix}/{extension-name}`, e.g. `io.modelcontextprotocol/oauth-client-credentials`... Official extensions use the `io.modelcontextprotocol` vendor prefix." On opt-in: "Extensions are always disabled by default and require explicit opt-in from the developer." On SDKs: "SDKs can choose to implement extensions, but it's not required for protocol conformance. SDK maintainers have full autonomy over which extensions they support." On negotiation: "Clients and servers advertise their support for extensions in the `extensions` field within their respective capability declarations" — clients in `_meta["io.modelcontextprotocol/clientCapabilities"]` per request, servers in the `server/discover` response. On mismatch: "If one side supports an extension but the other doesn't, the supporting side needs to either fall back to core protocol behavior or reject the request with an appropriate error if the extension is mandatory." Listed official extensions at fetch time: MCP Apps, MCP Tasks, OAuth Client Credentials, and Enterprise-Managed Authorization. Fetched 2026-08-23; the set of official extensions is expected to grow.

## S9 — MCP Tasks extension overview
URL: https://modelcontextprotocol.io/extensions/tasks/overview
- authority: official-docs
- supports: Supports Lesson 5 end to end — why blocking fails for long work, the task lifecycle and its terminal states, the polling loop, mid-flight input, and the requirement that both sides opt in.
- key-fact: On the problem: "Not every tool call returns instantly. Some operations — CI pipelines, batch processing, human approvals — take seconds, minutes, or longer. MCP Tasks let servers return a durable handle instead of blocking." Why not block: "Blocking ties up a connection for the duration of the operation. Many clients and transport intermediaries impose timeouts that make this impractical beyond a few seconds," and "A task ID is a durable handle. If the client disconnects or restarts, it can resume polling with the same ID." The lifecycle states: `working`, `input_required`, `completed`, `failed`, `cancelled`, where "`completed`, `failed`, and `cancelled` are terminal — once reached, the task's state does not change." The flow: the server returns "a `CreateTaskResult` (identified by `resultType: \"task\"`) containing a `taskId`, initial status, TTL, and suggested polling interval. The task is durably created before the response is sent"; the client "calls `tasks/get` with the `taskId`"; on `input_required` the client "fulfills these via `tasks/update`". On who decides: "**Server-directed.** The server decides per-request whether to create a task. Clients opt in once via the extension capability." The server-side rule: "Before returning a `CreateTaskResult`, verify that the client included the extension in its per-request capabilities. Never return a task to a client that did not declare support." On cancellation: "Cancellation is cooperative — the server acknowledges the intent but is not obligated to stop the work." And on availability: "MCP Tasks is an extension to the core MCP specification. Host support varies by client." Fetched 2026-08-23.

## S10 — Anthropic engineering: Writing effective tools for agents
URL: https://www.anthropic.com/engineering/writing-tools-for-agents
- authority: official-docs
- supports: Supports Lesson 4's central claim that a tool description is prompt-engineering rather than documentation, plus the course's guidance on tool count, namespacing, response size, and actionable error text.
- key-fact: On descriptions: "When writing tool descriptions and specs, think of how you would describe your tool to a new hire on your team. Consider the context that you might implicitly bring — specialized query formats, definitions of niche terminology, relationships between underlying resources — and make it explicit." And: "we now come to one of the most effective methods for improving tools: prompt-engineering your tool descriptions and specs. Because these are loaded into your agents' context, they can collectively steer agents toward effective tool-calling behaviors." On tool count: "More tools don't always lead to better outcomes. A common error we've observed is tools that merely wrap existing software functionality or API endpoints — whether or not the tools are appropriate for agents." On namespacing: "Namespacing (grouping related tools under common prefixes) can help delineate boundaries between lots of tools; MCP clients sometimes do this by default," with the caveat "We have found selecting between prefix- and suffix-based namespacing to have non-trivial effects on our tool-use evaluations. Effects vary by LLM and we encourage you to choose a naming scheme according to your own evaluations." On errors: "if a tool call raises an error (for example, during input validation), you can prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks." On evaluation: "Lots of tool errors for invalid parameters might suggest tools could use clearer descriptions or better examples." A worked instance is given: on Claude's web search tool, a parameter biased results "and degrading performance (we steered Claude in the right direction by improving the tool description)." Published 2025-09-11; fetched 2026-08-23. This is a durable design-principles source that predates the 2026-07-28 revision — the course cites it for description craft and tool-count judgment, never for current protocol mechanics.

## S12 — MCP: Build an MCP server
URL: https://modelcontextprotocol.io/docs/2026-07-28/develop/build-server
- authority: official-docs
- supports: Supports Lesson 4's worked example that a Python SDK derives the wire-level tool definition from the function's type hints and docstring, and Lesson 1's summary of the three server primitives.
- key-fact: On the primitives: "MCP servers can provide three main types of capabilities: **Resources**: File-like data that can be read by clients (like API responses or file contents); **Tools**: Functions that can be called by the LLM (with user approval); **Prompts**: Pre-written templates that help users accomplish specific tasks." On how a definition is produced: "The MCPServer class uses Python type hints and docstrings to automatically generate tool definitions, making it easy to create and maintain MCP tools." Fetched 2026-08-23 from the docs path for the 2026-07-28 revision; `https://modelcontextprotocol.io/docs/develop/build-server` redirects here. ## S15 — MCP blog: The New MCP Roadmap
URL: https://blog.modelcontextprotocol.io/posts/mcp-roadmap/
- authority: official-docs
- supports: Supports the course's statement of what is expected to move next — the basis for `topicCurrency.staleRisk` and for Lesson 6's note that agent identity is an open area rather than a solved one.
- key-fact: "Today we're excited to publish an updated roadmap for the Model Context Protocol (MCP), covering the next specification release and beyond," organised so that "The roadmap is organized into five priority areas." On the result of going stateless: "With the 2026-07-28 release, a remote MCP server is now no different from any other HTTP workload, making it easy to host and operate one on any infrastructure that developers and organizations already use for their APIs and services. The model has proven to scale, and we want to stretch it to cover other deployment modes as well, including local servers speaking Streamable HTTP over stdio." On long-running work: "Modern agentic workloads no longer fit the standard request-and-response pattern. Loops can run for longer, servers can push streamed results, and there is a clear need to steer work mid-flight. MCP has been growing to meet these requirements, introducing Tasks, `subscriptions/listen`, and progress notifications." On identity: "We want MCP servers to have a standardized way to recognize and trust those agent identities, built on existing standards rather than pasted API keys and long-lived tokens." Published 2026-08-22 by lead maintainers David Soria Parra and Den Delimarsky; fetched 2026-08-23. A roadmap states intent, not shipped behaviour — nothing in this course is built on it.
