# 第 1 讲：提示词复用与 Skill 边界

> 本讲目标：
> - 从一次真实重复任务中识别可复用工作流。
> - 区分一次性提示词、重复任务和 Skill 的职责。
> - 写出四行 Skill brief：触发、输入、输出、不处理。
>
> 前置条件：会使用一种 coding agent，并能编辑 Markdown | 上一页 [<< 课程目录](./README.md) | 下一讲 [02 >>](./02-skill-metadata.md)

## 每次都要重讲一遍的任务

你可能已经遇到过这种场景：每次让 Agent 写周报、审查 PR、整理会议记录或生成发布说明，都要重新交代语气、输入文件、输出格式、不要碰哪些目录。第一次这样写提示词很正常；第五次还在复制同一大段说明，就说明这里已经不是“提示词写得不够好”，而是有一个重复工作流没有被固定下来。

这一讲不要求你立刻写完整 Skill。我们先把一个反复出现的任务压缩成四行边界记录，让后面的 `SKILL.md` 有清楚的骨架。

## 解释

### 从一次具体任务开始

先看一个一次性提示词：

```text
帮我把昨天的客户访谈整理成一份中文纪要。重点保留客户原话，最后给出 3 条产品改进建议。不要改动原始 transcript。
```

这句话在单次任务中够用。问题出现在第二次、第三次：你又要说明“客户原话怎么保留”“建议要多具体”“哪些文件不能动”。一次性提示词是为当前对话临时写下的任务说明；它可以很短，也可以很长，但默认不会成为 Agent 以后自动发现的能力。

当同一类任务反复出现，而且每次都有相似输入、相似输出和相似边界时，它就是重复任务。重复任务不等于烦人的小事；它的关键特征是：你能说清楚什么时候该做、拿什么做、交付什么、哪些事不该顺手做。

### 把重复任务命名为可复用工作流

可复用工作流是一组可以被再次调用的步骤、约束和输出标准。Anthropic 把 Skill 描述为一个包含 `SKILL.md`、指令、脚本和资源的目录；OpenAI/Codex 也把 Agent Skills 用作面向 ChatGPT 与 Codex 的任务专用能力扩展。[^S1][^S4]

Skill 让 Agent 在合适任务中发现、读取并执行一组工作流资料。它比一次性提示词多了可发现的入口、稳定边界和按需资源，但不负责承包整个业务系统。

判断一个重复任务是否值得做成 Skill，可以先问四个问题：

- 触发：用户说什么或拿出什么材料时，Agent 应该想到它？
- 输入：Agent 必须拿到哪些文件、字段或上下文？
- 输出：Agent 最后应该交付什么格式的结果？
- 不处理：哪些相邻任务容易被误做，但不属于这个 Skill？

这四行就是本课使用的 Skill brief。它还不是正式规范字段，而是写 `SKILL.md` 前的职责边界草图。

### 收窄 Skill 的职责边界

职责边界说明这个 Skill 负责什么，也说明它不负责什么。边界太窄，Agent 只能处理一个样例；边界太宽，Agent 会把相邻任务也卷进来。Anthropic 建议从简单、可组合的方案开始，OpenAI 的当前指南也要求每个 Skill 聚焦一项工作。[^S4][^S5]

例如“帮我做内容”太宽；“把一份客户访谈 transcript 整理成带原话证据的中文纪要”更适合 Skill。它有明确触发、输入和输出，也能说清楚不处理：不做销售跟进、不改 transcript、不代替产品决策。

本讲术语表：

- 一次性提示词：只服务当前对话的一段任务说明。
- 重复任务：多次出现、输入和输出形态相似的任务。
- 可复用工作流：可再次调用的一组步骤、约束和输出标准。
- 职责边界：说明工作流处理什么、不处理什么的范围。

## 完整示例：访谈纪要 Skill brief

假设你每周都要整理客户访谈。原始任务是：

```text
读取 transcripts/ 里的访谈稿，输出一份中文纪要，保留客户原话，最后给产品建议。
```

把它改写成四行 Skill brief：

```text
触发：用户要求整理客户访谈、用户研究 transcript 或 sales call notes。
输入：一份或多份 transcript 文本，最好包含说话人和时间顺序。
输出：中文 Markdown 纪要，包含主题摘要、客户原话证据、问题清单和 3 条产品建议。
不处理：不修改原始 transcript，不替用户发送邮件，不决定路线图优先级。
```

这四行把重复解释变成了可复查边界，但它们不会逐项变成正式字段。写 `description` 时，放入能力、正向触发条件，以及确有必要的负向消歧；输入细节、完整输出要求和执行禁令留在正文。比如“不要把它用于发送邮件”若用于排除邮件任务，应浓缩进 `description`；“不要修改原始 transcript”则是 Skill 已加载后仍要遵守的正文规则。

## 半完成示例：发布说明 Skill brief

补完下面这份半成品。注意，“不处理”要挡住一个很容易顺手做错的相邻任务。

```text
触发：用户要求根据 Git commit、PR 或 changelog 草稿生成发布说明。
输入：________________________________。
输出：________________________________。
不处理：________________________________。
```

参考答案：

```text
输入：commit 列表、PR 摘要或现有 changelog 草稿，以及目标读者类型。
输出：面向用户的 Markdown 发布说明，按新增、修复、已知问题分组。
不处理：不修改代码，不创建 Git tag，不代替负责人决定是否发布。
```

你的措辞可以不同，但要能让 Agent 判断“什么时候该用”和“什么时候该停”。

## 练习

### Level 1（热身）

在你自己的真实工作目录中，找一个最近三次都向 Agent 重复解释过的任务，写出它的四行 Skill brief。不要新建正式 Skill，只在草稿 Markdown 或笔记里完成。

做法：打开那个目录，回看最近的任务说明或聊天记录，先复制一段最常重复的提示词，再把它压缩成“触发、输入、输出、不处理”四行。
<!-- rubric -->
- 四行都存在，且每行只描述一类信息。
- 触发能让 Agent 判断何时应该想到这个工作流。
- 不处理至少挡住一个真实相邻任务。
<!-- answer -->
合格答案会像边界记录，而不是完整说明书。例如“触发：用户要求从会议 transcript 生成纪要；输入：一份 transcript；输出：中文 Markdown 纪要；不处理：不发送邮件、不安排会议”。常见错误是把“请认真一点”“输出高质量”写进边界，这些词不能帮助 Agent 判断任务范围。
<!-- hint -->
先找你最常复制粘贴的那段提示词。
<!-- hint -->
如果“不处理”想不出来，回忆 Agent 曾经顺手多做过什么。

### Level 2（进阶）

把同一个重复任务分别写成“太窄版”“太宽版”和“合适版”三个 brief，并解释你为什么选择合适版。

做法：围绕同一真实任务写三组四行 brief。太窄版只覆盖一个样例，太宽版吞掉相邻流程，合适版保留稳定输入和稳定输出。
<!-- rubric -->
- 三个版本围绕同一任务，而不是三个不同任务。
- 太窄版和太宽版的风险各写出一句。
- 合适版的输出格式和不处理边界都可检查。
<!-- answer -->
示例：对“发布说明”来说，太窄版可能只处理某个仓库今天的 5 个 commit；太宽版可能包含改代码、打 tag、通知用户；合适版则只根据给定变更材料生成面向用户的发布说明。选择合适版的理由是：它能复用，但不会替代发布决策。
<!-- hint -->
太窄版通常会出现具体日期、具体文件名或一次性项目名。
<!-- hint -->
太宽版通常会出现“所有”“完整负责”“从头到尾”这类词。
<!-- /exercises -->

## 带走：一份能直接改写的 brief

这份四行 brief 已经标出了任务从哪里开始、需要什么、交付什么，以及在哪里停。接下来要把它翻译成正式 `SKILL.md`：发现阶段只保留足以选择 Skill 的信息，执行细节进入正文。
