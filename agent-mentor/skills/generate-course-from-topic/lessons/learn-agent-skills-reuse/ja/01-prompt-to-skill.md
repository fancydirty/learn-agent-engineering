# 第1回：プロンプトの再利用と Skill の境界

> 本講の目標：
> - 実際に繰り返しているタスクから、再利用可能なワークフローを見つけ出します。
> - 使い捨てプロンプト、繰り返しタスク、Skill の責務を区別します。
> - トリガー、入力、出力、対象外の 4 行からなる Skill ブリーフを書きます。
>
> 前提条件：何らかの coding agent を使え、Markdown を編集できること | 前のページ [<< コース目次](./README.md) | 次の講 [02 >>](./02-skill-metadata.md)

## 毎回説明し直しているタスク

こんな場面に心当たりがあるかもしれません。Agent に週報を書かせる、PR をレビューさせる、会議メモを整理させる、リリースノートを生成させるたびに、トーン、入力ファイル、出力形式、触ってはいけないディレクトリを毎回説明し直している、という場面です。最初のうちはそう書くのが普通です。しかし 5 回目になっても同じ長い説明をコピーしているなら、それは「プロンプトの書き方が悪い」のではなく、固定されていない繰り返しのワークフローがあるということです。

この講では、いきなり完全な Skill を書くことは求めません。まず繰り返し現れるタスクを 4 行の境界メモに圧縮し、後の `SKILL.md` に明確な骨格を用意します。

## 解説

### 具体的な 1 つのタスクから始める

まず、使い捨てプロンプトを見てみましょう。

```text
昨日の顧客インタビューを中国語のノートにまとめてください。顧客の原話を残すことを重視し、最後に製品改善の提案を 3 件示してください。元の transcript は変更しないでください。
```

この文は 1 回限りのタスクには十分です。問題は 2 回目、3 回目に起きます。「顧客の原話をどう残すか」「提案はどのくらい具体的にするか」「どのファイルに触れてはいけないか」をまた説明することになります。使い捨てプロンプトとは、現在の会話のためにその場で書くタスク説明です。短くても長くても構いませんが、デフォルトでは Agent が後から自動的に発見できる能力にはなりません。

同じ種類のタスクが繰り返し現れ、毎回似た入力、似た出力、似た境界があるなら、それは繰り返しタスクです。繰り返しタスクは面倒な雑務という意味ではありません。重要な特徴は、いつやるべきか、何を使ってやるか、何を届けるか、ついでにやるべきでないことは何かを、はっきり説明できることです。

### 繰り返しタスクに再利用可能なワークフローという名前を付ける

再利用可能なワークフローとは、再度呼び出せる一連の手順、制約、出力基準のことです。Anthropic は Skill を、`SKILL.md`、インストラクション、スクリプト、リソースを含むディレクトリとして説明しています。OpenAI と Codex も Agent Skills を、ChatGPT と Codex に向けたタスク特化の能力拡張として使っています。[^S1][^S4]

Skill は、Agent が適切なタスクで発見、読み込み、実行できるワークフロー資料のセットです。使い捨てプロンプトに比べて、発見可能な入口、安定した境界、必要時に読むリソースが増えますが、業務システム全体を請け負うものではありません。

繰り返しタスクが Skill 化に値するかは、4 つの質問で判断できます。

- トリガー：ユーザーが何と言ったとき、あるいはどんな材料を出したときに、Agent はそれを思い出すべきか。
- 入力：Agent が必ず受け取るべきファイル、フィールド、コンテキストは何か。
- 出力：Agent が最終的に届けるべき形式は何か。
- 対象外：誤って一緒にやりがちだが、この Skill には含まない隣接タスクは何か。

この 4 行が、このコースで使う Skill ブリーフです。これはまだ正式な仕様フィールドではなく、`SKILL.md` を書く前の責務境界のスケッチです。

### Skill の責務境界を絞る

責務境界は、この Skill が何に責任を持つかと、何に責任を持たないかを示します。境界が狭すぎると Agent は 1 つの事例しか扱えません。広すぎると Agent は隣接タスクまで巻き込みます。Anthropic はシンプルで組み合わせ可能な案から始めることを勧めており、OpenAI の現在のガイドも各 Skill が 1 つの仕事に集中することを求めています。[^S4][^S5]

たとえば「コンテンツ作りを手伝って」は広すぎます。「顧客インタビューの transcript を、原話の証拠付きの中国語ノートにまとめる」ほうが Skill に向いています。明確なトリガー、入力、出力があり、対象外も言い切れます。営業のフォローアップはしない、transcript は変更しない、製品判断の代行はしない、という具合です。

本講の用語：

- 使い捨てプロンプト：現在の会話だけに奉仕するタスク説明。
- 繰り返しタスク：複数回現れ、入力と出力の形が似ているタスク。
- 再利用可能なワークフロー：再度呼び出せる一連の手順、制約、出力基準。
- 責務境界：ワークフローが何を処理し、何を処理しないかの範囲。

## 完全な例：インタビューノート Skill ブリーフ

毎週、顧客インタビューを整理しているとします。元のタスクは次のとおりです。

```text
transcripts/ 内のインタビュー原稿を読み、中国語のノートを出力する。顧客の原話を残し、最後に製品への提案を付ける。
```

これを 4 行の Skill ブリーフに書き換えます。

```text
トリガー：ユーザーが顧客インタビュー、ユーザー調査の transcript、sales call notes の整理を求めたとき。
入力：1 件以上の transcript テキスト。話者と時系列が含まれていることが望ましい。
出力：中国語の Markdown ノート。テーマ要約、顧客の原話の証拠、質問リスト、製品への提案 3 件を含む。
対象外：元の transcript の変更、ユーザーに代わるメール送信、ロードマップの優先順位決定。
```

この 4 行は、繰り返しの説明を再確認できる境界に変えますが、そのまま 1 行ずつ正式フィールドになるわけではありません。`description` を書くときは、能力、肯定的なトリガー条件、そして本当に必要な否定的な曖昧さ解消だけを入れます。入力の詳細、完全な出力要件、実行上の禁止事項は本文に残します。たとえば「メール送信には使わない」はメール系タスクを除外するためのものなので `description` に圧縮して入れるべきですが、「元の transcript を変更しない」は Skill が読み込まれた後でも守るべき本文ルールです。

## 途中までの例：リリースノート Skill ブリーフ

次の半完成品を完成させてください。「対象外」には、つい一緒にやってしまいがちな隣接タスクを 1 つ遮断する内容を入れます。

```text
トリガー：ユーザーが Git commit、PR、changelog の下書きからリリースノートの生成を求めたとき。
入力：________________________________。
出力：________________________________。
対象外：________________________________。
```

参考回答：

```text
入力：commit のリスト、PR の要約、既存の changelog 下書き、および想定読者の種別。
出力：ユーザー向けの Markdown リリースノート。新機能、修正、既知の問題でグループ化する。
対象外：コードの変更、Git tag の作成、リリース可否の判断の代行。
```

言い回しが違っても構いませんが、Agent が「いつ使うべきか」と「いつ止まるべきか」を判断できる内容にしてください。

## 演習

### Level 1（ウォームアップ）

自分の実際の作業ディレクトリで、最近 3 回 Agent に同じ説明を繰り返したタスクを 1 つ見つけ、その 4 行の Skill ブリーフを書いてください。正式な Skill は新規作成せず、下書きの Markdown やメモの中で完成させます。

進め方：そのディレクトリを開き、最近のタスク説明やチャット履歴を見返します。まず最もよく繰り返しているプロンプトを 1 段コピーし、それを「トリガー、入力、出力、対象外」の 4 行に圧縮します。
<!-- rubric -->
- 4 行がすべて存在し、各行が 1 種類の情報だけを述べている。
- トリガーを読めば、Agent がいつこのワークフローを思い出すべきか判断できる。
- 対象外が、実在する隣接タスクを少なくとも 1 つ遮断している。
<!-- answer -->
合格回答は、完全な説明書ではなく境界メモのようになります。たとえば「トリガー：ユーザーが会議 transcript からのノート生成を求めたとき。入力：transcript 1 件。出力：中国語の Markdown ノート。対象外：メール送信と会議調整」。よくある間違いは「丁寧にやって」「高品質に出力して」を境界に書くことです。こうした語は Agent がタスク範囲を判断する助けになりません。
<!-- hint -->
まず、あなたが最もよくコピー＆ペーストしているプロンプトを探してください。
<!-- hint -->
「対象外」が思い浮かばなければ、Agent がかつて勝手に余計なことをやった例を思い出してください。

### Level 2（発展）

同じ繰り返しタスクについて、「狭すぎる版」「広すぎる版」「ちょうどよい版」の 3 つのブリーフを書き、なぜ「ちょうどよい版」を選んだのかを説明してください。

進め方：同じ実タスクについて 3 組の 4 行ブリーフを書きます。狭すぎる版は 1 つの事例しかカバーせず、広すぎる版は隣接フローまで飲み込み、ちょうどよい版は安定した入力と安定した出力を保ちます。
<!-- rubric -->
- 3 つの版がすべて同じタスクを扱っている（3 つの別タスクではない）。
- 狭すぎる版と広すぎる版のリスクをそれぞれ 1 文ずつ書いている。
- ちょうどよい版の出力形式と対象外の境界がチェック可能である。
<!-- answer -->
例：「リリースノート」なら、狭すぎる版はあるリポジトリの今日の 5 件の commit だけを処理し、広すぎる版はコード変更、tag 付け、ユーザー通知まで含め、ちょうどよい版は与えられた変更材料からユーザー向けリリースノートを生成するだけにします。ちょうどよい版を選ぶ理由は、再利用できてもリリース判断を代行しないからです。
<!-- hint -->
狭すぎる版には、具体的な日付、具体的なファイル名、一回限りのプロジェクト名が現れがちです。
<!-- hint -->
広すぎる版には「すべて」「完全に担当」「最初から最後まで」といった語が現れがちです。
<!-- /exercises -->

## 持ち帰り：そのまま書き換えられるブリーフ

この 4 行ブリーフには、タスクがどこから始まり、何が必要で、何を届け、どこで止まるかが示されています。次はこれを正式な `SKILL.md` に翻訳します。発見フェーズには Skill を選ぶのに十分な情報だけを残し、実行の詳細は本文に移します。
