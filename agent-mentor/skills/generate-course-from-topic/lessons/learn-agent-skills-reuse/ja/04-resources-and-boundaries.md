# 第4回：リソース・スクリプト・実行境界

> 本講の目標：
> - `references/`、`assets/`、`scripts/` の用途を区別します。
> - ある資料を指示、参考資料、テンプレート、スクリプトのどれに書くべきかを判断します。
> - 実際の Skill フォルダーでリソースのレイヤー分けを行います。プログラミング能力は不要です。
>
> 前提条件：メタデータ層、指示層、リソース層、オンデマンド読み込みを理解していること | 前の講 [<< 03](./03-progressive-disclosure.md) | 次の講 [05 >>](./05-testing-and-safety.md)

## リソース層にも境界が必要

第 3 回では長い資料を `SKILL.md` から分け出しました。しかし分け出した後にも新たな混乱が生じます。タグの説明、サンプルファイル、空のテンプレート、チェックコマンドがすべて一緒に置かれていては、Agent はどれが知識で、どれがコピーすべき形で、どれが安定して実行できる動作なのか分かりません。

同じ 1 つの Markdown が、ルールにも参考資料にも出力テンプレートにもなり得ます。Agent がそれをどう使うべきかで変わるのです。ここで判断するのは各コンテンツの居場所です。指示に残すか、Agent が読むためのものにするか、コピーして埋めるためのものにするか、決定論的スクリプトに任せるか。この判断にスクリプトの作成や実行は必要ありません。

## 解説

### `references/`：Agent が読む背景資料

`references/` は長い説明、用語集、タグ定義、レビュールール、サンプル分析を置くのに適しています。特徴は「読んで判断する」ことです。Agent がこれを読むのは、タスクの基準をよりよく理解するためであり、一字一句コピーするためではありません。

インタビューノート Skill では、`references/tag-guide.md` が `pain-point`、`workaround`、`buying-signal` の 3 つのタグを説明し、各タグの判断例を示せます。最終出力のスケルトンをここに置くべきではありません。参考資料の主な用途は説明だからです。

### `assets/`：Agent が再利用する形

`assets/` は安定した出力の形と静的素材を置くのに適しています。たとえば空のノート、設定テンプレート、画像、データ表です。テキストテンプレートのために別途 `templates/` ディレクトリを作る必要はありません。`assets/` に直接入れ、ファイル名で用途を示せば十分です。オープン仕様と OpenAI の現在のガイドはどちらもこのディレクトリ約定を採用しています。[^S2][^S4]

インタビューノートに毎回「要約、原話の証拠、テーマ、未解決の質問」の 4 セクションが必要なら、その骨格を `assets/note-template.md` に入れます。Agent は固定の形が必要なときにそれを読み、ユーザーの材料で空欄を埋めます。

### `scripts/`：決定論的操作のための場所

`scripts/` は、再現可能でルールが明確で結果をチェックできる操作を置くのに適しています。たとえば Markdown に必須の見出しが含まれるかをチェックする、CSV を統一フィールド名に変換する、ディレクトリ内にテンプレートが欠けていないかを数える、といった操作です。公式資料はスクリプトを Skill が構成できる要素の 1 つとして挙げ、インストール前に依存関係、リソース、外部ネットワークアクセスを監査するよう注意を促しています。[^S1][^S3]

このコースはコードを書くことを求めません。スクリプトが存在する価値があるかの判断は 3 点だけ見ます。ルールが固定されているか、手作業では間違えやすいか、実行結果をチェックできるか。すべて明確に「はい」なら、将来スクリプトを検討できます。意味判断を多く必要とするなら、指示か参考資料に残します。

### 決定論的境界：スクリプトに渡すべきでないもの

決定論的境界とは、「機械がルールどおりにやる」ことと「Agent が意味で判断する」ことの境界線です。スクリプトが得意なのは、見出しが存在するか、ファイル名が一致するか、フィールドが空かのチェックです。Agent が得意なのは、ある顧客の原話が本当にある結論を支持しているかの判断です。

インタビューノートでは、「出力に `## 原话证据` が含まれるかのチェック」はスクリプトにできます。「この原話が強い購入シグナルかどうかの判断」は、参考資料と Agent の判断の組み合わせが適しています。意味判断を無理にスクリプトに押し込むと、一見安定しているが実は硬直したルールができあがります。

本講の用語：

- `references/`：長い背景情報、ルール説明、判断基準を置く参考資料ディレクトリ。
- `assets/`：再利用可能なテンプレート、画像、データファイルを置く静的リソースディレクトリ。
- `scripts/`：ルールが明確で再現可能、チェック可能な操作を置くスクリプトディレクトリ。
- 決定論的境界：固定ルールによる実行と意味判断を分ける境界。

## 完全な例：インタビューノート Skill の 4 種類のコンテンツの振り分け

この架空の Skill を整理しているとします。

```text
interview-notes/
  SKILL.md
```

手元には 6 件のコンテンツがあります。

```text
1. ユーザーが transcript を渡したら、中国語の Markdown ノートを出力する。
2. 元の transcript を変更せず、顧客の原話を捏造しない。
3. pain-point、workaround、buying-signal のタグ説明。
4. 固定のノート骨格 1 つ。
5. 3 件の架空の transcript と、対応する良いノートの例。
6. 出力に「摘要、原话证据、开放问题」の 3 つの見出しが含まれるかをチェックする。
```

まず必読ルールを振り分けます。1 と 2 は毎回の実行で守るべきものなので、`SKILL.md` の本文に残します。

```markdown
## Instructions

When the user provides interview transcripts, produce Chinese Markdown notes.
Preserve quoted evidence and do not modify the original transcript.
Do not invent quotes that are not present in the source material.
```

次に説明が必要な判断基準を振り分けます。3 は参考資料です。

```text
references/tag-guide.md
```

その役割は Agent のタグ判断を助けることであり、最終ノートに固定のレイアウトを提供することではありません。

続いて再利用可能な形を振り分けます。4 はテンプレートです。

```text
assets/note-template.md
```

Agent はユーザーが固定構造を求めたときにこれを読み、実際の内容を埋めます。

5 は `references/examples.md` に入れられます。主な用途は、何が「良いノート」かを理解することだからです。例にプライベートな情報が含まれるなら公開 Skill には入れられません。ここでは公開可能または架空の材料を使う必要があります。

6 だけがスクリプト境界に近いものです。ルールが固定され、手作業のチェックでは見落としやすく、結果が「どの見出しが欠けているか」を明確に返せます。将来は次に置けます。

```text
scripts/check-note-headings.js
```

ただしプログラミングができなければ、まず `references/quality-check.md` のチェックリストとして書いても構いません。重要なのは、危険なスクリプトを思い付きで書かないこと、スクリプトにユーザーファイルを変更させないこと、まず境界をはっきりさせることです。

最終構造：

```text
interview-notes/
  SKILL.md
  references/
    tag-guide.md
    examples.md
    quality-check.md
  assets/
    note-template.md
  scripts/
    check-note-headings.js
```

ここの `scripts/` は将来の置き場所であり、この講ですぐ実装を求めるコードではありません。それがなぜ意味判断ではなく決定論的チェックに属するのかを説明できれば十分です。

## 途中までの例：コンテンツを正しい場所に置く

次はリリースノート Skill のリソースリストです。各項目を `SKILL.md`、`references/`、`assets/`、`scripts/` のどれかに振り分けてください。

```text
A. PR の要約を入力したら、ユーザー向けの Markdown リリースノートを出力する。
B. Git tag を作らず、デプロイも実行しない。
C. "breaking change"、"known issue"、"migration note" の判断説明。
D. リリースノートの固定構造：新機能、修正、既知の問題。
E. Markdown に 2 レベル見出しの「新機能」と「修正」が含まれるかをチェックする。
```

補完部分：

```text
`SKILL.md`：________________________________
`references/`：____________________________
`assets/`：_________________________________
`scripts/`：_______________________________
```

参考回答：

```text
`SKILL.md`：A、B。毎回のタスクで守るべき中核指示と境界。
`references/`：C。判断基準を説明するもので、Agent が読んで理解する必要がある。
`assets/`：D。再利用可能な出力スケルトンで、コピーしてから埋めるのに適している。
`scripts/`：E。固定の見出しチェックで、結果を明確に判定できる。
```

C をスクリプトに入れると、意味判断が硬直したキーワードマッチになります。D を `SKILL.md` に長々と書くと、入口が重くなります。

## 演習

### Level 1（ウォームアップ）

すでに書いた Skill 下書きを 1 つ選び、8 件のコンテンツを挙げて、`SKILL.md`、`references/`、`assets/`、`scripts/` の 4 種類に振り分けてください。実際にスクリプトを書く必要はありません。どの内容が将来スクリプト化できそうかを説明するだけで十分です。

進め方：Skill 下書きかブリーフを開き、各ルール、例、テンプレート、チェック項目を個別の項目に分解します。各項目に「毎回必読」「読んで判断」「コピーして埋める」「固定チェック」のどれかを付記します。
<!-- rubric -->
- 少なくとも 8 件のコンテンツを挙げている。
- 4 種類のうち少なくとも 3 種類にコンテンツがある。空の種類がある場合は理由を 1 文書く。
- 各コンテンツに振り分け理由が 1 文ある。
- スクリプト化に適さない意味判断を少なくとも 1 件指摘している。
<!-- answer -->
合格回答は、「入出力と対象外の境界」を `SKILL.md` に、「用語説明と良し悪しの例」を `references/` に、「固定レポート骨格」を `assets/` に、「見出しが存在するか、フィールドが空か」といった固定チェックを将来の `scripts/` 候補にします。よくある間違いは「内容に洞察があるかの判断」をスクリプトにすることです。意味に依存しすぎるため、参考基準と Agent の判断に戻すべきです。
<!-- hint -->
まずディレクトリ名は考えず、各コンテンツに 4 つのラベルのどれかを付けるだけにしてください。
<!-- hint -->
文の中に「本当に結論を支持しているかを判断する」とあれば、それはたいてい決定論的スクリプトではありません。

### Level 2（発展）

実際の練習用 Skill フォルダーでリソースのレイヤー分けを 1 回行ってください。空ファイルや下書きファイルの作成だけでも構いませんが、読めるディレクトリ、つまり `SKILL.md` と少なくとも 2 つのリソースファイルを形成してください。プライベートなデータは置かず、ファイルを変更・削除するスクリプトも書かないでください。

進め方：IDE かターミナルで練習用 Skill フォルダーを開きます。`SKILL.md` の本文を中核指示とリソース指向に絞り、少なくとも 1 つの `references/` ファイルと 1 つの `assets/` ファイルを新規作成します。将来スクリプトに適すると思う項目があれば、チェック対象を説明する `scripts/README.md` だけを作り、実行可能なコードは書きません。
<!-- rubric -->
- ディレクトリに少なくとも `SKILL.md`、`references/` ファイル 1 つ、`assets/` ファイル 1 つが含まれる。
- `SKILL.md` の本文にリソース指向があり、長い参考資料を詰め込んでいない。
- リソースファイル名と内容の見出しから用途が分かる。
- 実在のプライバシー材料がなく、危険なスクリプトがなく、ユーザーファイルを自動変更するコマンドもない。
<!-- answer -->
合格ディレクトリの例：`SKILL.md`、`references/tag-guide.md`、`assets/note-template.md`、`scripts/README.md`。`SKILL.md` には「タグ定義が必要なときは `references/tag-guide.md` を読む。固定の出力構造が必要なときは `assets/note-template.md` を読む」と書きます。`scripts/README.md` には「将来、必須見出しの存在をチェックできる」とだけ記録します。実行可能なスクリプトがまだなくても、これでリソースのレイヤー分けは完成しています。
<!-- hint -->
実際のフォルダーには、見出し 1 つと説明 2 行のような短いプレースホルダー内容でまず構いません。
<!-- hint -->
スクリプトを書きたくなったら、まずチェック対象を 1 文で書き換えてください。この講が求めるのは境界の明確さだけです。

## 持ち帰り：それぞれに居場所のあるレイヤー図

リソースのレイヤー分けが完了すると、入口ルール、参考資料、出力の形、固定チェックにそれぞれ居場所ができます。次の講ではこのレイヤー図を実際のタスクに戻し、Skill が使うべきときに現れ、引き受けるべきでないときに止まり、付属ファイルがリスクを持ち込んでいないかをチェックします。
