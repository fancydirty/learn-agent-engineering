# 제1강: 프롬프트 재사용과 Skill 경계

> 이번 강의 목표:
> - 실제로 반복되는 작업에서 재사용 가능한 워크플로를 식별합니다.
> - 일회성 프롬프트, 반복 작업, Skill의 역할을 구분합니다.
> - 트리거, 입력, 출력, 처리하지 않음 네 줄짜리 Skill brief를 작성합니다.
>
> 선수 조건: coding agent 하나를 사용할 수 있고 Markdown을 편집할 수 있어야 합니다 | 이전 [<< 코스 목차](./README.md) | 다음 [02 >>](./02-skill-metadata.md)

## 매번 다시 설명하게 되는 작업

이런 상황을 이미 겪어 보았을 것입니다. Agent에게 주간 보고서 작성, PR 리뷰, 회의 기록 정리, 릴리스 노트 생성을 시킬 때마다 어조, 입력 파일, 출력 형식, 건드리면 안 되는 디렉터리를 다시 설명해야 합니다. 처음 이렇게 프롬프트를 쓰는 것은 자연스럽습니다. 하지만 다섯 번째에도 같은 긴 설명을 복사하고 있다면, 그것은 "프롬프트를 충분히 잘 쓰지 못했다"는 문제가 아니라 고정되지 않은 반복 작업이 있다는 신호입니다.

이번 강의에서 바로 완전한 Skill을 작성하지는 않습니다. 먼저 반복해서 나타나는 작업 하나를 네 줄짜리 경계 기록으로 압축해서, 이후의 `SKILL.md`가 명확한 뼈대를 갖게 만들 것입니다.

## 설명

### 구체적인 작업 하나에서 시작하기

먼저 일회성 프롬프트 하나를 보겠습니다:

```text
어제 진행한 고객 인터뷰를 중국어 노트로 정리해 줘. 고객의 원래 발언을 그대로 유지하고, 마지막에 제품 개선 제안 3가지를 덧붙여 줘. 원본 transcript는 수정하지 마.
```

이 문장은 한 번의 작업에는 충분합니다. 문제는 두 번째, 세 번째에 나타납니다. "고객 원발언을 어떻게 유지할지", "제안을 어느 정도로 구체적으로 할지", "어떤 파일을 건드리면 안 되는지"를 또다시 설명해야 합니다. 일회성 프롬프트는 현재 대화를 위해 임시로 작성하는 작업 지시입니다. 짧을 수도 길 수도 있지만, 기본적으로 Agent가 나중에 자동으로 발견하는 능력이 되지는 않습니다.

같은 종류의 작업이 반복해서 나타나고, 매번 비슷한 입력, 비슷한 출력, 비슷한 경계를 가지면 그것은 반복 작업입니다. 반복 작업이 꼭 성가신 잡무를 의미하는 것은 아닙니다. 핵심 특징은 언제 해야 하는지, 무엇을 가지고 하는지, 무엇을 전달하는지, 어떤 일을 덩달아 하면 안 되는지를 명확히 말할 수 있다는 것입니다.

### 반복 작업에 재사용 워크플로라는 이름 붙이기

재사용 워크플로는 다시 호출할 수 있는 일련의 단계, 제약, 출력 기준입니다. Anthropic은 Skill을 `SKILL.md`, 지시문, 스크립트, 리소스를 포함하는 디렉터리로 설명하고, OpenAI/Codex도 Agent Skills를 ChatGPT와 Codex를 위한 작업별 기능 확장으로 사용합니다.[^S1][^S4]

Skill은 Agent가 적절한 작업에서 워크플로 자료 묶음을 발견하고, 읽고, 실행하게 해 줍니다. 일회성 프롬프트보다 발견 가능한 진입점, 안정적인 경계, 필요할 때 읽는 리소스를 더 갖지만, 비즈니스 시스템 전체를 떠맡지는 않습니다.

반복 작업이 Skill로 만들 가치가 있는지 판단하려면 먼저 네 가지 질문을 해 보세요:

- 트리거: 사용자가 무엇을 말하거나 어떤 자료를 꺼낼 때 Agent가 이것을 떠올려야 합니까?
- 입력: Agent가 반드시 받아야 하는 파일, 필드, 컨텍스트는 무엇입니까?
- 출력: Agent가 최종적으로 어떤 형식의 결과를 전달해야 합니까?
- 처리하지 않음: 덩달아 하기 쉽지만 이 Skill에 속하지 않는 인접 작업은 무엇입니까?

이 네 줄이 이 코스에서 사용하는 Skill brief입니다. 아직 정식 스펙 필드는 아니고, `SKILL.md`를 쓰기 전에 그리는 책임 경계 초안입니다.

### Skill의 책임 경계 좁히기

책임 경계는 이 Skill이 무엇을 책임지는지, 그리고 무엇을 책임지지 않는지를 설명합니다. 경계가 너무 좁으면 Agent가 샘플 하나만 처리할 수 있고, 너무 넓으면 Agent가 인접 작업까지 끌어들입니다. Anthropic은 단순하고 조합 가능한 핵심부터 시작하라고 권하고, OpenAI의 현재 가이드도 각 Skill이 하나의 작업에 집중할 것을 요구합니다.[^S4][^S5]

예를 들어 "콘텐츠 좀 만들어 줘"는 너무 넓습니다. "고객 인터뷰 transcript 하나를 원발언 증거가 담긴 중국어 노트로 정리한다"가 Skill에 더 적합합니다. 명확한 트리거, 입력, 출력이 있고, 처리하지 않음도 분명히 말할 수 있습니다. 영업 후속 조치를 하지 않고, transcript를 수정하지 않고, 제품 결정을 대신하지 않습니다.

이번 강의 용어:

- 일회성 프롬프트: 현재 대화만을 위한 작업 지시문.
- 반복 작업: 여러 번 나타나고 입력과 출력의 형태가 비슷한 작업.
- 재사용 워크플로: 다시 호출할 수 있는 일련의 단계, 제약, 출력 기준.
- 책임 경계: 워크플로가 무엇을 처리하고 무엇을 처리하지 않는지를 설명하는 범위.

## 완성 예시: 인터뷰 노트 Skill brief

매주 고객 인터뷰를 정리한다고 가정해 보겠습니다. 원래 작업은 이렇습니다:

```text
transcripts/ 안의 인터뷰 transcript를 읽고, 고객 원발언을 유지한 중국어 노트를 출력하고, 마지막에 제품 제안을 덧붙여 줘.
```

이것을 네 줄 Skill brief로 다시 쓰면:

```text
트리거: 사용자가 고객 인터뷰, 사용자 리서치 transcript 또는 sales call notes 정리를 요청할 때.
입력: 하나 이상의 transcript 텍스트. 화자와 시간 순서가 포함되어 있으면 가장 좋습니다.
출력: 주제 요약, 고객 원발언 증거, 질문 목록, 제품 제안 3가지를 담은 중국어 Markdown 노트.
처리하지 않음: 원본 transcript를 수정하지 않고, 사용자 대신 이메일을 보내지 않고, 로드맵 우선순위를 결정하지 않습니다.
```

이 네 줄은 반복되는 설명을 검토 가능한 경계로 바꾸지만, 각 줄이 그대로 정식 필드가 되는 것은 아닙니다. `description`을 쓸 때는 능력, 긍정적 트리거 조건, 그리고 꼭 필요한 부정적 구분만 넣습니다. 입력 세부 사항, 전체 출력 요구 사항, 실행 금지 사항은 본문에 남깁니다. 예를 들어 "이메일 발송에 사용하지 말 것"이 이메일 작업을 제외하기 위한 것이라면 `description`에 압축해 넣어야 하고, "원본 transcript를 수정하지 말 것"은 Skill이 로드된 후에도 지켜야 하는 본문 규칙입니다.

## 반쯤 완성된 예시: 릴리스 노트 Skill brief

아래 반쯤 된 brief를 완성해 보세요. "처리하지 않음"은 덩달아 하기 쉬운 인접 작업 하나를 반드시 막아야 합니다.

```text
트리거: 사용자가 Git commit, PR 또는 changelog 초안으로 릴리스 노트를 생성해 달라고 요청할 때.
입력: ________________________________.
출력: ________________________________.
처리하지 않음: ________________________________.
```

참고 답안:

```text
입력: commit 목록, PR 요약 또는 기존 changelog 초안, 그리고 대상 독자 유형.
출력: 신규 기능, 수정 사항, 알려진 문제로 그룹화한 사용자용 Markdown 릴리스 노트.
처리하지 않음: 코드를 수정하지 않고, Git tag를 만들지 않고, 릴리스 여부를 담당자 대신 결정하지 않습니다.
```

표현은 달라도 괜찮지만, Agent가 "언제 써야 하는지"와 "언제 멈춰야 하는지"를 판단할 수 있어야 합니다.

## 연습 문제

### Level 1 (워밍업)

자신의 실제 작업 디렉터리에서 최근 세 번 모두 Agent에게 같은 설명을 반복한 작업을 찾아 네 줄 Skill brief를 작성하세요. 정식 Skill을 새로 만들지 말고, 초안 Markdown이나 노트에서만 완성하세요.

방법: 그 디렉터리를 열고 최근 작업 지시나 채팅 기록을 돌아본 뒤, 가장 자주 반복한 프롬프트 한 단락을 복사하고, 그것을 "트리거, 입력, 출력, 처리하지 않음" 네 줄로 압축하세요.
<!-- rubric -->
- 네 줄이 모두 있고, 각 줄이 한 종류의 정보만 설명합니다.
- 트리거가 Agent가 언제 이 워크플로를 떠올려야 하는지 판단하게 해 줍니다.
- 처리하지 않음이 실제 인접 작업을 최소 하나는 막습니다.
<!-- answer -->
합격 답안은 완전한 설명서가 아니라 경계 기록처럼 보입니다. 예를 들어 "트리거: 사용자가 회의 transcript에서 노트 생성을 요청할 때; 입력: transcript 하나; 출력: 중국어 Markdown 노트; 처리하지 않음: 이메일을 보내지 않고 회의를 잡지 않습니다". 흔한 실수는 "성실하게 해 줘", "고품질로 출력" 같은 말을 경계에 쓰는 것인데, 이런 말은 Agent가 작업 범위를 판단하는 데 도움이 되지 않습니다.
<!-- hint -->
가장 자주 복사해 붙여 넣는 프롬프트부터 찾아보세요.
<!-- hint -->
"처리하지 않음"이 떠오르지 않으면, Agent가 덩달아 해 버린 적이 있는 일을 떠올려 보세요.

### Level 2 (심화)

같은 반복 작업을 "너무 좁은 버전", "너무 넓은 버전", "적절한 버전" 세 개의 brief로 각각 쓰고, 왜 적절한 버전을 골랐는지 설명하세요.

방법: 같은 실제 작업을 두고 네 줄짜리 brief 세 벌을 씁니다. 너무 좁은 버전은 샘플 하나만 다루고, 너무 넓은 버전은 인접 프로세스까지 삼키고, 적절한 버전은 안정적인 입력과 안정적인 출력을 유지합니다.
<!-- rubric -->
- 세 버전이 서로 다른 작업이 아니라 같은 작업을 다룹니다.
- 너무 좁은 버전과 너무 넓은 버전의 위험을 각각 한 문장으로 씁니다.
- 적절한 버전의 출력 형식과 처리하지 않음 경계가 검사 가능합니다.
<!-- answer -->
예시: "릴리스 노트"의 경우, 너무 좁은 버전은 어떤 저장소의 오늘 commit 5개만 처리할 수 있습니다. 너무 넓은 버전은 코드 수정, tag 생성, 사용자 알림까지 포함할 수 있습니다. 적절한 버전은 주어진 변경 자료로 사용자용 릴리스 노트를 만드는 일만 합니다. 적절한 버전을 고르는 이유는 재사용은 가능하지만 릴리스 결정을 대신하지 않기 때문입니다.
<!-- hint -->
너무 좁은 버전에는 보통 구체적인 날짜, 구체적인 파일명, 일회성 프로젝트명이 나타납니다.
<!-- hint -->
너무 넓은 버전에는 보통 "모든", "전체 담당", "처음부터 끝까지" 같은 단어가 나타납니다.

## 가져갈 것: 바로 고쳐 쓸 수 있는 brief

이 네 줄 brief는 작업이 어디서 시작하는지, 무엇이 필요한지, 무엇을 전달하는지, 어디서 멈추는지를 이미 표시했습니다. 다음 단계는 이것을 정식 `SKILL.md`로 옮기는 것입니다. 발견 단계에는 Skill을 선택하기에 충분한 정보만 남기고, 실행 세부 사항은 본문으로 보냅니다.
