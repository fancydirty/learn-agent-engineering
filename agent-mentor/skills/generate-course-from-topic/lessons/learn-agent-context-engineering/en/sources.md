## S1 — Anthropic: Effective context engineering for AI agents
URL: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- authority: official-docs
- supports: Supports Lesson 1's definition of context engineering and the attention-budget framing, Lesson 2's naming of compaction, structured note-taking and sub-agent architectures as the three techniques, Lesson 3's definition of compaction and its stated failure mode, Lesson 4's definition of structured note-taking, and Lesson 5's token figures for what a subagent returns.
- key-fact: "Context engineering refers to the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference." Also, on degradation: "context rot: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases. While some models exhibit more gentle degradation than others, this characteristic emerges across all models. Context, therefore, must be treated as a finite resource with diminishing marginal returns." Also: "LLMs have an 'attention budget' that they draw on when parsing large volumes of context. Every new token introduced depletes this budget by some amount, increasing the need to carefully curate the tokens available to the LLM." Also, the three techniques named: "compaction, structured note-taking, and multi-agent architectures." Also, defining compaction: "Compaction is the practice of taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary. Compaction typically serves as the first lever in context engineering to drive better long-term coherence." Also, on its failure mode: "The art of compaction lies in the selection of what to keep versus what to discard, as overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later." Also, on tuning it: "Start by maximizing recall to ensure your compaction prompt captures every relevant piece of information from the trace, then iterate to improve precision by eliminating superfluous content." Also, on the cheapest form: "An example of low-hanging superfluous content is clearing tool calls and results – once a tool has been called deep in the message history, why would the agent need to see the raw result again? One of the safest lightest touch forms of compaction is tool result clearing." Also, defining note-taking: "Structured note-taking, or agentic memory, is a technique where the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times." Also, on subagents: "Rather than one agent attempting to maintain state across an entire project, specialized sub-agents can handle focused tasks with clean context windows. The main agent coordinates with a high-level plan while subagents perform deep technical work or use tools to find relevant information. Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Also, on when each fits: "Compaction maintains conversational flow for tasks requiring extensive back-and-forth; Note-taking excels for iterative development with clear milestones." Also, on bigger windows: "it's likely that for the foreseeable future, context windows of all sizes will be subject to context pollution and information relevance concerns." Published 2025-09-29; page re-read in full on 2026-08-23.

## S2 — Chroma Research: Context Rot — How Increasing Input Tokens Impacts LLM Performance
URL: https://www.trychroma.com/research/context-rot
- authority: authoritative-guide
- supports: Supports Lesson 1's central empirical claim that recall degrades with input length rather than falling off a cliff at the window limit, and supplies the experimental setting (18 models, extended needle-in-a-haystack, LongMemEval, repeated words) that the claim's size depends on.
- key-fact: "LLMs do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows." Also, the setup: 18 models evaluated (Claude Opus 4, Sonnet 4, Sonnet 3.7, Sonnet 3.5, Haiku 3.5; GPT-4.1, 4.1 mini, 4.1 nano, 4o, 4 Turbo, 3.5 Turbo, o3; Gemini 2.5 Pro, 2.5 Flash, 2.0 Flash; Qwen3 235B-A22B, 32B, 8B) across an extended needle-in-a-haystack design varying needle-question similarity, distractor count and position, and haystack structure, plus LongMemEval and a Repeated Words task at lengths from 25 to 10,000 tokens. Also: "Across all experiments, model performance consistently degrades with increasing input length." Also: "We observe a clear pattern that performance degrades more quickly in input length with lower similarity needle-question pairs." Also, on LongMemEval, comparing a focused prompt averaging ~300 tokens with the full ~113k-token prompt: models showed "significantly higher performance on focused prompts compared to full prompts," and "This performance drop suggests that adding irrelevant context, and thereby adding an additional step of retrieval, significantly impacts a model's ability to maintain reliable performance." Authors Kelly Hong, Anton Troynikov, Jeff Huber; published 2025-07-14.

## S3 — Context Length Alone Hurts LLM Performance Despite Perfect Retrieval (Findings of EMNLP 2025)
URL: https://aclanthology.org/2025.findings-emnlp.1264/
- authority: authoritative-guide
- supports: Supports Lesson 1's claim that length itself, not only distraction or retrieval failure, degrades performance — the strongest available evidence that trimming irrelevant material is not merely a cost optimisation — and supplies the degradation range with the setting that produced it.
- key-fact: "our systematic experiments across 5 open- and closed-source LLMs on math, question answering, and coding tasks reveal that, even when models can perfectly retrieve all relevant information, their performance still degrades substantially (13.9%–85%) as input length increases but remains well within the models' claimed lengths." Also: "This failure occurs even when the irrelevant tokens are replaced with minimally distracting whitespace, and, more surprisingly, when they are all masked and the models are forced to attend only to the relevant tokens." Also: "A similar performance drop is observed when all relevant evidence is placed immediately before the question." Also, the mitigation tested: "prompting the model to recite the retrieved evidence before attempting to solve the problem." The 13.9%–85% figure is the span across the whole model-and-task grid at the longest padding lengths tested (up to 30,000 filler tokens), not a typical single-task drop; the per-cell table shows drops such as Llama on VarSum falling 48 points and Llama on GSM8K falling 7 points at 30K space tokens. Peer-reviewed, Findings of the Association for Computational Linguistics: EMNLP 2025.

## S4 — Lost in the Middle: How Language Models Use Long Contexts (TACL)
URL: https://arxiv.org/abs/2307.03172
- authority: authoritative-guide
- supports: Supports Lesson 3's claim that position inside the window changes whether information is used, which is why what a summary places where matters — cited in the course as a durable design principle from 2023, not as a capability snapshot of any current model.
- key-fact: "We find that performance can degrade significantly when changing the position of relevant information, indicating that current language models do not robustly make use of information in long input contexts. In particular, we observe that performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models." Also, on the shape: "language model performance is highest when relevant information occurs at the very beginning (primacy bias) or end of its input context (recency bias)." Tasks were multi-document question answering and key-value retrieval; the models tested were the 2023 generation (GPT-3.5-Turbo, Claude-1.3, MPT-30B-Instruct, LongChat-13B and others), so the U-shape is the finding to carry forward, not the specific model numbers. Liu, Lin, Hewitt, Paranjape, Bevilacqua, Petroni, Liang. arXiv v3 2023-11-20; published in TACL.

## S5 — Evaluating Long-Context Reasoning in LLM-Based WebAgents
URL: https://arxiv.org/abs/2512.04307
- authority: authoritative-guide
- supports: Supports Lesson 1's claim that the reader's symptoms — repeating itself and losing the original goal — are the documented failure signature of long agent context specifically, not a vague impression, and supplies the injection method and success-rate numbers.
- key-fact: "Through extensive evaluation of four popular models, Claude-3.7, GPT-4.1, Llama 4, and o4-mini, we observe a dramatic performance degradation as context length increases, with success rates dropping from 40-50% in baseline conditions to less than 10% in long context scenarios." Also, the method: contexts were built "by injecting irrelevant task trajectories between dependent subtasks, creating contexts ranging from 25,000 to 150,000 tokens." Also, the error analysis: "Our detailed error analysis reveals that agents primarily fail due to getting stuck in loops and losing track of original task objectives." The injected material is deliberately irrelevant trajectory noise, so these numbers are an adversarial upper bound on the effect, not a typical figure for a well-curated window. Submitted 2025-12-03.

## S6 — Classifier Context Rot: Monitor Performance Degrades with Context Length
URL: https://arxiv.org/abs/2605.12366
- authority: authoritative-guide
- supports: Supports Lesson 1's claim that degradation with length is a current-generation property rather than a solved one, measured on 2026 frontier models, and Lesson 4's claim that re-stating goals inside a long transcript partially restores performance.
- key-fact: "Monitoring coding agents for dangerous behavior using language models requires classifying transcripts that often exceed 500K tokens, but prior agent monitoring benchmarks rarely contain transcripts longer than 100K tokens. We show that when used as classifiers, current frontier models fail to notice dangerous actions more often in longer transcripts." Also: "Opus 4.6, GPT 5.4, and Gemini 3.1 miss these actions 2x to 30x more often when they occur after 800K tokens of benign activity than when they occur on their own." Also: "we see that when using Opus 4.6 (with thinking) as a monitor on MonitorBench (a dataset of attacks where an agent subtly disables a firewall), recall decreases from 98.6% to 88% when 800k tokens of benign actions are prepended." Also, on position: "Needle detection rate as a function of injection position in an ~800K transcript. Detection is worst in the middle, particularly without thinking." Also, on mitigations: "these weaknesses can be partially mitigated with prompting techniques such as periodic reminders throughout the transcript." The task is transcript classification, not the reader's own task type; the 2x-to-30x span is the range across attack types at 800K tokens of padding, an extreme length chosen to expose the effect. Sam Martin and Fabien Roger; submitted 2026-05-12.

## S7 — LangChain: Context Engineering for Agents
URL: https://www.langchain.com/blog/context-engineering-for-agents
- authority: authoritative-guide
- supports: Supplies the write / select / compress / isolate vocabulary that organises Lesson 2, with each of the four defined in the source's own words, and supports Lesson 5's framing of sub-agents as one way to isolate context.
- key-fact: "Writing context means saving it outside the context window to help an agent perform a task." Also: "Selecting context means pulling it into the context window to help an agent perform a task." Also: "Compressing context involves retaining only the tokens required to perform a task." Also: "Isolating context involves splitting it up to help an agent perform a task." Also, on where the four sit: "Context engineering is effectively the #1 job of engineers building AI agents." Also, on scratchpads versus memory: "Scratchpads help agents solve a task within a given session (or thread)," but "sometimes agents benefit from remembering things across many sessions." Also, on isolation: "One of the most popular ways to isolate context is to split it across sub-agents." Lance Martin / The LangChain Team; published 2025-07-02. The four-way split is a taxonomy proposed by this post, not a standard; the course uses it as an organising frame and says so.

## S8 — Drew Breunig: How Long Contexts Fail
URL: https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html
- authority: blog
- supports: Supports Lesson 1's four named ways a long context goes wrong (poisoning, distraction, confusion, clash), giving the reader vocabulary for distinguishing symptoms that all look like "the agent got worse."
- key-fact: "Context Poisoning is when a hallucination or other error makes it into the context, where it is repeatedly referenced." Also: "Context Distraction is when a context grows so long that the model over-focuses on the context, neglecting what it learned during training." Also: "Context Confusion is when superfluous content in the context is used by the model to generate a low-quality response." Also: "Context Clash is when you accrue new information and tools in your context that conflicts with other information in the context." Published 2025-06-22. This is a personal site rather than a vendor or peer-reviewed source; the course cites it for the four names and their definitions only, and backs every underlying empirical claim with S2, S3, S5, or S6.

## S9 — Anthropic: Effective harnesses for long-running agents
URL: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- authority: official-docs
- supports: Supports Lesson 3's claim that compaction alone is not sufficient for multi-window work, Lesson 4's central claim that notes on disk are what bridges sessions, and Lesson 4's two named failure patterns when they are absent.
- key-fact: "The core challenge of long-running agents is that they must work in discrete sessions, and each new session begins with no memory of what came before." Also: "Because context windows are limited, and because most complex projects cannot be completed within a single window, agents need a way to bridge the gap between coding sessions." Also, on compaction: "However, compaction isn't sufficient." Also, the first failure pattern observed: "the agent tended to try to do too much at once—essentially to attempt to one-shot the app. Often, this led to the model running out of context in the middle of its implementation, leaving the next session to start with a feature half-implemented and undocumented. The agent would then have to guess at what had happened, and spend substantial time trying to get the basic app working again. This happens even with compaction, which doesn't always pass perfectly clear instructions to the next agent." Also, the second: "After some features had already been built, a later agent instance would look around, see that progress had been made, and declare the job done." Also, the artifacts used: "an init.sh script, a claude-progress.txt file that keeps a log of what agents have done, and an initial git commit that shows what files were added." Also: "The key insight here was finding a way for agents to quickly understand the state of work when starting with a fresh context window, which is accomplished with the claude-progress.txt file alongside the git history." Also, the session-start instruction: "Read the git logs and progress files to get up to speed on what was recently worked on." Published 2025-11-26.

## S10 — Claude Code documentation: Explore the context window
URL: https://code.claude.com/docs/en/context-window
- authority: official-docs
- supports: Supports Lesson 1's inventory of what occupies a window before the reader types anything, and is Lesson 3's primary evidence for exactly which instructions survive a compaction boundary and which are lost — a mechanism-level statement no other source makes this explicitly.
- key-fact: On what loads first: "Before you type anything: CLAUDE.md, auto memory, MCP tool names, and skill descriptions all load into context." Also, a per-mechanism table titled "What survives compaction," which records that the system prompt and output style are "Unchanged; not part of message history"; project-root CLAUDE.md and unscoped rules are "Re-injected from disk"; auto memory is "Re-injected from disk"; rules with `paths:` frontmatter are "Lost until a matching file is read again"; nested CLAUDE.md in subdirectories are "Lost until a file in that subdirectory is read again"; and invoked skill bodies are "Re-injected, capped at 5,000 tokens per skill and 25,000 tokens total; oldest dropped first." Also, the explanation: "Path-scoped rules and nested CLAUDE.md files load into message history when their trigger file is read, so compaction summarizes them away with everything else." Also, on steering it: "run `/compact` with instructions, like `/compact focus on the auth bug fix`, before starting a long new task. The summary keeps what you choose instead of what the automatic pass guesses is important." Also: "Clear between tasks: run `/clear` when switching to unrelated work." Also: "Delegate large reads: send research to a subagent so the file contents stay in its context window, not yours." Also, on checking: "To see your actual context usage at any point, run `/context` for a live breakdown by category with optimization suggestions." Page states that its token figures are "representative numbers," not measurements of any particular session. Retrieved 2026-08-23; the page is versioned rather than dated.

## S11 — Claude Code documentation: How Claude Code works
URL: https://code.claude.com/docs/en/how-claude-code-works
- authority: official-docs
- supports: Supports Lesson 3's claim that early instructions are the material most likely to be lost at a compaction boundary, and Lesson 4's rule that anything that must survive belongs in a file rather than in conversation history.
- key-fact: "As you work, context fills up. Claude compacts automatically, but instructions from early in the conversation can get lost. Also: "Sessions are independent. Each new session starts with a fresh context window, without the conversation history from previous sessions." Also, on subagents: "A subagent starts fresh unless it's a fork, which starts with a copy of your conversation so far. ## S12 — Claude Code documentation: Create custom subagents
URL: https://code.claude.com/docs/en/sub-agents
- authority: official-docs
- supports: Supports Lesson 5's mechanism for subagents as a context boundary — what crosses the boundary in each direction, and the two costs that follow from the boundary being real.
- key-fact: "Use one when a side task would flood your main conversation with search results, logs, or file contents you won't reference again: the subagent does that work in its own context and returns only the summary." Also: "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions." Also, on the inbound cost: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there." Also, on the strongest use: "One of the most effective uses for subagents is isolating operations that produce large amounts of output. Running tests, fetching documentation, or processing log files can consume significant context. By delegating these to a subagent, the verbose output stays in the subagent's context while only the relevant summary returns to your main conversation." Also, on the exception: "A fork is a subagent that inherits the entire conversation so far instead of starting fresh. This drops the input isolation that subagents otherwise provide... The fork's own tool calls still stay out of your conversation and only its final result comes back, so your main context window stays clean." Also, when not to: "Consider Skills instead when you want reusable prompts or workflows that run in the main conversation context rather than isolated subagent context." Retrieved 2026-08-23; page is versioned rather than dated.

## S13 — Cognition: Don't Build Multi-Agents
URL: https://cognition.com/blog/dont-build-multi-agents
- authority: blog
- supports: Supports Lesson 5's counterweight — that isolation has a real cost, because an agent that cannot see the main thread's decisions makes its own — which is why the course scopes subagents to read-only, low-coupling work.
- key-fact: "Share context, and share full agent traces, not just individual messages." Also: "Actions carry implicit decisions, and conflicting decisions carry bad results." Also, on compressing a long trace into a summary so a later agent can act on it: "This is hard to get right," to the point that "Depending on the domain, you might even consider fine-tuning a smaller model (this is in fact something we've done at Cognition)." Walden Yan, published 2025-06-12. This is a vendor engineering blog arguing a position; the course cites it as a stated design tradeoff, not as measurement.

## S14 — Anthropic API documentation: Compaction
URL: https://platform.claude.com/docs/en/build-with-claude/compaction
- authority: official-docs
- supports: Supports Lesson 3's mechanism-level account of what a compaction boundary does to the message history, and supplies the default summarization instruction that shows what a summary is optimised to carry.
- key-fact: "Compaction extends the effective context length for long-running conversations and tasks by automatically summarizing older context when approaching the context window limit. It also keeps the active context small: as a conversation grows, response quality degrades, so compaction replaces older content with a concise summary." Also, the four steps: "1. Detects when input tokens reach your specified trigger threshold. 2. Generates a summary of the current conversation. 3. Creates a `compaction` block containing the summary. 4. Continues the response with the compacted context." Also, the decisive sentence for what a boundary means: "The API automatically drops all content blocks prior to the `compaction` block, continuing the conversation from the summary." Also, the published default summarization prompt: "The purpose of this summary is to provide continuity so you can continue to make progress towards solving the task in a future context, where the raw history above may not be accessible and will be replaced with this summary. Write down anything that would be helpful, including the state, next steps, learnings etc." Also, a documented limitation: "Compaction might fail when tools are defined: When your request includes `tools`, the model occasionally calls a tool during the internal summarization step instead of writing a summary." As of 2026-08-23 this API feature is in beta behind the `compact-2026-01-12` header, and its trigger `value` "must be at least 50,000 tokens." Retrieved 2026-08-23.

## S15 — Anthropic API documentation: Context editing
URL: https://platform.claude.com/docs/en/build-with-claude/context-editing
- authority: official-docs
- supports: Supports Lesson 2's claim that the cheapest compression lever is clearing tool results rather than summarizing, and Lesson 6's warning that clearing content has a cache cost that a budget has to account for.
- key-fact: "Context editing allows you to selectively clear specific content from conversation history as it grows. Beyond optimizing costs and staying within limits, this is about actively curating what Claude sees: context is a finite resource with diminishing returns, and irrelevant content degrades model focus." Also, on what tool-result clearing does: "The `clear_tool_uses_20250919` strategy clears tool results when conversation context grows beyond your configured threshold. This is particularly useful for agentic workflows with heavy tool use. Older tool results (like file contents or search results) are no longer needed once Claude has processed them." Also, on the cost: "Tool result clearing: Invalidates cached prompt prefixes when content is cleared. To account for this, clear enough tokens to make the cache invalidation worthwhile." Also, on where it sits relative to compaction: "For most use cases, server-side compaction is the primary strategy for managing context in long-running conversations. The strategies on this page are useful for specific scenarios where you need more fine-grained control over what content is cleared." Retrieved 2026-08-23; strategy identifiers are dated versions that change.
