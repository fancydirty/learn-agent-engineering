## S1 — Ambig-SWE: Interactive Agents to Overcome Underspecificity in Software Engineering
URL: https://arxiv.org/abs/2502.13069
- authority: authoritative-guide
- supports: Supports Lesson 1's claim that models cannot reliably tell a well-specified request from an underspecified one, Lesson 2's finding that agents default to non-interactive behaviour unless prompted, and the measured size of the gain when clarification does happen.
- key-fact: "Our findings reveal that models struggle to distinguish between well-specified and underspecified instructions. However, when models interact for underspecified inputs, they effectively obtain vital information from the user leading to significant improvements in performance, up to 74% over the non-interactive settings." Also, on the setup that produced that figure: three settings over the 500 issues of SWE-Bench Verified — Full (original issue, no interaction), Hidden (a GPT-4o-summarized underspecified issue, no interaction), and Interaction (the summarized issue plus a simulated user proxy holding the full issue, with interaction made compulsory by prompt). Also: "LLMs default to non-interactive behavior without explicit encouragement, and even with it, they struggle to distinguish between underspecified and well-specified inputs." Also, on question quality: "The most effective questions are specific, actionable, and task-level, while vague prompts or implementation details recoverable from the codebase add little value." Also, on the definition used: "We define underspecificity as missing information that would prevent an expert from being able to create a successful solution, using the same definition as SWE-Bench Verified annotation rubric." Vijayvargiya, Zhou, Yerukola, Sap, Neubig (Carnegie Mellon). arXiv v3 revised 2026-02-21; accepted at ICLR 2026. Figures read from the v3 PDF during this session, not from secondary coverage.

## S2 — Learning to Ask: When LLM Agents Meet Unclear Instruction
URL: https://arxiv.org/abs/2409.00557
- authority: authoritative-guide
- supports: Supports Lesson 2's mechanism for why an agent invents a missing value instead of asking for it, and Lesson 1's claim that missing information is the dominant defect in real user instructions rather than an edge case.
- key-fact: "We find that due to the next-token prediction training objective, LLM agents tend to arbitrarily generate the missed argument, which may lead to hallucinations and risks." Also, from 1,000 real user instructions written against 100 real APIs and hand-annotated into four defect types: "the most common issue in the instructions is 'Instructions Missing Key Information', with a significant 56.0% of all errors", followed by Instructions with Errors at 17.3% and Instructions Beyond Tool Capabilities at 15.3%. Also, on the remedy: prompting the agent to ask when it hits an obstacle raised one model's score on missing-information cases from 0.52 to 0.90. Wang et al.; EMNLP 2025; arXiv v4 revised 2026-04-29.

## S3 — Best practices for Claude Code
URL: https://code.claude.com/docs/en/best-practices
- authority: official-docs
- supports: Supports Lesson 3's central mechanism — that an agent stops when the work looks done unless a runnable check exists — Lesson 4's before/after prompt pairs, and Lesson 2's documented pattern of having the agent interview you before implementation.
- key-fact: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop: every mistake waits for you to notice it." Also: "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result." Also, a documented before/after pair: before, "implement a function that validates email addresses"; after, "write a validateEmail function. example test cases: user@example.com is true, invalid is false, user@.com is false. run the tests after implementing". Also: "Claude can infer intent, but it can't read your mind." Also, on specs: "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works." Also, on the interview pattern: "For larger features, have Claude interview you first." Also, a named failure pattern: "The trust-then-verify gap. Claude produces a plausible-looking implementation that doesn't handle edge cases." Retrieved 2026-08-23; page is versioned rather than dated.

## S4 — Anthropic: Prompting best practices
URL: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices
- authority: official-docs
- supports: Supports Lesson 4's rules for what makes an example work and how many to include, Lesson 1's colleague test, and Lesson 5's guidance that negative boundaries need to name concrete action classes rather than attitudes.
- key-fact: "Golden rule: Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too." Also, on examples: "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure," and they should be "Relevant: Mirror your actual use case closely. Diverse: Cover edge cases and vary enough that Claude doesn't pick up unintended patterns. Structured: Wrap examples in `<example>` tags." Also: "Include 3–5 examples for best results." Also, on stating reasons: "Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important, can help Claude better understand your goals" — illustrated by "NEVER use ellipses" being less effective than the same rule with its reason attached. Also, a published scope-limiting prompt: "Don't add features, refactor code, or make 'improvements' beyond what was asked. A bug fix doesn't need surrounding code cleaned up." Also: "Positive examples of the communication style you want tend to be more effective than instructions about what not to do." Retrieved 2026-08-23; covers the Claude 5 model family, and is versioned rather than dated.

## S5 — Anthropic: Prompting Claude Opus 5
URL: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5
- authority: official-docs
- supports: Supports Lesson 5's claim that scope expansion is a current, model-specific behaviour a brief has to counter, and Lesson 3's warning that instructions can be followed too literally.
- key-fact: "Claude Opus 5 can also expand the scope of a task, adding steps that weren't requested or applying its own judgment about what the task should be. For narrow tasks, constrain scope explicitly." The published constraining prompt reads in part: "Deliver what was asked, at the scope intended. Make routine judgment calls yourself, and check in only when different readings of the request would lead to materially different work." Also, on literal following: "If your review prompt says 'only report high-severity issues' or 'be conservative,' the model may follow that instruction literally and report less; ask it to report everything and filter in a separate pass instead." Retrieved 2026-08-23; describes Claude Opus 5 behaviour as of that date.

## S6 — Anthropic: Define success criteria and build evaluations
URL: https://platform.claude.com/docs/en/test-and-evaluate/develop-tests
- authority: official-docs
- supports: Supports Lesson 3's distinction between a criterion you can check and one that needs your judgment, and gives the vendor's own bad/good criterion pair used as the lesson's model.
- key-fact: "Good success criteria are: Specific: Clearly define what you want to achieve. Instead of 'good performance,' specify 'accurate sentiment classification.' Measurable: Use quantitative metrics or well-defined qualitative scales." Also, a published bad/good pair: bad, "Safe outputs"; good, "Less than 0.1% of outputs out of 10,000 trials flagged for toxicity by the content filter." Also, on multi-part criteria: bad, "The model should classify sentiments well"; good, a list naming an F1 threshold, a non-toxicity percentage, an error-severity split, and a response-time bound. Also: "Most use cases need multidimensional evaluation along several success criteria." Retrieved 2026-08-23; page is versioned rather than dated.

## S7 — OpenAI: Prompting (ChatGPT and Codex documentation)
URL: https://learn.chatgpt.com/docs/prompting
- authority: official-docs
- supports: Supports the four-part brief structure taught across the course as a second vendor's independent framing, and Lesson 5's rule that a small number of boundaries beats an attempt to control every step.
- key-fact: "For larger or more important tasks, include the parts that matter: Goal: What should ChatGPT do? Context: What information or sources will help? Output: What format, length, or level of detail do you need? Boundaries: What must stay unchanged? What should ChatGPT avoid or check with you before it acts?" Also: "Boundaries are the few instructions ChatGPT needs to avoid creating extra work or taking an action you didn't intend. Add one when changing the wrong detail would make the result unusable." Also: "Focus on the one or two boundaries that matter most. You don't need to control every step ChatGPT takes." Also, on a coding brief: "A useful Codex prompt names the behavior you want, points to the relevant code or reproduction steps, preserves important constraints, and says how to verify the change." Also, from a worked bug-fix prompt: "Constraints: - Do not change the API shape. - Keep the fix minimal and add a regression test if feasible." Retrieved 2026-08-23; page carries no visible publication date.

## S8 — GitHub: Best practices for using GitHub Copilot to work on tasks
URL: https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results
- authority: official-docs
- supports: Supports Lesson 3's claim that a second vendor names acceptance criteria as a component of a well-formed task, and Lesson 1's point that a task description handed to an agent is a prompt whether or not you wrote it as one.

## S9 — Anthropic: Harness design for long-running application development
URL: https://www.anthropic.com/engineering/harness-design-long-running-apps
- authority: official-docs
- supports: Supports Lesson 3's core sequencing claim — that agreeing on what done means before any code is written is a working practice with an observed effect — and Lesson 3's warning that an agent grading its own work skews positive.
- key-fact: "Before each sprint, the generator and evaluator negotiated a sprint contract: agreeing on what 'done' looked like for that chunk of work before any code was written. This existed because the product spec was intentionally high-level, and I wanted a step to bridge the gap between user stories and testable implementation. The generator proposed what it would build and how success would be verified." Also: "For each sprint, the generator and evaluator negotiated a contract defining the specific implementation details for the sprint, and the testable behaviors that would be tested to verify completion." Also, on how granular those criteria got: "The contracts were granular—Sprint 3 alone had 27 criteria covering the level editor." Also, on self-grading: "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre." Also, on making a subjective target gradable: "'Is this design beautiful?' is hard to answer consistently, but 'does this follow our principles for good design?' gives Claude something concrete to grade against." Published 2026-03-24.
