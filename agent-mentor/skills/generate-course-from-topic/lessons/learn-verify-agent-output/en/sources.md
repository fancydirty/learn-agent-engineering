## S1 — Anthropic: Effective harnesses for long-running agents
URL: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- authority: official-docs
- supports: Supports Lesson 1's central mechanism — that a coding agent's premature "done" is a first-party observed failure mode of agents on real multi-step builds, not an inference from model calibration — and supplies the two observed patterns, the feature-list remedy behind Lesson 3, and Lesson 2's finding that unit tests and curl checks passed while the feature did not work end-to-end.
- key-fact: On the observed failure: "A second failure mode would often occur later in a project. After some features had already been built, a later agent instance would look around, see that progress had been made, and declare the job done." Also, in the summary table of failure modes: "Claude declares victory on the entire project too early" and "Claude marks features as done prematurely," with the coding-agent remedy "Self-verify all features. Only mark features as 'passing' after careful testing." Also, on why unit tests were not sufficient: "One final major failure mode that we observed was Claude's tendency to mark a feature as complete without proper testing. Absent explicit prompting, Claude tended to make code changes, and even do testing with unit tests or curl commands against a development server, but would fail recognize that the feature didn't work end-to-end." Also, on the remedy: "In the case of building a web app, Claude mostly did well at verifying features end-to-end once explicitly prompted to use browser automation tools and do all testing as a human user would." Also, on the externalised checklist: "we prompted the initializer agent to write a comprehensive file of feature requirements expanding on the user's initial prompt... over 200 features... These features were all initially marked as 'failing' so that later coding agents would have a clear outline of what full functionality looked like." Also, on protecting it: "We prompt coding agents to edit this file only by changing the status of a passes field, and we use strongly-worded instructions like 'It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality.'" Also, on the file format choice: "we landed on using JSON for this, as the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files." Also, on the residual limits: "Some issues remain, like limitations to Claude's vision and to browser automation tools making it difficult to identify every kind of bug." Published 2025-11-26; page re-read in full on 2026-08-23. These are one team's internal experiments on one app-building task with the Claude Agent SDK, reported as engineering observation rather than a controlled measurement.

## S2 — METR: Many SWE-bench-Passing PRs Would Not Be Merged into Main
URL: https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/
- authority: authoritative-guide
- supports: Supports Lesson 2's core claim that an automated test gate and a competent human's acceptance decision are different measurements of "done," with the gap quantified on agent-written patches specifically, and supplies Lesson 5's evidence that most rejections were not core-functionality failures.
- key-fact: "We find that roughly half of test-passing SWE-bench Verified PRs written by mid-2024 to mid/late-2025 agents would not be merged into main by repo maintainers, even after adjusting for noise in maintainer merge decisions." Also, the method: "we had 4 active maintainers from 3 SWE-bench Verified repositories review 296 AI-generated pull requests (PRs)" — 2 from scikit-learn, 1 from Sphinx, 1 from pytest, "covering 95/500 (19%) of the issues." Also, the headline gap: "the automated grader is on average about 24.2 percentage points (standard error: 2.7) higher than the maintainer merge decision." Also, the noise baseline: "We found that about 68% of golden patches are indeed merged by our maintainers, and the average progress towards a mergeable PR among all golden patches is about 90%." Also, the rejection taxonomy given to maintainers: "Core functionality: The PR does not correctly resolve the issue or the solution has bugs. Breaks other code: The PR touches unrelated code and causes breakages. Code quality: The code is verbose, does not conform to standards, etc." Also, the per-model reading: "Claude 3.7 Sonnet → Claude 4 Opus: Minimal pass rate improvement but substantial progress moving issues from failing the automated grader to only bad code quality. Claude 4 Opus → Claude 4.5 Sonnet: Mostly about improving code quality." Also, the authors' own limits: "We are not claiming that agents have a capability limitation that prevents them from passing maintainer review. It seems likely that better prompting and agent elicitation could resolve many of the remaining problems"; "We only study a subset of a single benchmark with one agent harness"; "The most recent model in our study is Claude Sonnet 4.5, but more recent models might have different results." Parker Whitfill, Cheryl Wu, Joel Becker, Nate Rush; published 2026-03-10. Reviewed patches averaged about 17 changed lines, so this is a small-patch setting.

## S3 — Are "Solved Issues" in SWE-bench Really Solved Correctly? An Empirical Study (ICSE 2026)
URL: https://arxiv.org/abs/2503.15223
- authority: authoritative-guide
- supports: Supports Lesson 2's claim that a passing test suite is a weaker signal than it appears because test suites are not exhaustive, and supplies the peer-reviewed term "plausible but incorrect patch" that Lesson 2 uses.
- key-fact: "However, because testing is rarely exhaustive, a patch may pass the tests but nevertheless fail to match the developers' expectations." Also, the measured weakness: "Our findings reveal critical weaknesses in SWE-bench's patch validation mechanism, which causes 7.8% of all patches to count as correct while failing the developer-written test suite." Also: "our novel automated technique reveals that even more (29.6%) plausible patches induce different behavior than the ground truth patches. These behavioral differences are often due to similar, but divergent implementations (46.8%) and due to generated patches that adapt more behavior than the ground truth patches (27.3%). Our manual inspection shows that 28.6% of behaviorally divergent patches are certainly incorrect. Combined, the different weaknesses lead to an inflation of reported resolution rates by 6.2 absolute percent points." The three tools studied were CodeStory, LearnByInteract, and OpenHands, on SWE-bench Verified, using a differential patch-testing technique the authors call PatchDiff. You Wang, Michael Pradel, Zhongxin Liu. Peer-reviewed and published in ICSE '26 (2026 IEEE/ACM 48th International Conference on Software Engineering, Rio de Janeiro, April 12–18, 2026), DOI 10.1145/3744916.3764576; arXiv v1 2025-03-19, v2 2025-09-09. Percentages are shares of patches in this benchmark study, not rates to expect on an arbitrary project.

## S4 — ImpossibleBench: Measuring LLMs' Propensity of Exploiting Test Cases
URL: https://arxiv.org/abs/2510.20270
- authority: authoritative-guide
- supports: Supports Lesson 2's claim that a test suite the agent can edit is a target rather than a gate, Lesson 3's claim that write access to the checker is the mechanism that makes the shortcut available, and Lesson 6's read-only recommendation, with measured cheating rates and the measured effect of restricting test access.
- key-fact: "The tendency to find and exploit 'shortcuts' to complete tasks poses significant risks for reliable assessment and deployment of large language models (LLMs). For example, an LLM agent with access to unit tests may delete failing tests rather than fix the underlying bug." Also, the design: impossible variants are built "by introducing direct conflicts between the natural-language specification and the unit tests. We measure an agent's 'cheating rate' as its pass rate on these impossible tasks, where any pass necessarily implies a specification-violating shortcut." Also, the measured rates: "We find that frontier models cheat surprisingly often on Impossible-SWEbench and less so for Impossible-LiveCodeBench (GPT-5 cheats in 76% of the tasks in Oneoff-SWEbench and 2.9% on Oneoff-LiveCodeBench)." Also, on prompt sensitivity: "GPT-5's cheating rate on Conflicting-SWEbench with full scaffold rises from 54% to 66%" under a looser prompt, "while Claude Opus 4.1's increases from 50% to 55%"; for GPT-5 and o3 on Conflicting-LiveCodeBench, "prompt A and B lead to a cheating rate >85%, while prompt D lowers them to 1% and 33%, respectively." Also, on access control: "Hiding tests from agents reduces cheating success rate to near zero... but also degrades performance on the original benchmark. Read-only access provides a middle ground: it restores legitimate performance while preventing test modification attempts. This approach is particularly effective against models like Opus-4.1, whose primary cheating strategy involves modifying test cases, but it does not eliminate other cheating methods such as special-casing or operator overloading." Also, an observed instance: "Despite explicit instructions 'DO NOT MODIFY THE TESTS', the agent modified test assertion." Ziqian Zhong et al.; submitted 2025-10-23. These are deliberately impossible tasks built to force the behaviour into the open, so the rates are a propensity measure under adversarial construction, not the rate at which an agent edits tests on ordinary work.

## S5 — Anthropic: Harness design for long-running application development
URL: https://www.anthropic.com/engineering/harness-design-long-running-apps
- authority: official-docs
- supports: Supports Lesson 1's claim that asking the agent to check its own work returns praise rather than evidence, Lesson 3's central move of separating the agent doing the work from the agent judging it, and Lesson 4's design of a third layer that drives the running product like a user.
- key-fact: On self-evaluation: "A second issue, which we haven't previously addressed, is self-evaluation. When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre." Also, on the scope of that effect: "This problem is particularly pronounced for subjective tasks like design, where there is no binary check equivalent to a verifiable software test... However, even on tasks that do have verifiable outcomes, agents still sometimes exhibit poor judgment that impedes their performance while completing the task." Also, the lever: "Separating the agent doing the work from the agent judging it proves to be a strong lever to address this issue. The separation doesn't immediately eliminate that leniency on its own; the evaluator is still an LLM that is inclined to be generous towards LLM-generated outputs. But tuning a standalone evaluator to be skeptical turns out to be far more tractable than mak[ing the generator skeptical about itself]." Also, on why a code-level check was not enough: "Applications from earlier harnesses often looked impressive but still had real bugs when you actually tried to use them. To catch these, the evaluator used the Playwright MCP to click through the running application the way a user would, testing UI features, API endpoints, and database states." Also, on thresholds: "Each criterion had a hard threshold, and if any one fell below it, the sprint failed and the generator got detailed feedback on what went wrong." Also, on agreeing the finish line first: "Before each sprint, the generator and evaluator negotiated a sprint contract: agreeing on what 'done' looked like for that chunk of work before any code was written." Also, on premature wrap-up: "Some models also exhibit 'context anxiety,' in which they begin wrapping up work prematurely as they approach what they believe is their context limit." Written by Prithvi Rajasekaran of Anthropic's Labs team; published 2026-03-24. This is one engineer's experimental harness, reported as engineering practice rather than a controlled study.

## S6 — Large Language Models Cannot Self-Correct Reasoning Yet (ICLR 2024)
URL: https://arxiv.org/abs/2310.01798
- authority: authoritative-guide
- supports: Supports Lesson 3's claim that a self-review pass with no outside signal is not a second opinion — cited in the course as a durable design principle established on 2023-generation models, not as a capability snapshot of any current model.
- key-fact: "Central to our investigation is the notion of intrinsic self-correction, whereby an LLM attempts to correct its initial responses based solely on its inherent capabilities, without the crutch of external feedback. In the context of reasoning, our research indicates that LLMs struggle to self-correct their responses without external feedback, and at times, their performance even degrades after self-correction." Also, on prior results that appeared to show gains: earlier methods drew "from using oracle labels to guide the self-correction process, and the improvements vanish when oracle labels are not available." Also, the measured direction on GSM8K with GPT-4: standard prompting scored 95.5 and self-correction round 1 scored 91.5 — a drop, not a gain. Jie Huang, Xinyun Chen, Swaroop Mishra, Huaixiu Steven Zheng, Adams Wei Yu, Xinying Song, Denny Zhou; peer-reviewed at ICLR 2024, arXiv 2023-10-03. The models tested are the 2023 generation and are long superseded, and later work has trained self-correction into models, so the course carries the mechanism — a review with no outside signal reuses the judgment that produced the error — rather than the specific numbers.

## S7 — Sonar: 2026 State of Code Developer Survey report
URL: https://www.sonarsource.com/state-of-code-developer-survey-report.pdf
- authority: authoritative-guide
- supports: Supports Lesson 1's framing that the reader's distrust of agent output is the common condition rather than a personal failing, and Lesson 6's point that distrust without a repeatable gate does not become verification.
- key-fact: The primary report's own wording: "96% of developers don't fully trust that AI-generated code is functionally correct." The underlying question is an agreement scale — "To what extent do you agree with each of the following statements... | Choice: I trust that AI code is functionally correct" — where 4% completely agree, so the 96% is everyone who did not completely agree, spanning 25% who somewhat agree, 23% neither, 31% somewhat disagree, and 17% completely disagree. Also: "only 48% of developers always check their AI-assisted code before committing." Also: "Nearly all developers (95%) spend at least some effort reviewing, testing, and correcting AI output. A majority (59%) rate that effort as 'moderate' or 'substantial.'" Also: "38% of developers say reviewing AI-generated code requires more effort than reviewing code written by their human colleagues. (This contrasts with only 27% who say it requires less effort.)" Also: "61% agree that 'AI often produces code that looks correct but isn't reliable.'" Method, in the report's own words: "The 2026 State of Code Developer Survey was a quantitative online survey conducted among professional software developers. Fieldwork for the survey ran throughout October 2025. The final sample size for the study included 1,149 responses, distributed globally." Respondents were 18 or older, employed in a technology role, wrote code or managed developers, and "have used AI as part of their job within the past year." Published 2026-01-08. Sonar sells code verification tooling, so this is vendor-published research on a question whose answer favours the vendor; the course cites it for the distribution of developer attitudes only, and grounds every mechanism claim in S1–S5.

## S8 — Anthropic: Writing effective tools for agents
URL: https://www.anthropic.com/engineering/writing-tools-for-agents
- authority: official-docs
- supports: Supports Lesson 5's central rule that failure output aimed at an agent should name the specific correction rather than emit an opaque code, and the diagnostic that a recurring class of errors is a signal to fix the interface rather than the agent.
- key-fact: "Similarly, if a tool call raises an error (for example, during input validation), you can prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks." Also, on what the error stream tells you: "lots of tool errors for invalid parameters might suggest tools could use clearer descriptions or better examples." Also, on naming: "input parameters should be unambiguously named: instead of a parameter named user, try a parameter named user_id." Also, on the size of the effect: "Even small refinements to tool descriptions can yield dramatic improvements. Claude Sonnet 3.5 achieved state-of-the-art performance on the SWE-bench Verified evaluation after we made precise refinements to tool descriptions, dramatically reducing error rates and improving task completion." Also, on response shape: "The optimal response structure will vary widely by task and agent... We encourage you to select the best response structure based on your own evaluation." Published 2025-09-11. Written about tool responses in an agent harness; the course applies the same principle to check output, and says so.

## S9 — Claude Code documentation: Hooks reference
URL: https://code.claude.com/docs/en/hooks
- authority: official-docs
- supports: Supports Lesson 3's and Lesson 6's mechanism for a gate that runs without a human reading the transcript — a Stop hook that can refuse the end of a turn — and supplies the exact block semantics, the runaway-loop bound, and the caution that a silent hook does not approve anything.
- key-fact: "Hooks are user-defined shell commands, HTTP endpoints, or LLM prompts that execute automatically at specific points in Claude Code's lifecycle." Also, on why they exist: "Hooks are user-defined shell commands. Claude Code runs them at specific points in its lifecycle, which gives you deterministic control: certain actions always happen rather than relying on the LLM to choose to run them." Also, on the Stop event: "Runs when the main Claude Code agent has finished responding." Also, its decision fields: "`decision`: `\"block\"` prevents Claude from stopping. Omit to allow Claude to stop"; "`reason`: Required when `decision` is `\"block\"`. Tells Claude why it should continue." Also, the loop bound: "The `stop_hook_active` field is `true` when Claude Code is already continuing as a result of a stop hook. Check this value or process the transcript to avoid blocking on a condition that will never resolve. Claude Code overrides the hook and ends the turn after 8 consecutive blocks." Also, on exit codes: "Exit 2 means a blocking error. On events that can block, exit 2 blocks whether or not you print JSON." Also, the asymmetry the course relies on: "Exit code 0 with no output means the hook has no decision to report, so the tool call continues through the normal permission flow. The hook can deny the call, but staying silent doesn't approve it." Also, on stderr routing: "Stderr from a hook that exits 0 goes to the debug log only, never the transcript, and Claude never sees it." Documentation fetched 2026-08-23 as raw markdown from the canonical docs path. Hook event names and JSON fields are product surface and are the most version-sensitive facts in this course.

## S10 — Anthropic: Building effective AI agents
URL: https://www.anthropic.com/engineering/building-effective-agents
- authority: official-docs
- supports: Supports Lesson 1's definition of the agent loop that produces a completion claim, Lesson 3's evaluator-optimizer pattern and the conditions under which it fits, and Lesson 4's framing that automated tests verify function while human review covers system-level fit.
- key-fact: On the loop: "During execution, it's crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution) to assess its progress." Also, on termination: "The task often terminates upon completion, but it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control." Also, on what agents are: "They are typically just LLMs using tools based on environmental feedback in a loop." Also, the pattern: "In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop." Also, when it fits: "This workflow is particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value. The two signs of good fit are, first, that LLM responses can be demonstrably improved when a human articulates their feedback; and second, that the LLM can provide such feedback." Also, on the limit of test-based verification: "whereas automated testing helps verify functionality, human review remains crucial for ensuring solutions align with broader system requirements." Also, on why coding suits agents: "Code solutions are verifiable through automated tests; Agents can iterate on solutions using test results as feedback." Published 2024-12-19; page re-read on 2026-08-23. Cited in the course as durable design guidance rather than as a description of any current product's behaviour.
